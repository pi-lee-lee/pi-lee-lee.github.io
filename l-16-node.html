2. 원리 — 무엇을 옮기고, 무엇이 달라지고, 무엇이 같아야 하는가

2-1. 왜 순수 함수와 노드 껍질을 가르는가 — 시험할 수 있는 것만 믿을 수 있다

열다섯 쪽 동안 파이썬 파일마다 같은 줄을 적었다: "PURE: no port, no ROS, no clock." 그 한 줄이 있었기 때문에 python3 tests/test_grid.py 가 라이다를 뽑아 놓고 실행됐다. C++ 에서도 같은 선을 긋는데, 여기서는 그 선이 한 단계 더 앞에 있다.

파이썬에서 "ROS 를 쓰지 않는다"는 것은 실행 시점의 이야기였다 — import rclpy 를 함수 안으로 내려 두면(l-06 §3-4-2) ROS 가 없는 기계에서도 파일을 열 수 있다. C++ 에서는 #include 가 컴파일 시점에 해결되므로, 헤더 하나에 sensor_msgs/msg/laser_scan.hpp 가 들어가는 순간 그 헤더는 ROS 가 설치된 기계에서만 컴파일된다.

저장소에 이미 두 층이 다 있다. 08d §3-3 의 rpi5_vision/include/rpi5_vision/scan_projection.hpp 는 "ROS 에 묶이지 않은 순수 함수" 라고 적혀 있고 실제로 rclcpp 를 포함하지 않는다 — 대신 sensor_msgs/msg/camera_info.hpp · sensor_msgs/msg/laser_scan.hpp · tf2/LinearMath/Transform.h 를 포함한다. 그래서 노드를 띄우지 않고 시험할 수 있다는 성질은 그대로 얻는다. 이 쪽의 헤더는 08d 보다 한 단계 더 나아가 메시지 타입도 포함하지 않는다. 그래서 ROS 가 없는 기계에서 구문 검사가 된다(집필자가 그렇게 검사했다, §3-1-3).

두 선택이 각각 무엇을 얻는가 (어느 쪽이 낫다는 말이 아니다)

메시지 타입을 포함하는 헤더(08d) — 함수가 메시지를 통째로 받으므로 호출하는 쪽 코드가 한 줄이고, 필드를 옮겨 적다가 빠뜨릴 자리가 없다. 대가: ROS 가 있어야 컴파일된다.

필드만 받는 헤더(이 쪽) — ROS 없이 컴파일·시험된다. 대가: 메시지에서 필드를 꺼내 넘기는 줄이 노드 쪽에 생기고, 그 줄은 시험이 채점하지 않는다. 그 줄에서 angle_min 과 angle_max 를 바꿔 넘기면 시험은 전부 통과하고 지도만 틀린다 — 증상표의 마지막 행이 이 경우다.

차이가 없는 축: 만들어지는 결과와 속도(동일). 두 선택은 어디서 컴파일되는가와 어디에 검사되지 않는 줄이 남는가의 맞바꿈이다.

2-2. 왜 C++ 인가 — 그리고 왜 파이썬을 버리지 않는가

이 프로젝트의 언어 배정은 노드는 C++, 프로브와 실습 도구는 파이썬이다. 07 §3-10 의 scan_watch 가 C++ 인 것도, l-01 ~ l-15 의 도구가 파이썬인 것도 같은 규칙의 두 면이다. 이유는 취향이 아니라 두 코드가 실행되는 자리가 다르기 때문이다 — 하나는 내가 한 번 실행해 보고 결과를 읽는 것이고, 하나는 로봇이 켜져 있는 동안 계속 실행되는 것이다.

그런데 옮긴다는 말은 보통 버린다는 뜻으로 쓰인다. 여기서는 아니다. 파이썬 도구는 이미 시험을 통과한 구현이다. 새로 쓴 C++ 이 다른 수를 냈을 때 어느 쪽을 먼저 의심할지는 이 사실로 정한다. 정답지가 없으면 두 수가 다를 때 할 수 있는 일이 없다.

⚠ 그래서 옮기는 도중에 알고리즘을 고치지 않는다. 고치고 싶은 것이 생기면 파이썬 쪽을 먼저 고치고 시험을 다시 통과시킨 뒤 옮긴다. 순서를 바꾸면 대조 결과로 아무것도 판단할 수 없다.

2-3. 마운트 목록이 그 선이다 — 왜 scripts/ 는 컨테이너에 없는가

docker/docker-compose.yml 의 volumes 는 다섯 줄이다 — ../ros2_ws:/ros2_ws · /dev · /run/udev · /sys/class/gpio · ros-cache. scripts/ 는 없다. l-06 §2-5 가 이미 그 이유와 1회성 -v 조각을 실었다 — 여기서 다시 논증하지 않는다.

이 쪽에서 쓸모 있는 것은 그 결정의 다른 쪽 면이다. scripts/lidar_lab/ 을 상시 마운트하지 않기로 한 이유가 "실습 도구는 실행 중인 시스템의 부품이 아니다" 라면, 부품이 되려면 ros2_ws/ 쪽으로 옮겨 와야 한다는 말이 된다. 그리고 옮겨 오는 것은 전부가 아니라 남길 조각이다.

그 조각을 고르는 것이 이 쪽의 첫 실습이고, 고르는 기준은 "로봇이 켜져 있는 동안 이것이 계속 필요한가" 하나다. l-09 §3-4-4 의 마지막 문단이 이미 그 근거를 적어 두라고 했다 — 예산을 넘었을 때 어느 방법으로 고칠지 한 줄 적어 두면, 그 줄이 여기서 고르는 근거가 된다.

누적 순서 — 집필자가 해 봤더니 차이가 0 이었다

"덧셈의 순서를 바꾸면 부동소수 합이 달라진다"는 것은 참이지만 항상 달라진다는 뜻이 아니다. 집필자가 합성 기록 한 바퀴(측정된 점 339 개)의 거리 합을 앞에서부터와 뒤에서부터 두 번 계산해 봤더니 두 값이 마지막 비트까지 같았다(2026-09-23, Mac, python3). 내 파일에서는 다를 수도 있다. 그러니 "누적 순서 때문일 것이다"로 넘기지 말고, 실습 B 에서 차이가 난 항목을 하나 골라 그 값 하나만 양쪽에서 찍어 본다 — 차이의 자리를 보면 1·2·3·4 중 어느 것인지 바로 구분된다.

4번이 이 가이드를 관통하는 규약이다. l-04 §2-6 이 무반사를 null 로 고정한 것, l-12 가 "통로를 못 찾았다"를 0.0 이 아니라 None 으로 둔 것, l-15 의 무반사율이 잰 칸이 없으면 None 인 것이 전부 같은 결정이다. C++ 에는 None 이 없다. 그래서 옮길 때 고를 수 있는 방법이 셋 생기고, 이 가이드는 std::optional 을 쓴다.

C++ 에서 "못 쟀다"를 적는 법사실
std::optional<double>"값이 없다"가 타입에 적힌다. 값을 꺼내려면 값이 있는지 확인해야 하고, 확인하지 않고 쓰면 컴파일 오류는 나지 않지만 시험이 검출한다. 원소 하나당 double 하나 + 표시 1바이트(정렬 때문에 보통 16바이트)를 쓴다
NaN 을 표시로 쓴다크기가 double 그대로다. 대신 모든 비교가 오류 없이 거짓이 된다 — NaN < 1.0 도 NaN >= 1.0 도 거짓이라, 문턱 비교가 예외 없이 통과도 실패도 하지 않는다
-1.0 같은 값을 표시로 쓴다가장 짧다. 대신 그 값이 진짜로 나올 수 있는 양에는 쓸 수 없고, 표시를 아는 코드와 모르는 코드가 섞이면 -1 m 가 지도에 찍힌다

⚠ 어느 것을 골라도 지켜야 하는 것은 하나다 — 0.0 은 "0 m 에 물체가 있다"는 측정값이고 "못 쟀다"가 아니다. C++ 에서 이 구분을 가장 쉽게 놓치는 자리가 value_or(0.0) 과 if (!x) 다. §3-1-3 의 벡터가 정확히 그 자리를 채점한다.

2-5. 읽기가 틀리면 전부 틀린다 — 그래서 검사하는 로더를 옮긴다

l-04 §3-4-2 의 load_jsonl() 은 단순한 파서가 아니었다. 여섯 가지를 거부한다. 그리고 그 여섯이 거부하는 것은 파일이 열리지 않는 경우가 아니라, 잘 열리면서 오류 없이 틀린 값을 내는 경우다.

왜 C++ 로더가 파이썬 것보다 훨씬 긴가

파이썬 쪽은 json.loads(line) 한 줄로 끝났다. 표준 라이브러리에 JSON 이 들어 있기 때문이다. C++ 표준 라이브러리에는 없고, 이 프로젝트는 이 한 가지를 위해 외부 라이브러리를 늘리지 않는다(늘리면 package.xml · rosdep · 이미지 빌드도 함께 바꿔야 한다). 그래서 §3-1-2 의 둘째 블록은 한 줄짜리 JSON 만 처리하는 작은 읽개다. 지원하지 않는 입력이 나오면 추측하지 않고 예외를 던진다 — 예외를 던지는 것이 파서를 짧게 유지하는 유일한 방법이다.

이 불편이 바로 메시지 형식이 고정돼 있는 이유다. sensor_msgs/msg/LaserScan 은 필드가 열두 개로 고정돼 있고, ros2 interface show 로 누구나 같은 목록을 본다. 형식을 바꾸고 싶으면 읽는 쪽을 전부 같이 바꿔야 한다는 것을, 이 쪽에서 로더를 두 번째로 쓰면서 직접 겪어 알게 된다. .scan.jsonl 에 필드를 하나 더하고 싶어지면 — 파이썬 로더와 C++ 로더를 같이 고쳐야 한다.

2-7. 이제 시간이 예산이 된다

지금까지 도구는 파일을 입력으로 받았다. 파일 입력에는 시간 제한이 없다 — l-09 §3-4-4 에서 격자 한 장에 수십 ms 가 걸려도 처리가 오래 걸릴 뿐이었다. /scan 을 구독하면 사정이 달라진다. 콜백이 끝나기 전에 다음 장이 온다면, 그다음은 셋 중 하나다 — 큐에 쌓이거나, 버려지거나, 점점 밀린다. SensorDataQoS() 는 작은 큐 + BEST_EFFORT 라 보통 버려진다(그래서 오류가 안 난다).

그래서 예산이 생긴다: 콜백 한 번 ≤ 한 바퀴의 주기. 그 주기는 1000 ÷ 내 회전수 ms 이고, l-04 §3-2 에서 잰 값이다.

⚠ 5.5 Hz(주기 약 182 ms)를 예산으로 고정하지 않는다. 그 값은 데이터시트(rev.2.2 p.8 Fig 2-1)의 typical 이고 360 samples per scan 이라는 조건이 같은 칸에 붙어 있다. 내 기기가 그 조건에서 동작하는지는 내가 잰 회전수로 확인한다. 두 값이 많이 다르면 그 차이 자체를 기록한다 — l-04 가 그 대조의 자리를 이미 마련해 두었다.

그리고 예산을 넘는 것은 실패가 아니라 관찰이다. 넘었으면 고칠 방법이 셋 있고, 셋 다 이 가이드 밖이다.

  • 격자를 매번 새로 만들지 않고 고쳐 쓰기
  • 광선 수를 줄이기(l-10 의 솎기)
  • 콜백에서 무거운 일을 빼서 다른 스레드로 보내기

어느 방법인지 한 줄 적는 것이 §3-4 의 산출물이다.

namespace detail {

// A tiny JSON reader for ONE line. It is deliberately not a general library: it knows
// null / true / false / number / string / array / object and nothing else, and it
// THROWS on anything it does not understand rather than guessing.
struct Json {
  enum Kind { Null, Bool, Num, Str, Arr, Obj } kind = Null;
  double num = 0.0;
  bool bol = false;
  std::string str;                               // Str, and the raw text of a Num
  std::vector<Json> arr;                         // Arr
  std::vector<std::pair<std::string, Json>> obj; // Obj, in file order

  const Json* find(const std::string& key) const {
    for (const auto& kv : obj) { if (kv.first == key) return &kv.second; }
    return nullptr;
  }
};

class Reader {
public:
  explicit Reader(const std::string& text) : s_(text) {}

  Json parse_line() {
    Json v = value();
    ws();
    if (i_ != s_.size()) { fail("trailing text after the JSON value"); }
    return v;
  }

private:
  const std::string& s_;
  std::size_t i_ = 0;

  [[noreturn]] void fail(const std::string& why) const {
    throw std::runtime_error("column " + std::to_string(i_ + 1) + ": " + why);
  }
  void ws() { while (i_ < s_.size() && (s_[i_] == ' ' || s_[i_] == '\t' || s_[i_] == '\r')) { ++i_; } }
  char peek() const { return i_ < s_.size() ? s_[i_] : '\0'; }
  bool eat(char c) { ws(); if (peek() == c) { ++i_; return true; } return false; }
  void expect(char c) { if (!eat(c)) { fail(std::string("expected '") + c + "'"); } }

  bool literal(const char* word) {
    std::size_t n = 0; while (word[n]) { ++n; }
    if (s_.compare(i_, n, word) != 0) { return false; }
    i_ += n; return true;
  }

fail() 이 열 번호를 같이 적는다는 것에 주목한다. 한 줄이 4 000자를 넘는 파일에서 "JSON 이 아니다"만 나오면 어디를 볼지 알 수 없다.

  Json value() {
    ws();
    char c = peek();
    if (c == '{') { return object(); }
    if (c == '[') { return array(); }
    if (c == '"') { Json v; v.kind = Json::Str; v.str = string(); return v; }
    if (literal("null")) { return Json(); }
    if (literal("true")) { Json v; v.kind = Json::Bool; v.bol = true; return v; }
    if (literal("false")) { Json v; v.kind = Json::Bool; v.bol = false; return v; }
    return number();
  }

  Json object() {
    Json v; v.kind = Json::Obj;
    expect('{');
    if (eat('}')) { return v; }
    for (;;) {
      ws();
      if (peek() != '"') { fail("object key must be a string"); }
      std::string key = string();
      expect(':');
      v.obj.emplace_back(key, value());
      if (eat(',')) { continue; }
      expect('}');
      return v;
    }
  }

  Json array() {
    Json v; v.kind = Json::Arr;
    expect('[');
    if (eat(']')) { return v; }
    for (;;) {
      v.arr.push_back(value());
      if (eat(',')) { continue; }
      expect(']');
      return v;
    }
  }

  std::string string() {

      if (c == '"') { return out; }

      if (i_ >= s_.size()) { break; }

        case '\\': out.push_back('\\'); break;
        case '/': out.push_back('/'); break;
        case 'b': out.push_back('\b'); break;
        case 'f': out.push_back('\f'); break;
        case 'n': out.push_back('\n'); break;
        case 'r': out.push_back('\r'); break;
        case 't': out.push_back('\t'); break;
        default: fail("unsupported escape in a string");   // \uXXXX included: we refuse
      }
    }
    fail("string is not closed");
  }

  Json number() {

    const char* begin = s_.c_str() + i_;
    char* end = nullptr;
    double d = std::strtod(begin, &end);
    if (end == begin) { fail("not a JSON value"); }
    i_ += static_cast<std::size_t>(end - begin);

// that breaks the format -- the same six refusals l-04's load_jsonl() makes, because a
// quietly wrong file makes every page after it quietly wrong.
inline std::vector<Scan> load_jsonl(const std::string& path, Meta* meta_out = nullptr) {

    const std::string where = "line " + std::to_string(ln) + ": ";
    while (!line.empty() && (line.back() == '\r' || line.back() == ' ')) { line.pop_back(); }
    if (line.empty()) { continue; }

    detail::Json row;
    try {
      row = detail::Reader(line).parse_line();
    } catch (const std::exception& e) {
      throw std::runtime_error(where + "not JSON (" + e.what() + ")");
    }
    if (row.kind != detail::Json::Obj) { throw std::runtime_error(where + "not a JSON object"); }

    //     as evidence about MY device.

      const detail::Json* m = row.find("meta");
      if (m == nullptr || m->kind != detail::Json::Obj) {
        throw std::runtime_error("line 1 must be the head line: {\"meta\": {...}}");

      if (meta["unit"] != "m") {

      if (meta_out != nullptr) { *meta_out = meta; }

      continue;

static void check(const char* name, bool ok, const std::string& got) {
  ++cases;
  if (!ok) { std::printf("FAIL %-30s got %s\n", name, got.c_str()); ++fails; }
}
static void eq_int(const char* name, long got, long want) {
  check(name, got == want, std::to_string(got) + " want " + std::to_string(want));
}
static std::string g17(double v) {
  char buf[40];
  std::snprintf(buf, sizeof(buf), "%.17g", v);   // 17 digits: 59.99999999999999 is not 60
  return std::string(buf);
}
static void close_to(const char* name, double got, double want, double tol = 1e-9) {
  check(name, std::fabs(got - want) <= tol, g17(got) + " want " + g17(want));
}
static void eq_bool(const char* name, bool got, bool want) {
  check(name, got == want, std::string(got ? "true" : "false"));
}

static std::string write_tmp(const char* name, const std::string& body) {
  const std::string path = tmpdir + "/" + name;
  std::ofstream out(path);
  out << body;
  return path;
}

// Returns the message load_jsonl() threw, or "" when it did not throw at all.
static std::string refusal(const char* name, const std::string& body) {
  const std::string path = write_tmp(name, body);
  try {
    load_jsonl(path);
  } catch (const std::exception& e) {
    std::remove(path.c_str());
    return e.what();
  }
  std::remove(path.c_str());
  return "";
}

static bool mentions(const std::string& msg, const char* needle) {
  return !msg.empty() && msg.find(needle) != std::string::npos;
}

// Read through the size, so that the SKELETON reports FAIL instead of walking off the
// end of an empty vector. A test that crashes tells you nothing about the other cases.
static double ang(const Scan& s, std::size_t i) { return i < s.a.size() ? s.a[i] : -99.0; }
static double rng(const Scan& s, std::size_t i) {
  return (i < s.r.size() && s.r[i]) ? *s.r[i] : -99.0;
}
static bool has(const Scan& s, std::size_t i) { return i < s.r.size() && s.r[i].has_value(); }

// Same guard for what to_xy() returns. An implementation that DROPS no-returns gives a
// SHORTER vector, and xy[3] on it is undefined behaviour -- the vectors below have to
// report FAIL for that mistake, not read past the end of it.
static bool xyhas(const std::vector<std::optional<Point>>& v, std::size_t i) {
  return i < v.size() && v[i].has_value();
}
static double xyx(const std::vector<std::optional<Point>>& v, std::size_t i) {
  return xyhas(v, i) ? v[i]->first : -99.0;
}
static double xyy(const std::vector<std::optional<Point>>& v, std::size_t i) {
  return xyhas(v, i) ? v[i]->second : -99.0;
}

4. C++ 에는 None 이 없다. std::vector<double> 에 -1.0 을 "못 쟀다"로 쓰면 무엇이 일어나는가?

당장은 아무 일도 안 일어난다 — 아무 일도 안 일어나는 것이 문제다. -1.0 은 수라서 모든 계산이 그대로 진행된다: to_xy 는 원점에서 반대쪽 1 m 에 점을 찍고, 격자는 그 점까지 자유공간을 칠하고, 최소 거리로는 -1 이 뽑힌다. NaN 을 쓰면 다른 방식으로 오류 표시 없이 지나간다 — 모든 비교가 거짓이라 문턱 판정이 통과도 실패도 하지 않는다. std::optional 은 "값이 없다"를 타입에 적어 꺼내기 전에 값이 있는지 확인하게 만든다. 대가는 배열이 대략 두 배가 되는 것이다. 그리고 어느 것을 골라도 0.0 은 측정된 값이라는 선은 지켜야 한다 — l-04 §2-6 이 null 을 고른 것과 같은 결정이다.

5. C++ 로더에서 "머리 줄 검사"와 "오름차순 검사"를 빼면 무엇이 달라지는가? 언제 알게 되는가?

좋은 파일을 입력하는 동안에는 아무것도 달라지지 않는다. 두 구현이 똑같은 수를 내고 실습 B 도 통과한다. 달라지는 것은 나쁜 파일이 들어왔을 때다 — 출처가 없는 파일(누구 것인지 모른다)과 각도가 뒤섞인 파일(거리가 남의 각도에 대응됐다)이 오류 없이 통과한다. 알게 되는 시점은 보통 한참 뒤, 지도가 이상한데 이유를 못 찾을 때다. 검사를 넣어 두면 그 시점이 파일을 여는 순간으로 당겨진다 — 알게 되는 시점을 앞당기는 것이 검사의 가치다. ⚠ 그리고 없어진 검사는 사라진 코드라서 읽어도 드러나지 않는다. 그래서 §3-1-3 의 2군이 고장난 파일을 여섯 개 만들어 입력한다.

6. 격자를 /map 으로 내면 무엇이 일어나는가? 그리고 결과 메시지의 frame_id 를 내가 지어 적으면?

/map 은 09 의 slam_toolbox 가 발행하는 이름이다. 같은 이름으로 발행하면 발행자가 둘이 되고, 구독자(Nav2 코스트맵·Foxglove)가 어느 쪽을 그리는지는 메시지마다 달라진다. 오류는 나지 않는다. 그래서 이름을 /lidar_lab/grid · /lidar_lab/segments 로 둔다. frame_id 를 지어 적으면 — 예를 들어 드라이버가 laser_frame 으로 내는데 laser_link 라고 적으면 — TF 에 그 이름이 없어 Foxglove 가 그리지 못하거나 엉뚱한 자리에 그린다. 내 계산은 들어온 스캔의 좌표계에서 한 것이므로, 사실대로 적는 방법은 msg.header.frame_id 를 복사하는 것뿐이다.

7. (일부러 틀리면) std::fmod 의 결과가 음수일 때 +360 하는 줄을 지우면, 벡터 마흔 개 중 몇 개가 FAIL 하고 왜 나머지는 통과하는가?

넷이다 — wrap 으로 시작하는 넷. 집필자가 실제로 지워서 실행해 확인했다(2026-09-23, Mac). 나머지 서른여섯이 통과하는 이유는 그 벡터들의 angle_min 이 0 이기 때문이다. angle_min 이 0 이면 계산되는 각도가 처음부터 전부 양수라 fmod 만으로 충분하다. 요점 둘. ① 내 드라이버가 angle_min 을 0 으로 내면 이 잘못은 내 기기에서 계속 나타나지 않는다 — 안 나타나는 것과 없는 것은 다르다. ② 각도를 다시 정렬하지 않는 잘못도 정확히 같은 넷을 깨뜨린다. 벡터로 알 수 있는 것은 "틀렸다"까지이고 "왜"는 내가 찾는다.

비교본

체크포인트를 통과한 뒤에 내 코드와 견주어 보는 용도다. 먼저 열면 이 쪽에서 얻을 것이 줄어든다.

비교본 — scan_from_ranges() 하나 (집필자의 것, Mac 에서 마흔 벡터를 통과함) 
inline Scan scan_from_ranges(double angle_min_rad, double angle_increment_rad,
                             const std::vector<float>& ranges,
                             float range_min, float range_max, double t) {
  std::vector<std::pair<double, std::optional<double>>> pairs;
  pairs.reserve(ranges.size());
  for (std::size_t i = 0; i < ranges.size(); ++i) {
    double deg = std::fmod((angle_min_rad + static_cast<double>(i) * angle_increment_rad)
                               * 180.0 / M_PI, 360.0);
    if (deg < 0.0) { deg += 360.0; }
    const float d = ranges[i];
    const bool ok = std::isfinite(d) && d >= range_min && d <= range_max;
    pairs.emplace_back(deg, ok ? std::optional<double>(static_cast<double>(d)) : std::nullopt);
  }
  std::stable_sort(pairs.begin(), pairs.end(),
                   [](const std::pair<double, std::optional<double>>& x,
                      const std::pair<double, std::optional<double>>& y) {
                     return x.first < y.first;
                   });
  Scan out;
  out.t = t;
  out.a.reserve(pairs.size());
  out.r.reserve(pairs.size());
  for (const auto& p : pairs) { out.a.push_back(p.first); out.r.push_back(p.second); }
  return out;
}

내 것과 다를 수 있는 곳 — 정답이 하나가 아닌 자리다.

  • 정렬을 쓸 것인가. angle_min 이 음수면 이음매가 한 곳뿐이므로, 정렬 대신 그 자리에서 잘라 두 조각을 이어 붙이면 더 빠르다(O(n log n) 이 O(n) 이 된다). 벡터는 둘을 구별하지 않는다.
  • stable_sort 인가 sort 인가. 같은 각도가 둘 있을 때만 갈리고, 이 벡터들은 그 경우를 정해 두지 않았다. 갈리는 축이 없으면 동일이다.
  • 쌍을 무엇으로 담을 것인가. std::pair 대신 Scan 두 벡터를 직접 다뤄도 된다 — 다만 그때 둘을 따로 정렬하지 않도록 조심한다(§3-1-3 표의 셋째 줄이 그 잘못이다).
  • float 를 언제 double 로 넓힐 것인가. 여기는 갈리지 않는다 — 동일이다. float(binary32) → double(binary64) 변환은 무손실이다. 그래서 (double)d >= (double)range_min 은 모든 입력에서 d >= range_min 과 같은 답을 낸다. 집필자가 무작위 float 쌍 2 000 000 개로 대조했다(불일치 0, 2026-09-23, Mac). 위 코드가 float 끼리 비교하는 것은 취향이지 판정을 지키는 장치가 아니다. 정말로 잘리는 것은 반대 방향이다 — 결과를 다시 float32 메시지에 담을 때(§2-4 3번).
