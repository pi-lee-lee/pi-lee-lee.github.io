실습 A·B 의 명령과 도구(cp · sed · 시험 · core_dump)는 포트를 열지 않고 모터를 부르지 않는다 — 라이다가 꽂혀 있고 머리가 돌고 있었다면 그대로 돈다. 돈다고 간주한다. 실습 C·D 는 07 §3-5 의 드라이버를 띄우고, 드라이버가 머리를 돌린다. 내 노드는 포트를 열지 않는다. 드라이버를 끝낸 뒤에도 머리가 돌면 허브 쪽에서 라이다의 USB 케이블을 뽑는다(l-01 L2). 스캔 창을 렌즈 높이에서 정면으로 들여다보지 않는다 — 785 nm 적외선은 켜져 있어도 보이지 않는다(L1).

L1 · L2 는 l-01 이 정한 안전 규칙 번호다. L1 은 레이저 규칙, L2 는 도는 머리 규칙이다.

2. 원리 — 무엇을 옮기고, 무엇이 달라지고, 무엇이 같아야 하는가

2-1. 왜 순수 함수와 노드 껍질을 가르는가 — 시험할 수 있는 것만 믿을 수 있다

열다섯 쪽 동안 헤더마다 같은 줄을 적었다: "PURE: no port, no ROS, no clock." 그 한 줄이 있었기 때문에 scripts/lidar_lab/build/test_grid 가 라이다를 뽑아 놓고 실행됐다. C++ 의 #include 는 컴파일 시점에 해결되므로, 헤더 하나에 sensor_msgs/msg/laser_scan.hpp 가 들어가는 순간 그 헤더는 ROS 가 설치된 기계에서만 컴파일된다(l-06 §3-4-2 가 처음 만난 노드에서 이 선을 그었다).

저장소에 이미 두 층이 다 있다. 08d 는 본편의 쪽이고, 카메라와 라이다를 합쳐 물체를 추적하고 거리를 낸다. 08d §3-3 의 rpi5_vision/include/rpi5_vision/scan_projection.hpp 는 "ROS 에 묶이지 않은 순수 함수" 라고 적혀 있고 실제로 rclcpp 를 포함하지 않는다 — 대신 sensor_msgs/msg/camera_info.hpp · sensor_msgs/msg/laser_scan.hpp · tf2/LinearMath/Transform.h 를 포함한다. 그래서 노드를 띄우지 않고 시험할 수 있다는 성질은 그대로 얻는다. 이 쪽이 옮기는 헤더와 summary.hpp 는 08d 보다 한 단계 더 나아가 메시지 타입도 포함하지 않는다. 그래서 ROS 가 없는 호스트에서 컴파일된다(§3-2-3). 격자를 메시지로 바꾸는 src/grid_msg.hpp 하나만 08d 와 같은 꼴이다 — 메시지 타입을 포함하고 rclcpp 는 쓰지 않는다(§3-3-2).

두 선택이 각각 무엇을 얻는가 (어느 쪽이 낫다는 말이 아니다)

메시지 타입을 포함하는 헤더(08d) — 함수가 메시지를 통째로 받으므로 호출하는 쪽 코드가 한 줄이고, 필드를 옮겨 적다가 빠뜨릴 자리가 없다. 대가: ROS 가 있어야 컴파일된다.

필드만 받는 헤더(이 쪽) — ROS 없이 컴파일·시험된다. 대가: 메시지에서 필드를 꺼내 넘기는 줄이 노드 쪽에 생기고, 그 줄은 시험이 채점하지 않는다. 그 줄에서 angle_min 과 angle_max 를 바꿔 넘기면 시험은 전부 통과하고 지도만 틀린다 — 증상표의 마지막 행이 이 경우다.

차이가 없는 축: 만들어지는 결과와 속도(동일). 두 선택은 어디서 컴파일되는가와 어디에 검사되지 않는 줄이 남는가의 맞바꿈이다.

2-2. 옮긴다 = 복사 + 이름 두 가지

이 프로젝트의 언어 배정은 데이터가 지나가는 처리 로직은 C++, 사람이 확인하는 도구만 파이썬이다(결정 L8). l-01 ~ l-15 의 처리 로직이 이미 C++ 이고, 07 §3-10 의 scan_watch 도 C++ 다. 그래서 이 쪽은 다시 쓰지 않는다 — 옮긴다. 옮기는 방법은 결정 L7 이 정했다: 복사다.

바뀌는 것앞뒤왜 바꾸는가
자리scripts/lidar_lab/include/lidar_lab/ros2_ws/src/rpi5_lidar_tools/include/rpi5_lidar_tools/compose 가 마운트하는 쪽(§2-3). 패키지의 헤더는 include/<패키지 이름>/ 에 두는 것이 ament(ROS 2 의 빌드 체계) 패키지의 관례다
include 접두사#include "lidar_lab/geom.hpp"#include "rpi5_lidar_tools/geom.hpp"폴더 이름이 바뀌었기 때문이다. 안 바꾸면 컴파일러가 파일을 못 찾는다(§3-1-4)
이름공간namespace lidar_labnamespace rpi5_lidar_tools이름이 어느 폴더의 코드인지를 적는다. 같은 이름의 함수가 scripts/ 쪽에도 계속 있으므로, 둘이 한 프로그램에 섞여도 겹치지 않는다

바뀌는 것은 이 셋뿐이고 함수 본문은 한 글자도 바뀌지 않는다. 함수 본문이 그대로인지를 diff 로 확인한다 — 바뀐 줄이 전부 이름이 든 줄이면 옮기기가 끝난 것이다(§3-1-3).

⚠ 복사에는 값이 따른다. 같은 헤더가 두 벌(scripts/ 와 패키지) 생긴다. scripts/ 쪽은 실습 도구가 계속 빌드되도록 남기는 것이다(결정 L7). 그래서 나중에 어느 한 벌을 고치면 다른 한 벌도 고쳐야 한다 — 예를 들어 .scan.jsonl 에 필드를 더하면 읽는 쪽이 셋이 된다(두 벌의 scan_io.hpp 와 확인용 편의 도구 view/scanfile.py). 형식이 고정돼 있어야 하는 이유가 하나 더 생긴 셈이다(l-04 §2-6).

2-3. 마운트 목록이 그 선이다 — 왜 scripts/ 는 컨테이너에 없는가

docker/docker-compose.yml 의 volumes 는 다섯 줄이다 — ../ros2_ws:/ros2_ws · /dev · /run/udev · /sys/class/gpio · ros-cache. scripts/ 는 없다. l-06 §2-5 가 이미 그 이유와 1회성 -v 조각을 실었다 — 여기서 다시 논증하지 않는다. 1회성 -v 는 docker compose run 의 -v 로 그 한 번만 폴더를 컨테이너에 보여 주는 방법이다.

이 쪽에서 쓸모 있는 것은 그 결정의 다른 쪽 면이다. scripts/lidar_lab/ 을 상시 마운트하지 않기로 한 이유가 "실습 도구는 실행 중인 시스템의 부품이 아니다" 라면, 부품이 되려면 ros2_ws/ 쪽으로 복사돼야 한다는 말이 된다. 그리고 복사되는 것은 전부가 아니라 남길 조각이다.

2-4. 같은 헤더의 두 빌드가 갈릴 수 있는 자리

옮긴 헤더는 한 벌의 소스다. 그래도 빌드하는 자리가 둘이면 답의 마지막 자리가 갈릴 수 있다. 갈릴 수 있는 자리는 정해져 있다. 표의 Trixie 는 Pi 호스트의 OS 인 Raspberry Pi OS Trixie 다. "확인 과제"는 집필자가 확인하지 못해 내가 내 장치로 확인할 항목이다.

2-7. 이제 시간이 예산이 된다

지금까지 도구는 파일을 입력으로 받았다. 파일 입력에는 시간 제한이 없다. /scan 을 구독하면 사정이 달라진다. 콜백이 끝나기 전에 다음 장이 온다면, 그다음은 셋 중 하나다 — 큐에 쌓이거나, 버려지거나, 점점 밀린다. SensorDataQoS() 는 작은 큐 + BEST_EFFORT(놓친 메시지를 재전송받지 않는 전달 설정)라 보통 버려진다(그래서 오류가 안 난다).

그래서 예산이 생긴다: 콜백 한 번 ≤ 한 바퀴의 주기. 그 주기는 1000 ÷ 내 회전수 ms 이고, l-04 §3-2 에서 잰 값이다(l-15 의 "한 바퀴 ____ ms").

⚠ 5.5 Hz(주기 약 182 ms)를 예산으로 고정하지 않는다. 그 값은 데이터시트 성능 표의 typical(대표값)이고 360 samples per scan 이라는 조건이 같은 칸에 붙어 있다.2 내 기기가 그 조건에서 동작하는지는 내가 잰 회전수로 확인한다.

콜백 안의 계산은 앞 쪽에서 이미 쟀다 — from_scan() 한 장은 호스트 빌드(-O2)에서 1 ms 안쪽이었다(l-09 §3-4-4).3 노드에서는 두 가지가 달라진다. 첫째, 콜백은 scan_from_ranges() 와 발행까지 포함한다. 둘째, 07 의 colcon 명령은 빌드 종류(CMake 의 CMAKE_BUILD_TYPE)를 정하지 않아 최적화 없이(-O0) 빌드된다 — 같은 함수가 몇 배 느려진다.4 그래서 §3-3-5 에서 두 빌드 종류로 한 번씩 잰다. 내 Pi 의 값은 재 봐야 안다(확인 과제).

// What summarize() reports about one Scan.
struct Summary {
  std::size_t points = 0;      // s.size(): every slot, measured or not
  std::size_t no_returns = 0;  // the slots that to_xy() left EMPTY
  std::optional<Point> first;  // the measured point with the SMALLEST index, or empty
  std::optional<Point> last;   // the measured point with the LARGEST index, or empty
  Point sum{0.0, 0.0};         // x and y of the measured points added up, in index order
};

// One Scan -> its Summary. Invariants -- each is graded by a vector in tests/test_summary.cpp:
//   1. The points are to_xy(s) (l-08, moved unchanged). No trigonometry of its own here,
//      so both builds compare the SAME formula, not two copies of it.
//   2. no_returns counts EMPTY slots only. r == 0.0 is a measured point (l-04 2-6).
//   3. first / last skip empty slots: a revolution that begins with a no-return still has a
//      first point. With no measured point at all both stay EMPTY -- not (0.0, 0.0).
//   4. sum adds in double, in index order 0, 1, 2 ... The order is part of the result:
//      another order can change the last digit, and two builds that agree would then look
//      as if they did not.
inline Summary summarize(const Scan& s) {
  // TODO(you) [T1]: points = every slot. Then walk to_xy(s) ONCE, in index order: an empty
  //   slot is a no-return; a measured one may be the first, is the last so far, and is added
  //   to sum. Decide invariant 2 (r == 0.0) BEFORE you write the loop.
  (void)s;
  return {};
}

// The five lines. Numbers as repr_double() -- the shortest digits that read back to the
// same double; a fixed "%.6f" would hide a difference in the last digits -- and "none" for
// an empty point:
//   points 4
//   no-returns 1
//   first 1.0 0.0
//   last -3.6739403974420594e-16 -2.0
//   sum 0.9999999999999997 -2.0
inline std::string summary_text(const Summary& m) {
  auto xy = [](const std::optional<Point>& p) {
    return p ? repr_double(p->first) + " " + repr_double(p->second) : std::string("none");
  };
  return "points " + std::to_string(m.points) + "\n" +
         "no-returns " + std::to_string(m.no_returns) + "\n" +
         "first " + xy(m.first) + "\n" +
         "last " + xy(m.last) + "\n" +
         "sum " + repr_double(m.sum.first) + " " + repr_double(m.sum.second) + "\n";
}

}  // namespace rpi5_lidar_tools

// (summary.hpp, your T1).  (l-16, given in full)

//   270 deg, r = 2  -> x = 2 * cos(to_rad(270)) = -3.6739403974420594e-16, not 0.0

#include <string>

#include <vector>

namespace {

Scan scan(std::vector<double> a, std::vector<std::optional<double>> r) {
  Scan s;
  s.a = std::move(a);
  s.r = std::move(r);
  return s;
}

double xof(const std::optional<Point>& p) { return p ? p->first : -99.0; }
double yof(const std::optional<Point>& p) { return p ? p->second : -99.0; }

// Several lines as one, so a FAIL line stays one line: a newline between lines -> " | ".
std::string oneline(std::string text) {
  if (!text.empty() && text.back() == '\n') text.pop_back();
  std::string out;
  for (char c : text) out += (c == '\n') ? std::string(" | ") : std::string(1, c);
  return out;
}

}  // namespace

int main() {
  // 1. four slots: a point, a no-return, a MEASURED ZERO, a point.
  const Summary m = summarize(scan({0.0, 90.0, 180.0, 270.0}, {1.0, std::nullopt, 0.0, 2.0}));
  eq_int("1a points counts every slot", static_cast<long long>(m.points), 4);
  eq_int("1b no-returns counts the empty slot only (0.0 is a point)",
         static_cast<long long>(m.no_returns), 1);
  near("1c first is index 0 -> x", xof(m.first), 1.0);
  near("1d first is index 0 -> y", yof(m.first), 0.0);
  near("1e last is index 3 (270 deg, r=2) -> x", xof(m.last), 0.0);
  near("1f last is index 3 (270 deg, r=2) -> y", yof(m.last), -2.0);
  near("1g sum of x over the three measured points", m.sum.first, 1.0);
  near("1h sum of y over the three measured points", m.sum.second, -2.0);

  // 2. a revolution that BEGINS with a no-return still has a first point.
  const Summary b = summarize(scan({0.0, 90.0}, {std::nullopt, 3.0}));
  near("2a first skips the empty slot 0 -> y of index 1", yof(b.first), 3.0);
  // 3. a revolution that ENDS with a no-return: last is the last MEASURED point.
  const Summary e = summarize(scan({0.0, 90.0}, {3.0, std::nullopt}));
  near("3a last skips the empty last slot -> x of index 0", xof(e.last), 3.0);

  // 4. nothing measured: first and last stay EMPTY, they do not become (0.0, 0.0).
  const Summary n = summarize(scan({0.0, 90.0}, {std::nullopt, std::nullopt}));
  check("4a no measured point -> first none", !n.first.has_value(), str(n.first), "none");
  check("4b no measured point -> last none", !n.last.has_value(), str(n.last), "none");
  eq_int("4c two empty slots -> no-returns 2", static_cast<long long>(n.no_returns), 2);

  // 5. the sum is a double, added left to right (invariant 4).
  const Summary d = summarize(scan({0.0, 0.0, 0.0}, {0.1, 0.2, 0.3}));
  check("5a 0.1 + 0.2 + 0.3 in double, not float", d.sum.first == 0.6000000000000001,
        str(d.sum.first), "0.6000000000000001");
  const Summary o = summarize(scan({0.0, 0.0, 0.0}, {1e16, 1.0, 1.0}));
  check("5b index order: (1e16 + 1.0) + 1.0 = 1e16 (right to left gives 1.0000000000000002e16)",
        o.sum.first == 1e16, str(o.sum.first), "1e+16");

      "points 4\nno-returns 1\nfirst 1.0 0.0\nlast -3.6739403974420594e-16 -2.0\n"
      "sum 0.9999999999999997 -2.0\n";
  check("6a summary_text of vector 1", summary_text(m) == want6, oneline(summary_text(m)),
        oneline(want6));

  return finish("summary");
}

/* 완결 코드 T1 - ros2_ws/src/rpi5_lidar_tools/include/rpi5_lidar_tools/summary.hpp (summarize) */
inline Summary summarize(const Scan& s) {
  Summary m;
  m.points = s.size();
  const std::vector<std::optional<Point>> xy = to_xy(s);
  for (const std::optional<Point>& p : xy) {
    if (!p) {
      ++m.no_returns;
      continue;
    }
    if (!m.first) m.first = p;
    m.last = p;
    m.sum.first += p->first;
    m.sum.second += p->second;
  }
  return m;
}

코드 설명

  • m.points = s.size(); — 측정됐든 아니든 칸 전부다(1a).
  • const std::vector<std::optional<Point>> xy = to_xy(s); — 좌표는 l-08 의 to_xy() 가 만든다. 여기서 cos · sin 을 다시 쓰지 않는다(불변식 1) — 두 빌드가 같은 식을 견주게 하기 위해서다.
  • if (!p) { ++m.no_returns; continue; } — 빈 칸만 무반사다. to_xy() 는 r == 0.0 을 원점의 점으로 만들므로 여기서 따로 판단할 것이 없다(1b, l-04 §2-6).
  • if (!m.first) m.first = p; — 첫 점은 처음 만난 측정점이다. 앞의 빈 칸은 건너뛴다(2a).
  • m.last = p; — 측정점을 만날 때마다 덮어쓴다. 루프가 끝나면 마지막 측정점이 남는다(3a).
  • m.sum.first += p->first; — double 에, 번호 순으로 더한다(불변식 4, 5a · 5b).
  • 골격의 자리표시((void)s; · return {};)는 지웠다.

  • 다르게 써도 되는 곳 — 번호 i 로 반복하는 for (std::size_t i = 0; i < xy.size(); ++i) 도 같다. 무반사를 std::count_if 로 따로 세도 된다 — 다만 합은 번호 순 한 번이어야 한다.

std_msgs::msg::Header header(const std::string& frame, int sec, unsigned nanosec) {

int main() {

  g.cells = {-1, 0, 100, 0, -1, 100};  // row 0 (bottom) then row 1

  check("1a header.frame_id copied", m.header.frame_id == "laser", "'" + m.header.frame_id + "'",

  eq_int("1c header.stamp.nanosec copied", m.header.stamp.nanosec, 5);

  near("3a info.origin.position.x = ox", m.info.origin.position.x, -3.0);
  near("3b info.origin.position.y = oy", m.info.origin.position.y, -1.5);

  eq_int("4a data has width * height cells", static_cast<long long>(m.data.size()), 6);
  check("4b data = g.cells, value for value", as_ints(m.data) == as_ints(g.cells),
        str(as_ints(m.data)), str(as_ints(g.cells)));

  const nav_msgs::msg::OccupancyGrid k = to_message(header("laser_link", 0, 0), g);

완결 코드

/* 완결 코드 T2 - ros2_ws/src/rpi5_lidar_tools/src/grid_msg.hpp (to_message) */
inline nav_msgs::msg::OccupancyGrid to_message(const std_msgs::msg::Header& header, const Grid& g) {
  nav_msgs::msg::OccupancyGrid out;
  out.header = header;
  out.info.map_load_time = header.stamp;
  out.info.resolution = static_cast<float>(g.res);
  out.info.width = static_cast<unsigned>(g.nx);
  out.info.height = static_cast<unsigned>(g.ny);
  out.info.origin.position.x = g.ox;
  out.info.origin.position.y = g.oy;
  out.data = g.cells;
  return out;
}

코드 설명

  • out.header = header; — frame_id 와 stamp 를 통째로 복사한다. 지어내지 않고, 지금 시각을 찍지 않는다(§2-6, 1a ~ 1c · 5a).
  • out.info.map_load_time = header.stamp; — 이 칸은 "지도를 읽은 시각"이다. 한 바퀴로 만든 격자이므로 그 바퀴의 시각을 넣는다. 시험은 이 칸을 보지 않는다.
  • out.info.resolution = static_cast<float>(g.res); — 메시지의 칸이 float32 라서 좁힌다. 그래서 echo 가 0.05000000074505806 을 찍는다(2a, §3-3-4).
  • out.info.width · height — 셀 수 nx · ny(2b · 2c).
  • out.info.origin.position.x = g.ox; — 셀 (0, 0) 의 왼쪽 아래 모서리다. 센서 자리가 아니다(l-09 §2-4, 3a · 3b). 방향(orientation)은 채우지 않는다 — 메시지 정의가 w 의 기본값을 1 로 두어(float64 w 1) 빈 메시지도 "돌리지 않음"이다.
  • out.data = g.cells; — 값(−1 · 0 · 100)과 순서(행 우선, 아래 행부터)가 같아서 한 줄이다(§2-6, 4a · 4b).
  • 골격의 자리표시((void)header; · (void)g; · return nav_msgs::msg::OccupancyGrid();)는 지웠다.

  • 다르게 써도 되는 곳 — map_load_time 줄은 빼도 시험은 통과한다. data 를 assign(g.cells.begin(), g.cells.end()) 로 채워도 같다.

쓰는 API — nav_msgs::msg::OccupancyGrid(header · info · data) · std_msgs::msg::Header · Grid(l-09 의 grid.hpp).

3-3-5. 콜백 시간 — 내 주기와 견준다

내 회전수가 l-04 §3-2 에 적혀 있는가. 이 걸음의 합격선이 그 값 하나에서 나온다(1000 ÷ 내 회전수 ms). 없으면 ms 까지만 적고 l-04 로 돌아가 회전수를 재 온 뒤 표의 나머지를 채운다. ⚠ 5.5 Hz(주기 약 182 ms)를 대신 쓰지 않는다(§2-7).

  1. 시계는 이미 골격에 있다. steady_clock 을 쓰는 것에 주목한다 — 벽시계는 시각이 뒤로 갈 수 있어서 음수 구간이 나온다. 시계는 순수 함수 밖(콜백)에 있다 — l-09 §3-4-3 이 같은 선을 그었다.
  2. 1분쯤 실행하며 로그를 모은다. 로그는 1초에 한 줄이다(스로틀). 스로틀은 마지막 출력 뒤 1초가 지난 첫 콜백만 남기므로, 1분이면 콜백은 수백 번인데 줄은 약 60 줄이다 — 그래서 표본의 최대값은 실제 최대보다 작게 나올 수 있다. 최소값·중앙값·최대값 셋을 적는다.
  3. 빌드 종류를 바꿔 한 번 더 잰다. 07 의 명령은 최적화 없이 빌드한다(§2-7). 호스트의 lab_grid --time(-O2)과 같은 조건으로 견주려면 --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo 를 붙여 다시 빌드한다. RelWithDebInfo 는 최적화 -O2 로 빌드하는 빌드 종류다. 이 값은 패키지의 빌드 폴더에 남으므로, 다음 빌드도 그 종류다 — 되돌리려면 같은 자리에 -DCMAKE_BUILD_TYPE=(빈 값)를 준다.

3. scripts/lidar_lab/ 을 compose 에 상시 마운트하면 무엇이 편해지고, 이 프로젝트는 왜 그렇게 하지 않았는가?

편해지는 것: 노드가 scripts/ 의 헤더를 복사 없이 바로 include 할 수 있다. 실습 A 가 통째로 없어지고, 실습 D 의 1회성 -v 도 필요 없다.

하지 않는 이유는 성능이 아니라 그 파일들의 성격이다 — scripts/lidar_lab/ 은 "이해하려고 한 번 만들어 보는 도구"이지 실행 중인 시스템의 부품이 아니다(§2-3). 상시 마운트하면 로봇의 노드가 실습 폴더에 기대게 되고, 무엇이 로봇의 일부인지의 선이 흐려진다. 그 선이 불분명해지면 나중에 "이거 빼도 되나?" 를 판단할 근거가 사라진다. 그래서 부품이 되는 방법은 마운트가 아니라 ros2_ws/src/rpi5_lidar_tools/ 로 복사하는 것이고, 복사하는 것은 전부가 아니라 고른 조각이다.

4. 이름공간을 바꾸는 sed 만 빠뜨리면 빌드는 옮긴 파일이 아니라 새로 쓴 summary.hpp 에서 멈춘다. 왜 거기인가?

옮긴 헤더와 옮긴 시험은 둘 다 옛 이름공간 lidar_lab 을 그대로 쓰고 있다 — 헤더는 namespace lidar_lab, 시험은 using namespace lidar_lab;. 둘이 서로 맞으므로 그 파일들끼리는 컴파일된다. 멈추는 곳은 새로 쓴 쪽이다. summary.hpp 는 namespace rpi5_lidar_tools 안에서 Point · Scan · to_xy 를 찾는데, 그 이름은 아직 lidar_lab 에 있다. 그래서 ‘Point’ was not declared in this scope; did you mean ‘lidar_lab::Point’? 가 난다(증상표 둘째 행). 요점: 옮긴 것끼리만 보면 이름을 안 바꿔도 동작한다. 이름을 바꾸는 이유는 같은 이름의 함수가 scripts/ 쪽에도 남아 있어서, 둘이 한 프로그램에 섞여도 겹치지 않게 하려는 것이다(§2-2).

5. 실습 D 에서 first · last 는 같은데 sum 만 마지막 몇 자리가 갈렸다. 둘 중 한 빌드가 틀린 것인가?

아니다. 두 빌드는 같은 소스이고, 갈릴 수 있는 자리는 §2-4 의 표에 있다. 수학 라이브러리가 다르면 같은 각도의 cos 가 마지막 비트에서 다를 수 있다. first · last 는 점 하나씩이라, 그 두 각도가 마지막 비트에서 갈리는 각도일 때만 달라진다 — 그런 일은 드물다. sum 은 1 450 점을 모두 거치므로 그중 한 점만 달라도 그 차가 합에 남는다. 어느 라이브러리의 값이 "더 맞는지"는 이 대조로 알 수 없다 — 대조는 다르다는 것만 알려 준다(용어 표). 그래서 표의 답은 "같다 · 다르다"가 아니라 "몇째 자리부터 갈렸다" 이고, 정수 두 줄(points · no-returns)이 다를 때만 고칠 데가 있다.

6. 격자를 /map 으로 내면 무엇이 일어나는가? 그리고 결과 메시지의 frame_id 를 내가 지어 적으면?

/map 은 09 의 slam_toolbox 가 발행하는 이름이다. 같은 이름으로 발행하면 발행자가 둘이 되고, 구독자가 어느 쪽을 받는지는 메시지마다 달라진다. 오류는 나지 않는다 — 빌드도 실행도 된다(§3-3-2). frame_id 를 지어 적으면 — 예를 들어 드라이버가 laser_frame 으로 내는데 laser_link 라고 적으면 — TF 에 그 이름이 없어 Foxglove 가 그리지 못하거나 엉뚱한 자리에 그린다. 내 계산은 들어온 스캔의 좌표계에서 한 것이므로, 사실대로 적는 방법은 msg.header 를 복사하는 것뿐이다(§2-6).

7. 07 의 colcon 명령 그대로 빌드한 노드의 콜백이, 호스트에서 잰 from_scan() 보다 훨씬 느렸다. 무엇이 다른가?

둘이다. 첫째, 빌드 종류다 — 07 의 명령은 빌드 종류를 정하지 않아 최적화 없이(-O0) 빌드하고, 호스트의 scripts/lidar_lab 은 -O2 로 빌드한다(§2-7). 둘째, 재는 범위다 — 콜백 시간은 scan_from_ranges() 와 발행까지 포함하고, lab_grid --time 은 from_scan() 만 잰다. 그래서 §3-3-5 는 빌드 종류를 바꿔 한 번 더 재고, 표에 두 줄을 나란히 둔다. 같은 함수라도 어떻게 빌드했는지를 같이 적지 않은 시간은 견줄 수 없다.
