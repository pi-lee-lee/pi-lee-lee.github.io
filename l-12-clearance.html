2-2. 최소 거리는 방향을 모른다 — 그래서 수가 둘이어야 한다

"앞의 벽까지 1.4 m" 하나만 있으면 로봇은 멈추는 것 말고 할 수 있는 일이 없다. 벽을 따라가려면, 문을 통과하려면, 벽을 마주 보고 정렬하려면 그 면이 어느 쪽을 향하는지를 알아야 한다. 그리고 그 방향은 최소 거리 점이 어디 있는가로는 알 수 없다.

수직 거리부터 보자. 선분의 양 끝이 p0·p1 이고 센서가 원점 O 라면, 센서에서 그 직선까지의 수직 거리는 l-11 이 이미 쓴 식 그대로다.

perp_distance(seg) = point_line_distance(O, seg.p0, seg.p1)
                   = |cross(p1 - p0,  O - p0)| / |p1 - p0|

⚠ 새 식이 아니다. l-11 §2-2 의 식에 점 자리로 원점을 넣은 것이 전부다. 그래서 이 함수는 한 줄이고, §3-1-2 가 그 한 줄을 전량으로 준다 — 그 한 줄이 l-11 을 왜 했는지의 답이다. 점이었다면 "센서에서 벽까지"는 점마다 다른 수백 개의 수였지만, 면이 되었으므로 수 하나가 된다.

인자가 seg 하나뿐인 것도 우연이 아니다. 센서는 언제나 원점이라고 l-08 §2-2 가 좌표 계약에 적어 두었다. 계약이 없었다면 이 함수는 센서 위치를 인자로 받아야 했고, 그 인자를 빼먹은 호출이 오류 없이 틀린 거리를 냈을 것이다.

직선까지다 — 선분까지가 아니다

perp_distance 는 선분을 무한한 직선으로 늘려 거리를 잰다. 그래서 수직선의 발이 선분 밖으로 떨어질 수 있다 — 옆으로 비껴 있는 짧은 벽 조각 하나가 "1.0 m 앞"이라고 보고되는데 정작 그 방향에는 아무것도 없다. 시험 벡터 5·12 가 정확히 이 경우이고, 값은 버그가 아니라 정의다. 시험 벡터는 입력과 기대 출력을 정해 둔 시험 한 건이다(§3-5-2).

왜 잘라서(선분 안으로 제한해서) 재지 않는가 — 벽을 따라가려면 벽이 놓인 면이 필요하지 지금 보이는 조각의 끝이 필요한 것이 아니기 때문이다. 대신 발이 선분 안에 있는지는 따로 확인한다 — 그 확인이 foot_inside()(§3-1-3, T2)다. perp_distance() 에 조건을 넣어 늘리는 대신 확인을 이름 있는 함수로 따로 두었다. 그래서 도구 lab_clear 는 선분마다 거리와 함께 foot in / foot out 을 찍는다.

2-2-1. 이 쪽의 첫 일 — 법선에 뜻을 붙인다

l-11 §2-5-2 는 법선을 하나로 정했지만 뜻은 정하지 않았다: p0 → p1 방향을 반시계로 90° 돌린 것, 곧 (dx, dy) 에 대해 (-dy, dx). 같은 입력에 같은 답이 나오게 하는 것까지가 l-11 의 일이었고, "어느 쪽이 벽이고 어느 쪽이 나인가"는 이 쪽으로 넘어왔다.

그 법선은 점의 순서에 따라 정해진다. 같은 벽이라도 선분이 p0 → p1 로 적혔는지 거꾸로 적혔는지에 따라 법선이 정반대가 된다. 그리고 점의 순서는 내가 정한 것이 아니다 — 스캔의 각도 순서이고, 덩어리가 0° 이음매를 걸치면 순서가 달라진다(l-10 §2-2). 그래서 normal() 을 그대로 쓰면 같은 벽의 법선이 어떤 날은 앞을, 어떤 날은 뒤를 가리킨다.

규약 — 바깥 법선 (이 가이드 안에서 고정)

선분의 법선 n 둘 중, 센서에서 벽으로 가는 쪽을 바깥 법선이라 부르고 이 쪽의 모든 계산은 바깥 법선을 쓴다. 고르는 규칙은 부등호 하나다 — 센서가 원점이므로 센서에서 벽 위의 한 점으로 가는 벡터는 p0 자신이고,

n · p0  > 0   이면  n 이 이미 바깥 법선이다
n · p0  < 0   이면  -n 이 바깥 법선이다          (n · p0 = nx*p0x + ny*p0y)

이 한 줄을 통과하면 점의 순서가 뒤집혀도 답이 같아진다. 시험 벡터 9 가 정확히 이 성질을 채점한다 — 같은 벽을 Segment{p1, p0, n} 으로 뒤집어 넣어도 방위가 같아야 한다.

⚠ n · p0 == 0 인 경우는 벽이 센서를 지나간다는 뜻이다(수직 거리 0). 실물에서는 일어나지 않고, 일어났다면 값이 아니라 입력이 틀린 것이다.

그 다음은 짧다. 바깥 법선의 방향이 곧 그 면을 마주 보려면 돌아야 하는 각이다.

heading_to(seg) = normalize( atan2(n_out_y, n_out_x) )      n_out = 바깥 법선

0 이면 벽이 이미 정면이고, + 면 왼쪽으로 그만큼 돌면 마주 본다(l-08 의 좌표 계약: +y 가 왼쪽, 각은 반시계 +). 그리고 이 값이야말로 최소 거리가 결코 줄 수 없는 것이다 — 최소 거리는 스칼라 하나라 방향이라는 정보 자체가 들어 있지 않다.

2-2-2. 라디안이다, 그리고 [-π, π] 는 양 끝이 다 나온다

단위부터 정한다. heading_to 는 라디안을 돌려준다. 이유는 둘이다 — normalize()(l-08 §2-5)가 라디안이고, ROS 의 각도 규약이 라디안이다. 사람이 읽는 자리(화면·노트)에서만 to_deg()(l-06 의 angles.hpp)로 바꾼다.

⚠ 같은 도구 상자 안에서 l-11 의 corners(segments, min_angle_deg) 는 도(度)다. 섞으면 57.3배 틀린 값이 오류 없이 지나간다(1 rad = 57.29577951308232°). 이름 끝에 _deg 가 붙었는지가 유일한 표시이고, 증상 표에 그 행이 있다.

범위는 normalize() 가 정한다. 그 함수의 실제 치역은 [-π, π] 이고 — 여기가 중요하다 — 양 끝이 다 나온다. l-08 이 geom.hpp 의 normalize() 위 주석에 실측으로 적어 두었다(normalize(-kPi) comes back as -kPi). normalize(-π) 는 +π 가 아니라 -3.141592653589793 으로 돌아온다.

π 근처에서 생기는 문제 — 그리고 이 쪽이 그 문제를 피하는 방법

센서 바로 뒤의 벽은 방위가 +π 일 수도 -π 일 수도 있다. 기하는 똑같은데 부호가 뒤집힌다 — 점의 순서, 반올림, 덩어리가 이음매를 걸쳤는지 같은 것에 따라 갈린다. 그래서 이 쪽은 세 가지를 한다.

  • 방위를 빼지 않는다. h1 - h2 는 π 를 넘나들 때 뜻이 없다. 차가 필요하면 반드시 normalize(h1 - h2) 로 감는다. normalize() 는 이 일을 하려고 있다(l-08 §2-5).
  • 방위를 평균 내지 않는다. +179° 와 -179° 의 산술 평균은 0°, 곧 정반대 방향이다. 두 벽의 "가운데 방향"이 필요하면 각이 아니라 단위 벡터를 더해서 낸다.
  • 통로를 가를 때는 뒤쪽을 아예 잘라 낸다 — 다음 절이 그 규칙이다.

시험 벡터 11 은 이 성질 때문에 부호를 채점하지 않는다(std::fabs() 를 씌워 π 와만 견준다). 채점할 수 없는 것을 채점하는 시험은 맞는 구현도 통과시키지 못한다.

2-3. 통로 폭은 두 덩어리 사이의 틈이지 가장 가까운 점까지의 거리가 아니다

문을 지나갈 수 있는지를 정하는 것은 문설주 두 개 사이의 간격이다. 그런데 초보의 도구는 거의 언제나 센서에서 가장 가까운 점까지의 거리를 재고 그 거리를 폭이라 부른다. 두 수는 아무 관계가 없다. 센서가 문 한가운데에 있으면 양쪽 설주까지 각각 0.4 m 인데 문 폭은 0.8 m 다. 센서가 한쪽 설주 가까이 있으면 가장 가까운 점은 0.05 m 인데 문 폭은 그대로 0.8 m 다.

그래서 passage_width(clusters, direction) 는 이렇게 센다.

  1. 가려는 방향 direction(라디안)을 받는다. 가려는 방향이 없으면 통로도 없다 — 같은 두 덩어리가 어느 방향으로 가느냐에 따라 문설주가 되기도 하고 그냥 벽이 되기도 한다.
  2. 그 방향 앞쪽(±90° 안)에 있는 덩어리만 본다. 뒤쪽 것은 문설주가 아니다.
  3. 남은 것을 왼쪽 / 오른쪽으로 가르고, 각 쪽에서 가려는 방향에 가장 가까운 덩어리 하나씩을 고른다.
  4. 고른 두 덩어리의 점 대 점 최단 거리가 폭이다. 중심끼리의 거리가 아니다 — 시험 벡터 13 이 그 둘을 가른다(같은 입력에서 0.8 과 1.6000000000000003 으로 갈린다).1

⚠ 한쪽에 덩어리가 없으면 이 함수는 수를 내지 않는다. 그래서 반환 타입이 std::optional<double> 이고, 그 경우에 빈 값(std::nullopt)을 돌려준다. 도구는 빈 값을 none 으로 찍는다. 0.0 을 쓰지 않는다 — 이유는 l-04 가 기준 형식에서 무반사를 null 로 정한 것과 똑같다(l-04 §3-4-2). 기준 형식은 l-04 가 정한 기록 파일 .scan.jsonl 의 형식이고, 무반사는 레이저가 돌아오지 않아 거리를 못 잰 방향이다. 0.0 은 "폭이 0 이다(못 지나간다)"와 구별되지 않고, inf 는 "막는 것이 없다(마음껏 지나가라)"처럼 읽힌다. 빈 값은 "못 쟀다" 하나만 뜻한다.

C++ 의 double 에는 inf 와 NaN 이 값으로 들어 있다. 그래서 "없음"을 double 하나로 나타내면 계산이 만든 inf · NaN 과 섞인다. 빈 값을 따로 두는 까닭과 그 꺼내는 법은 l-04 §2-6-2 에 있다.

그리고 그 빈 값이 fits() 에 들어가면 false 다. "모른다"를 통과로 답하지 않는다. 이 규칙은 판정 함수가 가질 수 있는 가장 간단한 안전장치이고, 시험 벡터 24 · 25 가 이 규칙을 채점한다.

2-3-1. 왼쪽·오른쪽을 무엇으로 가르는가 — 그리고 왜 뒤를 잘라 내는가

덩어리 하나가 가려는 방향의 어느 쪽인지는 부호가 있는 각으로 정한다. 덩어리 중심의 방위에서 가려는 방향을 빼고, 반드시 감는다(§2-2-2).

s = normalize( atan2(cy, cx) - direction )        (cx, cy) = 덩어리의 중심(점들의 평균)

s > 0  왼쪽        s < 0  오른쪽        |s| ≥ π/2  앞쪽이 아니다 — 아예 보지 않는다

마지막 조건이 없으면 무슨 일이 생기는지가 이 절의 요점이다. 뒤쪽 180° 부근에서는 s 의 부호를 그대로 받아들일 수 없다 — 정확히 뒤에 있는 덩어리는 +π 와 -π 중 아무 쪽으로나 나오고(§2-2-2), 그러면 같은 덩어리가 어떤 날은 왼쪽, 어떤 날은 오른쪽이 된다.

더 나쁜 것은 이 문제가 오류 표시 없이 지나간다는 점이다. 한쪽 설주가 없는 장면(벽 하나에 붙은 모서리 같은 것)에서 뒤에 있던 아무 물건이 반대쪽 설주로 선택되고, 도구는 none 대신 그럴듯한 수를 낸다. 시험 벡터 17 이 그 장면이다 — 앞쪽 조건을 빼면 빈 값이어야 할 자리에서 2.08806130178211 이 나온다.1

그래서 뒤를 자르는 것은 π 근처를 피해 가는 요령이면서 동시에 물리적으로 맞는 규칙이다. 문설주는 가려는 방향의 옆에 있지 뒤에 있지 않다. 두 이유가 같은 한 줄의 조건으로 해결된다는 것이 이 규칙이 안전한 이유다. 요령일 뿐이었다면 언젠가 그 줄을 지우고 싶어졌을 것이다.

⚠ s 가 정확히 0 인 덩어리(중심이 가려는 방향 위에 있다)는 어느 쪽에도 넣지 않는다. 그 덩어리는 문설주가 아니라 문 한가운데를 막고 있는 것이고, 통로 폭이 아니라 다른 판정(정면 최소 거리, §3-2)이 다룰 장면이다.

2-4. 로봇 폭은 어디서 오는가 — 지금은 임시값이라고 적는다

판정에 들어가는 셋 중 둘(로봇 폭·여유)은 센서가 주지 않는다. 그런데 이 프로젝트에서 로봇 폭은 아직 확정된 수가 아니다. 있는 것을 정직하게 늘어놓으면 이렇다.

  d = 5.0 m  ->  0.13092960784593466 m       (약 13.1 cm)

그래서 "5 m 앞의 장애물이 스캔 면에 걸리는가"는 13 cm 폭의 물음이다. 그리고 스캔 면 자체의 높이 h_L(바닥에서 레이저 창까지)은 이 프로젝트가 아직 모른다. 데이터시트의 기구 치수도는 그 단일 치수를 주지 않는다.6 h_L 을 재는 것은 센서를 차체에 다는 09a 의 일이다. 09a 는 본편의 조립 · 실측 관문 쪽이다. 이 쪽은 그 수 없이 끝낼 수 있게 설계돼 있다 — 여기서 필요한 것은 "면이 하나뿐이다"라는 사실이지 그 면의 높이가 아니기 때문이다.

왜 이 한계가 09a 의 장착 높이 실측을 정당화하는가

장착 높이를 바꾸면 무엇이 보이지 않는가가 통째로 바뀐다. 낮게 달면 바닥의 턱·문지방·전선은 보이지만 책상 상판·손잡이가 사라지고, 높게 달면 그 반대다. 어느 높이도 전부를 보지 못한다 — 그래서 장착 높이는 취향이 아니라 "무엇을 포기할 것인가"의 선언이고, 그 선언을 하려면 먼저 이 쪽에서 못 보는 것이 실제로 어떤 오판을 만드는지를 봐야 한다. 실습 D 가 그 순서대로 진행한다.

2-6. 여기까지가 L 이다 — 이 두 수가 어디로 가는가

이 쪽이 내는 거리와 방위는 그대로 제어기의 입력이다. "벽에서 0.5 m 를 유지하며 따라간다"는 수직 거리를 목표값으로 하는 제어이고, "벽을 마주 보고 정렬한다"는 방위를 0 으로 몰아가는 제어다. 그 제어는 10 에서 다루고 L 은 여기서 멈춘다 — 멈추는 이유는 제어가 어려워서가 아니라 제어에는 모터가 필요하고, 이 가이드는 센서 한 대로 끝나는 것만 다루기 때문이다.

시간의 예산도 여기서 한 번 생각해 둔다. 한 바퀴가 5.5 Hz(주기 약 182 ms) 라면, 판정 한 번은 그 안에 끝나야 "매 스캔마다 판정한다"가 성립한다. 이 쪽의 계산은 전부 선분 몇 개·덩어리 몇 개에 대한 것이라 격자(l-09)보다 계산량이 훨씬 적다. 이것이 점을 도형으로 줄인 세 번째 이득이다(l-11 §2-1).

그리고 같은 판정이 이미 한 번 더 이 저장소에 있다. 09 는 본편의 SLAM · Nav2 쪽이고, Nav2 는 지도 위에서 경로를 찾아 주행하게 하는 ROS 2 의 패키지다. 09 §2-6 의 inflation_radius 는 "장애물을 이만큼 부풀려 놓고 경로를 찾는다"는 값이고, 부풀리는 양이 곧 로봇 반지름 + 여유다. 이 쪽에서 내가 손으로 하는 판정을 Nav2 는 지도 전체에 대해 미리 해 둔다.

여기서 적어 두면 09 에서 쓴다

09 §2-6 은 inflation_radius: 0.25 를 예로 싣고, 같은 쪽의 파라미터 표는 그 값을 robot_radius + 5~10 cm 로 설정하라고 적는다. 내가 §3-3-1 에서 잰 폭으로 그 규칙을 따르면 얼마가 되는지 계산해 노트에 적어 두라.

두 수가 다르게 나와도 여기서는 고치지 않는다 — 09 의 값은 09 가 소유하고, 그때 쓸 근거를 지금 만들어 두는 것이 이 쪽의 일이다. 다르다면 무엇이 달랐는지만 적는다.

시험 파일은 §3-5-2 에 전량으로 있다. A 를 시작하자마자 그 파일을 먼저 자리에 두고 빌드 · 실행하는 것이 요령이다 — 실패 줄의 목록이 곧 채울 순서가 된다.

안전 — 이 쪽은 일부러 틀리게 만드는 실습이 둘이다

§3-3 은 여유를 0 으로 두어 실제로는 못 지나갈 통로를 "통과 가능"으로 판정하게 만들고, §3-4 는 스캔 면 밖의 물건을 두어 같은 오판을 다른 방법으로 만든다. 둘 다 끝나면 되돌려 놓는다 — 놓은 턱·상자는 치우고, 여유는 내가 고른 값을 노트에 적는다.

특히 일부러 0 으로 친 여유를 내 여유로 쓰지 않는다. 여유는 명령줄의 마지막 수라 파일에는 남지 않는다. 대신 셸 기록과 노트에 남는다. 다음 쪽에서 그 명령을 되풀이할 때 0 이 따라가면 통로 판정이 늘 "통과"로 나오는데, 그 이유가 라이다에 있다고 생각하게 된다. §3-3-4 의 마지막 걸음과 "다음 행선지"에서 두 번 확인한다.

⚠ 이 쪽의 도구(lab_clear · lab_clear_try · lab_lines)는 포트를 열지 않고 모터를 부르지 않는다 — 라이다가 꽂혀 있고 머리가 돌고 있었다면 그대로 돈다. 돈다고 간주한다. 상자나 턱을 놓고 새로 한 장 기록하기로 했다면 l-04 의 lab_turn 으로 한다. 그 도구는 끝에 motor(fd, false) 로 머리를 멈춘다 — 끝난 뒤에도 돌면 USB 케이블을 뽑는다(l-01 의 L2). 보이지 않는 레이저 규칙 L1 도 l-01 이 소유한다. 머리 가까이에 손을 두지 않고, 얼굴을 센서 높이에 두지 않는다.

L1 · L2 는 l-01 이 정한 안전 규칙 번호다. L1 은 보이지 않는 785 nm 레이저에 관한 규칙이다 — 스캔 창을 렌즈 높이에서 정면으로 들여다보지 않는다. L2 는 도는 머리에 관한 규칙이다. 결정 L3 과는 다른 번호다.

/* 완결 코드 T1 - scripts/lidar_lab/include/lidar_lab/clear.hpp (heading_to) */
inline double heading_to(const Segment& seg) {
  Point n = seg.normal();
  if (n.first * seg.p0.first + n.second * seg.p0.second < 0.0) n = Point{-n.first, -n.second};
  return normalize(std::atan2(n.second, n.first));
}

코드 설명

  • n.first * seg.p0.first + n.second * seg.p0.second — 내적 n · p0 이다. 센서가 원점이므로 센서에서 벽 위의 한 점으로 가는 벡터는 p0 자신이다(§2-2-1).
  • < 0.0 이면 n = Point{-n.first, -n.second}; — 법선이 벽 반대쪽을 가리키므로 뒤집는다(불변식 1). 이 한 줄 덕분에 점의 순서가 바뀌어도 답이 같다(불변식 2, 벡터 9).
  • std::atan2(n.second, n.first) — y 가 먼저다. x 축(정면)에서 반시계로 잰 각이 라디안으로 나온다.
  • normalize(…) — l-08 의 geom.hpp 에 있는 함수다. 각을 [-π, π] 로 감는다(불변식 3).
  • 골격의 자리표시 (void)seg; 와 return 0.0; 은 지웠다.

  • 다르게 써도 되는 곳 — 하나다.8

/* 완결 코드 T2 - scripts/lidar_lab/include/lidar_lab/clear.hpp (foot_inside) */
inline bool foot_inside(const Segment& seg) {
  const double dx = seg.p1.first - seg.p0.first, dy = seg.p1.second - seg.p0.second;
  const double len2 = dx * dx + dy * dy;
  if (len2 == 0.0) return false;
  const double t = -(seg.p0.first * dx + seg.p0.second * dy) / len2;
  return t >= 0.0 && t <= 1.0;
}

코드 설명

  • dx · dy — 방향 d = p1 − p0 의 두 성분.
  • len2 = dx * dx + dy * dy — 길이의 제곱 d · d 이다. 제곱근을 구하지 않는다.
  • if (len2 == 0.0) return false; — 같은 점 두 개면 직선이 없다(불변식 4). 나누기 전에 거른다.
  • t = -(p0 · d) / len2 — 발 p0 + t·d 가 원점에서 내린 수선의 발이 되는 t 다. 발에서 원점으로 가는 벡터 −(p0 + t·d) 가 d 와 직각이라는 조건 (p0 + t·d) · d = 0 을 t 에 대해 푼 것이다.
  • return t >= 0.0 && t <= 1.0; — t = 0 이면 발이 p0, t = 1 이면 p1 이다. 양 끝을 포함한다(불변식 1, 벡터 29).
  • 센서 뒤의 벽도 같은 식이다(불변식 3, 벡터 30) — 발이 앞에 있는지는 묻지 않는다.
  • 골격의 자리표시 (void)seg; 와 return false; 는 지웠다.

  • 다르게 써도 되는 곳 — 둘이다.8

    ① 나누지 않고 along = -(p0 · d) 를 0 ≤ along ≤ len2 로 견줘도 31 개를 통과한다.

    ② 발의 좌표 F = perp_distance(seg) × (cos h, sin h) 를 구해도 된다(h = heading_to(seg)). (F − p0) · d ≥ 0 과 (F − p1) · d ≤ 0 을 보면 31 개를 통과한다. 다만 T1 의 답에 기대므로 T1 이 틀리면 이 함수도 같이 틀린다.

bool parse_double(const char* text, double& v) {
  char* end = nullptr;
  v = std::strtod(text, &end);
  return end != text && *end == '\0' && std::isfinite(v);
}

bool parse_int(const char* text, long lo, long hi, long& v) {
  char* end = nullptr;
  v = std::strtol(text, &end, 10);
  return end != text && *end == '\0' && v >= lo && v <= hi;
}

// The smallest measured range among the indices keep(i) accepts -> its index, or empty.
template <class Keep>
std::optional<std::size_t> min_range(const Scan& s, Keep keep) {
  std::optional<std::size_t> best;
  for (std::size_t i = 0; i < s.size(); ++i) {
    if (!s.r[i] || !keep(i)) continue;
    if (!best || *s.r[i] < *s.r[*best]) best = i;
  }
  return best;
}

void print_min(const char* label, const Scan& s, const std::optional<std::size_t>& i) {
  if (!i) {
    std::printf("%s r=none  (no measured point)\n", label);
    return;
  }
  std::printf("%s r=%.3f m  i=%zu  a=%.2f deg\n", label, *s.r[*i], *i, s.a[*i]);
}

  long turn = 1;
  for (int i = 1; i < argc; ++i) {
    if (std::strcmp(argv[i], "--turn") == 0 && i + 1 < argc) {
      if (!parse_int(argv[++i], 1, 100000, turn)) return usage();
    } else if (argv[i][0] == '-' && argv[i][1] == '-') {
      return usage();

      pos.push_back(argv[i]);

  }
  if (pos.size() != 5) return usage();

  long k = 0, j = 0;
  if (!parse_double(pos[1], gap) || gap <= 0.0) return usage();

      return 1;

      return 1;

    const std::vector<Segment> segs = fit_lines(cs[static_cast<std::size_t>(k)].pts, tol);
    if (static_cast<std::size_t>(j) >= segs.size()) {
      std::printf("no segment %ld in cluster %ld: it has %zu\n", j, k, segs.size());
      return 1;
    }
    const Segment& g = segs[static_cast<std::size_t>(j)];
    const Point n = g.normal();
    const double h = heading_to(g);

    std::printf("turn %ld of %zu  gap=%s m  tol=%s m  cluster %ld  seg %ld\n", turn, scans.size(),

                n.first * g.p0.first + n.second * g.p0.second);

                to_deg(h), foot_inside(g) ? "true" : "false");

                return std::fabs(normalize(to_rad(s.a[i]))) <= half;
              }));

  } catch (const std::exception& e) {
    std::printf("error: %s\n", e.what());
    return 1;
  }
  return 0;

// Arithmetic mean of pts -> (x, y) in metres. Given in full.
// passage_width() uses this, not l-10's Cluster::centroid(): the same number, but this page's
// grading sheet does not lean on another page's TODO (3-5-1). Never call it with an empty
// list -- passage_width() skips empty clusters first.
inline Point mean_point(const std::vector<Point>& pts) {
  double sx = 0.0, sy = 0.0;
  for (const Point& p : pts) {
    sx += p.first;
    sy += p.second;
  }
  const double n = static_cast<double>(pts.size());
  return {sx / n, sy / n};
}

완결 코드

/* 완결 코드 T3 - scripts/lidar_lab/include/lidar_lab/clear.hpp (passage_width) */
inline std::optional<double> passage_width(const std::vector<Cluster>& clusters,
                                           double direction_rad) {
  const Cluster* left = nullptr;
  const Cluster* right = nullptr;
  double left_s = 0.0, right_s = 0.0;
  for (const Cluster& c : clusters) {
    if (c.pts.empty()) continue;
    const Point m = mean_point(c.pts);
    const double s = normalize(std::atan2(m.second, m.first) - direction_rad);
    if (std::fabs(s) >= kPi / 2.0) continue;
    if (s > 0.0) {
      if (left == nullptr || std::fabs(s) < left_s) {
        left_s = std::fabs(s);
        left = &c;
      }
    } else if (s < 0.0) {
      if (right == nullptr || std::fabs(s) < right_s) {
        right_s = std::fabs(s);
        right = &c;
      }
    }
  }
  if (left == nullptr || right == nullptr) return std::nullopt;
  std::optional<double> best;
  for (const Point& p : left->pts) {
    for (const Point& q : right->pts) {
      const double d = std::hypot(p.first - q.first, p.second - q.second);
      if (!best || d < *best) best = d;
    }
  }
  return best;
}

코드 설명

  • const Cluster* left = nullptr; — 고른 덩어리를 복사하지 않고 가리킨다. 아직 못 골랐으면 nullptr 다. left_s · right_s 는 지금까지 고른 것의 |s| 다.
  • if (c.pts.empty()) continue; — 점이 없는 덩어리는 평균이 없다. split() 은 빈 덩어리를 만들지 않지만, 이 함수가 어떤 목록을 받아도 안전하게 해 둔다.
  • mean_point(c.pts) — 점들의 평균(전량). c.centroid() 를 부르지 않는 이유는 §3-3-2 의 작은 글씨다.
  • s = normalize(std::atan2(m.second, m.first) - direction_rad) — 평균점의 방위에서 가려는 방향을 빼고 감는다(불변식 2, 벡터 20).
  • if (std::fabs(s) >= kPi / 2.0) continue; — 앞쪽이 아니면 보지 않는다(불변식 1, 벡터 17 · 19). kPi 는 l-06 의 angles.hpp 에 있다.
  • if (s > 0.0) … else if (s < 0.0) — 왼쪽 · 오른쪽. s == 0.0 은 어느 쪽에도 들어가지 않는다(불변식 2). 각 쪽에서 |s| 가 더 작으면 바꾼다(불변식 3, 벡터 15).
  • if (left == nullptr || right == nullptr) return std::nullopt; — 한쪽이 비면 빈 값(불변식 5, 벡터 16 ~ 19).
  • std::optional<double> best; — 처음에는 빈 값이다. 두 겹 반복으로 모든 점 쌍의 std::hypot 을 재고, !best || d < *best 면 바꾼다. !best 를 먼저 보므로 빈 값을 꺼내 읽는 일이 없다(불변식 4, 벡터 13).
  • 골격의 자리표시((void) 두 줄과 return std::nullopt;)는 지웠다.

  • 다르게 써도 되는 곳 — 아래 넷은 모두 31 개를 통과한다. 어느 쪽이 맞고 틀린 문제가 아니다.8

    ① "가장 가까운 설주"를 무엇으로 고르는가. 여기는 각도로 고른다(|s| 가 가장 작은 것). 거리로 고르는 것도 말이 된다 — 가려는 방향에 가장 가까운 설주가 아니라 나에게 가장 가까운 설주를 쓰는 것이다(평균점까지의 std::hypot 이 가장 작은 것). 벡터 15 는 두 방법이 같은 답을 내는 장면이라 둘을 가르지 않는다. 내 방에서 둘이 갈리는 장면을 찾으면 그 장면이 내 판단이 필요한 자리다.

    ② s == 0.0 을 어디에 넣는가. 여기는 어느 쪽에도 넣지 않는다(§2-3-1). 왼쪽에 넣기로 정해도(s >= 0.0) 벡터는 전부 통과한다 — 다만 그러면 문 한가운데를 막고 있는 물건이 설주로 잘못 분류되어 통로가 실제보다 좁게 나온다. 어느 쪽이든 노트에 적어 두면 나중에 이상한 폭이 나왔을 때 볼 곳이 생긴다.

    ③ 평균점을 c.centroid() 로 내도 l-10 의 T2 가 맞으면 같은 값이다. 다만 l-10 의 T2 가 비어 있으면 13 · 14 · 15 · 20 이 got none 으로 실패한다 — 원인이 이 쪽에 없는 실패다. 그래서 이 쪽은 mean_point() 를 쓴다.

    ④ 점 쌍을 전부 순회하는 것. 덩어리가 각각 점 수백 개면 수만 번을 반복한다. 한 바퀴가 약 182 ms 인 것을 생각하면 아직 여유가 크지만(§2-6), 방이 커지면 여기가 먼저 느려진다. 각도 순서를 이용해 마주 보는 끝점 근처만 보는 방법이 있고, l-16 이 이 헤더를 패키지로 옮길 후보로 둘 때 다시 검토한다.

  • direction_rad 를 인자로 받는 이유 — 도구가 자동으로 "가장 넓은 통로"를 찾게 만들 수도 있지만, 그러면 "어디로 가고 싶은가"라는 결정이 도구 코드 안에 감춰진다. 그 결정은 이 가이드가 아니라 10 의 주행 계획이 내린다.

완결 코드

/* 완결 코드 T4 - scripts/lidar_lab/include/lidar_lab/clear.hpp (fits) */
inline bool fits(std::optional<double> width, double robot_width, double margin) {
  if (!width) return false;
  return *width >= robot_width + 2.0 * margin;
}

코드 설명

  • if (!width) return false; — std::optional 은 값이 있으면 참, 비었으면 거짓으로 읽힌다. "모른다"는 통과가 아니다(불변식 2, 벡터 24 · 25). 꺼내기 전에 거른다.
  • *width — 값이 있는 것을 확인한 뒤에만 꺼낸다. 비었는데 꺼내면 이 가이드의 빌드는 그 자리에서 중단한다(아래 표).
  • >= robot_width + 2.0 * margin — 여유는 한쪽 값이라 두 번 더한다(§2-4). 경계는 통과다(불변식 1, 벡터 21).
  • 골격의 자리표시((void) 세 줄과 return false;)는 지웠다.

  • 다르게 써도 되는 곳 — 하나다.8

    return width.has_value() && *width >= robot_width + 2.0 * margin; 한 줄로 써도 같다. && 는 왼쪽이 거짓이면 오른쪽을 계산하지 않으므로 빈 값을 꺼내지 않는다.

  • margin 에 기본값이 없는 이유 — §2-4 끝. 내가 정할 값을 함수의 기본값이 대신 정하면 그 판정은 내 판정이 아니다.

  1. 줄자로 그 통로를 잰다. 라이다가 본 것과 같은 높이에서 양쪽 면 사이를 잰다. 내 도구 ____ m · 줄자 ____ m · 차 ____ mm.

    ⚠ 도구 값이 더 크게 나오면 대개 덩어리가 끊긴 것이다 — 설주의 일부만 한 덩어리가 되어 가장 가까운 두 점이 실제 가장자리가 아니다. l-10 의 문턱을 줄여 다시 실행한다.

  2. 여유를 0 으로 두고 다시 실행한다(명령줄의 마지막 수만 0). fits 가 true 로 바뀌는 통로를 하나 찾는다(없으면 로봇 폭에 가까운 좁은 곳을 고르거나, 상자 둘을 그만큼 벌려 놓고 한 장 더 기록한다).

    그리고 실물로 확인한다 — 로봇 폭만큼 자른 판지나 막대를 들고 그 통로를 실제로 지나가 본다. 벽에 닿는가? 똑바로 들어가야만 통과하는가? 무엇이 일어났는지 적는다.

    ⚠ 빌려 온 파일이라면 — 내가 걸어 들어갈 수 없는 방의 기록이면 이 확인을 할 수 없다. fits 가 true 로 바뀌는 margin 값까지는 찾아 적고, 체크 항목에는 "현물 확인 못 함 — 빌려 온 기록" 이라고 적어 미통과로 둔다(§3-4-1 3번과 같은 처리다). 다음 쪽으로 가는 데 지장이 없다.

    다만 ⚠ 아래 3번은 빌려 온 파일이어도 한다. 현물 확인을 못 한 것과 0 을 내 여유로 남겨 두는 것은 다른 일이다.

  3. 되돌려 놓는다. 노트의 "내가 고른 여유" 칸이 §3-3-3 에서 고른 값인지, 0 이 아닌지 눈으로 확인한다. 여유는 명령줄의 수라 파일에는 남지 않지만, 셸 기록(위 화살표 키)과 노트에서 0 이 다음 실행으로 따라간다. 이 설정은 오류 표시 없이 따라가 뒤 쪽의 결과를 통째로 바꾼다.

2번에서 보게 되는 것이 여유가 무엇인지의 답이다. 여유 0 은 "완벽하게 조준하고 완벽하게 직진하면 이론상 지나간다"는 뜻이고, 실제 로봇은 그 둘을 다 못 한다. 그래서 여유는 센서의 값이 아니라 제어의 값이다 — 주행이 정확해질수록 줄일 수 있고, 그 정확도는 10 에서 결정된다.

3-4. 실습 D — 스캔 면 밖의 것 (코드 없음) 기록 파일

도구는 이제 "통과 가능"이라고 판정한다. 이 실습은 그 판정이 틀리는 장면을 실제로 만든다 — 코드는 한 줄도 고치지 않는다. 도구를 고쳐서 막을 수 있는 종류의 오판이 아니라는 것이 이 실습의 요점이다.

  1. 스캔 면의 높이를 잰다. 센서를 놓았던 그 자리에서, 바닥(또는 센서를 올려놓은 면)에서 회전 머리의 레이저 창 한가운데까지 줄자로 잰다: h_L = ____ m.

    ⚠ 데이터시트의 기구 치수도에는 이 치수가 단일 값으로 나와 있지 않다.11 그래서 재는 수밖에 없다. 못 재면 ____ 로 두고 아래 표의 판정만 한다.

  2. 그 높이에서 안 보이는 것을 하나 고른다. 실습 C 의 통로에서 바닥 가까이에 있는 것(문지방·전선·러그 가장자리·의자 가로대) 또는 머리 위에 있는 것(선반·책상 상판·손잡이)이면 된다. 통로에 아무것도 없으면 낮은 턱 하나를 놓는다 — 그 경우 라이다로 한 장 더 기록하면 "도구는 그대로 통과라고 한다"를 더 선명하게 볼 수 있지만 필요하지는 않다. 스캔에 안 찍히는 물건이므로 파일은 어차피 같고, 바로 이 점이 이 실습의 논점이다.

  • 왜 도구를 고쳐도 안 되는가. 문턱을 바꿔도, 덩어리를 다시 잘라도, 여유를 키워도 그 물건은 파일 안에 없다. 없는 것을 계산으로 복구할 방법은 없다. 여유를 아주 크게 두면 우연히 막을 수는 있다. 그러면 지나갈 수 있는 통로도 전부 막힌다. 이런 설정은 해결이 아니라 센서를 끄는 것에 가깝다.
  • 그러면 무엇이 답인가. ① 다른 센서(카메라·초음파·범퍼)로 다른 높이를 본다 ② 장착 높이를 포기할 것을 정해서 고른다 ③ 모르는 것을 모른다고 표시해 두고 속도를 낮춘다. 이 프로젝트가 고른 것은 ①이고(08d 가 카메라를 추가한다), ②는 09a 가 장착 높이를 실측으로 확정하는 이유다.
  • 두 줄이 같았다면(도구도 "못 지나간다"고 했거나, 실제로도 지나갔다) — 이 결과도 유효한 관찰이다. 무엇을 골랐기에 그랬는지 적는다. 대개 고른 물건이 스캔 면에 걸쳐 있었다는 뜻이고, 그러면 d × tan(1.5°) 줄과 대조해 본다.

⚠ 이 실습에서 놓은 턱·상자는 치운다. 실습 C 의 margin 과 함께, 일부러 만든 장면을 남겨 두면 다음 쪽에서 생기는 이상한 결과의 원인을 라이다에서 찾게 된다.

#include "lidar_lab/clear.hpp"

namespace {

// A segment whose perpendicular foot from the origin is at (dist, deg).
Segment wall(double dist, double deg, double half = 1.0) {
  const double c = std::cos(to_rad(deg)), s = std::sin(to_rad(deg));
  const double fx = dist * c, fy = dist * s;
  return Segment{{fx + s * half, fy - c * half}, {fx - s * half, fy + c * half}, 2};
}

// A door post: l-10's Cluster with the points only. idx is not read on this page.
Cluster post(std::vector<Point> pts) { return Cluster{pts, {}}; }

void near_opt(const std::string& name, const std::optional<double>& got, double want) {
  check(name, got.has_value() && std::fabs(*got - want) <= 1e-9, str(got), str(want));
}

}  // namespace

int main() {

  const Segment TILT = wall(1.4, 15.0);

       std::fabs(heading_to(ASIDE)), 0.0);

  const Cluster JAMB_R = post({{1.0, -0.4}, {1.0, -0.8}, {1.0, -1.2}});

  return finish("clear");
}

2. "앞의 벽까지 1.4 m" 하나만 있으면 로봇은 무엇을 할 수 없는가. 수가 둘이어야 하는 이유를 구체적인 동작 하나로 말해 보라

그리고 최소 거리로는 법선을 복원할 수 없다. 최소 거리 점은 벽이 기울면 정면이 아닌 곳으로 옮겨 가고, 그 점 하나만으로는 면이 어느 쪽으로 기울었는지 알 방법이 없다 — 면이 필요하고, 면은 l-11 이 만들어 주었다.

기준 형식이 무반사를 null 로 적기로 한 결정과 같은 종류다(l-04 §3-4-2). 논점도 같다 — "못 쟀다"와 "재었더니 이 값이다"는 다른 사건인데, 같은 표기를 쓰면 둘을 구별할 방법이 없어진다.

0.0 을 고르면 "폭이 0 이다(문이 막혔다)"와 섞인다. fits 는 두 경우 모두 false 를 내므로 당장은 안전해 보이지만, 로그를 보고 원인을 찾을 때 "문이 막혔다"와 "설주를 못 찾았다"를 가를 수 없다. 전자는 돌아가야 하고 후자는 문턱을 고쳐 다시 봐야 한다.

4. 통로를 가를 때 뒤쪽 덩어리를 잘라 내는 줄을 지우면 무엇이 일어나는가. 그리고 이 현상이 normalize() 의 어떤 성질과 관계있는가

두 가지가 한꺼번에 일어난다. 물리적으로, 문설주가 아닌 뒤쪽 물건이 설주로 선택되어 빈 값이어야 할 자리에 그럴듯한 수가 나온다 — 벡터 17 이 그 장면이고, 실제 출력은 2.08806130178211 이다.

수치적으로, 뒤쪽 180° 부근은 부호를 그대로 받아들일 수 없는 자리다. normalize() 의 치역은 [-π, π] 인데 양 끝이 다 나온다 — l-08 이 실측으로 normalize(-π) = -3.141592653589793 이라고 적어 두었다. 그래서 정확히 뒤에 있는 덩어리는 +π 로도 -π 로도 나올 수 있고, 같은 덩어리가 어떤 날은 왼쪽 어떤 날은 오른쪽이 된다. 왼쪽·오른쪽을 각의 부호로 가르는 이상 이 자리는 원리적으로 불안정하다.

두 이유가 같은 한 줄의 조건으로 해결된다는 것이 이 규칙이 안전한 이유다. 수치적 요령만이었다면 언젠가 "이건 임시방편인데" 하며 지웠을 텐데, 문설주는 옆에 있지 뒤에 있지 않다는 물리가 같은 줄을 요구한다. ⚠ 단 그 줄이 normalize() 를 대신하지는 못한다 — 통로 자체가 ±180° 이음매를 걸치면 감기가 없을 때 한쪽 설주가 통째로 버려진다(벡터 20).
