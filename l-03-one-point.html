2. 원리 — 왜 이 다섯 바이트를 믿을 수 있는가

2-1. 시작 바이트가 없는 흐름에서 경계를 찾는 법

06a 의 MCU 계약 v2 는 우리가 설계한 프레임이다. 그래서 머리 바이트를 붙이고 길이를 넣고 CRC 를 달았다 — 우리가 정했으니 우리가 찾을 수 있다. 라이다는 반대다. 남이 정한 프레임을 우리가 찾아내야 한다. 그리고 이 센서의 점에는 머리 바이트가 없다. 있는 것은 덩어리 안에 섞여 있는 검사 비트 두 개뿐이다.

비트어디규칙왜 이것으로 경계를 찾을 수 있는가
Sb0 의 비트0새 바퀴의 첫 점에서만 1한 바퀴에 한 번만 1 이다 — 이것만으로는 경계를 못 찾는다
~Sb0 의 비트1언제나 S 의 반대임의의 자리에서 이 두 비트가 다를 확률은 1/2 이다
Cb1 의 비트0언제나 1여기까지 곱하면 1/4. 다섯 바이트씩 계속 맞아 들어가면 확률이 빠르게 0 으로 간다

그러니까 한 자리를 보고 "여기가 점의 시작이다"라고 단정할 수는 없다. 1/4 은 꽤 큰 확률이다. 할 수 있는 것은 "여기가 시작이라면 다음 5바이트도, 그 다음 5바이트도 규칙을 지켜야 한다"를 따라가 보는 것이고, 어긋나는 순간 한 칸 밀어 다시 보는 것이다(§2-4). 경계를 한 번 맞히면 그 뒤로는 계속 맞는다 — 어긋나기 전까지는.

왜 이 두 비트가 "기기가 답해 주는" 자기검증인가

l-02 의 A5 5A 와 같은 종류의 장치다. 내가 이해한 대로 읽었더니 기기가 약속한 값이 그 자리에 있었다 — 그것이 내 이해가 맞았다는 증거다. 반대로 S 와 ~S 가 같거나 C 가 0 이면, 틀린 것은 센서가 아니라 내가 고른 시작 자리다. 이 쪽에서 학습자가 세는 "걸러진 자리의 수"는 내 도구가 실제로 경계를 잃고 있다는 양이다.

데이터시트는 이 배치를 싣지 않았다. 두 판 모두 6쪽에서 "If you need detailed data format and communication protocol, please contact SLAMTEC." 라 적고, 9쪽에서 다시 "Please contact SLAMTEC if you want detailed communication protocol" 이라 적는다. 목차에도 프로토콜 장이 없다. 그래서 "데이터시트에 따르면 b0 의 비트0 이 S 다"라고 쓸 수 없다. 이 쪽이 쓰는 출처는 셋이다:

2-2. 고정소수점 — 정수만으로 소수를 나르는 법과, 그 식이 나오는 자리

각도는 90.5° 처럼 소수가 필요하고 거리도 1000.25 mm 처럼 소수가 필요하다. 그런데 이 5바이트 안에는 소수점이 들어갈 자리가 없다 — 있는 것은 정수 비트뿐이다. 해법은 단순하다. 보낼 때 정수배로 곱하고 받을 때 나눈다. 곱하는 수를 2의 거듭제곱으로 잡으면 곱셈·나눗셈이 시프트 한 번이라 싸다. q6 은 64배(2의 6제곱), q2 는 4배(2의 2제곱)라는 뜻이다.

이제 왜 시프트가 저렇게 생겼는지를 도출한다. SDK 헤더의 구조체는 이렇게 생겼다(§2-1 ①):

typedef struct _sl_lidar_response_measurement_node_t {
    sl_u8    sync_quality;       // syncbit:1;syncbit_inverse:1;quality:6;
    sl_u16   angle_q6_checkbit;  // check_bit:1;angle_q6:15;
    sl_u16   distance_q2;
} __attribute__((packed)) sl_lidar_response_measurement_node_t;

여기서 셋을 읽어 낸다.

  1. 두 개의 16비트 필드는 리틀엔디안이다. 이 센서는 낮은 바이트를 먼저 보낸다. 그러니 angle_q6_checkbit = b1 | (b2 << 8) 이고 distance_q2 = b3 | (b4 << 8) 이다. 이 한 줄이 틀리면 값이 그럴듯하게 틀린다 — 오류가 나지 않는다(§2-5).
  2. 16비트 안에서 검사 비트가 맨 아래 한 칸을 차지한다. check_bit:1 이 먼저 쓰였으니 그것이 비트0 이고, angle_q6 는 그 위 15비트다. 그래서 angle_q6 = (b1 | (b2 << 8)) >> 1 이다 — 헤더의 ..._ANGLE_SHIFT 가 1 인 것이 이 1칸이다.
  3. q6 을 벗긴다. 각도(도) = angle_q6 / 64.0. 마찬가지로 거리(mm) = distance_q2 / 4.0.

정리하면 식은 이 둘이다. 외우지 말고 위 세 걸음에서 다시 뽑을 수 있으면 된다 — 다음 센서의 헤더는 다르게 생겼을 것이다.

angle_deg = ((b2 << 8 | b1) >> 1) / 64.0        (= ((b1 >> 1) | (b2 << 7)) / 64.0 — 같은 식이다)
dist_mm   =  (b4 << 8 | b3)        / 4.0
quality   =   b0 >> 2                            (위 6비트. 마스크가 아니라 시프트다)

필드 폭에서 나오는 한계값도 같이 적어 둔다. 산술이므로 식을 같이 남긴다.

2-3. 거리 0 은 "아무것도 없다"가 아니라 "못 쟀다"

점을 풀다 보면 거리가 정확히 0 인 점이 섞여 나온다. 이것을 어떻게 읽느냐가 뒤의 다섯 쪽을 가른다.

먼저 사실부터. 데이터시트 Figure 1-4(rev.2.2 · v3.0 둘 다 6쪽)는 Distance 를 "Current measured distance value between the rotating core of the RPLIDAR A1 and the sampling point", 단위 mm 라고만 적고 0 이 무엇을 뜻하는지 말하지 않는다. 0 을 "잴 수 없었음"으로 읽는 근거는 ① 물리(측정 기준점이 rotating core 이므로 0 mm 는 회전축 한가운데를 뜻하는데, 사양의 최소 거리가 0.15 m 다 — 0 은 물체의 위치일 수 없다)와 ② 같은 모델의 기록(NOMINAL(gen1-record, 2026-07-14) — rplidar_ctl.py:19 가 dist_mm = ... (0 = invalid / no return) 이라 적었다)이다. 내 기기에서 확인하는 법은 §3-2-4 에 있다 — 아무것도 없는 방향(허공·천장 쪽)에서 0 이 나오고, 손을 대면 그 방향만 0 이 아닌 값으로 바뀌는지 본다.

왜 이 한 줄이 중요한가

"없다"와 "못 쟀다"는 로봇에게 정반대의 뜻이다. 앞은 "지나가도 된다", 뒤는 "모른다"다. 0 을 "거리 0 m 에 물체"로 읽으면 내 코앞에 벽이 생기고, 0 을 버리면서 "그 방향은 비었다"로 읽으면 유리문 앞으로 그대로 걸어간다. l-09 의 격자가 칸을 점유 · 자유 · 미지 셋으로 나누는 이유가 여기서 시작하고, 이 가이드의 기록 형식이 무반사를 0 도 inf 도 아닌 null 로 적는 이유도 같다(l-04 가 그 결정을 다룬다). 이 쪽에서는 0 을 버리지 않는다. parse_point 는 거리 0 인 점도 정상으로 돌려준다 — 버릴지 말지는 쓰는 쪽이 정할 일이다.

2-4. 재동기 방식이 수율을 바꾼다 — 같은 센서, 다른 점 수

검사가 틀렸을 때 어디서부터 다시 볼 것인가. 답이 하나가 아니고, 고른 답이 내가 받는 점의 수를 바꾼다. 두 방식이 있다.

2-5. 검사 비트가 통과해도 산술은 틀릴 수 있다

§2-1 의 두 비트는 경계만 채점한다. 경계를 맞게 잡고도 그 5바이트를 잘못 읽는 길이 여럿 있고, 검사 비트는 그 중 어느 것도 잡지 못한다.

제일 잘 드러나는 예를 하나 편다. 아래는 5바이트 BD 01 2D A0 0F 을 §2-2 대로 푼 것이다.

  b0 = BD = 1011 1101    비트0 = S  = 1     새 바퀴의 첫 점이다
                         비트1 = ~S = 0     S 와 다르다 ─► 통과
                         비트2~7   = quality = 101111 = 47
  b1 = 01 = 0000 0001    비트0 = C  = 1     ─► 통과
  b2 = 2D                angle_q6 = (2D << 8 | 01) >> 1 = 0x2D01 >> 1 = 5760
  b3 = A0                  각도   = 5760 / 64 = 90.0 도
  b4 = 0F                dist_q2  = (0F << 8 | A0) = 0x0FA0 = 4000
                           거리   = 4000 / 4  = 1000.0 mm

이제 b1 과 b2 를, b3 과 b4 를 맞바꿔 읽어 본다 — 리틀엔디안을 빅엔디안으로 잘못 읽는 아주 흔한 실수다. 바이트 자체는 그대로이므로 S · ~S · C 는 여전히 통과한다. 그런데 값은 90.0° · 1000.0 mm 에서 2.34375° · 10243.75 mm 로 바뀐다. 각도는 88도 옮겨 갔고 거리는 10배가 됐는데 아무 오류도 나지 않는다.

그래서 이 쪽은 시험 벡터로 산술을 채점한다

"점이 나온다"는 것은 경계를 찾았다는 증거일 뿐이고 값이 맞다는 증거가 아니다. §3-1-3 의 열 개 벡터는 각 벡터가 어떤 잘못을 잡는지 집필자가 실제로 잘못된 구현을 만들어 돌려 보고 적은 것이다(§3-1-3 의 표). 벡터를 통과해야 §3-1-4 로 간다.

그리고 시험 벡터도 완전하지 않다. 벡터가 잡지 못하는 것이 하나 남는데 — 각도가 시계 방향으로 커지는지 반시계 방향으로 커지는지는 5바이트 안에 없다. 그것은 실물에서만 닫히고, 이 쪽의 실습 B 가 그 첫 관찰이며 l-08 이 정면으로 다룬다.

  2. parse_point 를 채운다. 길이 → 프레이밍 두 비트 → 산술 순서로. 힌트: 리틀엔디안 16비트를 만드는 방법은 b1 | (b2 << 8) 이고, 파이썬에는 int.from_bytes(b5[1:3], "little") 도 있다. 어느 쪽을 쓰든 좋지만 왜 그것이 같은 값인지 말할 수 있어야 한다.
  3. 채점받는다. 아래 시험 파일을 scripts/lidar_lab/tests/test_point.py 로 그대로 두고 돌린다. 열 개가 다 통과할 때까지 stream 으로 넘어가지 않는다.
  4. stream 을 채운다. 재동기 한 걸음을 이름 있는 상수로 뽑아 둔다(예: RESYNC_STEP). 실습 C 가 그 상수 하나만 바꿔서 돌아갈 수 있어야 한다. 몇으로 둘지는 지금 정하지 않아도 된다 — 재는 것이 실습 C 다.

#   b0 = (q << 2) | (1 if S else 2)
#   u  = (round(deg * 64) << 1) | 1 ; b1, b2 = u & 0xFF, (u >> 8) & 0xFF

CASES = [

    ("BD 01 2D A0 0F", (90.0, 1000.0, 47)),       # 1 normal point, S = 1 (start of a revolution)

    ("02 01 00 58 02", (0.0, 150.0, 0)),          # 3 angle 0.0, quality 0, near the spec minimum

    ("00 01 2D A0 0F", None),                     # 8 S == ~S == 0  -> not a node boundary

3-2. 실습 B — 손을 30 cm 앞에 댄다

점이 흐르는 것과 그 점이 내 방을 가리키는 것은 다른 일이다. 이 실습은 그 둘을 잇는 가장 싼 관찰이다 — 자와 손 하나면 된다.

3-2-1. 확인

  • 센서가 l-01 에서 잡아 둔 받침 위에 그대로 있고 기준선 표시가 보인다. 실습 중에 움직이면 관찰이 무효다.
  • 센서 앞 1 m 안에 사람·의자·컵이 없다. 손 말고 다른 것이 움직이면 어느 각도가 손인지 알 수 없다.
  • 자 또는 줄자가 있고, 어디서부터 30 cm 를 잴 것인지 미리 정했다. ⚠ 데이터시트의 기준점은 rotating core(회전 머리)이지 몸통 겉면이 아니다(§3-1-1 대조 표 ②). 몸통 겉면에서 재면 그 차이만큼 어긋난다 — 어디서 쟀는지를 값과 함께 적는 것이 이 실습의 절반이다.
  • ⚠ 손만 댄다. 얼굴·머리를 센서 높이에 두지 않는다(§3 머리의 안전 규칙).

3-2-3. 채우기 — 관찰의 순서

  1. 기준을 먼저 찍는다. 손 없이 한 번 돌려 출력을 파일로 받아 둔다. 이것이 없으면 "바뀌었다"를 말할 수 없다.
  2. 손을 정면 30 cm 에 두고 다시 돌린다. 300 근처의 거리가 나오는 각도 구간을 찾는다 — 한 점이 아니라 여러 점이 같이 바뀐다(손은 폭이 있다).
  3. 치운다. 그 구간이 원래 값으로 돌아오는지 본다. 안 돌아오면 센서가 움직인 것이다 — §3-2-1 로 돌아간다.
  4. 손을 옆으로 옮긴다. 각도 구간이 어느 쪽으로 움직이는가. ⚠ 여기서 "시계 방향이면 각도가 커진다" 같은 결론을 아직 내리지 않는다 — 어느 쪽이 0° 인지를 아직 정하지 않았기 때문이다. 지금 적을 것은 "왼쪽으로 옮기니 각도가 커졌다/작아졌다" 한 줄이고, 이것을 l-08 이 받아 방향 규약을 닫는다.
  5. 허공을 본다. 아무것도 없는 방향(천장 쪽·창밖)에서 거리가 어떻게 나오는가. 0 인가, 큰 값인가, 점이 아예 안 오는가. 셋 다 있을 수 있다 — 무엇이 나왔는지 적는다(§2-3).

2. 이 센서의 점에는 시작 바이트가 없다. 그런데도 경계를 찾을 수 있는 이유는? 그리고 왜 "한 자리만 보고" 단정할 수 없는가

덩어리 안에 검사 비트 둘이 심어져 있기 때문이다 — b0 의 비트0·비트1 이 서로 반대여야 하고(S ≠ ~S), b1 의 비트0 이 1 이어야 한다(C == 1). 임의의 자리가 이 둘을 우연히 만족할 확률은 1/2 × 1/2 = 1/4 로, 한 번으로는 아무것도 증명하지 못한다.

증명이 되는 것은 5바이트 간격으로 계속 맞아 들어갈 때다. n 개가 이어지면 우연일 확률이 4의 n제곱분의 1로 떨어진다. 그래서 경계 찾기는 "한 점을 판정하는 일"이 아니라 "가설을 세우고 이어 가 보는 일"이다. 06a 의 계약 v2 와 정확히 반대다 — 그쪽은 우리가 머리 바이트와 길이와 CRC 를 설계했으므로 한 번에 단정할 수 있다.

3. angle_q6 는 왜 16비트 전체가 아니라 15비트인가? 그리고 그 1비트가 >> 1 을 부르는 과정을 구조체에서 다시 뽑아 보라

16비트 필드의 맨 아래 한 칸을 검사 비트 C 가 쓰기 때문이다. SDK 헤더의 주석이 check_bit:1;angle_q6:15; 이고, 먼저 쓰인 것이 낮은 비트다. 그래서 16비트를 통째로 만든 뒤(b1 | (b2 << 8) — 리틀엔디안) 한 칸 내리면 각도가 나온다. 헤더의 ..._ANGLE_SHIFT 가 1 인 것이 이 한 칸이다.

남는 것이 15비트이므로 담을 수 있는 최대는 32767 ÷ 64 = 511.984375° 다. 360° 를 넘는 자리가 남아 있다는 것이 중요하다 — 14비트로 마스크하면 360° 근처가 조용히 접히고, 그 점은 한 바퀴에 한 번 나타나 l-04 의 회전 자르기를 흔든다. 시험 벡터 2·5 가 오직 이것을 위해 있다.

4. 거리 0 을 "그 방향은 비어 있다"로 읽으면 무엇이 잘못되는가? 그리고 그 판단의 근거는 어느 등급인가

"비었다"는 지나가도 된다는 뜻이고 "못 쟀다"는 모른다는 뜻이다. 유리문·검은 천·측정 범위 밖은 전부 "못 쟀다"인데 이것을 "비었다"로 읽으면 로봇이 그쪽으로 간다. 반대로 0 을 "거리 0 m 에 물체"로 읽으면 코앞에 없는 벽이 생긴다. 이 셋을 분리하는 것이 l-09 의 점유 · 자유 · 미지 세 상태다.

근거의 등급은 미확인 1차다. 데이터시트는 0 의 뜻을 말하지 않고, 같은 모델(A1M8)을 쓴 1세대 코드가 0 = invalid / no return 이라 적었을 뿐이다(NOMINAL(gen1-record, 2026-07-14)) — 그 개체가 내 개체인지는 아직 확인되지 않았다. 내 기기에서 닫는 절차가 §3-2-4 셋째 행이다.

5. (일부러 틀리면) parse_point 에서 b3 과 b4 를 맞바꿔 읽으면 무엇이 보이는가? 검사 비트는 왜 이것을 못 잡는가

아무 오류도 나지 않고 점이 계속 흐른다. 검사 비트 S · ~S · C 는 전부 b0 과 b1 에 있어서 b3 · b4 를 어떻게 읽든 관여하지 않는다. 그래서 프레이밍은 통과하고 거리만 엉뚱해진다 — 예를 들어 A0 0F 를 뒤집어 읽으면 1000.0 mm 가 10243.75 mm 가 된다(§2-5).

이것이 이 쪽이 시험 벡터를 두는 이유다. 벡터 1·2·3·6 이 거리 바이트 순서를 잡는다. 반대로 벡터 4(거리 0)와 5(양쪽이 FF)는 두 바이트가 같거나 대칭이라 못 잡는다 — 벡터를 고르는 일 자체가 설계다.

6. 재동기 걸음을 5로 두면 점의 개수만으로는 무엇이 잘못됐는지 알 수 없다. 무엇을 봐야 하는가

이웃한 점들의 각도가 조금씩 커지는가를 봐야 한다. 경계를 제대로 잡고 있으면 센서가 도는 대로 각도가 순서대로 늘어난다. 경계를 잃은 채 우연히 검사 비트가 맞은 5바이트만 통과시키고 있으면 각도가 아무 데나 튄다.

걸음이 5면 한 번 어긋난 위상이 유지된다 — 진짜 경계는 언제나 5의 배수만큼 떨어진 자리에 있는데 잘못된 자리에서 5씩 뛰고 있으므로 영영 만나지 못한다. 걸음이 1이면 늦어도 5칸 안에 진짜 경계를 밟는다. 개수는 줄어든 정도로만 보이고, 진짜 증상은 각도의 이어짐에서 보인다.

def parse_point(b5):
    """One measurement node -> (deg, mm, quality), or None if this is not a node boundary."""
    if len(b5) != 5:
        return None                                   # short buffer: "not yet", not an error
    b0, b1, b2, b3, b4 = b5

    if (b0 & SYNC_MASK) == ((b0 >> 1) & SYNC_MASK):   # S and ~S must differ
        return None
    if not (b1 & CHECK_MASK):                         # C must be 1
        return None

    quality = b0 >> QUALITY_SHIFT                     # top 6 bits
    angle_q6 = ((b2 << 8) | b1) >> ANGLE_SHIFT        # little endian u16, then drop the check bit
    dist_q2 = (b4 << 8) | b3                          # little endian u16, no flag bits here
    return (angle_q6 / 64.0, dist_q2 / 4.0, quality)

내 것과 다를 수 있는 곳 — 어느 쪽이 맞고 틀린 문제가 아니다.

  • 반환값의 모양. 여기는 None 하나로 "경계가 아니다"를 말한다. 예외를 던지거나 (ok, 값) 꼴로 돌려주는 설계도 있다 — 다만 stream() 이 초당 수천 번 부르는 자리라 예외는 비싸다는 것은 사실이다.
  • 16비트를 만드는 방법. (b2 << 8) | b1 대신 int.from_bytes(b5[1:3], "little") 를 써도 같다. 전자는 헤더의 비트 배치가 그대로 보이고, 후자는 엔디안을 낱말로 적어 둔다.
  • 길이 검사를 어디서 하는가. 여기는 parse_point 안에서 한다 — 그래서 stream() 의 버퍼 끝 처리가 단순해진다. 반대로 호출자가 항상 5바이트를 보장하게 하고 여기서는 안 보는 설계도 있다. 그 경우 시험 벡터 10 을 지워야 하고, 그러면 짧은 버퍼에서 죽는 길이 열린다.
  • 거리 0 을 여기서 버리는가. 이 비교본은 버리지 않는다(§2-3). 버리는 설계도 돌아가지만, 그러면 "못 쟀다"라는 정보가 이 줄에서 사라져 l-09 의 미지 칸을 만들 수 없게 된다.
