Raspberry Pi 5 + ROS 2 Humble
자율주행 디바이스 학습 가이드

LiDAR·카메라·MCU를 갖춘 로봇을 ROS 2의 노드 구조에 맞게 직접 구성해서 실제로 주행시키는 것이 이 가이드의 끝입니다. 주 언어는 C++, 보조는 Python이며, 영상 처리는 OpenCV, 객체 검출은 YOLO(그리고 Hailo-8 가속)를 씁니다.

이 가이드의 원칙

배우는 주체는 도구가 아니라 사용자 본인입니다. 모든 단계는 개요 → 원리(왜) → 실습 → 검증 체크포인트 → 이해 확인 순서로 되어 있고, 체크포인트는 "떴다"가 아니라 "내가 직접 명령을 쳐서 눈으로 확인했다"가 통과 기준입니다. 이해 확인 질문에 답할 수 없으면 그 단계를 다시 읽습니다.

1. 이 가이드를 쓰는 법

  1. 순서대로 갑니다. 각 단계는 앞 단계의 산출물(장치 인식, 컨테이너, TF 트리, /odom…)을 전제로 합니다. 특히 05(TF)를 건너뛰면 07 이후에서 반드시 막힙니다.
  2. 편집은 Mac, 실행은 Pi. 이 저장소는 Mac에 있고 코드 편집·git 만 합니다. ros2·colcon·docker 명령은 전부 Pi 에서(대부분 Pi 의 Docker 컨테이너 안에서) 실행합니다. 각 명령 앞에 Mac / Pi 호스트 / 컨테이너 표시를 두었습니다.
  3. 코드는 직접 칩니다. 가이드의 C++/Python 코드는 보고 베끼는 것이 아니라 손으로 치고, 한 줄씩 왜 있는지 설명할 수 있게 되는 것이 목표입니다. 저장소의 ros2_ws/src/ 에 있는 기존 코드는 "읽고 이해할 참고 구현"입니다.
  4. 체크포인트를 체크합니다. 각 페이지 끝의 체크박스는 이 브라우저에 저장되고, 아래 §8 과 왼쪽 목차에 진행률로 모입니다.
  5. 막히면 99 로. ROS 2 문제의 대부분은 "코드가 틀렸다"가 아니라 "연결이 안 되어 있다"입니다. 로그를 읽기 전에 그래프를 봅니다.

2. 당신이 알고 있는 구조 → ROS 2 노드 그래프

당신이 이미 이해하고 있는 추상 구조는 이것입니다.

  ① 라이다로 공간을 스캔한다
  ② 카메라로 보이는 물체를 판정하고, 같은 물체를 따라가며(추적), 라이다와 합쳐 거리를 잰다
  ③ 요청(목표)에 대해 계획을 세운다
  ④ 이동한다 — 세부 제어(모터·전원)는 MCU 가 맡는다
  ⑤ 이동하는 동안 "계획 대비 얼마나 수행됐는가"를 계속 판정한다

ROS 2 에서는 이 다섯 개가 노드가 되고, 노드 사이의 데이터가 토픽·서비스·액션이 됩니다. 아래 그림이 이 가이드를 끝냈을 때 Pi 위에서 실제로 돌아갈 그래프입니다. 상자를 클릭하면 그 노드를 만드는 단계로 갑니다.

이 프로젝트의 핵심 두 축

팔도 없고 조작기도 없다. 라이다·카메라로 어디로 갈지 계획을 도출하는 것(③, Pi 쪽: 09·10)과, 그 계획을 땅에 전달하는 4륜 모터 제어(④, MCU 쪽: 06a·06)가 이 로봇의 핵심이다. 나머지 단계(센서 연결, 인지, 시각화)는 이 두 축을 먹여 살리는 지원 계층이다. 우선순위가 갈릴 때는 이 기준으로 정한다.

센서·구동 (하드웨어 경계) 인지·추정 계획·감독 제어 형상·TF ROS 밖 실선 = 토픽 · 점선 = TF 조회

다섯 개의 추상 단위가 어디로 갔는지 대응시키면 이렇습니다.

왜 이 그림을 먼저 보는가 — 위에서 아래로

MCU 부터 올라오면 위로 갈수록 "이걸 어디에 어떻게 붙이지"라는 확장점이 폭발합니다. 반대로 완성된 그래프를 먼저 놓고 각 상자를 하나씩 채우면, 매 단계에서 "이 노드가 무엇을 받고 무엇을 내야 하는가"가 이미 정해져 있습니다. 노드의 인터페이스(토픽 이름·메시지 타입·프레임 이름) 가 계약이고, 구현은 그 계약을 채우는 일입니다. 그래서 이 가이드의 모든 단계 페이지는 "이 노드가 그래프의 어디에 있는가"로 시작합니다.

3. 노드 단위 학습 순서 — 왜 이 순서인가

순서는 데이터가 흐르는 방향과 검증 가능성으로 정했습니다. 각 단계의 출력이 다음 단계의 입력입니다.

  환경          기초                 구동·센서              비전                                자율주행
  01 ─ 02  ──►  03 ─ 04 ─ 05  ──►   06a ─ 06 ─ 07  ──►   08 ─ 08a ─ 08b ─ 08c ─ 08d  ──►   09 ─ 10
  장치 인식     개념  C++노드 TF      프로토콜 odom  scan     영상  OpenCV YOLO  Hailo  추적·거리     지도·경로  조립·감독
                          ▲                                                                         │
                          └────────── TF 가 없으면 07 이후 어느 것도 공간에 놓이지 않는다 ──────────┘
  • 03 → 04 → 05 는 도구가 아니라 언어 습득입니다. 토픽·서비스·액션·파라미터·QoS(03), 그것을 C++ 로 쓰는 법(04), 그리고 좌표계(05). 이 셋이 있어야 뒤의 모든 노드를 "읽고 쓸" 수 있습니다.
  • 06(MCU) 이 07(LiDAR) 보다 먼저인 이유: SLAM 은 /odom 없이는 돌지 않고, 가짜 MCU(simulate:=true) 로 하드웨어 없이 ROS 쪽을 먼저 검증할 수 있기 때문입니다.
  • 08 → 08a → 08b → 08c 는 같은 인터페이스를 점점 빠르게 만드는 과정입니다. 영상을 받는다(08) → OpenCV 로 다룬다(08a) → YOLO 로 /detections 를 낸다(08b, CPU 라 느림) → 같은 /detections 를 Hailo 로 낸다(08c, 실시간). 인터페이스가 같으니 하위 노드는 아무것도 바꾸지 않습니다. 08d 는 그 /detections 위에 추적(/tracks)과 라이다 융합 거리(/objects)를 얹습니다 — 검출기는 그대로 두고 소비자만 늘립니다.
  • 09 → 10 은 새 기능이 아니라 조립입니다. 남이 만든 SLAM/Nav2 를 구조를 이해한 채로 붙이고, 마지막에 당신의 감독 노드가 그 위에 올라갑니다.

5. 학습 계획

총 약 71~116시간, 주 8시간이면 9~15주입니다. 시간의 폭이 큰 것은 하드웨어 문제(전원, 케이블, 버전 불일치)가 개인마다 다르게 나오기 때문입니다. 단계는 건너뛰지 않되, 같은 Phase 안에서는 막힌 곳을 두고 다음 단계의 "원리" 절만 먼저 읽는 것은 괜찮습니다.

산출물: hardware/INVENTORY.md 의 빈칸이 실측값으로 채워진다.

7. 학습 중 지킬 습관

# ① 무엇이 돌고 있는가
ros2 node list
ros2 topic list

# ② 이 노드는 무엇과 연결되어 있는가
ros2 node info /mcu_bridge

# ③ 이 토픽에 정말 데이터가 흐르는가 (초당 몇 번?)
ros2 topic hz /odom
ros2 topic echo /odom --once

ros2 topic info /scan -v
