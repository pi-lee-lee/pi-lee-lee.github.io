2. 원리 — 왜 이 두 가지가 같은 쪽에 있는가

2-1. 재는 값을 먼저 정한다 — 카운트에서 mm/s 까지

PID 의 입력은 "오차"다. 오차를 만들려면 목표와 측정이 같은 단위여야 한다. 계약 v2 의 목표는 mm/s(06a §4-3)이므로 측정도 mm/s 로 만든다. 재료는 fw-09 가 이미 만들어 두었다 — encoder_delta(wheel) 는 그 바퀴의 직전 호출 이후 카운트 변화를 부호까지 붙여 돌려준다. 1 kHz 박자마다 한 번씩 부르면 창의 길이는 언제나 1 ms 다.

측정 [mm/s] = encoder_delta(wheel) [counts / 1 ms]  x  TICK_TO_MM_S

TICK_TO_MM_S = 2 x pi x WHEEL_RADIUS_MM / ENCODER_CPR / DT
             = 2 x 3.14159 x 90 / 94000 / 0.001
             = 6.0158 ... [mm/s per (count per ms)]        <- 공칭값으로 계산한 예시

이 숫자가 곧 속도의 최소 계단이다. 1 ms 창에서 카운트는 정수로만 변하므로 측정 속도도 6 mm/s 단위로만 움직인다 — 같은 계산과 그 표는 fw-09 §2-6 에 있고 여기서 다시 세우지 않는다. 거기서 따라 나온 결론 하나를 이 쪽이 받는다: "속도가 안 나온다"는 판정의 문턱을 6 mm/s 아래로 둘 수 없다(1 ms 창 하나로는). 창을 넓히면 계단이 잘아지는 대신 판정이 늦어진다 — 어느 창을 쓸지는 내가 정한다.

등급 — 이 축 전체가 아직 공칭값 위에 서 있다

WHEEL_RADIUS_MM 90 은 공칭 지름 180 mm 의 절반이다(hardware/INVENTORY.md 6절 "바퀴 지름" 행 — NOMINAL(gen1-record), 실측 지름 칸은 아직 ____). ENCODER_CPR 은 fw-09 에서 내가 잰 값이거나 아직 공칭 94,000 이다. 그러니 이 쪽에서 나오는 mm/s 는 축척이 몇 % 틀려 있을 수 있는 수다. 그래도 제어에는 문제가 없다 — 목표와 측정이 같은 축척으로 틀려 있으면 게인이 그 차이를 흡수한다. 문제가 되는 것은 이 숫자를 바깥과 견줄 때(오도메트리 · 지도 축척)이고, 그것은 관문 09a 의 일이다. 그래서 이 쪽의 합격선은 "몇 mm/s 이내"라는 남의 숫자가 아니라 내가 찍은 곡선을 보고 내가 정하는 값이다.

2-2. 고정 dt 의 이산 PID — 세 항이 각각 무엇을 고치는가

연속 시간의 PID 는 적분과 미분으로 쓰여 있지만, MCU 는 1 ms 마다 한 번씩만 깨어난다. 적분은 더하기가 되고 미분은 차이 나누기 dt 가 된다. dt 가 고정이라는 것이 이 모든 것의 전제다 — fw-06 이 하드웨어 격자로 박자를 만든 이유가 여기서 값을 한다.

항이산 꼴무엇을 고치는가혼자 쓰면 남는 것
Pkp * err지금 벌어진 차이에 비례해 민다정상상태 오차 — 마찰을 이기는 듀티가 필요하면 오차가 0 이 될 수 없다(오차가 0 이면 출력도 0 이니까)
Iki * (integ += err * dt)남은 차이를 시간에 걸쳐 쌓아 없앤다와인드업(§2-3)과 느린 진동
Dkd * (err - prev_err) / dt차이가 빨라지는 것을 미리 깎는다(제동)잡음 증폭 — 측정이 6 mm/s 씩 계단으로 뛰므로 그 한 칸이 kd / dt = kd x 1000 배로 커진다

세 번째 줄이 이 로봇에서 특히 아프다. 측정이 한 칸 튀는 것만으로 D 항이 kd x 6000 만큼 출렁인다 — 그래서 속도 루프의 D 는 흔히 0 이다(1세대도 Kd 0 이었다). D 를 쓰고 싶으면 먼저 측정 창을 넓혀 계단을 잘게 만들어야 한다. 그 순서를 뒤집으면 "게인을 올렸더니 소리가 난다"로 끝난다.

왜 dt 를 구조체에 담아 다니지 않는가

pid.h 는 PID_DT_S 0.001f 를 파일 안에 못박는다. 박자는 하나뿐이고(TIM6), 바퀴마다 다를 수 없기 때문이다. 대신 그 사실이 깨질 자리를 한 군데로 모은 것이다 — 언젠가 박자를 500 Hz(2 ms)로 바꾼다면 고칠 곳은 이 한 줄과 CubeMX 의 ARR 둘뿐이고, 그 둘이 어긋나면 게인이 조용히 두 배가 된다. 골격의 주석에 그 연결을 적어 두는 이유다.

2-3. 적분 와인드업 — 고장이 아니라 산수의 결과다

출력에는 한계가 있다(듀티는 ±1000 ‰ 를 넘지 못하고, 내가 정한 DUTY_LIMIT_BENCH_PERMILLE 은 그보다 더 낮다). 한계에 닿아 있는 동안에도 오차는 남아 있고, 적분은 그 오차를 계속 더한다. 더해 봐야 출력은 변하지 않는데 적분값만 자란다. 그러다 오차의 부호가 바뀌면 — 목표를 0 으로 내리거나 반대로 돌리면 — 쌓인 적분을 다 깎을 때까지 출력이 한계에 붙어 있다. 바퀴는 명령을 무시하고 계속 돈다.

 목표 --+----+                     오차                 적분값
        |    |                  +----+                +--------+
   0 ---+    +---------      0 -+    +--------      0 -+        +-------
                                                        \   와인드업이 없으면 여기서 바로 내려온다
   출력 (한계에 붙어 있는 구간)
        +----------------------------+                  +-------+
   0 ---+                            +------       0 ---+       +--------
                                     ^                          ^
                              목표를 내린 시각                와인드업이 있으면 여기까지 늦는다

막는 법은 하나가 아니다. 셋 다 "포화 중에는 적분을 자라지 못하게 한다"는 같은 말을 다르게 쓴 것이다.

꼴하는 일대가
조건부 적분(conditional integration)출력이 포화하면 이번에 더한 만큼을 도로 뺀다가장 짧다. 포화 경계에서 적분이 계단으로 멈췄다 움직인다
백캘큘레이션(back-calculation)포화 전후의 차이 (sat - u) 에 비례해 적분을 되돌린다부드럽다. 되돌리는 세기 상수가 게인의 단위에 매여 있다 — 남의 값을 옮기면 무력해진다(아래 상자)
적분 클램프(integral clamping)적분값 자체를 범위 안에 가둔다가장 단순하다. 가두는 범위를 어디에 둘지가 또 하나의 정해야 할 값이 된다

이 쪽은 어느 것을 쓰라고 정하지 않는다. 정하는 것은 셋 다 만족해야 하는 성질이고, 그 성질을 §3-1 의 호스트 시험이 벡터로 채점한다: 200 ms 동안 출력이 포화해 있어도 적분값은 한 틱치(1 ms 어치)보다 더 자라지 않는다.

1세대 무부하 튜닝값(기록, 2026-07-19)을 값으로 옮기지 못하는 이유

1세대는 1 kHz 속도 PID 를 Kp 0.60 / Ki 1.50 / Kd 0 / 백캘큘레이션 Kt 2.0 으로 돌렸다(1세대 펌웨어 FW/control/include/motor_ctrl.h:91,149-206). 그런데 1세대의 오차 단위는 count/s 이고 출력 풀스케일은 500 tick 이었다 — 이 프로젝트는 mm/s 와 1000 ‰ 다. 같은 숫자가 다른 물리량을 가리킨다. 그래서 이 값들은 NOMINAL 로도 쓸 수 없고 "기록"으로만 인용한다. 집필 중에 실제로 확인한 것 하나: 위의 Kt 2.0 을 그대로 옮긴 백캘큘레이션 구현은 §3-1 의 와인드업 벡터에서 떨어진다(되돌리는 세기가 이 게인 스케일에서는 너무 약해 적분이 200 ms 동안 거의 그대로 자란다). 게인을 옮기면 안 된다는 말이 추상적인 주의가 아니라 컴파일해서 보이는 결과라는 뜻이다.

2-4. P → I → D 순서로 잡는다 — 그리고 게인이 0 인 채로 먼저 한 번 찍는다

게인 셋을 한꺼번에 움직이면 무엇이 무엇을 바꿨는지 알 수 없다. 순서는 하나다.

  1. 전부 0 으로 한 번 찍는다. step 의 CSV 에서 목표는 계단인데 측정과 듀티는 바닥에 붙은 평평한 선이 나온다. 이것이 기준선이다 — 포획 · 덤프 · 그림 그리기가 다 도는지를 게인과 무관하게 먼저 확인한다.
  2. P 만. 진동 직전까지 올린다. "직전"은 CSV 에서 측정 곡선이 목표 주위를 넘실거리기 시작하는 지점이다. 그 값을 적고 절반쯤으로 내린다.
  3. I 를 더한다. 정상상태에서 남는 차이(목표선과 측정선의 간격)가 사라질 때까지. 너무 올리면 오버슛이 커지고 진동이 느려진다.
  4. D 는 필요할 때만 조금. §2-2 의 셋째 줄을 먼저 읽는다.
  5. 네 바퀴를 따로 본다. 같은 게인으로 네 바퀴의 곡선이 겹치지 않으면 그것은 게인이 아니라 배선 · 부호 · 기계의 문제다.

게인은 robot_params.h 의 PID_KP_MILLI · PID_KI_MILLI · PID_KD_MILLI 에 정수 밀리 단위로 산다(1200 = 1.2). 명령 창의 pid set kp 1200 은 RAM 의 값만 바꾼다 — 리셋하면 헤더의 값으로 돌아간다. 마음에 드는 값을 찾으면 헤더에 옮겨 적는 것은 내 손이고, 그 뒤에 저장까지 가는 길은 fw-16 이다.

이 세 키에는 _Static_assert 가드를 두지 않는다

fw-08 의 PWM_CMD_HOLD_MS 나 DUTY_LIMIT_BENCH_PERMILLE 은 빈칸(0)이 위험한 쪽으로 동작해서 가드로 빌드를 세웠다. 게인은 반대다 — kp = 0 이면 듀티가 0 이고, 그것이 가장 안전한 상태다. 게다가 튜닝하려면 먼저 빌드해서 돌려 봐야 하고, 돌려 봐야 값을 정할 수 있다. 가드를 두면 그 고리를 스스로 막는다. 그래서 게인만은 0 으로 태어나 빌드되고, 첫 step 이 평평한 선을 내는 것이 정상이다. 같은 이유로 ./scripts/check_nominal.sh 는 이 세 줄을 EMPTY 로 계속 셀 것이다 — 그 개수가 0 이 되는 것은 fw-19 의 조건이지 이 쪽의 조건이 아니다.

2-5. 멈출 때 적분을 0 으로 — 1세대가 실물로 배운 것

1세대 벤치에서 이런 일이 있었다(기록, 2026-07-18): 정지 명령을 줬는데 상태는 RUN 이고 듀티가 −4 tick 남아 있었다. 감속하는 동안 쌓인 음의 적분이 백캘큘레이션의 고정점에서 얼어붙어, 목표가 0 인데도 아주 작은 듀티를 계속 내보내고 있었다. 고친 방법은 규칙 하나였다 — 목표가 0 이고 측정 속도가 바닥이면 적분을 0 으로 하고 정지 상태로 간다. 감속 램프 자체는 그대로 두었다(화물 때문에 급정지를 피해야 해서).

이 쪽이 가져오는 것은 그 구조다. 값("바닥"이 몇 mm/s 인가)은 §2-1 의 계단 크기와 내 측정 창에서 나오므로 내가 정한다. 골격에서 이 규칙이 들어가는 자리는 두 군데다: 목표가 0 으로 내려올 때, 그리고 보호가 트립해서 출력을 끊을 때(§2-7). 둘 다 "다시 시작할 때 과거를 들고 가지 않는다"는 같은 말이다.

2-6. 폐루프와 보호 3종이 같은 쪽에 있는 이유

1세대의 가장 비싼 사고는 이것이다(기록, 2026-07-18): 엔코더의 GND 선이 끊겼다. 속도가 항상 0 으로 읽혔다. PID 는 "목표 5000, 측정 0" 을 보고 오차를 계속 적분했다. 듀티는 최대로 갔고 바퀴는 전속으로 돌았다. 폴트는 한 건도 뜨지 않았고 정지 명령으로도 세우지 못했다.

왜 아무것도 못 잡았는가. 그때 있던 보호 셋이 동시에 눈이 멀어 있었다 — 1세대 기록은 이것을 "3중 블라인드"라고 부른다.

있던 보호왜 못 봤는가
스톨 판정"목표 ≥ 6000" 이라는 절대 게이트가 있었는데 그날 목표는 5000 이었다 — 판정 자체가 켜지지 않았다
부호 이상 판정측정 속도가 0 이라 부호가 없다. "부호가 다르다"가 성립하지 않는다
과전류 판정바퀴가 공중이라 전속으로 돌아도 전류가 작다(무부하 1개 약 0.5 A — 1세대 실측)

그래서 새 폴트 하나가 생겼다: FEEDBACK_LOST — "이 듀티를 주고 있는데 이만큼의 속도가 안 나온다". 되먹임 자체가 죽은 것을 되먹임의 빈자리로 잡는다.

이 쪽에서 같이 해야 하는 이유

고리를 닫는 코드와 고리의 고장을 잡는 코드를 다른 쪽에서 쓰면, 그 사이의 기간 동안 벤치에는 "측정이 틀리면 최대 듀티로 가는 장치"가 그대로 놓여 있게 된다. 이 가이드가 PID 와 보호 3종을 한 쪽에 묶은 것은 분량 때문이 아니라 그 기간을 0 으로 만들기 위해서다. 실습 B(계단 응답)를 하고 실습 C(보호)를 미루지 않는다. 미뤄야 한다면 그동안 DUTY_LIMIT_BENCH_PERMILLE 을 더 낮춰 두고(fw-08 §2-9 의 상한이 PID 출력에도 그대로 걸린다) 바퀴를 공중에 둔 채로만 돌린다.

IWDG(하드웨어 워치독)는 이것을 막지 못한다는 점도 여기서 못박아 둔다. 그날 펌웨어는 멈추지 않았다 — 1 kHz 루프도 주 루프도 정상으로 돌고 있었고 kick 도 제때 들어갔다. IWDG 가 잡는 것은 "죽은 것"이고, 이것은 "살아서 틀리는 것"이다. 둘은 다른 장치가 맡는다.

2-7. 보호는 두 방향으로 틀린다 — 판정식의 구조가 전부다

1세대 총평이 이것을 한 줄로 적어 두었다: "보호 장치는 두 방향으로 틀린다(못 잡는다 / 잘못 잡는다). 셋 다 로직이 아니라 선을 어디에 긋느냐가 틀렸다." 아래 두 사고가 각각 한 방향이고, 고친 방법이 그대로 이 쪽 판정식의 구조가 된다. 숫자는 가져오지 않는다.

날짜(1세대 기록)무슨 일왜 틀렸나구조를 어떻게 고쳤나
2026-07-19정상 급가속을 FEEDBACK_LOST 로 오판 — 4모터가 동시에 트립. 같은 날 목표 100000 은 통과하고 105000 은 실패했다 처음 판정식이 |속도| x 2 < |목표| 였다 — 문턱이 목표에 비례했다. 슬루로 듀티가 천천히 오르는 동안 듀티 게이트는 300 ms 에 열리는데 속도는 아직 목표의 절반에 못 미친다 문턱을 지금 인가하고 있는 듀티에 비례시켰다: |속도| < |듀티| x (건강한 속도:듀티 비) / FRAC. 1세대는 FRAC = 4 를 썼다(= "이 듀티가 낼 속도의 25 % 도 안 난다")

여기서 두 가지 일반 규칙이 나온다.

  • 문턱은 "지금 무엇을 하고 있는가"에 매단다(인가 듀티), "무엇을 바라는가"(목표)에 매달지 않는다. 목표는 순간에 뛰지만 실제 구동은 천천히 오르기 때문이다.
  • 판정은 국면을 가린다. 구동 · 제동 · 타력은 물리적으로 다른 구간이고, 구동 국면에서만 참인 규칙을 제동 국면에 적용하면 정상을 고장이라 부른다.

그리고 반대 방향의 대가가 blind band 다. 오트립을 막으려고 게이트를 두면(목표가 작을 때는 판정하지 않는다, 듀티가 낮을 때는 판정하지 않는다) 그 구간에서는 진짜 고장도 안 보인다. 1세대의 STALL 은 "목표 < A" 구간이, FEEDBACK_LOST 는 "목표 < 2000" 구간이 그대로 눈먼 곳으로 남았다. 이것은 없앨 수 있는 결함이 아니라 골라야 하는 값이다 — 그래서 §3-3 의 호스트 시험에는 "그 게이트 아래에서는 아무리 오래 둬도 STALL · FEEDBACK_LOST 가 트립하지 않는다"가 통과해야 하는 벡터로 들어 있다. 눈먼 곳이 어디인지를 내가 알고 골랐다는 증거다. 셋의 눈먼 곳이 같은 자리에 있는 것은 아니다 — 아래 표를 보면 목표 게이트와 듀티 게이트를 가진 것은 STALL 과 FEEDBACK_LOST 둘이고, FEEDBACK_SIGN 에는 속도 게이트 하나뿐이다. 그래서 앞의 둘이 눈을 감는 낮은 듀티에서도 FEEDBACK_SIGN 은 판정한다(§3-3 의 벡터가 그 사실도 채점한다) — 되먹임 부호가 뒤집힌 상태는 듀티가 작아도 위험하다는 판단이 그 구조에 들어 있는 것이고, 대신 저듀티 구간의 오트립 여지가 남는다.

2-8. 듀티 슬루를 우회하지 않는다 — 전기적인 이유다

"긴급 정지 · 긴급 회피는 램프를 건너뛰고 바로 최대로" 는 그럴듯하게 들린다. 1세대는 그 경로를 실제로 만들다가 듀티 슬루만은 우회 금지로 결론냈다(기록, 2026-07-19). 이유가 제어가 아니라 전기다 — 슬루를 없애면 네 모터가 동시에 0에서 최대로 뛰면서 버스 전압이 꺼지고, 5 V 레일이 브라운아웃되고, 회피하는 도중에 제어 자체를 잃는다. 같은 회차에서 잰 값: 4모터 0→정격의 피크 전류 1.97 A, 버스 23.46 V(무부하). 부하가 걸리면 이보다 커진다는 것이 이 숫자의 뜻이다.

1세대가 쓴 시간은 가속 1500 ms · 감속 400 ms · 방향 전환 정지 200 ms 였다(기록). 이 값들은 옮기지 않는다 — 배터리 · 배선 저항 · 사전충전 회로가 확인되기 전에는 근거가 없는 숫자다. 이 쪽의 골격에도 슬루는 들어 있지 않다. 슬루가 없는 상태의 계단 응답을 먼저 봐야 "PID 가 어디까지 빠른가"를 알 수 있고, 그 다음에 "전원이 어디까지 견디는가"를 재서 슬루를 정할 수 있기 때문이다. 그 순서가 뒤집히면 슬루가 만든 느림을 게인으로 오해해 계속 올리게 된다. 슬루를 넣을지 · 얼마로 할지는 이 쪽의 기록을 보고 내가 정하고, 부하에서 다시 보는 것은 fw-20 이다.

그래서 이 쪽의 실습은 DUTY_LIMIT_BENCH_PERMILLE 아래에서만 돈다

PID 의 출력도 motor_set() 을 지나며 fw-08 에서 내가 정한 상한에 잘린다(fw-08 §2-9 의 상한이 명령 경로든 제어 경로든 같은 자리에서 걸린다). 슬루가 없는 이 골격에서 그 상한이 사실상의 슬루 노릇을 한다 — 목표를 낮게 주고 상한을 낮게 두면 0→최대 계단 자체가 일어나지 않는다. 계단 응답을 크게 찍고 싶어 상한을 올리기 전에 이 절을 다시 읽는다.

2-9. 1 kHz 는 실시간으로 찍을 수 없다 — RAM 에 잡아 두었다가 끝나고 덤프한다

계단 응답을 보려면 1 ms 마다의 목표 · 측정 · 듀티가 필요하다. 그것을 그때그때 찍으면 어떻게 되는지는 산수로 나온다. VCP 는 460800 8N1 이고 1바이트가 10비트이므로 초당 46 080 B다(fw-06 §2-1 의 같은 계산). 한 행이 1999,200,198,-412,0 + 줄바꿈 = 약 20 B 라면 1 kHz 로는 초당 20 000 B — 대역은 남는다. 그런데 문제는 대역이 아니다.

  • 찍는 행위가 재려는 것을 망가뜨린다. 콘솔 송신은 블로킹이다(fw-03) — 20 B 한 줄에 20 ÷ 46 080 = 0.00043 초 = 0.43 ms 가 걸리고, 그 시간 동안 주 루프는 다른 아무것도 못 한다. 1 kHz 루프의 지터를 재려고 만든 창이 지터의 원인이 된다.
  • ISR 에서는 애초에 찍을 수 없다. 1 kHz 콜백 안에서 LOG_* · printf 금지는 fw-03 부터의 규칙이고(글자는 주 루프가 찍는다), 블로킹 송신을 선점 1 짜리 ISR 안에서 하면 그 아래 모든 것이 멈춘다.
  • 네 바퀴를 다 찍으면 행이 커져 위의 여유가 사라진다. 계약 v2 의 상태 프레임도 같은 선을 쓰고 있다(50 Hz).

그래서 꼴은 하나다: ISR 이 RAM 배열에 채워 넣고, 다 찬 뒤에 주 루프가 한 번에 덤프한다. 덤프하는 동안 모터는 이미 서 있고(step 이 끝나면서 목표가 0 이 된다) 명령 창은 그 시간만큼 응답하지 않는다. 그 시간이 곧 아래의 워치독 예산 행이다.

2-10. 1 kHz 콜백 안의 순서 — 단조 사슬로 잡는다

fw-06 이 만든 HAL_TIM_PeriodElapsedCallback() 안은 이제 여러 쪽이 한 줄씩 넣는 자리가 됐다. 이 쪽이 control_step_1khz() 를 더하면 세 개가 된다. fw-11 §2-6 이 그 자리를 미리 비워 두었다 — "전원 뒤, 출력 앞". 이 쪽은 그 예약석에 앉는다.

{

순서의 근거를 규칙 하나로 쓴다: 뒤에 오는 단계는 앞 단계의 출력을 줄이기만 하고 키우지 못한다(단조 사슬). 2 는 전원이 준비되지 않았으면 EN 을 내린다. 3 은 목표에 맞춰 듀티를 쓰되 보호가 트립하면 0 으로 만든다. 4 는 pwm 명령의 유지 시간이 끝났으면 0 으로 만든다. 5 는 아무것도 바꾸지 않는다. 이 규칙이 있으면 뒤에 무엇이 더 붙어도 순서를 다시 논의하지 않는다 — "출력을 줄이는 것"은 뒤에, "출력을 만드는 것"은 앞에.

3 과 4 의 순서는 이 규칙의 직접적인 결과다. 4 를 3 앞에 두면, 유지 시간이 끝나 듀티를 0 으로 만든 바로 그 틱에 3 이 다시 듀티를 써 버린다 — fw-08 이 만든 안전 장치가 소리 없이 약해진다. 두 *_step_1khz() 의 계약은 이렇게 적어 둔다.

2-12. 명령 워치독 200 ms — 계약이 정한 값이고, IWDG 와 다른 장치다

계약 v2 는 이렇게 적어 두었다(06a §4-3): "MCU: 200 ms 동안 워치독을 되감는 프레임이 없으면 → 정지 (= 50 Hz 명령 10개 결손)". 이 값은 임시값이 아니라 계약값이다. 그래서 robot_params.h 의 CMD_WATCHDOG_MS 는 EMPTY 가 아니라 200 으로 태어나고 주석은 /* contract v2 */ 다.

구현은 두 줄로 끝난다. control_set_target() 이 명령 시각을 갱신하고, control_step_1khz() 가 그 나이를 1 ms 씩 세어 200 을 넘으면 목표를 0 으로 만든다. "목표를 0 으로" 까지가 이 쪽의 일이다 — 그것을 fault 비트로 올리고 이벤트 0x83 을 내보내는 것, 그리고 계약 경로(Pi 없이 mcu_probe.py 로 송신을 끊어 보는 시험)에서 다시 판정하는 것은 fw-18 의 몫이다. 06a §4-2 의 fault 비트 표와 이벤트 코드 표는 (제안) 이라고 적혀 있고, 어느 비트 · 어느 코드를 쓸지 정하는 것은 내 과제다 — 이 쪽은 그 자리를 비워 둔다.

두 워치독을 섞어 부르지 않는다
  • 하드웨어 워치독(IWDG, fw-06) — 펌웨어가 죽은 것을 잡는다. 못 잡는 것: 살아서 틀리는 것(§2-6), 명령이 끊긴 것.
  • 명령 워치독(200 ms, 이 쪽) — 상위가 말을 멈춘 것을 잡는다. 못 잡는 것: MCU 자신이 멈춘 것, 전원이 사라진 것.
  • 전원 상실 — 이것은 워치독이 아니라 MOTOR_EN 의 풀다운이 맡는다(fw-08 · fw-11). USB 를 뽑는 시험은 워치독 시험이 아니라 이것의 시험이다(fw-06 §2-9).

세 장치를 같은 문장에서 "워치독" 한 낱말로 부르면, 하나를 시험하고 셋 다 됐다고 믿게 된다. 1세대가 실제로 그랬다.

결정 대기 — 무엇이 워치독을 되감는가

계약 문서의 이전 판은 "200 ms 무프레임", 본편 06 §1-1 의 표는 "200 ms 무명령"이라 적어 두 쪽이 갈려 있었다. 둘은 다른 규칙이다(06a §4-3 의 상자).

(가) 유효한 0x01(속도 명령)만 되감는다 — "상위가 명령을 보내고 있는가"를 본다. 되감는 자리가 control_set_target() 안이라 통신 모듈은 워치독을 몰라도 된다. 나중에 설정 프레임(0x02)이 생겨도 그것만 오고 속도 명령이 끊기면 200 ms 뒤 선다.
(나) CRC 를 통과한 모든 프레임이 되감는다 — "링크가 살아 있는가"를 본다. 되감는 자리는 프레임 파서(통신 모듈)다. 0x02 를 구현한 뒤 설정 프레임만 계속 오면 MCU 는 마지막 목표를 유지한 채 계속 달린다.

차이가 없는 축(동일): 지금 계약에서 Pi → MCU 프레임은 0x01 하나뿐이라 지금은 두 규칙의 동작이 같다 · CRC 가 틀린 프레임은 어느 쪽에서도 되감지 않는다 · 200 ms 라는 값 · Pi 쪽 0.5 s 워치독.

이 가이드의 기본 진행은 (가) 다 — 되감는 자리가 control_set_target() 안이면 이 쪽의 코드만으로 닫히기 때문이고, 권고가 아니다. (나)로 가면 되감는 줄이 fw-17 의 파서로 옮겨 가고 이 쪽의 골격에서 그 한 줄이 빠진다.

결정 대기 — TEXT 모드의 step 과 200 ms 가 어떻게 공존하는가

제어 · 안전 모듈은 TEXT 와 V2 에서 같은 코드다(LINK_MODE 는 app.c 한 군데에서만 갈린다). 그래서 명령 창으로 계단 응답을 찍는 동안에도 명령 워치독은 살아 있다 — 2초짜리 step 을 그냥 두면 200 ms 뒤 목표가 0 이 되어 버린다.

기본 진행[제안]: step 이 포획 구간 동안 control_set_target() 을 200 ms 보다 짧은 간격으로 다시 부른다 — 즉 50 Hz 로 명령을 보내는 상위 노릇을 대신한다. 그리고 step … once 는 목표를 한 번만 넣는다 → 워치독이 목표를 0 으로 만드는 행이 CSV 에 그대로 보인다(그것이 이 쪽의 발동 체크 하나다).

다른 선택지(채택하지 않은 이유는 우열이 아니라 "제어 모듈은 두 모드에서 같은 코드"와의 정합이다): TEXT 빌드에서 워치독을 끈다 — 제어 모듈이 모드에 따라 갈리고 TEXT 에서 워치독 경로가 한 번도 시험되지 않는다 / step 전용 목표 경로를 따로 둔다 — 워치독을 우회하는 계약 밖 입구가 하나 생긴다.

/* 완결 코드 T1 - User/Src/Control/pid.c */

힌트 T2 — pid_step() · 고정 dt 의 PID 한 스텝

할 일 — 입력은 오차 err(목표 − 측정, mm/s), 출력은 듀티 명령(permille)이고 언제나 [out_min, out_max] 안이다(I1). 안에서 바뀌는 상태는 둘 — 적분 integ 와 직전 오차 prev_err. 1 kHz ISR 이 바퀴마다 한 번 부르므로 printf 도 블로킹도 없다 — 산수뿐이다. 아래는 조건부 적분 꼴이다(§2-3 의 첫 행). 세 꼴 다 시험을 통과한다 — 다른 둘은 코드 설명의 "다르게 써도 되는 곳"에 있다.

완결 코드

/* 완결 코드 T2 - User/Src/Control/pid.c (조건부 적분 꼴) */
float pid_step(speed_pid_t *p, float err)
{
  p->integ += err * PID_DT_S;                                   /* I2: 이번 err 가 이번 적분에 들어 있다 */
  float u = p->kp * err
          + p->ki * p->integ
          + p->kd * (err - p->prev_err) / PID_DT_S;             /* I3: 리셋 뒤 prev_err 는 0 */
  p->prev_err = err;                                            /* 이번 오차를 쓴 "뒤에" 갱신한다 */
  if      (u > p->out_max) { u = p->out_max; p->integ -= err * PID_DT_S; }   /* I4: 더한 만큼 도로 뺀다 */
  else if (u < p->out_min) { u = p->out_min; p->integ -= err * PID_DT_S; }
  return u;                                                     /* I1: 언제나 [out_min, out_max] 안 */
}

코드 설명

  • p->integ += err * PID_DT_S; — 적분은 "오차 × 시간"의 합이다. PID_DT_S(0.001) 를 곱하는 것이 그 "× 시간"이고, 그래서 ki 의 단위가 (mm/s · s) 당 permille 이 된다. u 를 계산하기 전에 더하는 것이 I2 — group 3 의 첫 CHECK(100)가 "이번 오차가 이미 이번 출력에 들어 있다"를 본다.
  • float u = p->kp * err + p->ki * p->integ + p->kd * (err - p->prev_err) / PID_DT_S; — 세 항을 한 식으로. D 항은 "오차의 변화율" = (이번 − 직전) ÷ dt. / PID_DT_S 가 float 나눗셈인 것에 주의한다 — 1 / 1000 처럼 정수끼리 쓰면 0 이다(아래 표).
  • p->prev_err = err; — 이번 오차를 쓴 뒤에 갱신한다. 위 식보다 앞에 두면 (err - prev_err) 가 늘 0 이라 D 항이 죽는다(group 2 가 잡는다).
  • if (u > p->out_max) { u = p->out_max; p->integ -= err * PID_DT_S; } — 포화다(I1). 그리고 같은 줄에서 방금 더한 적분을 도로 뺀다 — 이것이 조건부 적분(I4). 출력이 한계에 붙어 있는 동안 적분은 더 자라지 않으므로, 오차의 부호가 바뀌면 곧바로 한계에서 떨어진다(§2-3 의 그림). else if 로 아래쪽도 같게.
  • return u; — 이 줄에 오는 u 는 세 갈래(위로 잘림 · 아래로 잘림 · 안) 어디서 왔든 한계 안이다 — I1 은 "검사"가 아니라 구조에서 나온다.
  • 골격의 (void)p; (void)err; 와 return 0.0f; 는 지웠다.
  • 다르게 써도 되는 곳 — ① 와인드업 방지의 꼴: 적분 클램프는 integ 를 더한 직후 ±(out_max / ki) 로 가두고(ki != 0 일 때만 — 0 으로 나누지 않게) 포화 줄에서는 integ 를 건드리지 않는다. 백캘큘레이션은 포화 뒤 integ += kt * (sat - u_raw) 로 되돌린다 — 되돌리는 세기 kt 가 게인의 단위에 매인다(§2-3 의 상자). 집필 중 조건부 적분 · 클램프 둘을 실제로 돌려 둘 다 PASS pid 16 cases(2026-10-03). ② D 항을 아예 빼고 kd 필드만 남길 수 있다(§2-2) — 그러면 group 2 의 세 CHECK 는 kd 로 채점하므로 시험 파일에서 같이 뺀다. 시험 파일도 내 것이다. ③ 적분을 u 뒤에 더하는 꼴도 옳다 — 그러면 group 3 의 기대값이 한 칸씩 밀리므로(0 · 100 · 200) 시험도 같이 고친다.

/* firmware/host_tests/test_pid.c — pid_step() / pid_reset() 의 벡터(pid.c, 순수).
   정확한 값은 손이 아니라 python3 로 계산했다(각 group 위의 주석을 본다).
   group 1-3 은 계약을 못박고, group 4 는 와인드업 없는 적분이라면 떨어질 수 없는 동작을 본다. */
#include <assert.h>
#include <stdio.h>
#include "Control/pid.h"

static int cases = 0;
#define CHECK(c) do { cases++; if (!(c)) { printf("FAIL line %d: %s\n", __LINE__, #c); return 1; } } while (0)
/* float 는 허용 오차로 비교한다, == 로는 절대 비교하지 않는다 */
static int near(float a, float b) { float d = a - b; if (d < 0) d = -d; return d <= 1e-3f; }

int main(void)
{
  /* group 1 — P 만. u = kp*err, 포화. python3: 2*100 = 200, 2*-100 = -200, 2*1000 = 2000 -> 1000 */
  { speed_pid_t p = { 2.f, 0.f, 0.f, 0.f, 0.f, -1000.f, 1000.f };
    pid_reset(&p);
    CHECK(near(pid_step(&p,  100.f),  200.f));
    CHECK(near(pid_step(&p, -100.f), -200.f));
    CHECK(near(pid_step(&p, 1000.f), 1000.f));     /* I1: out_max 에서 잘린다 */
    CHECK(near(pid_step(&p,-1000.f),-1000.f));     /* I1: out_min 에서 잘린다 */
    CHECK(near(pid_step(&p,    0.f),    0.f)); }

  /* group 2 — D 만, 리셋 직후. python3: 0.01*(10-0)/0.001 = 100, 다음 (10-10) -> 0, 다음 (0-10) -> -100 */
  { speed_pid_t p = { 0.f, 0.f, 0.01f, 0.f, 0.f, -1000.f, 1000.f };
    pid_reset(&p);
    CHECK(near(pid_step(&p, 10.f),  100.f));       /* I3: 리셋 뒤 prev_err == 0 */
    CHECK(near(pid_step(&p, 10.f),    0.f));
    CHECK(near(pid_step(&p,  0.f), -100.f)); }

  /* group 3 — I 만. python3: ki*sum(err*dt) = 1000*0.1 = 100, 다음 200, 다음 300 */
  { speed_pid_t p = { 0.f, 1000.f, 0.f, 0.f, 0.f, -1000.f, 1000.f };
    pid_reset(&p);
    CHECK(near(pid_step(&p, 100.f), 100.f));       /* I2: 이번 호출의 err 가 이미 이번 호출의 적분에 들어 있다 */
    CHECK(near(pid_step(&p, 100.f), 200.f));
    CHECK(near(pid_step(&p, 100.f), 300.f)); }

  /* group 4 - 와인드업 방지. 식이 아니라 동작을 본다: 200 ms 동안의 포화가 적분에
     200 ms 어치 오차를 쌓아서는 안 된다. 단순한 적분은 여기서 200*1000*0.001 = 200 만큼 자란다. */
  { speed_pid_t p = { 1.f, 1000.f, 0.f, 0.f, 0.f, -1000.f, 1000.f };
    pid_reset(&p);
    float u = pid_step(&p, 1000.f);
    CHECK(near(u, 1000.f));                        /* 첫 스텝에서 이미 포화 */
    float integ0 = p.integ;
    for (int i = 0; i < 200; i++) { u = pid_step(&p, 1000.f); }
    CHECK(near(u, 1000.f));                        /* 여전히 포화 */
    float grow = p.integ - integ0; if (grow < 0.f) { grow = -grow; }
    CHECK(grow <= 1.0f);                           /* I4: 많아야 한 스텝어치, 200 이 아니다 */
    CHECK(pid_step(&p, -1000.f) < p.out_max);      /* 그 결과: 포화에서 곧바로 빠져나온다 */
    /* 그리고 리셋 뒤에는 제어기가 그 무엇도 기억하지 않는다 */
    p.kp = 2.f; p.ki = 0.f; pid_reset(&p);
    CHECK(near(pid_step(&p, 100.f), 200.f)); }

  printf("PASS pid %d cases\n", cases);
  return 0;
}

void control_step_1khz(void)      /* 1 kHz ISR, 선점 우선순위 1 */
{
  /* 1. 명령 워치독 (2-12) */
  /* TODO(you) [T4]: 명령이 200 ms 넘게 끊겼으면 목표를 0 으로 - 힌트 카드 T4
       1) age = (uint32_t)(tick_get_ms() - s_last_cmd_ms)  <- 한 바퀴 돌아도(wrap) 안전한 뺄셈, fw-02 의 app_loop() 와 같다
       2) age > CMD_WATCHDOG_MS 이면: 목표 둘 다 0, s_wd_stopped = 1u, 그리고 네 바퀴 모두 pid_reset() (2-5)

  /* 2..5 바퀴마다: 측정 -> 오차 -> PID -> (보호) -> 부호 -> 듀티 */
  int16_t duty[NW];                      /* PID 가 낸 명령 [permille]. 전진 = + (목표 · 측정과 같은 부호 규약) */
  float   meas[NW];                      /* 측정 속도 [mm/s]. 6. 의 포획이 다시 쓴다 */
  for (uint8_t i = 0u; i < (uint8_t)NW; i++) {
    /* TODO(you) [T5]: 바퀴 하나의 측정 -> 오차 -> PID -> (보호) -> 부호 -> 듀티 - 힌트 카드 T5
         1) meas[i] = (float)encoder_delta(i) * TICK_TO_MM_S               1 ms 당 카운트 -> mm/s
         2) int16_t tgt = s_target_mm_s[i & 1u]                             짝수 = 왼쪽, 홀수 = 오른쪽
         3) duty[i] = (int16_t)pid_step(&s_pid[i], (float)tgt - meas[i])    [permille], 전진 = +
         4) (실습 C, 2차) protect_step() 이 트립하면 duty[i] = 0, pid_reset(), LD3 켜기

                                                                            duty[i] 는 목표 · 측정과 같은 부호 규약으로
                                                                            남긴다 (보호와 포획이 읽는다)
       채우기 시작하면 아래 두 줄(빌드용 자리표시)은 지운다. */
    duty[i] = 0; meas[i] = 0.0f;
    (void)s_pid; (void)s_motor_sign;              /* 빈 골격에서 -Wunused-variable 을 막는다 */
  }

  /* 6. step 실행 중이면 한 행을 포획한다. 저장만 하고 절대 찍지 않는다 (2-9). */
  /* TODO(you) [T6]: step 포획 한 행 - 힌트 카드 T6
       1) s_cap_left > 0u 이고 s_cap_n < STEP_CAP_MAX 일 때만
       2) 첫 행(s_cap_n == 0u)이면 s_cap_t0 = tick_get_ms()
       3) step_row_t *r = &s_cap[s_cap_n++]
       4) r->t_ms = tick_get_ms() - s_cap_t0, r->target 과 r->duty 는 s_cap_wheel 의 것,
          r->meas = meas[s_cap_wheel] 을 int16 범위로 자른 뒤 반올림, r->prot = 0u (실습 C 에서 s_prot[s_cap_wheel].tripped)
       5) --s_cap_left
     채우기 시작하면 아래 두 줄(빌드용 자리표시)은 지운다. */

  (void)s_cap; (void)s_cap_wheel;                 /* 빈 골격에서 -Wunused-variable 을 막는다 */
}

3-2-3. 직접 채우기

  1. 빈칸 넷부터. robot_params.h 의 게인 셋은 0 인 채로 두고(§2-4), control.c 의 STEP_CAP_MAX 에 내 값을 적는다. 정하는 기준 둘: RAM(sizeof(step_row_t) × 행 수)과 덤프 시간(§2-9 의 식 — 이쪽은 RAM 의 바이트 수가 아니라 글자로 찍히는 한 행의 길이로 센다, 위 다섯 열이면 약 20 B). 두 숫자는 다르다: 위 골격의 step_row_t 는 uint16_t 하나 + int16_t 셋 + uint8_t 하나 = 멤버 9 B 지만 정렬 때문에 sizeof 는 10 이다(집필 중 Mac cc 로 확인). 그래서 2000 행이면 RAM 20 kB, 덤프는 2000 x 20 x 1000 ÷ 46 080 = 약 868 ms 다 — 이 값이 §2-9 의 워치독 예산 행에 그대로 들어가고, 내 IWDG 주기와 견주는 것도 이 값이다. 열을 바꾸면 둘 다 바뀌므로 내 구성으로 직접 세어 정한다. 이 값을 비워 두면 빌드가 static assertion failed … control.c: STEP_CAP_MAX is still EMPTY 에서 멈춘다(길이 0 짜리 배열은 C 가 아니다 — 가드가 없으면 더 알아보기 어려운 오류가 난다).
  2. MOTOR_SIGN_* 넷이 fw-11 에서 실측값으로 채워져 있는지 확인한다. 안 채워져 있으면 이 파일의 가드가 빌드를 세운다 — 그것이 정상이고, 값은 fw-11 §3-2-4 로 돌아가 통전해서 잰다. 추측해서 적지 않는다.
  3. control_set_target(). 세 줄이지만 순서를 생각한다(주석의 질문). 답을 노트에 적는다.
  4. control_step_1khz() 의 for 루프. 순서가 곧 §2-10 의 단조 사슬이다: 재고 → 오차 → PID → 부호 → motor_set(). s_target_mm_s 두 칸은 각각 16비트라 하나씩은 찢어지지 않지만 둘이 짝으로는 찢어질 수 있다(한 틱 동안 왼쪽은 새 값, 오른쪽은 옛 값). 그것이 이 로봇에서 문제인지 판단하고 노트에 적는다 — 문제라면 둘을 32비트 하나에 담는 길이 있다.
  5. 명령 워치독. 뺄셈은 uint32_t 로 한다(tick_get_ms() 는 49일에 한 바퀴 돈다). 만료에서 하는 일은 셋: 목표 0, 표시 세우기, 적분 리셋(§2-5 를 안 하면 다음 명령의 첫 틱이 옛 적분을 들고 시작한다).
  6. cmd_step(). 가장 길다. 3)의 재주입 간격을 200 ms 보다 넉넉히 짧게 잡는다(예: 50 ms — 계약의 50 Hz 와 같은 박자). wdg_service_main() 을 빠뜨리면 덤프 도중 IWDG 가 보드를 리셋한다.
  7. 엮기. app_init() 에 control_init(); 와 control_cli_register(); 를(motor_* · encoder_* 다음에), 1 kHz 콜백 안 power_step_1khz(); 와 motor_step_1khz(); 사이에 control_step_1khz(); 한 줄을(§2-10), 최상위 CMakeLists.txt 의 # Add user sources here 에 User/Src/Control/pid.c 와 User/Src/Control/control.c 를 등록한다.

위 걸음과 골격의 번호가 이렇게 짝을 이룬다: 걸음 3 = T3 · 걸음 4 = T5 · 걸음 5 = T4 · 걸음 6 = T9. 걸음에 따로 없는 T6(포획) · T7(스냅샷) · T8(pid 명령) · T10(초기화)은 골격의 순서대로 채운다 — T10 을 비워 두면 게인이 헤더의 값이 아니라 0 이다. 막힌 자리의 카드를 연다 — 카드는 접혀 있을 뿐 잠겨 있지 않다.

힌트 T3 — control_set_target() · 새 목표를 넣고 명령 워치독을 되감는다

할 일 — 입력은 왼쪽 · 오른쪽 목표 속도(mm/s). 끝났을 때: 두 목표가 들어 있고, "마지막 명령 시각"이 지금이고, 워치독 표시가 지워져 있다. 부르는 쪽은 둘 — 지금은 cmd_step()(T9), fw-17 부터는 통신 모듈. 1 kHz ISR 이 세 줄 가운데 어디서든 끼어들 수 있다는 것이 이 함수의 전부다.

완결 코드

/* 완결 코드 T3 - User/Src/Control/control.c */
void control_set_target(int16_t vl_mm_s, int16_t vr_mm_s)   /* 어느 문맥에서든 */
{
  s_target_mm_s[0] = vl_mm_s;        /* 1) 목표부터. 시각이 아직 옛것이면 ISR 은 기껏해야 이것을 0 으로 만든다 */
  s_target_mm_s[1] = vr_mm_s;
  s_last_cmd_ms    = tick_get_ms();  /* 2) 그다음 시각. 이 줄부터 워치독은 위 목표를 "살아 있는 명령" 으로 본다 */
  s_wd_stopped     = 0u;             /* 3) 표시는 맨 마지막에 지운다 */
}

코드 설명

  • s_target_mm_s[0] = vl_mm_s; · [1] = vr_mm_s; — 목표부터. 두 칸은 volatile int16_t 라 각각은 한 번에 쓰인다(Cortex-M7 의 16비트 저장은 찢어지지 않는다). 둘이 짝으로는 찢어질 수 있다 — 한 틱 동안 왼쪽은 새 값, 오른쪽은 옛 값(§3-2-3 의 4 가 그 판단을 내게 맡겼다).
  • s_last_cmd_ms = tick_get_ms(); — 그다음 시각. 이 줄이 명령 워치독을 되감는 유일한 자리다(§2-12 의 (가)). 통신 모듈은 워치독을 몰라도 된다 — 이 함수를 부르는 것으로 끝이다.
  • s_wd_stopped = 0u; — 표시는 맨 마지막. ISR 이 세우고(T4) 이 함수만 지운다.
  • 왜 이 순서인가(골격의 질문) — 시각을 먼저 쓰면, ISR 이 그 사이에 돌 때 "살아 있는 명령"으로 옛 목표를 본다. 옛 목표가 새 것보다 크면 한 틱 동안 로봇이 명령보다 빠르다. 목표를 먼저 쓰면, ISR 이 그 사이에 돌 때 "만료된 명령"으로 새 목표를 보고 0 으로 만든다 — 느려질 뿐이다. 그 대가도 적어 둔다: 만료 직후의 첫 명령이 ISR 과 겹치면 그 명령은 통째로 0 이 되고 다음 명령(50 Hz 면 20 ms 뒤)이 되살린다. 이 쪽에서는 그 방향이 옳은 방향이다.
  • 골격의 (void)vl_mm_s; (void)vr_mm_s; 는 지웠다.
  • 다르게 써도 되는 곳 — 세 줄을 __disable_irq(); … __enable_irq(); 로 감싸 ISR 이 끼어들 수 없게 하면 순서를 따질 일이 없어진다. 대가는 1 kHz 틱이 수십 ns 늦어질 수 있다는 것과, "왜 이 순서인가"를 더는 생각하지 않게 된다는 것이다. 둘 다 옳은 설계다 — 어느 쪽이든 이유를 노트에 적는다.

쓰는 API — uint32_t tick_get_ms(void);(fw-06 의 System/tick.h). 어느 문맥에서든 부를 수 있다. 1 ms 마다 1 씩 늘고 49.7 일에 한 바퀴 돈다 — 그래서 T4 의 뺄셈이 uint32_t 다.

힌트 T4 — control_step_1khz() · 1. 명령 워치독

할 일 — 마지막 명령으로부터 몇 ms 지났는지 세고, CMD_WATCHDOG_MS(계약의 200) 를 넘었으면 목표를 0 으로, 표시를 세우고, 네 제어기의 적분을 지운다. 1 kHz ISR 의 첫 단계다 — 뒤의 2..5 가 이 틱에 "목표 0" 을 보게 하려면 앞에 있어야 한다. IWDG 는 건드리지 않는다(§2-12 — 다른 장치다).

완결 코드

/* 완결 코드 T4 - User/Src/Control/control.c 의 control_step_1khz() 안, 1. */
  /* 1. 명령 워치독 (2-12) */
  const uint32_t age = (uint32_t)(tick_get_ms() - s_last_cmd_ms);   /* 한 바퀴 돌아도(wrap) 안전한 뺄셈 */
  if (age > CMD_WATCHDOG_MS) {
    s_target_mm_s[0] = 0;                                            /* 만료 중에는 틱마다: 목표 둘 다 0 */
    s_target_mm_s[1] = 0;
    s_wd_stopped = 1u;                                               /* 표시. 지우는 쪽은 control_set_target() 뿐 */
    for (uint8_t i = 0u; i < (uint8_t)NW; i++) { pid_reset(&s_pid[i]); }   /* 과거를 들고 가지 않는다 (2-5) */
  }

코드 설명

  • const uint32_t age = (uint32_t)(tick_get_ms() - s_last_cmd_ms); — 부호 없는 뺄셈. tick_get_ms() 가 한 바퀴 돌아 작은 수가 돼도 결과는 올바른 "경과 ms" 다(232 로 되감기는 것이 정의된 동작이라서 — fw-02 의 app_loop() · fw-09 의 encoder_delta_raw() 와 같은 꼴). const 는 "이 틱 안에서 다시 바뀌지 않는 값"이라는 표시다.
  • if (age > CMD_WATCHDOG_MS) — 계약의 글자는 "200 ms 동안 없으면". > 는 201 ms 째에, >= 는 200 ms 째에 선다 — 1 ms 차이이고 어느 쪽이든 되지만, 고른 것을 노트에 적는다(§3-2-4 의 once 행 번호가 그 답이다).
  • s_target_mm_s[0] = 0; [1] = 0; — 만료 중에는 틱마다 0 을 쓴다. 한 번만 쓰고 말면 그 사이 control_set_target() 의 목표 두 줄(T3 의 1)과 겹칠 때 옛 목표가 살아난다.
  • s_wd_stopped = 1u; — 표시. 지금은 아무도 읽지 않는다 — fw-18 이 이것을 fault 비트로 올린다. 지우는 쪽은 control_set_target() 뿐이다.
  • for (…) { pid_reset(&s_pid[i]); } — §2-5 의 규칙 "목표가 0 으로 내려올 때 적분을 0 으로". 틱마다 다시 불러도 해가 없다(이미 0 을 0 으로). 이것이 없으면 다음 명령의 첫 틱이 옛 적분을 들고 시작한다 — 체크포인트 stop-resets-integrator.
  • (uint8_t)NW — NW 는 enum(= 4) 이라 int 다. uint8_t i 와 비교할 때 캐스트로 부호를 맞춘다(fw-08 의 motor.c 와 같은 습관).
  • 이 자리에는 자리표시가 없었다 — 비어 있어도 빌드되고, 그러면 워치독이 없는 로봇이다.

쓰는 API — tick_get_ms()(T3 과 같다) · pid_reset()(T1).

힌트 T5 — control_step_1khz() · 2..5 바퀴마다 측정 → PID → (보호) → 듀티

할 일 — 바퀴 하나에 대해: 1 ms 창의 카운트를 mm/s 로, 목표와의 오차를 PID 에, 그 출력을(실습 C 부터는 보호를 거쳐) 드라이버에. §2-10 의 단조 사슬이 이 루프 안에서도 성립한다 — PID 가 만들고, 보호가 줄이고, motor_set() 이 벤치 상한으로 한 번 더 자른다. 아래는 실습 C 까지 넣은 2차 모습이다 — 실습 B 를 구울 때는 주석이 가리키는 여섯 줄(const protect_in_t in 부터 닫는 } 까지) 앞에 // 를 붙여 막는다(아직 s_prot 가 없다). /* … */ 로 감싸지 않는다 — 세 줄의 끝에 이미 블록 주석이 있어 중첩되고, 줄마다 감싸 보니 arm-gcc 가 warning: "/*" within comment [-Wcomment] 에 이어 error: expected expression before '/' token 으로 멈췄다(2026-10-03 확인).

완결 코드

/* 완결 코드 T5 - User/Src/Control/control.c 의 control_step_1khz() 안, 2..5 (2차까지 넣은 모습) */
  /* 2..5 바퀴마다: 측정 -> 오차 -> PID -> (보호) -> 부호 -> 듀티 */
  int16_t duty[NW];                      /* PID 가 낸 명령 [permille]. 전진 = + (목표 · 측정과 같은 부호 규약) */
  float   meas[NW];                      /* 측정 속도 [mm/s]. 6. 의 포획이 다시 쓴다 */
  for (uint8_t i = 0u; i < (uint8_t)NW; i++) {
    meas[i]     = (float)encoder_delta(i) * TICK_TO_MM_S;      /* 1 ms 당 카운트 -> mm/s */
    int16_t tgt = s_target_mm_s[i & 1u];                       /* 짝수 = 왼쪽, 홀수 = 오른쪽 */
    float   u   = pid_step(&s_pid[i], (float)tgt - meas[i]);   /* 오차 -> [permille], 이미 ±DUTY_LIMIT_BENCH_PERMILLE 안 */
    duty[i]     = (int16_t)u;
    /* 2차 (실습 C, 3-3-4 의 3): PID 와 motor_set() 사이에 보호가 앉는다. 실습 B 를 구울 때는 아래 여섯 줄 앞에 // 를 붙여 막는다 (줄 끝 주석 때문에 블록 주석으로 감싸면 중첩된다) */
    const protect_in_t in = { tgt, (int32_t)meas[i], duty[i] };
    if (protect_step(&s_prot[i], &s_prot_cfg, &in) != 0u) {
      duty[i] = 0;                                             /* 이 바퀴만 끊는다. 넷을 다 세울지는 fw-18 의 결정 */
      pid_reset(&s_pid[i]);                                    /* 다시 시작할 때 과거를 들고 가지 않는다 (2-5) */
      HAL_GPIO_WritePin(LD3_GPIO_Port, LD3_Pin, GPIO_PIN_SET); /* 빨강 = fault 래치 */
    }
    motor_set(i, (int16_t)(s_motor_sign[i] * duty[i]));        /* MOTOR_SIGN 이 "전진" 을 드라이버의 부호로 바꾼다 (fw-11).
                                                                  motor_set() 이 내 벤치 상한으로 한 번 더 자른다 */
  }

코드 설명

  • int16_t duty[NW]; float meas[NW]; — 루프 밖의 배열 둘. 6. 의 포획(T6)이 s_cap_wheel 번째 값을 다시 읽어야 하므로 루프 안의 지역 변수로는 안 된다. 골격의 int16_t duty[NW]; 한 줄이 이 두 줄이 됐다.
  • meas[i] = (float)encoder_delta(i) * TICK_TO_MM_S; — 직전 호출 이후의 카운트(부호 적용, fw-09 실습 B) × "카운트 하나가 1 ms 에 몇 mm/s 인가"(TICK_TO_MM_S, 첫 블록의 매크로). (float) 캐스트가 없으면 int32_t × float 라 어차피 float 로 승격되지만, 뜻을 눈에 보이게 적는다.
  • int16_t tgt = s_target_mm_s[i & 1u]; — i & 1u 는 "홀수인가": FL(0) · RL(2) 는 왼쪽 목표, FR(1) · RR(3) 는 오른쪽. enum 의 순서(FL, FR, RL, RR)가 이 한 비트를 가능하게 한다.
  • float u = pid_step(&s_pid[i], (float)tgt - meas[i]); · duty[i] = (int16_t)u; — 오차는 목표 − 측정. 반환값은 이미 ±DUTY_LIMIT_BENCH_PERMILLE 안이라(T10 이 그렇게 넣는다) int16_t 로 자르는 캐스트는 안전하다. duty[i] 는 "전진 = +" 인 채로 둔다 — 골격의 옛 주석은 여기서 MOTOR_SIGN 을 곱했지만, 그러면 보호(sgn(target) == sgn(duty))와 포획의 duty 열이 MOTOR_SIGN = -1 인 바퀴에서 거꾸로 읽힌다. 부호는 드라이버에 쓰는 마지막 줄에서만.
  • const protect_in_t in = { tgt, (int32_t)meas[i], duty[i] }; — 보호에 넘길 셋을 구조체 하나로. 순서는 protect.h 의 필드 순서(목표 · 측정 · 듀티)다. (int32_t)meas[i] 는 소수를 버린다 — 보호의 문턱은 mm/s 정수라 충분하다.
  • if (protect_step(&s_prot[i], &s_prot_cfg, &in) != 0u) { … } — 래치된 비트가 하나라도 있으면: 이 바퀴의 듀티 0, 적분 0(§2-5 의 둘째 자리), LD3 ON(빨강 = fault 래치 — fw_style 의 LED 역할). 끊는 범위는 이 바퀴 하나이고 넷을 다 세울지 · MOTOR_EN 을 내릴지는 fw-18 의 결정이다(§3-3-4 의 3).
  • motor_set(i, (int16_t)(s_motor_sign[i] * duty[i])); — 여기서만 MOTOR_SIGN. int8_t × int16_t 는 int 로 승격되므로 (int16_t) 로 되돌린다. motor_set() 이 DUTY_LIMIT_BENCH_PERMILLE 로 한 번 더 자른다(fw-08) — PID 의 한계와 같은 값이라 평소에는 아무 일도 안 하지만, 두 겹인 것이 맞다.
  • 골격의 duty[i] = 0; meas[i] = 0.0f; 는 지웠다.
  • 다르게 써도 되는 곳 — ① 보호에 넘기는 duty 를 "이번 틱에 드라이버에 쓴 값"(protect.h 의 주석)으로 읽어 motor_set() 뒤에 보호를 두는 꼴도 생각할 수 있다 — 그러면 트립한 틱에 듀티가 한 번 나간다. 이 쪽은 단조 사슬(§2-10)대로 PID 와 motor_set() 사이에 둔다. ② 트립했을 때 네 바퀴를 다 0 으로 하는 것은 fw-18 에서 정한다 — 여기서 미리 해도 틀리지 않는다.

힌트 T6 — control_step_1khz() · 6. step 포획 한 행

할 일 — step 이 돌고 있으면(s_cap_left > 0) 이 틱의 목표 · 측정 · 듀티 · 보호 비트를 RAM 의 다음 행에 적는다. 저장만 하고 절대 찍지 않는다(§2-9). 찍는 것은 cmd_step()(T9)이 다 끝난 뒤 main 문맥에서 한다.

완결 코드

/* 완결 코드 T6 - User/Src/Control/control.c 의 control_step_1khz() 안, 6. */
  /* 6. step 실행 중이면 한 행을 포획한다. 저장만 하고 절대 찍지 않는다 (2-9). */
  if (s_cap_left > 0u && s_cap_n < STEP_CAP_MAX) {
    if (s_cap_n == 0u) { s_cap_t0 = tick_get_ms(); }           /* 첫 행의 틱. 그래서 t_ms 는 행 번호와 같다(틱을 빠뜨리지 않았다면) */
    step_row_t *r = &s_cap[s_cap_n++];                         /* 다음 빈 행을 가리키고, 행 수를 하나 올린다 */
    float m = meas[s_cap_wheel];
    if (m >  32767.0f) { m =  32767.0f; }                      /* int16 에 담기 전에 자른다 (2-13: gdb 뒤의 큰 튐) */
    if (m < -32768.0f) { m = -32768.0f; }
    r->t_ms   = (uint16_t)(tick_get_ms() - s_cap_t0);
    r->target = s_target_mm_s[s_cap_wheel & 1u];
    r->meas   = (int16_t)(m + ((m >= 0.0f) ? 0.5f : -0.5f));   /* 반올림: 자르기 전에 0.5 를 더한다(음수는 뺀다) */
    r->duty   = duty[s_cap_wheel];
    r->prot   = s_prot[s_cap_wheel].tripped;                   /* 2차 (3-3-4 의 3). 실습 B 에서는 이 자리에 0u */
    --s_cap_left;
  }

코드 설명

  • if (s_cap_left > 0u && s_cap_n < STEP_CAP_MAX) — 두 조건. 첫째는 "포획 중인가", 둘째는 배열 밖에 쓰지 않는 가드다. cmd_step() 이 ms > STEP_CAP_MAX 를 거절하므로(T9) 둘째가 걸릴 일은 없어야 하지만, ISR 에서의 배열 밖 쓰기는 가장 찾기 어려운 고장이라 두 겹으로 둔다.
  • if (s_cap_n == 0u) { s_cap_t0 = tick_get_ms(); } — 첫 행의 틱을 ISR 이 찍는다. 그러면 t_ms 가 행 번호와 같아진다(0, 1, 2, …) — 틱을 빠뜨리지 않았다면. §3-2-4 가 "t_ms 와 행 번호가 어긋나면 그 자체가 관찰"이라 한 것이 이 성질 위에 서 있다.
  • step_row_t *r = &s_cap[s_cap_n++]; — 다음 빈 행의 주소를 잡고(&), 행 수를 하나 올린다(++ 가 뒤에 있으니 "쓴 뒤에 올린다"). 아래 다섯 줄은 r-> 로 그 행에 쓴다 — s_cap[s_cap_n].t_ms = … 를 다섯 번 쓰는 것보다 짧고, 색인을 한 번만 계산한다.
  • float m = meas[s_cap_wheel]; if (m > 32767.0f) … — int16_t 에 담기 전에 범위를 자른다. 범위 밖의 float 를 정수로 캐스트하는 것은 정의되지 않은 동작이다(아래 표의 진단 메시지). 평소 속도는 수백 mm/s 라 걸릴 일이 없지만 §2-13 의 "gdb 뒤의 큰 튐"이 바로 그 경우다.
  • r->t_ms = (uint16_t)(tick_get_ms() - s_cap_t0); — 첫 행으로부터의 ms. STEP_CAP_MAX 가 65 535 이하면 uint16_t 에 들어간다.
  • r->target = s_target_mm_s[s_cap_wheel & 1u]; — T5 와 같은 "홀수 = 오른쪽". 워치독이 0 으로 만든 뒤라면 여기 0 이 찍힌다 — once 의 관찰이 이 열이다.
  • r->meas = (int16_t)(m + ((m >= 0.0f) ? 0.5f : -0.5f)); — 반올림. 캐스트는 소수를 버리므로(0 쪽으로) 0.5 를 더하고(음수는 빼고) 버리면 반올림이 된다. roundf() 를 써도 되지만 <math.h> 와 링크 옵션이 따라온다.
  • r->duty = duty[s_cap_wheel]; · r->prot = s_prot[s_cap_wheel].tripped; — T5 가 남긴 배열에서. prot 은 실습 B 에서는 0u 로 두었다가 실습 C 에서 바꾼다.
  • --s_cap_left; — 남은 행 수를 하나 줄인다. 이 줄이 cmd_step() 의 while 을 끝낸다 — 빼먹으면 아래 표의 첫 행이다.
  • 골격의 (void)duty; (void)meas; 는 지웠다.
  • 다르게 써도 되는 곳 — s_cap_t0 를 cmd_step() 에서 포획을 걸 때 찍어도 된다(골격의 처음 주석이 그랬다). 그러면 첫 행의 t_ms 가 0 또는 1 로 흔들리고(걸고 나서 첫 틱까지의 시간), 행 번호와 1 어긋날 수 있다 — 어느 쪽이든 되지만 §3-2-4 를 읽을 때 그 1 을 알고 있어야 한다.

힌트 T8 — cmd_pid() · 게인을 보고 · 바꾸는 명령

할 일 — 세 꼴을 받는다: pid · pid show → 한 줄 보고, pid set <kp|ki|kd> <milli> → 네 바퀴의 게인을 바꾸고 OK pid, 그 밖 → ERR pid bad-arg. 출력 꼴은 fw-05 §2-4 의 규약(첫 낱말 = 명령 이름, 키=값, 단위는 키 끝에, 값은 정수). main 문맥 — printf 해도 된다.

완결 코드

/* 완결 코드 T8 - User/Src/Control/control.c */
static long gain_milli(float g)          /* 1.2f -> 1200. 0.7f * 1000 은 699.9999 라서 반올림이 필요하다 */
{
  return (long)(g * 1000.0f + ((g >= 0.0f) ? 0.5f : -0.5f));
}

static void cmd_pid(int argc, char *argv[])      /* main 문맥 */
{
  if (argc == 1 || (argc == 2 && strcmp(argv[1], "show") == 0)) {           /* "pid" · "pid show" */
    printf("pid kp_milli=%ld ki_milli=%ld kd_milli=%ld\r\n",
           gain_milli(s_pid[0].kp), gain_milli(s_pid[0].ki), gain_milli(s_pid[0].kd));
    return;
  }
  if (argc == 4 && strcmp(argv[1], "set") == 0) {                           /* "pid set <kp|ki|kd> <milli>" */
    const bool is_kp = (strcmp(argv[2], "kp") == 0);
    const bool is_ki = (strcmp(argv[2], "ki") == 0);
    const bool is_kd = (strcmp(argv[2], "kd") == 0);
    char *end = NULL;
    long  m   = strtol(argv[3], &end, 10);
    if ((!is_kp && !is_ki && !is_kd) || *end != '\0') { printf("ERR pid bad-arg\r\n"); return; }
    const float g = (float)m / 1000.0f;
    for (uint8_t i = 0u; i < (uint8_t)NW; i++) {                            /* 네 바퀴 모두 같은 게인 */
      if      (is_kp) { s_pid[i].kp = g; }
      else if (is_ki) { s_pid[i].ki = g; }
      else            { s_pid[i].kd = g; }
    }
    printf("OK pid\r\n");                   /* 적분은 건드리지 않는다: 이유는 카드의 코드 설명 */
    return;
  }
  printf("ERR pid bad-arg\r\n");

코드 설명

  • static long gain_milli(float g) — 보고용 도우미. 0.7f * 1000 은 float 에서 699.9999… 라 그냥 자르면 699 가 찍힌다 — 0.5 를 더해(음수는 빼) 반올림한다(T6 의 반올림과 같은 꼴). 파일 안 static 이라 밖에서는 안 보인다.
  • if (argc == 1 || (argc == 2 && strcmp(argv[1], "show") == 0)) — "pid" 는 인자 없이(argc == 1), "pid show" 는 둘. strcmp() 는 같으면 0 을 돌려준다 — == 0 이 "같다"다(fw-05 의 디스패치와 같은 문법). argv[1] == "show" 는 글자가 아니라 주소를 비교한다(아래 표).
  • printf("pid kp_milli=%ld …", gain_milli(s_pid[0].kp), …) — 네 바퀴가 같은 게인이라 [0] 만 찍는다. %ld 는 long 의 서식 — gain_milli() 의 반환형과 짝이다(틀리면 arm-gcc 가 -Wformat 으로 말한다).
  • if (argc == 4 && strcmp(argv[1], "set") == 0) — argc 를 먼저 본다. argv[3] 을 읽기 전에 그것이 있는지 확인하는 것이다 — && 는 왼쪽이 거짓이면 오른쪽을 보지 않는다(단락 평가).
  • const bool is_kp = … 셋 — 세 번 strcmp 하고 결과를 이름 붙여 둔다. 아래 루프에서 다시 비교하지 않으려는 것이다.
  • long m = strtol(argv[3], &end, 10); if (… || *end != '\0') — fw-05 · fw-08 의 cmd_pwm() 과 같은 숫자 읽기. end 가 문자열 끝('\0')을 가리키지 않으면 뒤에 숫자 아닌 글자가 있었다는 뜻 → bad-arg. <stdlib.h> 가 필요하다 — 첫 블록의 include 에 한 줄이 늘어난 이유다.
  • const float g = (float)m / 1000.0f; — 밀리 정수 → 실수 게인. (float) 캐스트 없이 m / 1000 이면 정수 나눗셈이다(T10 의 표).
  • for (…) { if (is_kp) { s_pid[i].kp = g; } … } — 네 바퀴 모두 같은 게인(§2-4 의 5 는 "네 바퀴를 따로 본다" 지만 게인은 하나다 — 곡선이 다르면 게인이 아니라 기계의 문제라서).
  • printf("OK pid\r\n"); — 적분은 건드리지 않는다. 리셋해야 하는가(골격의 질문): 게인을 바꾸는 순간 ki * integ 가 뛰므로 한 번 덜컹할 수 있다 — 그러나 step 이 시작할 때 pid_reset() 을 부르고(T9), 게인은 step 사이에 바꾼다. 그래서 여기서는 안 지운다. 주행 중에 바꾸는 명령이라면 답이 달라진다 — 이유를 노트에 적는다.
  • 마지막 printf("ERR pid bad-arg\r\n"); — 위 두 if 에 걸리지 않은 전부.
  • 골격의 (void)argc; (void)argv; 는 지웠다.
  • 다르게 써도 되는 곳 — ① 바퀴마다 다른 게인을 받는 꼴(pid set fl kp 1200)도 가능하다 — 명령 꼴이 달라지고 보고 줄이 넷이 된다. ② 보고를 %d 와 (int) 로 써도 된다 — 서식과 형의 짝만 맞으면.

쓰는 API — long strtol(const char *s, char **end, int base);(<stdlib.h>) · int strcmp(const char *a, const char *b);(<string.h>, 같으면 0) · printf(). 전부 main 문맥에서만.

힌트 T9 — cmd_step() · 계단을 넣고 포획하고 덤프한다

할 일 — 이 쪽의 관측 창이다. step <fl|fr|rl|rr> <target_mm_s> <ms> [once] 를 해석하고, 포획을 걸고, 목표를 넣고, 포획이 끝날 때까지 main 문맥에서 돌면서(일부러 블로킹 — 그동안 명령 창은 듣지 않는다, §3-2-4 의 경고 상자) 워치독을 먹이고 목표를 재주입하다가, 끝나면 모터를 세우고 CSV 를 덤프한다. 길어서 둘로 나눠 싣는다 — 한 함수다.

완결 코드 (1/2 — 해석 · 포획 걸기 · 목표 넣기)

/* 완결 코드 T9 - User/Src/Control/control.c (1/2: 해석 · 포획 걸기 · 목표 넣기) */
#define STEP_TARGET_MAX_MM_S  0     /* ____ 벤치에서 step 이 받는 |target| 의 상한 [mm/s]. 0 이면 목표 0 말고는 전부 거절한다 */
#define STEP_REINJECT_MS      50u   /* once 가 아닐 때 목표를 다시 넣는 간격 [ms]. 3-2-3 의 6 이 든 예(계약의 50 Hz) - 바꿔도 된다 */
_Static_assert((STEP_REINJECT_MS) < (CMD_WATCHDOG_MS), "control.c: STEP_REINJECT_MS must be shorter than CMD_WATCHDOG_MS");

static void cmd_step(int argc, char *argv[])     /* main 문맥. 이 함수는 일부러 블로킹한다 */
{
  /* 1) 해석: step <fl|fr|rl|rr> <target_mm_s> <ms> [once] - 틀린 것은 전부 bad-arg */
  int w = -1;
  if (argc == 4 || argc == 5) {
    if      (strcmp(argv[1], "fl") == 0) { w = FL; }
    else if (strcmp(argv[1], "fr") == 0) { w = FR; }
    else if (strcmp(argv[1], "rl") == 0) { w = RL; }
    else if (strcmp(argv[1], "rr") == 0) { w = RR; }
  }
  if (w < 0) { printf("ERR step bad-arg\r\n"); return; }
  char *end = NULL;
  const long tgt = strtol(argv[2], &end, 10);
  if (*end != '\0' || tgt < -(long)STEP_TARGET_MAX_MM_S || tgt > (long)STEP_TARGET_MAX_MM_S) { printf("ERR step bad-arg\r\n"); return; }
  const long ms = strtol(argv[3], &end, 10);
  if (*end != '\0' || ms < 1 || ms > STEP_CAP_MAX) { printf("ERR step bad-arg\r\n"); return; }
  const bool once = (argc == 5);
  if (once && strcmp(argv[4], "once") != 0) { printf("ERR step bad-arg\r\n"); return; }
  if (power_get_state() != POWER_ARMED) { printf("ERR step not-ready\r\n"); return; }   /* fw-11 */

  /* 2) 포획을 먼저 건다 - 그래야 0 번 행이 생긴다 */
  pid_reset(&s_pid[w]);                        /* 앞 회차의 적분을 들고 시작하지 않는다 (2-5) */
  protect_reset(&s_prot[w]);                   /* 2차 (3-3-4 의 3): 새 step 은 래치를 푼다. 실습 B 에서는 이 줄이 없다 */
  s_cap_n     = 0u;                            /* 첫 행의 틱(s_cap_t0)은 ISR 이 첫 행을 쓸 때 찍는다 (T6) */
  s_cap_wheel = (uint8_t)w;
  s_cap_left  = (uint16_t)ms;                  /* 이 줄부터 ISR 이 행을 채운다 */

  /* 3) 이 바퀴가 있는 쪽에 목표를 넣고, 포획이 끝날 때까지 main 문맥에서 돈다 */
  const int16_t vl = (w & 1) ? 0 : (int16_t)tgt;        /* 짝수 = 왼쪽 */
  const int16_t vr = (w & 1) ? (int16_t)tgt : 0;        /* 홀수 = 오른쪽 */
  control_set_target(vl, vr);
  uint32_t last_inject = tick_get_ms();
  while (s_cap_left > 0u) {
    wdg_service_main();                                                    /* 2-9: IWDG 는 계속 먹인다 */
    if (!once && (uint32_t)(tick_get_ms() - last_inject) >= STEP_REINJECT_MS) {
      control_set_target(vl, vr);                                          /* 2-12: 상위의 50 Hz 노릇 */
      last_inject = tick_get_ms();
    }
  }

  • #define STEP_REINJECT_MS 50u + _Static_assert(… < CMD_WATCHDOG_MS …) — 재주입 간격. §3-2-3 의 6 이 든 예(계약의 50 Hz)이고 바꿔도 된다 — 다만 200 보다 짧아야 한다는 것을 컴파일러가 지키게 했다.

  • const long ms = …; if (… ms < 1 || ms > STEP_CAP_MAX) — 행 수. STEP_CAP_MAX 를 넘으면 "자리 없음". 이 검사가 T6 의 가드와 짝이다 — 이것이 없으면 ISR 이 STEP_CAP_MAX 에서 쓰기를 멈추지만 s_cap_left 는 0 이 안 되어 while 이 영영 돈다(아래 표).
  • const bool once = (argc == 5); if (once && strcmp(argv[4], "once") != 0) … — 다섯째 인자는 "once" 만 받는다.
  • if (power_get_state() != POWER_ARMED) { printf("ERR step not-ready\r\n"); return; } — fw-11. EN 이 안 올라간 채 포획하면 평평한 선이 나오는데, 그것을 "게인이 0 이라서"로 읽게 된다 — 헷갈리는 길을 미리 막는다.
  • pid_reset(&s_pid[w]); protect_reset(&s_prot[w]); — 과거를 지운다(§2-5 · §3-3-4 의 3 "새 step 은 래치를 푼다"). protect_reset 줄은 실습 C 에서 더한다.

  • for (…) { wdg_service_main(); printf("%u,%d,%d,%d,%u\r\n", …); prot |= r->prot; if (r->prot != prev) { trips++; prev = r->prot; } } — 행마다 IWDG 를 먹인다(§2-9 의 워치독 예산 행이 바로 이 루프다 — 2000 행이면 약 868 ms). prot |= 는 "래치된 적 있는 비트 전부", trips 는 prot 열이 바뀐 행의 수 — 래치가 선 횟수다.

  • 골격의 (void)argc; (void)argv; 는 지웠다.
  • 다르게 써도 되는 곳 — ① trips 의 뜻: "비트가 바뀐 횟수" 대신 "래치된 비트의 수"(prot 의 1 비트 개수)로 정의해도 된다 — 어느 쪽인지 노트에 적는다. ② 재주입 간격 50 ms 는 예다. ③ s_cap_t0 를 여기서 찍는 꼴은 T6 의 "다르게 써도 되는 곳". ④ 덤프 중 printf 대신 fw-07 의 DMA 송신을 쓰면 이 루프가 짧아진다 — 그 대신 버퍼가 필요하다.

할 일 — main 에서 한 번, motor_init() 과 encoder_init() 뒤에. 네 제어기에 robot_params.h 의 게인(밀리 정수 → 실수)과 포화 한계(벤치 상한)를 넣고 리셋한다. 그리고 부팅 직후의 명령 워치독 상태를 정한다.

완결 코드

/* 완결 코드 T10 - User/Src/Control/control.c */
void control_init(void)      /* main 에서 한 번, motor_init() 과 encoder_init() 뒤에 */
{
  for (uint8_t i = 0u; i < (uint8_t)NW; i++) {
    s_pid[i].kp      = (float)PID_KP_MILLI / 1000.0f;             /* 밀리 정수 -> 실수 게인 */
    s_pid[i].ki      = (float)PID_KI_MILLI / 1000.0f;
    s_pid[i].kd      = (float)PID_KD_MILLI / 1000.0f;
    s_pid[i].out_min = -(float)DUTY_LIMIT_BENCH_PERMILLE;         /* fw-08 의 벤치 상한이 곧 PID 의 포화 한계 */
    s_pid[i].out_max =  (float)DUTY_LIMIT_BENCH_PERMILLE;
    pid_reset(&s_pid[i]);
  }
  /* 부팅 때 워치독이 이미 만료돼 있게: "마지막 명령" 을 (CMD_WATCHDOG_MS + 1) ms 전으로 둔다 */
  s_last_cmd_ms = (uint32_t)(tick_get_ms() - (CMD_WATCHDOG_MS + 1u));
}

코드 설명

  • s_pid[i].kp = (float)PID_KP_MILLI / 1000.0f; — 밀리 정수(1200 = 1.2)를 실수로. (float) 캐스트와 1000.0f 둘 중 하나만 있어도 실수 나눗셈이지만, PID_KP_MILLI / 1000 이라고 쓰는 순간 정수 나눗셈이 되어 1200 은 1 이 되고 700 은 0 이 된다 — 컴파일러는 아무 말도 하지 않는다(아래 표).
  • out_min = -(float)DUTY_LIMIT_BENCH_PERMILLE; out_max = +… — fw-08 의 벤치 상한이 곧 PID 의 포화 한계다. 그래서 와인드업 방지(T2)가 내 벤치 상한에서 작동한다 — ±1000 으로 두면 motor_set() 이 자르기는 하지만 PID 는 포화를 모른 채 적분을 쌓는다.
  • pid_reset(&s_pid[i]); — s_pid 는 static 이라 0 으로 태어나지만, "리셋된 상태로 시작한다"를 코드에 적는다.
  • s_last_cmd_ms = (uint32_t)(tick_get_ms() - (CMD_WATCHDOG_MS + 1u)); — 골격의 질문의 답. "마지막 명령"을 201 ms 전으로 두면 첫 틱부터 age > 200 이라 워치독이 이미 만료돼 있다 — 부팅 직후의 로봇은 "명령을 받은 적 없는" 상태여야 한다. 부호 없는 뺄셈이라 tick_get_ms() 가 아직 작아도(부팅 직후 0 근처) 되감겨서 큰 수가 되고, T4 의 뺄셈이 그것을 다시 되감아 201 을 낸다.
  • 자리표시가 없던 자리다 — 비어 있어도 빌드된다. 그러면 게인도 한계도 0 이라 듀티가 0 에 갇힌다(안전하지만 step 이 영영 평평하다).
  • 다르게 써도 되는 곳 — s_last_cmd_ms = 0 으로 두는 것: 부팅 뒤 200 ms 동안은 "살아 있는 명령"으로 본다. 목표가 0 이라 해는 없지만 s_wd_stopped 가 그동안 0 이다 — fw-18 이 그 표시를 fault 로 올리면 부팅 직후 200 ms 의 뜻이 달라진다. 어느 쪽이든 되지만, 질문의 답은 적어 둔다.

이제 §2-4 의 순서대로 게인을 올린다. 한 번에 하나씩, 매번 같은 step 명령으로. 볼 것은 넷이다 — 올라가는 데 걸린 시간 · 넘어간 정도(오버슛) · 정상상태에서 남은 차이 · 떨리는가. 마음에 드는 곡선이 나오면 그 pid set 값들을 robot_params.h 에 옮겨 적고, 곡선 하나를 노트에 남긴다(그림 파일이든 숫자 몇 줄이든). 그 기록을 보고 내 합격선을 정하는 것이 이 실습의 끝이다 — "정착 시간 ____ ms 이내, 오버슛 ____ % 이내, 정상상태 오차 ____ mm/s 이내" 를 내 손으로 적는다.

여기서 얻는 두 숫자를 놓치지 않는다
  • 무부하 최대 속도 — 목표를 올려 가며 측정 속도가 더 이상 따라오지 않는 지점이 내 로봇의 무부하 상한이다. 이 값을 노트와 hardware/INVENTORY.md 6절 "최대 선속도" 행의 재료로 적는다 (그 칸을 닫는 것은 바닥에서 재는 관문 09a 다 — 여기 값은 공중에 뜬 바퀴의 값이고 공칭 바퀴 지름 위에 서 있다).
  • 건강한 속도 : 듀티 비 — 정상상태에서 meas_mm_s ÷ duty_permille. 실습 C 의 FBLOST_SPEED_PER_PERMILLE_MILLI 가 이 수에서 나온다(§2-7). 여러 듀티에서 같은지 보고, 다르면 어느 구간의 값을 쓸지 정한다.

마지막으로 명령 워치독을 눈으로 본다. 같은 명령에 once 를 붙이면 목표를 한 번만 넣는다.

> step fl 200 1000 once

CSV 의 target_mm_s 열이 어느 행에서 0 으로 바뀐다. 그 행의 t_ms 가 곧 워치독이 발동한 시각이고, 견줄 값은 계약의 200 ms 다(CMD_WATCHDOG_MS). 그 행 번호를 노트에 적는다. Mac 의 시계로 재지 않는다 — 이 숫자는 MCU 의 tick 이고, 그것이 판정 기준인 이유는 Mac 쪽 지연이 섞이지 않기 때문이다(fw-18 이 계약 경로에서 같은 판정을 다시 한다). t_ms 열과 행 번호가 어긋나 있으면 그 자체가 관찰이다 — 1 kHz 틱을 빠뜨렸다는 뜻이고, stat 의 overrun 을 같이 본다.

  • (uint32_t)0 - (uint32_t)v — 먼저 v 를 부호 없는 수로 바꾸고(음수는 2의 보수 그대로 큰 수가 된다), 0 에서 뺀다. 부호 없는 뺄셈은 넘쳐도 정의돼 있다(232 로 되감긴다) — 그래서 INT32_MIN 에서 정확히 2 147 483 648 이 나온다. -v 라고 쓰면 부호 있는 수의 부정이고, 그 한 값에서 정의되지 않은 동작(UB)이다. fw-09 의 encoder_delta_raw() 와 같은 꼴의 함정이다.

힌트 T14 — protect_step() · 바퀴 하나의 1 ms 판정

할 일 — 입력은 상태 p, 문턱 c(전부 c-> 에서 — 이 파일은 robot_params.h 를 모른다), 이번 틱의 목표 · 측정 · 듀티 in. 출력은 래치된 비트. 끝났을 때 참이어야 하는 것: 세 조건이 "지속 시간만큼 연속으로" 참이었던 비트만 섰고, 한 번 선 비트는 그대로다. 1 kHz ISR 안에서 바퀴마다 불린다 — printf 없음, 블로킹 없음. §2-7 의 표가 그대로 코드가 된다.

완결 코드

/* 완결 코드 T14 - User/Src/Control/protect.c */
uint8_t protect_step(protect_t *p, const protect_cfg_t *c, const protect_in_t *in)
{
  /* 1) 크기 - 전부 uint32, mag() 로 (P6: INT32_MIN 에서도 정의된다) */
  const uint32_t at = mag(in->target_mm_s);
  const uint32_t am = mag(in->meas_mm_s);
  const uint32_t ad = mag((int32_t)in->duty_permille);

  /* 2) 구동 국면인가: 목표가 있고, 듀티가 목표와 같은 쪽으로 밀고 있다 (P5) */
  const int driving = (sgn(in->target_mm_s) != 0)
                   && (sgn(in->target_mm_s) == sgn((int32_t)in->duty_permille));

  /* 3) 조건 셋 - 2-7 표의 한 행씩, AND 로 */
  const int st = (at >= c->stall_target_min_mm_s)          /* A: 이 아래는 blind band */
              && (am <  c->stall_speed_max_mm_s)           /* B: "움직이지 않음" */
              && (ad >= c->stall_duty_min_permille);       /* C: 실제로 밀고 있을 때만 */
  const uint32_t thr = ad * c->fblost_speed_per_permille_milli / 1000u;   /* P4: 문턱은 듀티를 따른다 */
  const int fl = (at >= c->fblost_target_min_mm_s)         /* blind band: 이 아래에서는 판정하지 않는다 */
              && (ad >= c->fblost_duty_min_permille)       /* 구동이 실제로 밀고 있을 때만 */
              && (am <  thr);                              /* "이 듀티를 주는데 그만큼의 속도가 안 나온다" */
  const int fs = driving
              && (am >= c->fbsign_speed_min_mm_s)          /* 이 아래는 잡음으로 본다 */
              && (sgn(in->meas_mm_s) != 0)
              && (sgn((int32_t)in->duty_permille) != sgn(in->meas_mm_s));

  /* 4) 지속 카운터: 참이면 +1 (0xFFFF 에서 포화), 거짓이 되는 순간 0 (P3) */
  p->stall_ms  = st ? (uint16_t)((p->stall_ms  < 0xFFFFu) ? p->stall_ms  + 1u : p->stall_ms)  : 0u;
  p->fblost_ms = fl ? (uint16_t)((p->fblost_ms < 0xFFFFu) ? p->fblost_ms + 1u : p->fblost_ms) : 0u;
  p->fbsign_ms = fs ? (uint16_t)((p->fbsign_ms < 0xFFFFu) ? p->fbsign_ms + 1u : p->fbsign_ms) : 0u;

  /* 5) 지속 시간에 닿았고 조건이 아직 참이면 래치 (P1: 지우는 것은 protect_reset() 뿐) */
  if (st && p->stall_ms  >= c->stall_hold_ms)  { p->tripped |= (uint8_t)PROT_STALL; }
  if (fl && p->fblost_ms >= c->fblost_hold_ms) { p->tripped |= (uint8_t)PROT_FBLOST; }
  if (fs && p->fbsign_ms >= c->fbsign_hold_ms) { p->tripped |= (uint8_t)PROT_FBSIGN; }
  return p->tripped;
}

코드 설명

  • const uint32_t at = mag(in->target_mm_s); 등 셋 — 크기부터. 문턱은 전부 크기(부호 없음)라 비교 상대도 부호 없는 수여야 한다 — 부호 있는 in->meas_mm_s 와 그냥 비교하면 음수가 아주 큰 수로 읽힌다(아래 표). (int32_t)in->duty_permille 은 int16_t 를 mag() 의 인자형에 맞춘 것이다.
  • const int driving = (sgn(target) != 0) && (sgn(target) == sgn(duty)); — 구동 국면(P5). 목표가 0 이면 "구동"이 아니고, 제어기가 되밀고 있으면(목표 +, 듀티 −) 제동이다. 이 한 줄이 1세대 2026-07-19 의 둘째 사고를 막는다(§2-7 표의 둘째 행).
  • st — STALL 의 세 조건을 && 로. at >= A 와 am < B 가 같이 서려면 A > B 여야 한다는 것이 표의 각주이고, 3-3-4 의 2 에서 _Static_assert 가 된다.
  • const uint32_t thr = ad * c->fblost_speed_per_permille_milli / 1000u; — 문턱은 듀티를 따른다(P4). 곱한 뒤 나누므로 ad(≤ 1000) × 기울기 가 uint32 안에 들어야 한다 — 기울기가 4 백만을 넘지 않으면 된다. §2-7 은 "나눗셈을 없애려는 것"이라 적었지만 골격의 식에는 / 1000u 가 하나 남는다 — 기울기(건강한 비 ÷ FRAC)의 나눗셈을 미리 해 둔 것이고, 이 상수 나눗셈 하나는 1 kHz 에서 문제가 아니다. 없애고 싶으면 기울기의 단위를 바꾼다(다르게 써도 되는 곳).
  • fl — 두 게이트(목표 · 듀티)와 am < thr. 게이트 아래가 blind band 다(P2) — 벡터 4 가 "그 아래에서는 1000 ms 를 둬도 안 선다"를 채점한다.
  • fs — driving 이 앞에 있고, 속도 게이트, 그리고 sgn(meas) != 0. 마지막 조건이 없으면 속도 0 에서 sgn(duty) != 0 이 늘 참이 되어 벡터 9(전부 0 인 cfg)가 떨어진다 — 그 벡터가 "0 은 보호를 죽인다"를 보이는 벡터인데, 이 조건이 빠지면 거꾸로 FEEDBACK_SIGN 이 선다.
  • p->stall_ms = st ? (uint16_t)((p->stall_ms < 0xFFFFu) ? p->stall_ms + 1u : p->stall_ms) : 0u; — 지속 카운터(P3). 참이면 +1(0xFFFF 에서 포화 — 65 초 넘게 참이어도 되감기지 않게), 거짓이면 0. "연속으로"는 이 : 0u 한 조각이다. 바깥 (uint16_t) 캐스트는 + 1u 가 unsigned int 로 승격되는 것을 다시 16비트로 되돌린다(없으면 arm-gcc 가 조용히 잘라 넣지만 -Wconversion 을 켜면 경고다).
  • if (st && p->stall_ms >= c->stall_hold_ms) { p->tripped |= (uint8_t)PROT_STALL; } — 래치(P1). |= 는 비트를 세우기만 한다. 조건 st && 를 다시 보는 것은 카운터가 포화한 채 남는 경우를 막기 위해서가 아니라(거짓이면 0 이 됐다), "지금도 참"을 명시하는 것이다 — 걸음 5 의 글자 그대로.
  • return p->tripped; — 골격이 이미 그렇게 돌려줬다. 골격의 (void)c; (void)in; (void)mag; (void)sgn; 는 지웠다 — 넷 다 이제 쓴다.
  • 다르게 써도 되는 곳 — ① 카운터를 uint16_t 로 포화시킬지, 지속 시간에 닿으면 세기를 멈출지 — 둘 다 P3 을 만족한다. ② 세 조건을 const int 셋으로 나눌지 한 if 로 묶을지는 취향이지만, 나눠 두면 어느 조건에서 걸렸는지를 디버거로 한 번에 볼 수 있다. ③ 트립한 뒤 래치를 어떻게 푸는가는 여기 없다 — 내 결정이고 fw-18 의 자리다.

쓰는 API — 없다(순수 파일). mag() · sgn() 은 T11 · T12.

이 열 개에는 control.c 에서 가드를 붙인다 — 0 이면 어떤 보호도 트립하지 않기 때문이다(아래 시험의 마지막 벡터가 그것을 보인다). 실습 B 까지는 이 열 줄도 가드도 없었다: 보호를 엮는 이 실습에서 같이 넣는다.

다만 열 개가 같은 뜻으로 0 인 것은 아니다. 0 이면 판정이 죽는 것은 둘이다 — STALL_SPEED_MAX_MM_S(|속도| < 0 은 참이 될 수 없다)와 FBLOST_SPEED_PER_PERMILLE_MILLI(문턱이 0 이라 같은 이유). 나머지, 특히 게이트 둘(*_TARGET_MIN_* · *_DUTY_MIN_*)에게 0 은 "blind band 를 두지 않는다"는 뜻있는 선택일 수 있다 — 그런데 != 0 가드는 그 선택을 못 쓰게 만든다. 가드를 열 개 다 두는 것은 "열 개를 한 번씩은 들여다보게" 하려는 forcing function 이다. blind band 를 정말 두지 않기로 했다면 0 이 아니라 아주 작은 값 + 그 이유를 적은 주석으로 쓴다 — "안 정한 0" 과 "정해서 0" 을 구분할 방법이 소스에 있어야 한다.

  /* stall  */ 300u, 20u, 200u, 5u,
  /* fblost */ 100u, 200u, 100u, 3u,      /* 기울기 100 -> 문턱 = |duty| * 0.1 mm/s */
  /* fbsign */ 50u, 2u
};

/* 같은 틱을 n 번 돌리고 래치된 비트를 반환한다 */
static uint8_t run(protect_t *p, int32_t tgt, int32_t meas, int16_t duty, int n)
{
  protect_in_t in = { tgt, meas, duty };
  uint8_t r = 0;
  for (int i = 0; i < n; i++) { r = protect_step(p, &CFG, &in); }
  return r;
}

2. 게인을 전부 0 으로 두고 step 을 한 번 찍는 것이 왜 첫 걸음인가

그 CSV 는 제어에 대해 아무것도 말해 주지 않지만 제어가 아닌 것 전부에 대해 말해 준다: 1 kHz 포획이 요청한 행 수만큼 돌았는가, t_ms 가 행 번호와 맞는가(틱을 빠뜨리지 않았는가), 덤프가 워치독을 넘기지 않았는가, 목표가 계단으로 들어가고 200 ms 안에 재주입되는가, 터미널 로그가 제대로 잡히는가. 이 중 하나라도 틀린 상태에서 게인을 올리면, 나중에 이상한 곡선을 보고 그 원인을 게인에서 찾게 된다. 기준선은 "나중에 달라진 것이 무엇 때문인지 말할 수 있게" 만드는 장치다 — fw-06 이 PID 를 올리기 전에 빈 박자의 지터부터 잰 것과 같은 이유다.

3. FEEDBACK_LOST 의 문턱을 목표가 아니라 인가 듀티에 비례시키는 이유를, 1세대가 겪은 두 사건으로 설명해 보라

목표는 명령이 바뀌는 순간에 계단으로 뛴다. 그러나 실제 구동(듀티)은 슬루와 제어기의 응답 때문에 천천히 오른다. 문턱을 목표에 매달면, 목표가 뛴 직후부터 "이만큼 속도가 나와야 한다"는 기대치가 이미 최대인데 실제 듀티는 아직 낮다 — 정상 가속이 곧바로 고장으로 보인다. 1세대는 2026-07-19 에 정확히 이것을 겪었다(목표 100000 은 통과, 105000 은 4모터 동시 트립). 문턱을 지금 인가하고 있는 듀티에 비례시키면 기대치도 실제 구동과 함께 자라므로 그 구간이 사라진다. 그런데 같은 날 다른 시험에서 진짜 단선은 여전히 잡혔다(엔코더 1개를 물리적으로 뽑고 시험). 이것이 중요하다 — 오트립을 줄이는 수정이 검출까지 죽이지 않았는지는 따로 확인해야 한다. 이 쪽의 체크 항목 fblost-trips-on-unplug 와 no-false-trip-fast-accel 이 그 한 쌍이다.

4. 하드웨어 워치독(IWDG)이 1세대의 엔코더 GND 단선 폭주를 막지 못한 이유는

펌웨어가 죽지 않았기 때문이다. 1 kHz 루프도 주 루프도 정상으로 돌았고 kick 도 제때 들어갔다. IWDG 가 보는 것은 "이 코드가 아직 돌고 있는가" 하나뿐이고, "돌고 있는 코드가 옳은 값을 보고 있는가"는 보지 않는다. 되먹임이 죽으면 루프는 더 열심히 돈다 — 오차가 크니 적분이 자라고 듀티가 최대로 간다. 살아 있다는 신호는 오히려 더 확실해진다. 그래서 장치가 셋으로 나뉜다: IWDG = 죽은 것, 명령 워치독 = 상위가 말을 멈춘 것, 보호 3종 = 살아서 틀리는 것. 셋을 같은 낱말로 부르면 하나를 시험하고 셋 다 됐다고 믿게 된다.

5. (일부러 틀리면) control_step_1khz() 를 1 kHz 콜백 안의 motor_step_1khz() 뒤로 옮기면 무엇이 보이는가

평소에는 아무 차이도 보이지 않는다 — motor_step_1khz() 는 pwm 명령이 무장해 둔 유지 시간이 있을 때만 일을 하고, 제어가 도는 동안 그 값은 0 이기 때문이다. 그것이 이 실수가 위험한 이유다. 차이가 나는 것은 pwm 을 쓴 직후뿐이다: 유지 시간이 끝나 motor_step_1khz() 가 네 바퀴를 0 으로 만든 바로 그 틱에 뒤따라 오는 제어가 다시 듀티를 써 버린다. fw-08 이 만든 "명령 워치독이 생기기 전 구간의 안전 장치"가 소리 없이 없어진다. 일반화하면 §2-10 의 단조 사슬이다 — 출력을 줄이는 단계는 언제나 만드는 단계 뒤에. 콜백에 무엇이 더 붙든 이 규칙 하나로 순서가 정해진다.

6. (안전) 이 쪽에서 STALL 을 벤치에서 발동시키지 않는 이유와, 그 대신 무엇으로 STALL 이 옳은지 확인하는가

모터는 감속비 1:47 의 유성기어 모터다(정격 토크 145.4 kgf·cm — 1세대 기록). 출력축을 손이나 공구로 붙잡아 멈추는 것은 사람과 기계 양쪽에 위험하고, 스톨 전류(기록상 22 A)가 배선과 드라이버에도 걸린다. 대신 판정식이 옳은가는 호스트 시험으로 확인한다 — 조건 넷이 다 참일 때 지속 시간만큼 뒤에 래치되는가, 그리고 A > B 덕분에 정상 저속 주행이 걸리지 않는가. 이것이 "경로 통과"이고, 실제 발동은 조건(저속 · 짧은 시간 · 듀티 상한)을 걸 수 있는 fw-20 으로 미룬다. 체크 항목 이름 stall-path-host-only 가 그 미룸을 명시한다 — 미룬 것을 미뤘다고 적어 두지 않으면 나중에 "했다"가 된다.

7. 값만 채점하는 호스트 시험 벡터가 통과시켜 버리는 잘못에는 어떤 것이 있고, 그것을 무엇이 잡는가

정의되지 않은 동작(UB)이다. 이 쪽에서 실제로 본 예: mag() 를 -v 로 쓰면 v == INT32_MIN 에서 부호 있는 넘침이 나는데, 두 값이 우연히 같아서 24개 벡터가 전부 통과한다(§3-3-3 의 상자). 컴파일러는 UB 를 "일어나지 않는다"고 가정하고 최적화하므로, 같은 소스가 최적화 수준이나 컴파일러 버전에 따라 다르게 동작할 수 있다 — 벤치에서 맞다가 Release 빌드에서 틀리는 종류의 버그다. 잡는 것은 -fsanitize=undefined 를 더한 둘째 줄이고, 합격 조건은 "조용한 것"이다(PASS 가 찍혀도 그 위에 runtime error: 가 있으면 실패). 같은 함정을 fw-09 의 엔코더 차분에서 이미 한 번 만났다.
