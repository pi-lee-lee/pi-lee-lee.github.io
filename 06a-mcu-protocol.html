06a · MCU 프로토콜 선정

MCU 아키텍처와 통신 프로토콜 — 두꺼운 제어기, 얇은 통신 계층

이 문서는 코드가 아니라 결정을 내리는 문서다. 여기서 정하는 것은 세 가지다. ① MCU 가 무엇을 책임지는가(제어와 안전의 전권), ② MCU 와 Pi 가 어떤 형식으로 이야기하는가(A. micro-ROS / B. 커스텀 시리얼), ③ 두 트랙(펌웨어·ROS)이 공유할 사양서(계약 v2). 06 단계의 C++ 브리지와 MCU 펌웨어는 여기서 확정한 계약을 각자 구현한다.

이 단계가 끝나면

A/B 의 차이가 페리페럴 제어 코드가 아니라 통신 계층에만 있다는 것을 설명하고, 디버깅 가시성 기준으로 하나를 골라 이유를 말할 수 있다. 전원·모터·엔코더·IMU 를 MCU 가 전권으로 다루는 구조를 그림으로 그릴 수 있고, 각 루프가 왜 그 주기(Hz·ms)로 도는지 사다리로 설명할 수 있다. 그리고 IMU·이벤트 프레임이 포함된 계약 v2 를 문서로 확정했다.

그래프에서의 위치mcu_bridge 상자와 NUCLEO 펌웨어(ROS 밖) 사이의 선 — 시리얼 프레임. 그리고 펌웨어 상자 자체의 책임 범위
전제03 (토픽·QoS), 04 (노드 작성), 05 (TF)
예상 소요1~2시간 (읽기 + 결정 + 계약 확정)
언어결정 문서 (코드 없음)

1. 개요 — 선택해도 바뀌지 않는 것

어느 통신 방식을 골라도 이해해야 하는 개념은 동일하다.

   ① cmd_vel(v, ω)  →  좌/우 바퀴 속도       차동구동 역운동학
   ② 엔코더 틱      →  이동거리·회전량 →  odom   정운동학 + 적분
   ③ 단위 번역 경계  (m/s ↔ PWM/틱)          "어디서 번역하는가"
   ④ 워치독         (명령이 끊기면 정지)        안전 설계
   ⑤ TF 발행        (odom → base_footprint)   05단계와 연결

그리고 MCU 펌웨어의 페리페럴 코드도 동일하다. 엔코더 타이머, 모터 PWM, 속도 PID, 전원 감시, IMU 수신, 워치독은 A 든 B 든 같은 코드다. 두 방식이 다른 곳은 그 위에 얹히는 상위 노드와의 통신 계층 한 층뿐이다.

   ┌──────────────────────────────── MCU 펌웨어 ────────────────────────────────┐
   │  통신 계층  (A: micro-ROS 접착 코드  |  B: 프레임 코덱)   ← 여기만 다르다  │
   ├────────────────────────────────────────────────────────────────────────────┤
   │  제어·안전 모듈  set_target(vl, vr) / get_state() / fault_flags()          │
   │    엔코더 TIM · PID · PWM · 전원 감시 · IMU 수신 · 워치독 · 긴급 정지      │  ← 같다
   └────────────────────────────────────────────────────────────────────────────┘
용어를 먼저 정리한다

이 가이드에서 "브리지"는 Pi 쪽 노드(rpi5_mcu_bridge_cpp)를 가리킨다. MCU 펌웨어는 브리지가 아니라 제어기다. 우리가 만들 구조는 두꺼운 펌웨어(제어와 안전의 전권) + 얇은 통신 계층 + Pi 의 얇은 번역 노드이며, 펌웨어의 두께는 통신 방식이 아니라 §2-6 의 아키텍처 결정에서 온다.

2. 원리 — 두 선택지와 MCU 아키텍처

2-1. 선택을 가르는 질문

MCU 에 지금 무엇이 올라가 있고, 내가 펌웨어를 다시 구울 수 있는가?

우리 보드는 NUCLEO-H723ZG(Cortex-M7 @ 550 MHz, 1 MB Flash, 564 KB RAM)이고 펌웨어는 처음부터 우리가 쓴다. 폐쇄된 기성 펌웨어를 쓰는 경우("기존 명령셋에 맞추기")는 이 프로젝트에 해당하지 않으므로 다루지 않는다. 남는 선택지는 A 와 B 둘이고, 사양은 어느 쪽에도 제약이 아니다. micro-ROS 는 micro_ros_stm32cubemx_utils 의 humble 브랜치로 H7 을 공식 지원한다(MPU 설정 필요, FreeRTOS 태스크 스택 10 kB 이상 권고).

정정해 둘 것: 이 문서의 초안은 A 를 "펌웨어 전면 재작성"이라고 요약했는데, 그것은 틀렸다. 제어·안전 모듈은 그대로이고 통신 계층을 직접 쓰는 대신 스택을 통합하는 것이 A 다. 내가 치는 코드 줄 수는 오히려 B 보다 적다. 대신 통합 범위와 블랙박스가 크다.

2-3. B. 커스텀 시리얼 + 브리지 노드 — 이 프로젝트 권장

        │
        ▼

배우게 되는 것 — 자율주행 통합에서 가장 전이력이 높은 내용

  • rclcpp 로 실전 노드 작성: 파라미터, QoS 선택, 타이머, TF 브로드캐스트, POSIX 시리얼
  • 워치독과 안전 설계, 그리고 시각 정렬(MCU 틱 ↔ ROS 시각)
장점단점
와이어와 토픽을 둘 다 볼 수 있다 — 아래 디버깅 4계층프레임/CRC/파서를 직접 설계·구현해야 한다 (수백 줄)

배우는 개념이 다른 로봇/센서에도 그대로 적용된다메시지가 늘면 프레임 정의를 손으로 관리해야 한다 (§4-5 의 도구로 완화)

디버깅 가능성 — 학습자가 과소평가하고 나중에 후회하는 축

  ① 전선에 바이트가 흐르는가   →  pyserial 로 hexdump, 또는 로직 애널라이저
  ② 프레임이 올바른가         →  CRC 검증, 길이 필드

A 에서는 ①②③이 스택 안에 감춰져 있어 "안 된다"만 알 수 있다. 처음 배우는 사람에게 이 차이는 며칠과 몇 시간의 차이가 된다.

2-5. 결정 — B 를 먼저, 그리고 코드 구조로 못 박는다

B (커스텀 시리얼)를 먼저 한다
  1. 잃는 것이 없다. 제어·안전 모듈은 A 로 가더라도 그대로 쓴다.
  2. 경계가 눈에 보인다. 통합에서 문제가 나면 4계층 중 어디인지 좁힐 수 있다.
  3. 이미 뼈대가 있다. protocol.py 의 CRC8 과 가짜 MCU(LoopbackProtocol)로 ROS 쪽을 먼저 검증할 수 있고, 06 에서 그것을 C++ 로 옮기며 배운다.

전환을 쉽게 만드는 것은 결정이 아니라 코드 구조다. 펌웨어를 처음부터 두 모듈로 나눈다.

   control.c / control.h      ← 제어·안전 모듈. 밖으로 내놓는 함수는 이것뿐:
        void     control_set_target(int16_t vl_mm_s, int16_t vr_mm_s);   // 상위가 원하는 속도
        void     control_get_state(state_t *out);                        // 틱·전압·전류·틱 시각
        uint8_t  control_fault_flags(void);                              // 안전 상태 (거부권)

   comm_frame.c   (B)         ← 프레임 코덱. 위 함수만 호출한다
   comm_microros.c (A)        ← micro-ROS 접착 코드. 위 함수만 호출한다      ← 둘 중 하나만 링크

A 로 옮길 때 바뀌는 것은 comm_*.c 한 파일과 빌드 설정이다. 다만 정직하게 적어 두면, 그때 메시지 모델이 ROS 타입으로 바뀌고 FreeRTOS 태스크 구조가 들어오므로 "프레임만 바꾸는 일"보다는 크다. 그래도 제어 모듈은 손대지 않는다.

원칙: 전원, 모터, 엔코더, IMU 등 외부 모듈은 MCU 가 제어하고, 배터리 저전압·과전류·과경사(전복) 같은 위험 상태에서는 Pi 를 거치지 않고 MCU 가 전원을 끊거나 정지한 뒤 Pi 에 보고한다. Pi 가 죽어도, Wi-Fi 가 끊겨도, ROS 노드가 멈춰도 이 판단은 동작해야 하므로 펌웨어 안에 있어야 한다. 이것은 §3-2 의 "빠른 루프는 하드웨어 가까이"와 10 단계의 3단 방어가 전제하는 구조다.

Pi 쪽에 따라오는 요구 — MCU 는 거부권을 가진 장치다

브리지는 MCU 가 보고한 fault 비트와 이벤트를 /mcu/fault 같은 토픽으로 올리고, 10 단계의 감독 노드는 그것을 구독해 목표를 취소한다. MCU 가 정지한 상태에서 Nav2 가 계속 /cmd_vel 을 보내도 MCU 는 무시한다 — 그래서 상위가 그 사실을 알아야 "왜 안 움직이지"가 침묵이 되지 않는다. 06 의 브리지 골격에서 TODO(you) 로 남긴 fault 처리가 이것이다.

이 결정이 통신 방식과 무관하다는 점을 다시 적어 둔다. A 든 B 든 안전 로직은 펌웨어 안에 있고, 달라지는 것은 사건을 보고하는 형식뿐이다(B: 이벤트 프레임과 fault 비트, A: MCU 가 발행하는 토픽).

2-8. IMU — 어디에 두고, 어느 것을 쓰는가

IMU 는 MCU 에 둔다. 판단 기준은 "그 데이터를 누가 몇 Hz 로 소비하는가"다.

  • 전복·과경사 정지, 경사에서의 출력 보정, 요 각속도 직진 보정, 4모터 슬립 억제는 제어 루프 안에서 엔코더와 같은 박자로 써야 한다. Pi 를 거치면 시리얼·DDS 지연과 지터가 제어 루프에 들어간다.
  • 기울기 기반 긴급정지는 §2-6 의 원칙대로 Pi 프로세스의 생사에 좌우되면 안 된다.
  • MCU 는 센서의 데이터 준비 신호나 타이머와 동기화된 시각을 찍을 수 있지만, Pi 의 리눅스 I2C 는 실시간성이 없다.

ROS 가 IMU 에서 필요로 하는 것은 하나뿐이다. sensor_msgs/Imu 를 50~200 Hz 로 받아 robot_localization 의 EKF 가 /odom 과 융합해 회전 오차를 줄이는 것. 그래서 MCU 는 IMU 를 자기 제어에 쓰면서 동시에 샘플을 Pi 로 흘려보내고, 브리지는 /imu/data_raw 로 발행하며, EKF 가 odom → base_footprint TF 를 대신 내므로 브리지의 publish_tf 는 false 가 된다(05 의 "부모는 하나" 규칙). 실내에서 자력계 방위는 모터와 철골 때문에 수십 도씩 틀어지므로 EKF 에는 각속도와 가속도만 넣고 자력계는 쓰지 않는다.

32비트 카운터를 고르는 것이 왜 설계인가

16비트 타이머는 65536 마다 랩어라운드가 일어나 보정 로직이 필요하고, 그 버그는 "가끔 오도메트리가 순간이동한다"로 나타나 재현이 어렵다. 32비트면 현실적인 주행 시간 동안 그 걱정이 없다. 하드웨어 선택으로 소프트웨어 버그 한 종류를 없애는 것 — 임베디드 설계의 감각이다. 이 프로젝트는 H723 의 TIM23/TIM24 덕에 4륜 모두 32비트로 간다 — 그 대가로 이더넷 핀(PA1)을 내준다. 16비트 타이머의 랩어라운드는 "안 다뤄도 되게 만든" 첫 설계 결정이다.

3-3-C. 3.3 V 로직 — 배선 전에 반드시 확인 HW

4-4. 계약이 정하지 않는 것 — 각 트랙이 알아서 하는 것

  • MCU 안의 PID 게인, PWM 주파수, 엔코더 CPR, 전원 임계값, 과경사 각도 — 펌웨어의 일. Pi 는 mm/s 를 보내면 그 속도로 돌거나, 거부되면 fault 로 알려 준다고만 믿는다.
  • Pi 안의 운동학, 오도메트리 적분, EKF, TF, QoS — 브리지와 ROS 의 일. MCU 는 틱과 IMU 를 보내면 Pi 가 알아서 위치를 만든다고만 믿는다.
  • 이 경계 덕분에 나중에 통신 계층을 micro-ROS 로 바꿔도 제어 모듈은 그대로다 — ③ 단위 번역 경계가 한 군데라는 뜻이 이것이다.

🤔 이해 확인

1. A/B 중 무엇으로 골라도 반드시 이해해야 하는 것은 무엇인가?
① 차동구동 역운동학 ② 정운동학과 오도메트리 적분 ③ 단위 번역 경계 ④ 워치독 ⑤ TF 발행. 그리고 페리페럴 제어·안전 코드 전부. 통신 방식은 이 코드 위의 통신 계층과 어떻게 디버깅하는지만 바꾼다.
2. micro-ROS 를 고르면 MCU 코드가 많아지는가?
아니다. 내가 치는 줄 수는 오히려 줄어든다. 대신 rclc 와 Micro XRCE-DDS 스택을 통합해야 하고(툴체인, FreeRTOS, MPU, 전송 훅, agent 버전 일치), 와이어의 바이트를 직접 읽을 수 없게 된다. 많아지는 것은 코드가 아니라 통합 범위와 블랙박스다. 제어·안전 모듈은 B 와 똑같다.
3. micro-ROS 를 쓰면 "Pi 쪽에 아무것도 안 만들어도 된다"가 맞는가? 산업 표준인가?
둘 다 반만 맞다. micro_ros_agent 를 컨테이너로 계속 띄워야 하고 MCU 클라이언트와 버전이 맞아야 한다. DDS-XRCE 는 OMG 표준이고 micro-ROS 는 ROS 2 세계의 공식 경로지만, CAN/EtherCAT/Modbus 같은 산업 필드버스는 아니다.
4. 초보 학습자에게 디버깅 가능성이 왜 성능보다 중요한가?
처음에는 반드시 막힌다. 그때 어느 계층의 문제인지 좁힐 수 있으면 몇 시간, 못 좁히면 며칠이 걸린다. B 는 와이어→프레임→파싱→ROS 네 계층을 따로 볼 수 있고, A 는 토픽만 보인다.
5. 속도 PID 와 저전압 차단을 ROS 노드에 두면 무엇이 나빠지는가? C++ 로 쓰면 해결되는가?
PID 는 시리얼·DDS 왕복 지연과 지터가 루프에 들어가 게인을 올릴 수 없고 억지로 올리면 진동한다. 저전압 차단은 Pi 나 Wi-Fi 가 죽으면 같이 죽는다. C++ 로 써도 해결되지 않는다 — 문제는 언어가 아니라 루프가 지나가는 경로다. 빠른 루프와 안전은 하드웨어 가까이.
6. IMU 를 Pi 에 붙이면 안 되는 이유는?
전복 정지, 경사 보정, 슬립 억제는 1 kHz(1 ms) 제어 루프 안에서 엔코더와 같은 박자로 써야 하는데 Pi 를 거치면 지연과 지터가 들어간다. 기울기 기반 긴급정지가 Pi 프로세스의 생사에 좌우되면 안 된다. Pi 의 리눅스 I2C 는 실시간성이 없다. ROS 가 필요로 하는 것은 EKF 융합용 50~200 Hz 샘플뿐이며, 그것은 MCU 가 시리얼로 흘려보내면 된다.
7. "MCU 는 IMU 를 1 kHz 로 쓴다"는 무슨 뜻인가? 센서가 100 Hz 인데 가능한가?
1 ms 타이머 루프가 매 바퀴 IMU 의 최신값 변수를 읽어 그 바퀴의 PID·안전 판단에 반영한다는 뜻이다. 센서의 새 값은 100~200 Hz 라 나머지 바퀴는 직전 값으로 계산한다. "수신"이 아니라 "읽기"이고, 센서 출력 속도와 루프 속도는 별개다.
8. 엔코더 타이머와 I2C 센서와 UART 센서는 "누가 박자를 만드는가"에서 어떻게 다른가?
엔코더 타이머는 엔코더 엣지가 하드웨어 카운터를 직접 올린다(마스터 없음, CPU 비용 0). I2C/SPI 는 MCU 가 마스터라 읽기마다 MCU 가 트랜잭션을 시작하고 버스 시간이 든다. UART 는 대등한 통신이라 센서가 스스로 스트림을 보내고 MCU 는 DMA 로 받는다. 그래서 WT901 을 UART 로 붙이면 제어 루프 옆에 버스 점유가 없다.
9. 엔코더 카운트를 "차분"이 아니라 "누적값"으로, 그리고 프레임에 tick_ms 를 넣기로 한 이유는?
누적값이면 CRC 오류로 프레임 하나가 버려져도 다음 프레임에서 이동량이 회복된다. tick_ms 가 있어야 엔코더 샘플과 IMU 샘플을 같은 시각축에 놓을 수 있고, 그래야 EKF 가 두 센서를 맞게 융합한다. 브리지는 첫 프레임에서 ROS 시각과의 오프셋을 잡아 환산한다.
10. Pi 가 "명령이 없을 때도 50 Hz 로 0 을 보내는" 규칙이 없으면 무엇이 깨지는가?
MCU 워치독이 성립하지 않는다. "정지 명령이 오고 있음"과 "아무것도 안 옴"이 구분되지 않기 때문이다. 항상 보내면 후자에서만 워치독이 걸린다. 06 의 C++ 브리지 타이머는 cmd_vel 유무와 무관하게 매 주기 프레임을 쓴다.
11. MCU 가 과전류로 정지했는데 Nav2 는 계속 /cmd_vel 을 보낸다. 시스템은 어떻게 되어야 하는가?
MCU 는 명령을 무시하고(거부권) 이벤트 프레임과 fault 비트로 보고한다. 브리지는 그것을 /mcu/fault 토픽으로 올리고, 감독 노드는 목표를 취소해 Nav2 가 명령을 멈추게 한다. 상위가 모르면 "왜 안 움직이지"가 침묵이 된다 — 그래서 fault 보고가 계약에 들어 있다.
