  • A/B 의 차이가 페리페럴 제어 코드가 아니라 통신 계층에만 있다는 것을 설명하고, 디버깅 가시성 기준으로 하나를 골라 이유를 말할 수 있다.

1. 개요 — 선택해도 바뀌지 않는 것

어느 통신 방식을 골라도 이해해야 하는 개념은 동일하다.

   ① cmd_vel(v, ω)  →  좌/우 바퀴 속도       차동구동 역운동학
   ② 엔코더 틱      →  이동거리·회전량 →  odom   정운동학 + 적분
   ③ 단위 번역 경계  (m/s ↔ PWM/틱)          "어디서 번역하는가"
   ④ 워치독         (명령이 끊기면 정지)        안전 설계
   ⑤ TF 발행        (odom → base_footprint)   05단계와 연결

그리고 MCU 펌웨어의 페리페럴 코드도 동일하다. 엔코더 타이머, 모터 PWM, 속도 PID, 전원 감시, IMU 수신, 워치독은 A 든 B 든 같은 코드다. 두 방식이 다른 곳은 그 위에 얹히는 상위 노드와의 통신 계층 한 층뿐이다.

   ┌──────────────────────────────── MCU 펌웨어 ────────────────────────────────┐
   │  통신 계층  (A: micro-ROS 접착 코드  |  B: 프레임 코덱)   ← 여기만 다르다  │
   ├────────────────────────────────────────────────────────────────────────────┤
   │  제어·안전 모듈  set_target(vl, vr) / get_state() / fault_flags()          │
   │    엔코더 TIM · PID · PWM · 전원 감시 · IMU 수신 · 워치독 · 긴급 정지      │  ← 같다
   └────────────────────────────────────────────────────────────────────────────┘
용어를 먼저 정리한다

이 가이드에서 "브리지"는 Pi 쪽 노드(rpi5_mcu_bridge_cpp)를 가리킨다. MCU 펌웨어는 브리지가 아니라 제어기다. 우리가 만들 구조는 두꺼운 펌웨어(제어와 안전의 전권) + 얇은 통신 계층 + Pi 의 얇은 번역 노드다. 펌웨어의 두께는 통신 방식이 아니라 §2-6 의 아키텍처 결정으로 정해진다.

2. 원리 — 두 선택지와 MCU 아키텍처

2-1. 선택을 가르는 질문

MCU 에 지금 무엇이 올라가 있고, 내가 펌웨어를 다시 구울 수 있는가?

우리 보드는 NUCLEO-H723ZG(Cortex-M7, 1 MB Flash, 564 KB RAM)이고 펌웨어는 처음부터 우리가 쓴다. 폐쇄된 기성 펌웨어를 쓰는 경우("기존 명령셋에 맞추기")는 이 프로젝트에 해당하지 않으므로 다루지 않는다. 남는 선택지는 A 와 B 둘이고, 사양은 어느 쪽에도 제약이 아니다.

최대 550 MHz 는 조건부다. 전압 스케일 VOS0 그리고 옵션 바이트 CPU_FREQ_BOOST = 1 일 때만 550 MHz 이고, 부스트가 없으면 VOS0 의 상한은 520 MHz 다(DS13313 Rev 5 표 12). 부스트의 대가는 ITCM · DTCM 의 ECC 가 꺼지는 것이고 얻는 것은 +5.8 % 다. 이 프로젝트는 부스트를 쓰지 않고 520 MHz 로 운용한다(결정 9 개정, 2026-09-29). 옵션 바이트가 공장 기본값 0 인지 읽어 확인하는 절차는 fw-03 에 있다.

micro-ROS 는 micro_ros_stm32cubemx_utils 의 humble 브랜치로 H7 을 공식 지원한다(MPU 설정 필요, FreeRTOS 태스크 스택 10 kB 이상 권고).

        void     control_get_state(state_t *out);                        // 틱·전압·전류·틱 시각

A 로 옮길 때 바뀌는 것은 comm_*.c 한 파일과 빌드 설정이다. 다만 정직하게 적어 두면, 그때 메시지 모델이 ROS 타입으로 바뀌고 FreeRTOS 태스크 구조가 들어오므로 "프레임만 바꾸는 일"보다는 크다. 그래도 제어 모듈은 손대지 않는다.

결정 대기 — 이벤트(0x83)와 IMU 샘플(0x82)이 통신 모듈에 전달되는 경로

위의 네 함수만으로는 이벤트의 code · detail · tick_ms 를 통신 모듈이 꺼낼 방법이 없다. 그리고 06 §3-6 의 기존 코드에서는 안전·센서 코드가 event_send() · imu_send() 를 직접 부른다. 제어 쪽이 통신 쪽 함수를 호출하는 역방향이라 위 그림의 "위 함수만 호출한다"와 다르다. 방법은 셋이고, 와이어 계약(§4-2)은 어느 방법이든 동일하다.

  • (가) 끌어가기 — 제어 모듈이 이벤트를 큐에 쌓고 통신 모듈이 control_pop_event() 로 꺼낸다. 공개 함수가 넷에서 다섯이 되고, 큐 메모리가 필요하고, 이벤트가 폴링 주기만큼 늦는다. 호출 방향은 통신 → 제어 한쪽뿐이다.
  • (나) 싱크 등록 — 통신 모듈이 초기화 때 콜백을 넘긴다. 공개 함수가 하나 느는 것은 (가)와 동일, 지연은 없다. 콜백이 1 kHz 문맥에서 불리므로 통신 쪽의 넣기 동작이 그 문맥에서 안전해야 한다.
  • (다) 06 그대로 — 제어 쪽이 event_send() · imu_send() 를 부르고 링크 때 comm_*.c 가 그 심볼을 제공한다. 공개 함수는 넷 그대로다. 호출이 양방향이 되므로 "통신 모듈만 바꾼다"의 경계를 다시 정의해야 한다.

펌웨어 가이드의 기본 진행은 (가)다. 모듈 경계를 "역방향 호출 0건"이라는 grep 한 줄로 검사할 수 있는 꼴이기 때문이고, 권고가 아니다. 구현은 fw-13 · fw-17, 경계 검사는 fw-19. 정한 것은 5절에 적는다.

Pi 쪽에 따라오는 요구 — MCU 는 거부권을 가진 장치다

브리지는 MCU 가 보고한 fault 비트와 이벤트를 /mcu/fault 같은 토픽으로 올리고, 10 단계의 감독 노드는 그 토픽을 구독해 목표를 취소한다. MCU 가 정지한 상태에서 Nav2 가 계속 /cmd_vel 을 보내도 MCU 는 무시한다. 그래서 상위 노드가 정지 사실을 받아야 "왜 안 움직이지"의 원인을 알 수 있다. 06 의 브리지 골격에서 TODO(you) 로 남긴 fault 처리가 이 요구를 구현하는 자리다.

이 결정이 통신 방식과 무관하다는 점을 다시 적어 둔다. A 든 B 든 안전 로직은 펌웨어 안에 있고, 달라지는 것은 사건을 보고하는 형식뿐이다(B: 이벤트 프레임과 fault 비트, A: MCU 가 발행하는 토픽).

2-8. IMU — 어디에 두고, 어느 것을 쓰는가

IMU 는 MCU 에 둔다. 판단 기준은 "그 데이터를 누가 몇 Hz 로 소비하는가"다.

  • 전복·과경사 정지, 경사에서의 출력 보정, 요 각속도 직진 보정, 4모터 슬립 억제는 제어 루프 안에서 엔코더와 같은 박자로 써야 한다. Pi 를 거치면 시리얼·DDS 지연과 지터가 제어 루프에 들어간다.
  • 기울기 기반 긴급정지는 §2-6 의 원칙대로 Pi 프로세스의 실행 여부에 좌우되면 안 된다.
  • MCU 는 센서의 데이터 준비 신호나 타이머와 동기화된 시각을 찍을 수 있지만, Pi 의 리눅스 I2C 는 실시간성이 없다.

ROS 가 IMU 에서 필요로 하는 것은 하나뿐이다. sensor_msgs/Imu 를 50~200 Hz 로 받아 robot_localization 의 EKF 가 /odom 과 융합해 회전 오차를 줄이는 것. 그래서 MCU 는 IMU 를 자기 제어에 쓰면서 동시에 샘플을 Pi 로 보내고, 브리지는 그 샘플을 /imu/data_raw 로 발행한다. odom → base_footprint TF 는 EKF 가 대신 발행하므로 브리지의 publish_tf 는 false 가 된다(05 의 "부모는 하나" 규칙). 실내에서 자력계 방위는 모터와 철골 때문에 수십 도씩 틀어지므로 EKF 에는 각속도와 가속도만 넣고 자력계는 쓰지 않는다.

두 센서 모두 내부 융합 프로세서가 있어 새 값은 100~200 Hz 다(WT901 은 설정을 마친 뒤의 값이고, 출고 상태는 10 Hz 다). 그래서 다음 절의 "1 kHz 로 쓴다"를 정확히 이해해야 한다.

2-9. 주기 사다리 — Hz 와 ms, 그리고 "1 kHz 로 쓴다"의 뜻

3-3-A. STM32H7 의 메모리 함정 — 먼저 DTCM, 캐시는 그 다음

H7 에서 DMA 를 처음 쓰는 사람이 거의 반드시 한 번은 겪는 문제이고, 미리 알면 디버깅 시간을 하루쯤 줄인다. 흔히 "H7 의 DMA 문제 = D-Cache"로 알려져 있지만, CubeMX 가 만든 기본 프로젝트에서 먼저 만나는 것은 캐시가 아니라 버퍼가 놓인 자리다. 사실 셋이 겹친다.

  • DMA1/DMA2 는 DTCM 에 접근하지 못한다. 두 컨트롤러의 메모리 버스와 주변장치 버스는 "all internal memories except ITCM and DTCM"에만 이어져 있다(RM0468 §2.1.6 "DMA1 and DMA2 controllers"). DTCM(0x2000 0000, 128 KB)은 CPU 만 쓰는 메모리다.
  • CubeMX 의 기본 링커 스크립트는 변수를 전부 DTCM 에 둔다. H723 용으로 생성되는 STM32H723xG_flash.ld 는 .data · .bss · 힙 · 스택을 >DTCMRAM 에 배치한다. 그래서 아무 표시 없이 선언한 전역 배열은 DTCM 에 들어간다.
  • D-Cache 는 기본이 꺼져 있다. CubeMX 의 CORTEX_M7 설정에서 켜기 전에는 생성된 main.c 에 SCB_EnableDCache() 호출이 없다. 캐시 문제는 켠 뒤에만 생긴다.

둘째·셋째는 개발 머신에서 CubeMX 로 생성한 H723 프로젝트의 .ld 와 main.c 에서 확인한 사실이다. 네 프로젝트에서도 같은지는 grep -n DTCMRAM *.ld 와 grep -n SCB_EnableDCache Core/Src/main.c 로 직접 확인한다. CubeMX 판이 바뀌면 달라질 수 있다.

그래서 같은 DMA 코드가 버퍼의 자리와 캐시 설정에 따라 세 가지 상태로 갈린다. 증상도 다르고 고치는 곳도 다르므로 한 덩어리로 외우면 안 된다.

SB57 이 기본(ON)이면 이더넷 PHY 의 RMII REF_CLK 50 MHz 출력이 PA1 에 연결되어 있다(UM2407 Rev 6 §7.6.7 · 표 13 · 표 14). 제거는 납땜이 아니지만 다시 잇는 것은 납땜이다. 그래서 되돌릴 수 없는 작업으로 취급한다. 잃는 것은 이더넷이다. 나머지 솔더 브리지는 건드리지 않는다(확정 핀맵은 UM2407 의 기본 상태와 맞고, 다시 이어야 하는 SB 는 없다).

채택하지 않은 대안 — PHY 파워다운. UM2407 §7.6.7 Note 2 에 PHY 의 기본 제어 레지스터(주소 0x00) bit 11 로 기준 클록을 끄는 방법이 있다. 채택하지 않은 이유는 사실 둘이다. ① 그 레지스터를 쓰려면 MDIO(PA2 · PC1)와 ETH MAC 을 활성화해야 하고, 리셋부터 그 설정이 끝날 때까지의 구간에는 클록이 그대로 나온다. 엔코더 출력과 충돌하는 시간이 매 부팅마다 생긴다. ② 파워다운 중에 그 핀이 Hi-Z 인지는 PHY 데이터시트가 없어 확인하지 못했다.

제거 절차와 DMM 확인(CN11-30 ↔ PHY 쪽 패드 불통 등)은 fw-01 과 hardware/pinmap-h723.md 4절에 있다.

핀이 Zio/Morpho 커넥터의 어디에 나오는지는 hardware/pinmap-h723.md 2절(출처 UM2407 표 18~22)에 전부 있다. 솔더 브리지의 "기본 상태"는 UM2407 의 값일 뿐 내 보드의 실제 상태가 아니다. fw-01 에서 전원을 끈 채 DMM 도통으로 확인하고 INVENTORY 2절에 적는다.

32비트 카운터를 고르는 것이 왜 설계인가

16비트 타이머는 65536 마다 랩어라운드가 일어나 보정 로직이 필요하고, 그 버그는 "가끔 오도메트리가 순간이동한다"로 나타나 재현이 어렵다. 32비트면 현실적인 주행 시간 동안 그 걱정이 없다. 하드웨어 선택으로 소프트웨어 버그 한 종류를 없애는 것이 임베디드 설계의 감각이다. 이 프로젝트는 H723 의 TIM23/TIM24 덕에 4륜 모두 32비트 카운터를 쓴다. 그 대가로 이더넷 핀(PA1)을 엔코더에 쓰고 이더넷을 포기한다. 16비트 랩어라운드를 "다루지 않아도 되게 만든" 것이 이 프로젝트의 첫 설계 결정이다.

3-3-C. 3.3 V 로직 — 배선 전에 반드시 확인 HW 벤치

STM32H7 의 GPIO 는 3.3 V 다. 흔한 모터 드라이버 모듈과 엔코더는 5 V 로 동작한다. 5 V 엔코더 A/B 신호를 5V 비허용 핀에 바로 넣으면 MCU 가 손상된다.

WT901 은 공급 3.3 ~ 5 V(모듈에 LDO 내장) · 소비 25 mA 미만 · 핀 레벨 3.3 V / 5 V 호환이다(WT901 매뉴얼 V4.0 §1 ~ §3). BNO055 모듈 보드의 전원 입력 사양은 INVENTORY 2절의 빈칸이다. 어느 쪽이든 Nucleo 3V3 로 급전한다. 그 이유는 아래 표의 "FT 인가" 행과 "전원을 어디서 따는가" 행에 있다.

확인 항목방법

왜 펌웨어 가이드는 PWM 이 아니라 "명령 창"부터 만드는가 — 계약 v2 는 바퀴별 값을 싣지 않는다

이 문서의 이전 판은 트랙 2 를 ① PWM ② 엔코더 ③ 속도 PID ④ IMU ⑤ 전원 감시·안전 ⑥ 프레임 송수신 순서로 그렸다. 그 순서대로 하면 ①~⑤를 하는 동안 MCU 내부 값을 볼 관측 수단이 없다. ⑥(계약 v2)을 맨 앞으로 당기는 방법도 있지만, 계약을 넓히지 않는 한 계약 v2 만으로는 관측 수단이 되지 않는다. 이유는 §4-2 의 표에 있다.

  • 0x01 은 좌/우 속도 명령 [mm/s] 두 값이다. 듀티를 직접 줄 수 없다 — PID 를 만들기 전의 개루프 시험(PWM · 엔코더 방향 확인)에는 쓸 수 없는 입력이다.
  • 0x81 의 l_tick / r_tick 은 좌 · 우 각각 앞뒤 평균이고 "바퀴별 값은 MCU 안에서만 쓴다". 4개 엔코더를 하나씩 확인하거나 바퀴별 계단 응답을 보는 데 필요한 값이 와이어에 없다.
  • 듀티 · ADC 채널별 값 · 1 kHz 루프의 지터도 계약에 없고, 설정 프레임 0x02 / 0x84 는 "처음에는 구현하지 않는다".

그래서 결정(2026-09-22): 텍스트 명령 창(CLI)을 앞에, 계약 v2 는 뒤에. ST-LINK VCP(USART3) 하나를 빌드 스위치 LINK_MODE 로 TEXT / V2 로 바꿔 쓴다. TEXT 에서는 enc · pwm · adc · step 같은 명령으로 계약 밖의 값을 보고, V2 에서는 같은 포트가 이진 프레임 전용이 된다. 제어·안전 모듈은 두 모드에서 같은 코드다(§2-5 의 구조에 벤치용 관측 수단이 하나 더 추가된 꼴).

이 결정의 대가(사실)는 셋이다.

  • 최종 펌웨어에 TEXT / V2 두 경로가 남는다.
  • V2 모드에는 CLI 가 없어 관측 수단이 probe 스크립트와 gdb 뿐이다.
  • 계약의 200 ms 명령 워치독은 TEXT 모드에서도 동작하므로 계단 응답 명령과 어떻게 공존시킬지를 따로 정해야 한다(결정 대기 — fw-13).

고르지 않은 쪽(계약 v2 와 probe 를 먼저)에서는 첫 통전 시점에 200 ms 워치독과 세 구현(C · C++ · Python)의 CRC 일치가 이미 확보돼 있다. 대신 바퀴별 값을 보려면 계약에 진단용 TYPE 을 추가해야 하고, 그러면 이 문서 · protocol.hpp · 브리지를 같이 고치게 된다. 안전 출력단(EN · IWDG)을 첫 통전보다 앞에 두는 것은 어느 순서에서도 가능하다. 이 축은 동일하다.

결정 대기 — MCU 의 200 ms 워치독을 무엇이 되감는가

이 문서의 이전 판은 "200 ms 무프레임", 06 §1-1 의 표는 "200 ms 무명령"이라고 적어 두 쪽의 기술이 서로 달랐다. 둘은 다른 규칙이다.

  • (가) 유효한 0x01(속도 명령)만 되감는다 — "Pi 가 명령을 보내고 있는가"를 본다. 나중에 0x02 같은 다른 TYPE 이 생겨도, 그 TYPE 만 오고 속도 명령이 끊기면 200 ms 뒤에 정지한다. 되감는 자리가 제어 모듈의 control_set_target() 안이면 통신 모듈에는 워치독 코드가 필요 없다. 06 §3-6 의 기존 펌웨어 코드가 이 꼴이다(사실일 뿐 권고가 아니다).
  • (나) CRC 를 통과한 모든 프레임이 되감는다 — "링크가 유지되고 있는가"를 본다. 되감는 자리는 프레임 파서(통신 모듈)다. 0x02 를 구현한 뒤에 설정 프레임만 계속 오고 속도 명령이 멈추면, MCU 는 마지막 속도 목표를 유지한 채 계속 달린다.

두 규칙에서 동일한 것은 넷이다.

  • 지금 계약에서 Pi → MCU 프레임은 0x01 하나뿐이라(선택 항목 0x02 를 구현하지 않는 동안) 동작이 같다.
  • CRC 가 틀린 프레임은 어느 쪽에서도 되감지 않는다.
  • 200 ms 라는 값.
  • Pi 쪽 0.5 s 워치독.

정해지면 이 표와 06 §1-1, 펌웨어 가이드의 제어 모듈(fw-13)과 안전 상태기계(fw-18)가 같은 용어를 쓰도록 맞춘다. 5절에 적을 칸이 있다.

4-4. 계약이 정하지 않는 것 — 각 트랙이 정하는 것

  • MCU 안의 PID 게인, PWM 주파수, 엔코더 CPR, 전원 임계값, 과경사 각도 — 펌웨어의 일. Pi 쪽은 mm/s 를 보내면 그 속도로 바퀴가 돌거나, 거부되면 fault 로 알려 준다는 것만 전제한다.
  • Pi 안의 운동학, 오도메트리 적분, EKF, TF, QoS — 브리지와 ROS 의 일. MCU 쪽은 틱과 IMU 를 보내면 Pi 가 위치를 계산한다는 것만 전제한다.
  • 이 경계 덕분에 나중에 통신 계층을 micro-ROS 로 바꿔도 제어 모듈은 그대로다. ③ 단위 번역 경계가 한 군데라는 말은 이 뜻이다.

🤔 이해 확인

1. A/B 중 무엇으로 골라도 반드시 이해해야 하는 것은 무엇인가?
① 차동구동 역운동학 ② 정운동학과 오도메트리 적분 ③ 단위 번역 경계 ④ 워치독 ⑤ TF 발행. 그리고 페리페럴 제어·안전 코드 전부. 통신 방식은 이 코드 위의 통신 계층과 어떻게 디버깅하는지만 바꾼다.
2. micro-ROS 를 고르면 MCU 코드가 많아지는가?
아니다. 내가 치는 줄 수는 오히려 줄어든다. 대신 rclc 와 Micro XRCE-DDS 스택을 통합해야 하고(툴체인, FreeRTOS, MPU, 전송 훅, agent 버전 일치), 와이어의 바이트를 직접 읽을 수 없게 된다. 많아지는 것은 코드가 아니라 통합 범위와 블랙박스다. 제어·안전 모듈은 B 와 똑같다.
3. micro-ROS 를 쓰면 "Pi 쪽에 아무것도 안 만들어도 된다"가 맞는가? 산업 표준인가?
둘 다 반만 맞다. micro_ros_agent 를 컨테이너로 계속 띄워야 하고 MCU 클라이언트와 버전이 맞아야 한다. DDS-XRCE 는 OMG 표준이고 micro-ROS 는 ROS 2 세계의 공식 경로지만, CAN/EtherCAT/Modbus 같은 산업 필드버스는 아니다.
4. 초보 학습자에게 디버깅 가능성이 왜 성능보다 중요한가?
처음에는 반드시 막힌다. 그때 어느 계층의 문제인지 좁힐 수 있으면 몇 시간, 못 좁히면 며칠이 걸린다. B 는 와이어→프레임→파싱→ROS 네 계층을 따로 볼 수 있고, A 는 토픽만 보인다.
5. 속도 PID 와 저전압 차단을 ROS 노드에 두면 무엇이 나빠지는가? C++ 로 쓰면 해결되는가?
PID 는 시리얼·DDS 왕복 지연과 지터가 루프에 들어가 게인을 올릴 수 없고 억지로 올리면 진동한다. 저전압 차단은 Pi 가 멈추거나 Wi-Fi 가 끊기면 같이 멈춘다. C++ 로 써도 해결되지 않는다. 문제는 언어가 아니라 루프가 지나가는 경로다. 빠른 루프와 안전은 하드웨어 가까이.
6. IMU 를 Pi 에 연결하면 안 되는 이유는?
전복 정지, 경사 보정, 슬립 억제는 1 kHz(1 ms) 제어 루프 안에서 엔코더와 같은 박자로 써야 하는데 Pi 를 거치면 지연과 지터가 들어간다. 기울기 기반 긴급정지는 Pi 프로세스의 실행 여부에 좌우되면 안 된다. Pi 의 리눅스 I2C 는 실시간성이 없다. ROS 가 필요로 하는 것은 EKF 융합용 50~200 Hz 샘플뿐이며, 그 샘플은 MCU 가 시리얼로 보내면 된다.
7. "MCU 는 IMU 를 1 kHz 로 쓴다"는 무슨 뜻인가? 센서가 100 Hz 인데 가능한가?
1 ms 타이머 루프가 매 주기 IMU 의 최신값 변수를 읽어 그 주기의 PID·안전 판단에 반영한다는 뜻이다. 센서의 새 값은 100~200 Hz 라 나머지 주기에는 직전 값으로 계산한다. "수신"이 아니라 "읽기"이고, 센서 출력 속도와 루프 속도는 별개다.
8. 엔코더 타이머와 I2C 센서와 UART 센서는 "누가 박자를 만드는가"에서 어떻게 다른가?
엔코더 타이머는 엔코더 엣지가 하드웨어 카운터를 직접 올린다(마스터 없음, CPU 비용 0). I2C/SPI 는 MCU 가 마스터라 읽기마다 MCU 가 트랜잭션을 시작하고 버스 시간이 든다. UART 는 대등한 통신이라 센서가 요청 없이 스트림을 보내고 MCU 는 DMA 로 받는다. 그래서 WT901 을 UART 로 연결하면 제어 루프 옆에 버스 점유가 없다.
9. 엔코더 카운트를 "차분"이 아니라 "누적값"으로, 그리고 프레임에 tick_ms 를 넣기로 한 이유는?
누적값이면 CRC 오류로 프레임 하나가 버려져도 다음 프레임에서 이동량이 회복된다. tick_ms 가 있어야 엔코더 샘플과 IMU 샘플을 같은 시각축에 놓을 수 있고, 그래야 EKF 가 두 센서를 맞게 융합한다. 브리지는 첫 프레임에서 ROS 시각과의 오프셋을 계산해 환산한다.
10. Pi 가 "명령이 없을 때도 50 Hz 로 0 을 보내는" 규칙이 없으면 무엇이 성립하지 않는가?
MCU 워치독이 성립하지 않는다. "정지 명령이 오고 있음"과 "아무것도 안 옴"이 구분되지 않기 때문이다. 항상 보내면 후자에서만 워치독 정지가 일어난다. 06 의 C++ 브리지 타이머는 cmd_vel 유무와 무관하게 매 주기 프레임을 쓴다.
11. MCU 가 과전류로 정지했는데 Nav2 는 계속 /cmd_vel 을 보낸다. 시스템은 어떻게 되어야 하는가?
MCU 는 명령을 무시하고(거부권) 이벤트 프레임과 fault 비트로 보고한다. 브리지는 그 보고를 /mcu/fault 토픽으로 올리고, 감독 노드는 목표를 취소해 Nav2 가 명령을 멈추게 한다. 상위 노드가 정지 사실을 받지 못하면 "왜 안 움직이지"의 원인을 알 수 없다. 그래서 fault 보고가 계약에 들어 있다.
