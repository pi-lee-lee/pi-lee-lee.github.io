08c · Hailo-8 가속

Hailo-8 영상 추론 — 같은 /detections 를 실시간으로, CPU 는 비운 채로

08b 에서 만든 C++ CPU 검출기는 파이프라인이 맞다는 것을 증명했다. 그러나 1~3 FPS 이고 CPU 를 다 먹는다. 이 단계는 새 기능을 붙이는 단계가 아니라 같은 인터페이스를 내는 다른 백엔드를 만드는 단계다. overlay 노드도, 10 단계의 감독 노드도, 런치파일도 하나도 바뀌지 않는다 — 그것이 03 단계에서 배운 "느슨한 결합"의 실물이다.

이 단계가 끝나면

호스트와 컨테이너의 HailoRT 버전을 일치시키고, 카메라 영상에서 객체를 검출해 /detections (vision_msgs/Detection2DArray) 를 08b 와 같은 토픽·같은 메시지·같은 파라미터 이름으로 실시간(15~30 FPS) 발행한다. 추론 중에도 CPU 사용률이 50% 미만이고, 08b 의 detection_overlay 가 아무 수정 없이 박스를 그린다.

그래프에서의 위치detector 상자(인지 계층). 08b 의 yolo_detector 와 같은 자리, 같은 /detections 를 실시간으로
전제01 §3-4 (hailo-all + 데모 성공), 02 §2-5 (버전 락), 08b (/detections 인터페이스와 overlay)
예상 소요4~8시간 (버전 맞추기가 절반)
언어Python (HailoRT API) · C++ 은 선택

1. 개요

1-1. 08b 가 남긴 것과 남기지 못한 것

08b 의 yolo_detector 는 ONNX 모델을 OpenCV DNN 으로 돌려 /detections 를 냈다. 전처리·출력 텐서 해석·NMS·좌표 역변환을 직접 구현했기 때문에 "검출 결과가 무엇으로 이루어져 있는가"는 이미 안다. 남은 문제는 두 가지다.

  • 속도. Pi 5 CPU 에서 YOLOv8n 640×640 은 1~3 FPS 다. 주행 중 장애물 인지로는 쓸 수 없다.
  • 자원. 추론이 CPU 4코어를 점유하면 SLAM 과 제어 루프까지 같이 느려진다. 이것이 진짜 문제다.

1-2. 왜 Hailo 가 필요한가 — 숫자로

   CPU 만 쓸 때 (08b)                     Hailo 를 쓸 때 (08c)
   ┌─────────────────────┐                ┌────────────────────┐
   │ CPU 4코어           │                │ CPU 4코어          │
   │  ├ 추론 ████████ 95%│                │  ├ SLAM    ███ 30% │
   │  ├ SLAM  ░ (굶음)   │                │  ├ Nav2    ██ 20%  │
   │  └ Nav2  ░ (굶음)   │                │  └ 여유    █████   │
   └─────────────────────┘                └────────────────────┘
                                          ┌────────────────────┐
                                          │ Hailo-8: 추론 전담 │  26 TOPS, PCIe
                                          └────────────────────┘

핵심 가치는 FPS 자체가 아니라 "CPU 를 비워 주는 것"이다. 자율주행은 인지·계획·제어가 동시에 돌아야 하고, 그 중 하나라도 굶으면 전체가 실패한다. Hailo-8 은 추론을 전용 칩으로 옮겨 CPU 가 나머지 일에 집중하게 한다.

1-3. 이 단계의 형태 — 백엔드 교체

                     08b                                   08c
  /camera/image_raw ──► [ yolo_detector (C++) ] ──┐    /camera/image_raw ──► [ hailo_detect (Python) ] ──┐
                          OpenCV DNN · CPU        │                            HailoRT · /dev/hailo0     │
                                                  ▼                                                     ▼
                                          /detections  (vision_msgs/Detection2DArray)  ← 같은 토픽, 같은 메시지
                                                  │
                          ┌───────────────────────┼──────────────────────────┐
                          ▼                       ▼                          ▼
                 detection_overlay (08a)   mission_supervisor (10)      rosbag / Foxglove
                          "이 셋은 백엔드가 무엇인지 모른다. 알 필요도 없다."

두 노드는 파라미터 이름까지 같다(model_path, names_path, conf_threshold, nms_threshold, input_size, class_filter). 그래서 10 단계의 런치파일은 detector:=yolo / detector:=hailo 인자 하나로 백엔드를 고른다.

1-4. 01 단계에서 이미 확인한 것

# Pi 호스트에서 — 01단계 §3-4 에서 했던 것
rpicam-hello -t 10s --post-process-file \
  /usr/share/rpi-camera-assets/hailo_yolov8_inference.json

이게 돌아갔다면 하드웨어와 드라이버는 이미 검증된 것이다. 남은 일은 "그 결과를 ROS 토픽으로 만드는 것"뿐이다. 막혔을 때 "Hailo 가 고장났나"를 의심하기 전에 이 명령을 다시 쳐 보면 의심 범위가 절반으로 줄어든다.

2. 원리 — 왜

2-1. 버전 락 — 이 단계 최대의 함정

02 단계 §2-5 에서 예고한 문제를 여기서 만난다.

   호스트 (Raspberry Pi OS)                 컨테이너 (Ubuntu 22.04 jammy)
   ┌──────────────────────┐                ┌────────────────────────────┐
   │ hailo_pci (커널 모듈)│◄ /dev/hailo0 ─►│ libhailort + hailort wheel │
   │  버전 4.x.y (DKMS)   │                │  버전 4.x.y                │
   └──────────────────────┘                └────────────────────────────┘
              └──────────── 이 둘이 정확히 같아야 한다 ─────────────────┘

드라이버는 호스트에, 런타임 라이브러리는 컨테이너에 있다. HailoRT 는 이 둘의 버전이 다르면 장치를 아예 인식하지 않는다. "사소한 버전 차이만 있어도 SDK 가 하드웨어를 감지하지 못한다"가 공식 문서의 표현이다. /dev/hailo0 이 보여도 "No Hailo device found" 가 난다.

호스트를 apt upgrade 하면 호스트 쪽만 올라간다

어제까지 되던 추론이 오늘 갑자기 "No Hailo device found" 를 내고, ROS 코드는 하나도 안 건드렸으므로 원인을 엉뚱한 데서 찾게 된다. 호스트를 업그레이드한 뒤에는 반드시 §3-1 의 양쪽 검증을 다시 하고, 다르면 컨테이너 이미지를 다시 빌드한다.

2-2. 두 가지 아키텍처 — 선택

A. ROS 노드에서 HailoRT 직접 호출 (권장)

  /camera/image_raw ──► [ hailo_detect 노드 ] ──► /detections
                              │
                              └─► HailoRT (hailo_platform) ──► /dev/hailo0
장점단점
ROS 표준 구조, 타임스탬프/TF 정확버전 락 관리 필요
런치파일로 통합 관리, 백엔드 교체가 인자 하나전처리·후처리를 직접 구현 (08b 에서 이미 했다)
rosbag 으로 기록·재생·재현 가능컨테이너용 Python wheel 을 별도로 확보해야 함 (§2-8)

B. 호스트 rpicam-apps / picamera2 파이프라인 + 결과 전달

  [ 호스트: picamera2 + Hailo 후처리 ] ──JSON (UDP/유닉스 소켓)──► [ 컨테이너: 브리지 노드 ] ──► /detections
장점단점
버전 락 문제 없음 (호스트 Python 이 호스트 드라이버와 함께 apt 로 맞춰짐)시스템이 컨테이너 안팎으로 쪼개짐
RPi 가 제공하는 파이프라인 그대로, 빠른 시작타임스탬프 동기가 부정확 (촬영 시각을 ROS 시계로 옮겨야 함)
카메라를 호스트가 잡으므로 08 의 libcamera 문제와 무관rosbag 재생으로 재현 불가, 카메라를 컨테이너와 동시에 못 씀

A 를 목표로 하되, 막히면 B 로 먼저 동작시키고 나중에 옮긴다. "일단 돌아가는 것"이 "완벽한 구조"보다 학습에 유리하다. B 의 개요는 §3-6 에 있다.

2-3. 메시지 타입 — 왜 vision_msgs 인가 (다시)

ros2 interface show vision_msgs/msg/Detection2DArray
ros2 interface show vision_msgs/msg/Detection2D
Detection2DArray
  std_msgs/Header header                 ← 촬영 시각 + camera_optical_link
  Detection2D[] detections
      std_msgs/Header header
      ObjectHypothesisWithPose[] results
          ObjectHypothesis hypothesis
              string class_id            ← "person", "car" ...
              float64 score              ← 신뢰도 0~1
          geometry_msgs/PoseWithCovariance pose   (2D 검출에서는 비워 둔다)
      BoundingBox2D bbox
          vision_msgs/Pose2D center
              vision_msgs/Point2D position   ← x, y (픽셀, 박스 중심)
              float64 theta
          float64 size_x                 ← 박스 너비 (픽셀)
          float64 size_y                 ← 박스 높이
      string id
왜 커스텀 메시지를 만들지 않는가

표준 타입을 쓰면 08a 의 overlay 노드가 그대로 박스를 그리고, 10 의 감독 노드가 그대로 사람을 세며, 나중에 다른 인지 노드로 교체해도 하위 노드가 그대로 동작한다. 인터페이스가 계약이고 구현은 그 계약을 채우는 일이다 — 이 페이지 전체가 그 문장의 증명이다. Humble 의 필드 경로는 results[i].hypothesis.class_id, bbox.center.position.x 다(results[i].class_id 가 아니다).

2-4. 노드가 해야 할 일 — 다섯 단계와 반드시 지킬 것

  ① /camera/image_raw 구독  (센서 QoS, depth 1)
       ↓
  ② 전처리: 모델 입력 크기로 리사이즈, RGB uint8      ← .hef 가 요구하는 입력 규격에 맞춘다 (§3-2 parse-hef)
       ↓
  ③ HailoRT 추론 실행                                ← 여기만 08b 와 다르다
       ↓
  ④ 후처리: 박스 디코드 (NMS 포함 출력이면 그대로, raw 면 08b 처럼 NMS), 원본 좌표로 역변환
       ↓
  ⑤ Detection2DArray 발행 — header.stamp 는 입력 이미지의 stamp 그대로
항목이유
header 는 입력 이미지의 것을 복사추론 시점이 아니라 촬영 시점이 기준. TF 조회가 이 값을 쓴다. 100 ms 뒤의 로봇 자세로 물체 위치를 계산하면 수십 cm 가 틀어진다
프레임 드롭 허용추론이 카메라보다 느리면 최신 프레임만 처리. 큐에 쌓으면 지연이 무한 증가 — 1분 뒤에는 30초 전 영상을 보고 판단한다
QoS 는 BEST_EFFORT오래된 프레임을 재전송받아 봐야 쓸모없다. 발행도 같은 QoS — 10 의 감독 노드도 BEST_EFFORT 로 구독해야 연결된다
모델 로딩은 생성자에서 1회콜백마다 로드하면 매번 수백 ms. 장치 핸들(VDevice)도 노드 수명 동안 하나
입력 해상도를 파라미터로모델 교체 시 코드 수정 없이 대응. 08b 와 같은 파라미터 이름을 쓴다

2-5. 모델 — .hef 와 Model Zoo

Hailo 는 .hef(Hailo Executable Format) 파일을 쓴다. ONNX/TFLite 를 그대로 쓸 수 없고 컴파일이 필요하다.

경로내용
Hailo Model Zoo이미 컴파일된 .hef 제공 (YOLOv8, YOLOv11 등, Hailo-8 용과 Hailo-8L 용이 다르다) — 여기서 시작
hailo-all 설치본/usr/share/hailo-models/ 에 기본 모델이 들어 있다 (호스트)
직접 컴파일Dataflow Compiler 필요. x86 리눅스에서만 동작. 08b 에서 만든 ONNX 를 넣는 길이지만 별도의 큰 주제
용도모델 계열비고
장애물/사람 검출YOLOv8n / YOLOv11n가장 무난. COCO 80종. 08b 와 같은 모델을 고르면 결과를 1:1 비교할 수 있다
주행 가능 영역세그멘테이션출력 처리가 무겁다
거리 보조단안 깊이 추정라이다가 있으므로 우선순위 낮음

우리 목표(자율주행)에는 객체 검출이면 충분하다. 거리는 라이다가 훨씬 정확하게 알려 준다. 처음에는 Model Zoo 의 기성 .hef 를 쓴다. .hef 는 Hailo-8(26 TOPS) 용과 Hailo-8L(13 TOPS) 용이 따로 있다 — AI HAT+ 26 TOPS 는 Hailo-8 이다. hailortcli fw-control identify 의 Device Architecture 로 확인한다.

2-6. ONNX 와 HEF 의 출력은 다르다 — 그래서 어댑터가 필요하다

08b · ONNX (OpenCV DNN)08c · HEF (HailoRT)
출력 형태raw 텐서 [1, 84, 8400] — 8400개 후보 × (4 좌표 + 80 클래스 점수)대개 NMS 후처리가 포함되어 "클래스별 박스 리스트"가 바로 나온다 (정규화된 [y_min, x_min, y_max, x_max, score] 형태가 흔함)
NMS노드가 직접 (cv::dnn::NMSBoxes)칩/런타임이 이미 했음 — 다시 하면 안 됨. NMS 없는 .hef 라면 08b 와 같은 절차 필요
좌표중심+크기, 입력 픽셀모서리, 0~1 정규화인 경우가 많음 (parse-hef 와 실제 출력을 찍어 확인)
신뢰도/클래스 임계노드가 적용컴파일 시 임계값이 박혀 있을 수 있음 — conf_threshold 파라미터는 그 위에서 한 번 더 거른다
노드 구조에 주는 영향

08b 의 파서를 그대로 재사용할 수 없다. 그래서 노드를 "ROS 배선(구독·발행·드롭·헤더)" + "백엔드(프레임 → 박스 리스트)" 두 층으로 나누고, 백엔드가 지켜야 할 계약을 하나로 고정한다: infer(rgb_frame) → [(x1, y1, x2, y2, score, class_id), ...] 원본 프레임 픽셀 좌표. 좌표 순서와 정규화 해제는 백엔드 안에서 끝낸다. 이 계약 덕분에 §3-4 의 FakeBackend 로 하드웨어 없이 ROS 쪽을 먼저 검증할 수 있다.

2-7. 왜 이 노드만 Python 인가

이 프로젝트의 주 언어는 C++ 이다. 그런데 이 노드는 Python 으로 쓴다. 이유는 언어 성능이 아니라 벤더 SDK 의 형편이다.

  • HailoRT 의 예제·문서·커뮤니티 코드는 Python 이 압도적으로 많다 (hailo-rpi5-examples, Hailo-Application-Code-Examples). API 가 버전마다 바뀔 때 Python 예제가 가장 먼저 갱신된다.
  • 연산은 칩이 한다. 노드가 하는 일은 리사이즈·박스 디코드·메시지 채우기뿐이라 Python 으로도 30 FPS 를 넘긴다. CPU 사용률이 높다면 언어가 아니라 리사이즈가 병목이다(§3-8).
  • C++ API(libhailort)도 있다. 이 노드가 안정된 뒤 C++ 로 옮기는 것은 좋은 확장 과제이고, 계약(§2-6)이 같으므로 하위 노드는 여전히 모른다.

2-8. 컨테이너의 Python 은 호스트의 Python 이 아니다

호스트(Raspberry Pi OS Trixie)의 hailo-all 은 호스트 Python(3.13) 용 hailo_platform 을 설치한다. 컨테이너(Ubuntu 22.04)의 Python 은 3.10 이다. 같은 HailoRT 버전이라도 wheel 은 Python 버전별로 다르다.

   호스트:   hailort  4.x.y  +  python3-hailort (cp313)        ← apt 가 드라이버와 함께 맞춰 줌
   컨테이너: hailort_4.x.y_arm64.deb  +  hailort-4.x.y-cp310-cp310-linux_aarch64.whl   ← 직접 확보
                      ▲ 버전 같아야 함                ▲ cp310 이어야 import 됨

그래서 Dockerfile 에 버전이 같은 .deb 와 cp310 wheel 두 파일이 필요하다. Hailo Developer Zone(계정 필요)에서 받는다. "호스트에서는 import hailo_platform 이 되는데 컨테이너에서는 안 된다"의 원인이 이것이다.

2-9. 검출 결과를 주행에 쓰려면 — 08d 예고

   검출 박스 (픽셀)  ─┐
                      ├──► 같은 방향의 /scan 거리 ──► "전방 1.2 m 에 사람"
   camera_info ───────┘        (라이다와 융합, 08d)
   (초점거리, 주점)

카메라와 라이다를 융합하는 것이 실전 설계다. 카메라(+Hailo)는 무엇인가(사람/차/개)를 알고 거리는 부정확하다. 라이다는 얼마나 먼가를 정확히 알고 무엇인지는 모른다. 두 센서의 TF(camera_optical_link ↔ laser_link)가 정확해야 한다 — 05 단계의 실측이 여기서 효력을 발휘한다. 지금은 /detections 를 안정적으로 초당 10장 이상 내는 것이 목표다 — 08d 의 추적은 프레임 사이 IoU 에 기대므로 08b 의 2 fps 로는 성립하지 않는다(08d §2-1). Detection2D.id 는 비워 둔다. 추적기가 채운다.

3-3. 설치된 HailoRT 의 Python API 를 찾는 법

이 가이드는 HailoRT API 호출을 코드에 박지 않는다

HailoRT Python API 는 버전에 따라 클래스 이름과 호출 순서가 달라져 왔다(스트림 기반 API 와 그 이후의 추론 모델 API 가 공존한다). 여기에 특정 버전의 코드를 적어 두면 당신의 버전에서 틀린 코드가 될 확률이 높고, 그 오류는 "Hailo 가 안 된다"로 보여 버전 락 문제와 구분되지 않는다. 대신 자기 버전의 예제를 찾아 읽는 절차를 익힌다. 이것은 다른 벤더 SDK 를 만날 때도 그대로 쓰는 기술이다.

#!/usr/bin/env python3
"""hailo_detect — /camera/image_raw → Hailo-8 → /detections (vision_msgs/Detection2DArray)

08b 의 yolo_detector(C++) 와 같은 토픽·같은 메시지·같은 파라미터 이름을 쓴다.
하위 노드(detection_overlay, mission_supervisor)는 이 둘을 구분하지 못한다 — 그것이 목표다.
"""
import time

import numpy as np
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSHistoryPolicy, QoSProfile, QoSReliabilityPolicy
from cv_bridge import CvBridge
from sensor_msgs.msg import Image
from vision_msgs.msg import Detection2D, Detection2DArray, ObjectHypothesisWithPose


class HailoBackend:
    """HailoRT 백엔드 — 설치된 버전의 API 로 채운다.

    계약: infer(rgb_frame) 는 (x1, y1, x2, y2, score, class_id) 튜플 리스트를
          **원본 프레임 픽셀 좌표**로 돌려준다. 이 계약만 지키면 노드의 나머지는 백엔드가 무엇이든 동일하다.

    구현에 들어가야 할 단계 (3-3 에서 찾은 자기 버전의 예제를 여기에 옮긴다):
      ① 장치 핸들(VDevice)을 연다 — 노드 수명 동안 1회
      ② HEF 를 로드하고 네트워크를 구성한다 — 입력/출력 스트림 정보(이름·shape)를 얻는다 (3-2 표와 대조)
      ③ 입력: 프레임을 모델 입력 크기(예: 640×640, RGB, uint8)로 리사이즈해 넣는다
      ④ 출력: 스트림을 읽는다
      ⑤ NMS 포함 출력이면 클래스별 박스 리스트를 디코드, raw 텐서이면 08b 와 같은 방식으로 NMS
      ⑥ 좌표를 원본 프레임 크기로 되돌린다 (정규화 해제 + 리사이즈 비율 역변환, 좌표 순서 [x,y,x,y] 로 통일)
    """

    def __init__(self, hef_path: str, input_size: int):
        self.input_size = input_size
        # TODO(you): 설치된 HailoRT 버전의 API 로 구현 — 3-3 에서 찾은 예제를 여기에 옮긴다 (①②)
        raise NotImplementedError('HailoBackend: 3-3 절을 보고 구현하십시오')

    def infer(self, rgb_frame: np.ndarray):
        # TODO(you): ③④⑤⑥
        raise NotImplementedError


class FakeBackend:
    """하드웨어 없이 ROS 쪽 배선을 검증하기 위한 가짜 백엔드 (06 단계의 simulate:=true 와 같은 발상).
    항상 화면 중앙에 class_id 0 ('person') 박스 하나를 돌려준다."""

    def __init__(self, hef_path: str, input_size: int):
        pass

    def infer(self, rgb_frame):
        h, w = rgb_frame.shape[:2]
        time.sleep(0.02)                                     # 추론 시간 흉내 (20 ms)
        return [(w * 0.3, h * 0.3, w * 0.7, h * 0.9, 0.9, 0)]


class HailoDetect(Node):
    def __init__(self):
        super().__init__('hailo_detect')
        # 08b 의 yolo_detector 와 같은 파라미터 이름 — 런치파일이 백엔드를 구분할 필요가 없다
        self.declare_parameter('model_path', '')
        self.declare_parameter('names_path', '')
        self.declare_parameter('conf_threshold', 0.4)
        self.declare_parameter('nms_threshold', 0.5)       # NMS 포함 .hef 라면 백엔드가 무시한다
        self.declare_parameter('input_size', 640)
        self.declare_parameter('class_filter', [''])       # 빈 문자열 하나 = 필터 없음
        self.declare_parameter('fake_backend', False)

        g = lambda n: self.get_parameter(n).value  # noqa: E731
        self.conf = float(g('conf_threshold'))
        self.class_filter = [c for c in g('class_filter') if c]
        self.names = self._load_names(g('names_path'))

        backend_cls = FakeBackend if bool(g('fake_backend')) else HailoBackend
        self.backend = backend_cls(g('model_path'), int(g('input_size')))   # ★ 모델 로딩은 여기서 1회

        self.bridge = CvBridge()
        self.busy = False

        # 센서 QoS(BEST_EFFORT) + depth 1 → DDS 큐에 항상 최신 프레임 하나만 남는다
        qos = QoSProfile(reliability=QoSReliabilityPolicy.BEST_EFFORT,
                         history=QoSHistoryPolicy.KEEP_LAST, depth=1)
        self.sub = self.create_subscription(Image, '/camera/image_raw', self.on_image, qos)
        self.pub = self.create_publisher(Detection2DArray, '/detections', qos)
        self.get_logger().info(
            f'hailo_detect 시작 | backend={backend_cls.__name__} model={g("model_path")}')

    @staticmethod
    def _load_names(path):
        if not path:
            return {}
        with open(path, encoding='utf-8') as f:
            return {i: line.strip() for i, line in enumerate(f) if line.strip()}

    def on_image(self, msg: Image):
        if self.busy:            # 프레임 드롭: 처리 중에 들어온 프레임은 버린다
            return               # (기본 실행기는 단일 스레드라 depth=1 만으로도 충분하지만,
        self.busy = True         #  나중에 MultiThreadedExecutor 로 바꿔도 안전하도록 둔다)
        try:
            # 카메라(camera_ros)는 format RGB888 을 ROS 인코딩 'bgr8' 로 발행한다. Hailo 모델이 RGB 를 원하면
            # 원본 인코딩이 무엇이든 'rgb8' 을 명시적으로 요청해 cv_bridge 가 변환하게 한다 (parse-hef 로 입력 포맷 확인).
            rgb = self.bridge.imgmsg_to_cv2(msg, desired_encoding='rgb8')
            t0 = time.perf_counter()
            boxes = self.backend.infer(rgb)
            dt_ms = (time.perf_counter() - t0) * 1000.0

            out = Detection2DArray()
            out.header = msg.header          # ★ 촬영 시각·프레임 그대로 — 추론 시각이 아니다
            for (x1, y1, x2, y2, score, cls_id) in boxes:
                if score < self.conf:
                    continue
                name = self.names.get(int(cls_id), str(int(cls_id)))
                if self.class_filter and name not in self.class_filter:
                    continue
                det = Detection2D()
                det.header = msg.header
                hyp = ObjectHypothesisWithPose()
                hyp.hypothesis.class_id = name              # Humble: results[i].hypothesis.class_id
                hyp.hypothesis.score = float(score)
                det.results.append(hyp)
                det.bbox.center.position.x = float((x1 + x2) / 2.0)   # Humble: bbox.center.position.x
                det.bbox.center.position.y = float((y1 + y2) / 2.0)
                det.bbox.size_x = float(x2 - x1)
                det.bbox.size_y = float(y2 - y1)
                out.detections.append(det)
            self.pub.publish(out)
            self.get_logger().info(f'{len(out.detections)} det, {dt_ms:.1f} ms',
                                   throttle_duration_sec=2.0)
        except Exception as exc:  # noqa: BLE001
            self.get_logger().error(f'추론 실패: {exc}', throttle_duration_sec=2.0)
        finally:
            self.busy = False


def main(args=None):
    rclpy.init(args=args)
    node = HailoDetect()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        if rclpy.ok():
            rclpy.shutdown()


if __name__ == '__main__':
    main()

camera_ros 는 format: RGB888 로 설정해도 ROS 메시지의 encoding 은 bgr8 이다(DRM fourcc 의 리틀엔디안 명명 때문에 이름과 바이트 순서가 반대로 읽힌다). 그래서 "카메라가 rgb8 로 보낸다"고 가정하지 말고, imgmsg_to_cv2(msg, 'rgb8') 처럼 원하는 인코딩을 명시적으로 요청해 cv_bridge 가 변환하게 한다 — 원본이 무엇이든 결과는 RGB 다. 실제 인코딩은 ros2 topic echo /camera/image_raw --field encoding --once 로 확인한다. 색 순서가 바뀌면 검출률이 눈에 띄게 떨어지는데 에러는 나지 않는다 — 08a 에서 다룬 함정이다.

setup.py 의 entry_points 는 --node-name 이 만든 한 줄('hailo_detect = rpi5_hailo_detect.hailo_detect:main')이면 된다.

✅ 검증 체크포인트

🤔 이해 확인

1. Hailo 를 쓰는 진짜 이유가 "FPS 향상"이 아니라 무엇인가?
CPU 를 비워 주는 것. 자율주행은 인지·SLAM·경로계획·제어가 동시에 돌아야 한다. CPU 로 추론하면 4코어가 포화되어 SLAM 과 제어 루프가 굶고, 전체 시스템이 실패한다. 추론을 전용 칩으로 옮기면 CPU 가 나머지 일에 집중할 수 있다.
2. 검출 결과의 header.stamp 에 추론 완료 시각을 넣으면 무엇이 잘못되는가?
TF 는 그 타임스탬프 시점의 로봇 자세를 조회한다. 추론에 100 ms 가 걸렸다면 로봇은 이미 그만큼 이동했고, 검출된 물체의 위치를 100 ms 뒤의 로봇 자세 기준으로 계산하게 된다. 이동 중이라면 수십 cm 오차가 난다. 촬영 시각을 써야 한다. 그래서 노드는 out.header = msg.header 로 입력 헤더를 통째로 복사한다.
3. 카메라 30 FPS, 추론 15 FPS 일 때 모든 프레임을 처리하면?
큐에 초당 15프레임씩 쌓여 지연이 무한히 증가한다. 1분 뒤에는 30초 전 영상을 보고 판단하게 된다. 주행 중이면 사고다. 구독 depth 를 1 로 두고 처리 중 들어온 프레임은 버려서 항상 최신 프레임만 처리해야 한다.
4. 호스트를 apt upgrade 했더니 "No Hailo device found" 가 났다. 원인은?
호스트의 hailo_pci 드라이버와 HailoRT 가 업그레이드됐지만 컨테이너의 libhailort/wheel 은 그대로라 버전이 어긋난 것. 같은 버전의 .deb/.whl 을 받아 컨테이너 쪽을 맞춘다 — A: Dockerfile 의 HAILORT_VERSION 을 바꿔 재빌드, B: 컨테이너에서 설치 (02 단계 §2-2). ROS 코드는 원인이 아니다.
5. "전방 1.2 m 에 사람이 있다"를 알려면 카메라와 라이다는 각각 무엇을 담당하는가?
카메라(+Hailo)는 "무엇인가"(사람)를, 라이다는 "얼마나 먼가"(1.2 m)를 담당한다. 두 정보를 합치려면 camera_optical_link 와 laser_link 사이 TF 가 정확해야 한다 — 05 단계의 실측이 여기서 쓰인다. 10 단계에서 다룬다.
6. .hef 와 ONNX 의 출력 형식 차이가 노드 구조에 어떤 영향을 주는가?
ONNX 는 raw 텐서([1,84,8400])라 노드가 NMS 를 해야 하고, .hef 는 대개 NMS 가 포함되어 박스 리스트가 나온다(좌표 순서·정규화도 다를 수 있다). 그래서 08b 의 파서를 재사용할 수 없고, 노드를 "ROS 배선"과 "백엔드"로 나눈 뒤 백엔드 계약을 infer(rgb) → [(x1,y1,x2,y2,score,cls)] 원본 픽셀 좌표로 고정한다. 차이는 백엔드 안에서 흡수되고, 그 덕분에 FakeBackend 로 ROS 쪽을 먼저 검증할 수 있다.
7. 호스트에서는 import hailo_platform 이 되는데 컨테이너에서는 안 된다. 왜인가?
호스트 hailo-all 이 설치한 Python 바인딩은 호스트 Python(3.13) 용이고, 컨테이너는 Ubuntu 22.04 의 Python 3.10 이다. wheel 은 Python 버전별로 다르므로 같은 HailoRT 버전의 cp310 wheel 을 따로 받아 Dockerfile 에서 설치해야 한다. 버전은 같되 빌드 대상이 다른 파일이다.
8. 이 단계에서 overlay 노드와 감독 노드를 한 줄도 고치지 않은 것이 왜 중요한가?
인터페이스(/detections, vision_msgs/Detection2DArray, 같은 파라미터 이름)가 계약이고 백엔드는 그 계약의 구현이기 때문이다. 하위 노드가 백엔드를 모르므로 CPU ↔ Hailo 교체가 런치 인자 하나로 끝난다. 03 단계의 "느슨한 결합"이 실제로 시간을 절약해 준 첫 사례다. 나중에 C++ HailoRT 나 다른 가속기로 옮겨도 마찬가지다.
