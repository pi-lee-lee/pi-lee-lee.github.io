2. 원리 — 왜 주소 하나로 죽은 자리를 알 수 있는가

2-1. 예외에 들어가는 순간 CPU 가 스택에 남기는 것

Cortex-M 은 예외(인터럽트 · fault)에 들어갈 때 소프트웨어의 도움 없이 레지스터 여덟 개를 그때 쓰던 스택에 밀어 넣는다. 핸들러가 C 함수처럼 생겨도 되는 이유가 이것이다 — 호출 규약이 "함수가 망가뜨려도 되는 레지스터"로 정한 것들을 CPU 가 미리 치워 준다. 우리에게 중요한 것은 그 여덟 칸 가운데 두 칸이다.

 자리 (SP 기준)   내용     hardfault_frame_t 의 칸
 SP + 0x1C        xPSR     xpsr     ← 가장 먼저 밀려 들어간다 (가장 높은 주소)
 SP + 0x18        PC       pc       ← 돌아갈 주소 = "어디서 죽었는가"
 SP + 0x14        LR       lr       ← 죽은 함수를 부른 쪽으로 돌아갈 주소 = "누가 불렀는가"
 SP + 0x10        R12      r12
 SP + 0x0C        R3       r3
 SP + 0x08        R2       r2
 SP + 0x04        R1       r1
 SP + 0x00        R0       r0       ← 예외 진입 직후의 SP 가 여기를 가리킨다

이 순서를 직접 확인할 수 있는 자리가 H7 팩 안에 있다. FreeRTOS 의 Cortex-M7 포트는 새 태스크를 만들 때 "예외에서 막 돌아올 것처럼" 가짜 프레임을 손으로 쌓는다 — $FW_H7/Middlewares/Third_Party/FreeRTOS/Source/portable/GCC/ARM_CM7/r0p1/port.c:198-206 에 위에서부터 xPSR · PC · LR · (R12 · R3 · R2 · R1) · R0 순서가 주석과 함께 적혀 있다. 이 가이드는 RTOS 를 쓰지 않지만 프레임의 생김새를 보여 주는 1차 자료로는 충분하다.

핸들러 안의 LR 은 돌아갈 주소가 아니다. 예외에 들어가면 CPU 는 LR 에 EXC_RETURN 이라는 특수한 값을 넣는다. 값의 목록은 $FW_H7/Drivers/CMSIS/Include/core_cm7.h:1863-1868 에 있다.

0xFFFFFFF1EXC_RETURN_HANDLER다른 핸들러 안에서 예외가 났다. 돌아가면 MSP 를 쓴다
0xFFFFFFF9EXC_RETURN_THREAD_MSP보통 코드(thread)에서 났고 그 코드는 MSP 를 쓰고 있었다
0xFFFFFFFDEXC_RETURN_THREAD_PSP보통 코드에서 났고 그 코드는 PSP 를 쓰고 있었다(RTOS 의 태스크)
0xFFFFFFE1 · E9 · ED…_FPU위 셋과 같고, 부동소수 상태까지 같이 쌓였다

F9 와 FD 를 이진수로 적어 보면 다른 비트는 하나뿐이다(1001 ↔ 1101). 그 비트가 "프레임이 어느 스택에 있는가"를 말해 준다 — 어느 비트인지는 §3-2-3 에서 직접 찾아 호스트 시험으로 확인한다. 이 가이드의 펌웨어는 RTOS 가 없어서 리셋 뒤 줄곧 MSP 하나만 쓴다. 그래서 실제로 보게 될 값은 0xFFFFFFF9 계열이다. 그래도 PSP 쪽을 한 줄로 같이 다루는 까닭은 비용이 한 줄이고, 다루지 않으면 나중에 스택을 나누는 날 핸들러가 조용히 틀린 주소를 읽기 때문이다.

등급 — 추정

_FPU 값이 찍히는 경우(부동소수 연산을 한 뒤의 fault)에도 앞의 여덟 칸의 자리는 같고 그 뒤에 부동소수 레지스터가 더 쌓인다는 것은 Cortex-M 의 일반 동작으로 알려진 것이다. 이 Mac 에는 Arm 의 구조 문서가 없어 1차 출처로 확인하지 못했다. 내 보드에서 exc_return 이 E9 로 찍히면 그때의 pc 가 여전히 옳은 함수를 가리키는지 노트에 적어 둔다.

그래서 핸들러는 "프롤로그 없는" 함수여야 한다. 프레임의 주소는 "예외 진입 직후의 SP"다. 그런데 C 컴파일러는 함수 첫머리에 자기 몫의 레지스터를 스택에 밀어 넣는 코드(프롤로그)를 붙인다 — 그 순간 SP 가 움직인다. 이 Mac 의 CubeCLT GCC 14.3.1 로 -O0 빌드한 HardFault_Handler 를 역어셈블해 보면 첫 두 명령이 push {r7} · add r7, sp, #0 다. SP 가 4 바이트(한 칸) 내려갔으므로, 그 뒤에 읽은 SP 를 프레임의 시작으로 믿으면 모든 칸이 한 칸씩 밀린다 — pc 칸에 실제로는 LR 이 들어온다. 죽은 자리가 아니라 "죽은 함수를 부른 쪽"을 가리키게 되는데, 그럴듯한 코드 주소라서 틀린 줄도 모르기 쉽다. 밀리는 칸 수는 컴파일러 · 최적화 수준 · 핸들러 본문에 따라 달라진다.

GCC 의 naked 속성은 프롤로그 · 에필로그를 만들지 않게 한다. 생성물의 void HardFault_Handler(void) 정의 자체는 고칠 수 없지만(USER CODE 블록 밖이다), GCC 는 앞선 선언에 붙인 속성을 뒤의 정의에 합친다. 그래서 USER CODE BEGIN PFP 블록에 void HardFault_Handler(void) __attribute__((naked)); 한 줄을 두면 된다. 속성이 실제로 먹었는지는 믿지 말고 역어셈블로 본다(§3-2-4) — 첫 명령이 push 가 아니어야 한다.

왜 생성물에 손을 대는가

이 가이드의 규칙은 "내 코드는 전부 User/, 생성물에는 호출 한 줄"이다(firmware/README.md 규칙 1). HardFault 핸들러는 그 예외 셋 가운데 하나다 — 벡터 테이블이 가리키는 HardFault_Handler 의 정의가 생성물 Core/Src/stm32h7xx_it.c 안에 있어서, User/ 에 같은 이름을 또 정의하면 링크에서 부딪힌다. 그래서 생성물에는 USER CODE 블록 세 군데에 몇 줄만 두고(포함 한 줄 · 선언 한 줄 · 어셈블리 네 줄) 나머지는 전부 User/Src/Tools/hardfault.c 로 뺀다.

하나 더. HardFault 핸들러는 설정할 수 있는 어떤 인터럽트보다도 우선순위가 높다(고정). 그 안에서는 SysTick 이 끼어들지 못하므로 HAL_GetTick() 이 멈춘다. HAL_Delay() 는 그 값이 늘기를 기다리는 빈 루프라서(stm32h7xx_hal.c:405-419) 영원히 돌아오지 않는다. fault 핸들러에서 쓸 수 있는 것은 "기다리지 않는" 동작뿐이다 — 메모리에 적기, 핀 하나 켜기, 폴링 송신.

2-3. 디버거로 멈춰도 주변장치는 계속 돈다

중단점에서 멈추는 것은 CPU 코어다. 타이머 · 워치독 같은 주변장치는 자기 클럭으로 계속 돈다. 멈춘 동안에도 도는 것과 서는 것을 가르면 이렇다.

2-4. V2 모드에는 글자 창이 없다 — 그때 남는 창이 gdb 다

이 가이드는 VCP 하나를 빌드 스위치 LINK_MODE 로 두 가지 용도에 쓴다. TEXT 모드에서는 명령 창(CLI)과 LOG_* 글자가 나가고, V2 모드에서는 Pi 와 주고받는 이진 프레임만 나간다. V2 에서 글자가 한 줄이라도 새면 프레임이 깨지므로 LOG_* 는 컴파일 단계에서 사라진다. 그리고 계약 v2 에는 바퀴별 카운트 · 듀티 · 수신 오류 카운터 같은 벤치 관측값이 없다(06a §4-2) — 그것을 보려고 계약을 넓히지도 않는다.

그러면 V2 모드에서 "CRC 오류가 몇 번 났는가", "수신이 몇 번 재무장됐는가"를 무엇으로 보는가. 모듈 안의 static 카운터를 gdb 로 읽는다. 그래서 이 쪽의 실습 A 가 일부러 static 변수를 읽고 바꾸는 것으로 되어 있다.

  • 이 가이드의 규칙은 "전역 변수를 모듈 밖으로 내놓지 않는다"다. gdb 에게는 상관없다 — static 도 ELF 의 심볼 표에 있으므로 p s_loop_count 로 읽힌다. 같은 이름이 여러 파일에 있으면 p 'app.c'::s_loop_count 처럼 파일을 짚는다.
  • gdb 는 CPU 를 세운 동안에만 메모리를 읽는다(이 쪽에서 쓰는 방식 기준). 카운터를 읽는 그 짧은 동안 제어 루프도 선다 — §2-3 의 예고 상자가 V2 모드에서 그대로 적용된다. fw-18 이 모터를 돌리는 절에서 gdb 를 쓸 때 이 조건을 다시 확인한다.
  • 보드를 리셋하지 않고 나중에 붙는 방법이 있다. ST-LINK_gdbserver 의 -g(--attach) — "리셋이나 새 프로그램 다운로드 없이 돌고 있는 프로그램에 붙는다"(UM2576 §1.1). 이미 이상해진 보드의 카운터와 s_last 를 현장 그대로 읽는 길이다. 실습 B 의 마지막에 해 본다.
  • SWD 와 VCP 는 USB 케이블 한 가닥을 같이 쓴다(ST-LINK/V3E, UM2407 §7.3). 벤치에서는 그 케이블이 Mac 에 꽂혀 있어 둘 다 Mac 의 것이지만, 조립 뒤에는 Pi 에 꽂힌다 — 그때 gdb 를 붙이려면 케이블을 Mac 으로 옮기거나 Mac 을 로봇 곁에 둬야 한다. 조립 뒤의 재플래시 · 관측 동선을 어떻게 할지는 fw-20 에서 정하는 결정 대기 항목이다.
  • 코드가 읽지 않고 쓰기만 하는 변수는 최적화 빌드에서 컴파일러가 저장을 줄이거나 없앨 수 있다(C 언어가 허용한다). 이 Mac 의 GCC 14.3.1 -Os 로 작은 예를 컴파일했을 때는 저장이 남아 있었지만, 그것은 보장이 아니다. gdb 로만 읽을 변수의 저장을 보장받고 싶으면 volatile 로 선언한다 — 대가는 그 변수에 대한 최적화를 포기하는 것이다.

3. 실습

실습은 둘이다. A 는 붙어서 멈추고 읽고 바꾸는 것, B 는 일부러 죽이고 죽은 자리를 이름으로 바꾸는 것. 끝자리 번호의 뜻은 다른 쪽과 같다(1 = CubeMX, 2 = 골격, 3 = 직접 채우기, 4 = 굽고 보기). 빌드와 플래시는 fw-02 가 만든 firmware/tools/build.sh · firmware/tools/flash.sh 만 부른다. 모터 드라이버 · 센서는 아무것도 꽂지 않는다.

3-1-3. 직접 채우기

  1. 위의 TODO 셋을 채운다. 막히면 아래 카드 T1 ~ T3 을 연다. fw-02 의 app_loop() 는 기다리지 않고 곧바로 돌아오는 함수라서 1 초에도 수없이 불린다 — s_loop_count 는 "LD1 이 뒤집힌 횟수"가 아니라 "주 루프가 돈 바퀴 수"다.
  2. Debug 프리셋으로 빌드되는지 확인한다. Release 는 -Os -g0 이라 변수도 줄 번호도 ELF 에 없다(§2-2). fw-02 의 build.sh 는 FW_PRESET 을 따로 주지 않으면 Debug 다 — 셸에 FW_PRESET=Release 가 남아 있지 않은지만 본다(echo $FW_PRESET).
  3. gdbserver 가 ST-LINK 를 잡고 있는 동안에는 flash.sh 가 실패한다(둘 다 같은 ST-LINK 를 쓴다 — UM2576 부록 A 의 오류 코드 1 "something is already connected to the board, such as STM32CubeProgrammer"). 순서는 굽고 → 서버를 띄운다. 다시 구우려면 서버를 먼저 끈다. 다른 길도 있다: gdb 안에서 load 를 치면 gdbserver 가 STM32CubeProgrammer 를 불러 직접 굽는다(UM2576 §2.3). 어느 쪽이든 결과는 같다(동일). 이 가이드는 굽는 길을 flash.sh 하나로 두려고 앞의 순서로 적는다.

위 걸음과 골격의 번호가 이렇게 짝을 이룬다: 걸음 1 = T1 · T2 · T3. 막힌 자리의 카드를 연다 — 카드는 접혀 있을 뿐 잠겨 있지 않다.

힌트 T1 — app_init() · s_blink_ms 에 fw-02 의 주기를 넣는다

할 일 — 입력은 없다. 끝났을 때 참이어야 하는 것: s_blink_ms 에 fw-02 에서 고른 주기 [ms] 가 들어 있고, 그 숫자(또는 이름)는 코드에서 이 한 곳에만 나온다. app_init() 은 main() 이 모든 MX_*_Init() 뒤에 한 번 부른다(fw-02).

완결 코드

/* 완결 코드 T1 - User/Src/app.c 의 app_init() 안 */
  s_blink_ms = HEARTBEAT_MS;               /* fw-02 에서 고른 주기 [ms]. 이름은 fw-02 에서 쓴 것 그대로 */

코드 설명

  • s_blink_ms = HEARTBEAT_MS; — HEARTBEAT_MS 는 fw-02 의 app_loop() 에서 비교에 썼던 그 이름이다. fw-02 에서 매크로 이름을 다르게 지었으면 그 이름을, 숫자를 그대로 썼으면 그 숫자를 적는다. 이 가이드가 숫자를 적지 않은 것은 주기가 학습자의 선택이기 때문이다(fw-02 §3-3-3).
  • 왜 app_init() 에 있는가 — static 변수는 .bss 에 있어 부팅 때 0 으로 시작한다. 0 이면 T3 의 비교 (now - last) >= 0 이 늘 참이라 LD1 이 바퀴마다 뒤집힌다(눈에는 어둡게 켜진 것처럼 보인다). 첫 바퀴 전에 값이 있어야 하므로 초기화 자리인 app_init() 이다.
  • volatile(선언에 있다) — "이 변수는 컴파일러가 모르는 사이에 바뀔 수 있으니 매번 메모리에서 다시 읽어라". fw-05 T2 에서는 ISR 이 바꾸는 변수에 붙였고, 여기서는 gdb 가 바꾼다. 없으면 T3 의 비교에서 컴파일러가 값을 레지스터에 들고 있어 gdb 가 써 넣은 새 값이 반영되지 않을 수 있다(-O0 에서는 대개 반영되지만 보장이 아니다 — §2-4 마지막 항목).
  • 다르게 써도 되는 곳 — 선언에서 바로 static volatile uint32_t s_blink_ms = HEARTBEAT_MS; 로 초기화해도 된다(동일). 그때는 app_init() 의 이 줄이 없다.

힌트 T2 — app_loop() · 이번 바퀴를 센다

할 일 — app_loop() 가 불릴 때마다 s_loop_count 가 정확히 1 는다. 끝났을 때 참이어야 하는 것: hbreak app_loop 에서 continue 할 때마다 p s_loop_count 가 1 씩 는다. 펌웨어 안에서는 아무도 이 값을 읽지 않는다 — gdb 만 읽는다(§2-4).

완결 코드

/* 완결 코드 T2 - User/Src/app.c 의 app_loop() 첫 줄 */
  s_loop_count++;                          /* 한 바퀴 = 1. LD1 이 뒤집힌 횟수가 아니다 */

코드 설명

  • s_loop_count++; — x++ 는 "x 를 1 올린다"(x = x + 1 과 같다). 변수가 32비트라 넘치면 0 으로 돌아가지만 이 쪽의 쓸모(두 값의 차가 1 인가)에는 지장이 없다.
  • 왜 함수의 첫 줄인가 — 어떤 if 안에도 들어가지 않아야 "주 루프가 돈 바퀴 수"가 된다. 심박의 if 안에 넣으면 "LD1 이 뒤집힌 횟수"가 되어 §3-1-4 의 continue 한 번에 1 이 아니라 거의 늘 같은 값이 나온다.
  • volatile 이 없다 — 쓰기만 하는 변수는 최적화 빌드에서 저장이 줄거나 사라질 수 있다(§2-4 마지막 항목). Debug(-O0) 빌드에서는 남는다. 다르게 써도 되는 곳: gdb 로만 읽을 변수의 저장을 Release 에서도 보장받고 싶으면 선언에 volatile 을 붙인다 — 대가는 그 변수에 대한 최적화를 포기하는 것이다.

힌트 T3 — app_loop() · 상수 대신 s_blink_ms 와 비교한다

할 일 — fw-02 의 심박 코드는 그대로 두고, 비교에 쓰던 상수 한 자리만 변수 s_blink_ms 로 바꾼다. 끝났을 때 참이어야 하는 것: gdb 가 s_blink_ms 에 다른 값을 써 넣으면 다음 뒤집기부터 주기가 바뀐다 — 다시 굽지 않고.

완결 코드

/* 완결 코드 T3 - User/Src/app.c 의 app_loop() 안, fw-02 의 심박을 고친 모습 */
  static uint32_t last_ms;                 /* 마지막으로 뒤집은 시각 [ms], 부팅 때 0 */
  uint32_t now_ms = HAL_GetTick();

  if ((uint32_t)(now_ms - last_ms) >= s_blink_ms) {   /* fw-02 의 HEARTBEAT_MS 자리에 변수 */
    last_ms = now_ms;
    HAL_GPIO_TogglePin(LD1_GPIO_Port, LD1_Pin);
  }

코드 설명

  • 이 블록은 fw-02 §3-3-3 에서 쓴 심박 그대로다 — 바뀐 글자는 >= HEARTBEAT_MS 가 >= s_blink_ms 로 된 것 하나다. fw-02 에서 변수 이름을 다르게 지었으면 그대로 둔다.
  • static uint32_t last_ms; — 함수 안의 static: 함수가 돌아가도 값이 남는다(fw-05 T9 와 같다). 초기값은 0.
  • (uint32_t)(now_ms - last_ms) >= s_blink_ms — 부호 없는 뺄셈은 HAL_GetTick() 이 32비트 끝에서 0 으로 돌아가도 차가 맞다(fw-02 이해 확인 4). 오른쪽이 volatile 변수라서 컴파일러는 비교할 때마다 메모리에서 다시 읽는다 — gdb 가 써 넣은 값이 바로 다음 비교에 보인다. 이 비교가 루프 안에 있어야 하는 이유다(증상 표 "변수를 읽는 자리가 루프 밖이다").
  • 왜 상수를 두 자리에 두지 않는가 — app_init() 의 대입(T1)과 여기의 비교에 같은 매크로가 둘 다 남아 있으면 gdb 가 변수를 바꿔도 비교는 상수를 본다. 숫자는 T1 한 곳, 여기는 변수.
  • 다르게 써도 되는 곳 — fw-02 에서 열어 둔 선택 그대로다: last_ms = now_ms 와 last_ms += s_blink_ms(앞의 것은 루프가 늦으면 늦은 만큼 밀리고, 뒤의 것은 평균 주기를 지키는 대신 오래 멈췄다 돌아오면 밀린 만큼 연달아 뒤집는다 — LED 에서는 어느 쪽이든 된다(동일)), TogglePin 과 "상태 변수 + WritePin"(동일).

쓰는 API — 둘 다 fw-02 에서 쓴 것이다. uint32_t HAL_GetTick(void)(stm32h7xx_hal.c:338, __weak): SysTick 핸들러가 1 ms 마다 올리는 uwTick 을 돌려준다, 인자 없음. void HAL_GPIO_TogglePin(GPIO_TypeDef *GPIOx, uint16_t GPIO_Pin)(stm32h7xx_hal_gpio.h:267): 핀 하나를 뒤집는다, 반환 없음. 문맥은 둘 다 주 루프.

남는 while (1) — GCC 에서만 통하는 꼴이다

생성물의 while (1) 은 USER CODE 밖이라 지울 수 없다. 그래서 어셈블리를 채운 뒤에도 naked 함수 안에 C 문장 하나가 남는다. GCC 매뉴얼(14.3, §6.33.5 ARM Function Attributes 의 naked)은 "basic asm 만 안전하고, basic asm 과 C 코드를 섞는 것은 동작하는 것처럼 보여도 지원되지 않는다"고 적는다. 이 Mac 의 CubeCLT GCC 14.3.1 은 -O0 · -Os 모두 경고 없이 그 문장을 b.w hardfault_capture 뒤의 도달하지 않는 b.n 한 줄로 만든다(§3-2-4 ① 의 역어셈블에서 보인다) — b.w 가 돌아오지 않으므로 동작에는 지장이 없다. 같은 CubeCLT 에 든 starm-clang 21.1.1 은 같은 소스에 error: non-ASM statement in naked function is not supported 를 내고 while (1) 줄을 가리킨다(이 Mac 에서 확인). 툴체인을 GCC 밖으로 바꾸는 날에는 이 핸들러의 방법을 다시 정해야 한다.

  1. 호스트 시험부터 만든다. 아래 파일을 firmware/host_tests/test_hardfault.c 로 둔다(디렉터리가 없으면 만든다). 골격 그대로 돌리면 첫 assert 에서 멈춘다 — 정상이다.
  2. hardfault_decode() 를 채운다. §2-1 의 그림이 곧 답의 재료다. 시험의 case 1 이 통과하면 자리가 맞은 것이다.
  3. hardfault_frame_on_psp() 를 채운다. 0xFFFFFFF9 와 0xFFFFFFFD 를 이진수로 적어 다른 비트를 찾는다. case 3 이 _FPU 값과 핸들러 값까지 넣어 확인한다.
  4. hardfault_capture() 를 채운다. 힌트: fault 상태 레지스터는 CMSIS 의 SCB->CFSR · SCB->HFSR(core_cm7.h:470-471). LD3 는 fw-02 에서 단 User Label 로 켠다(HAL_GPIO_WritePin). 콘솔이 있으면 LOG_ERR("hardfault", …) 한 줄 — 값은 %08lx 에 (unsigned long) 으로 넘긴다. HAL_Delay 나 "기다리는" 호출을 넣지 않는다(§2-1 끝). "ISR 안에서 LOG_* 를 부르지 않는다"는 fw-03 의 규칙에 이 한 줄은 예외다 — 그 규칙의 이유는 블로킹 송신이 ISR 을 붙잡아 다른 일을 늦춘다는 것인데, fault 핸들러는 돌아가지 않는 막다른 길이라 늦출 것이 남아 있지 않다(FW_ASSERT 가 글자를 찍고 멈추는 것과 같은 자리다).
  5. HardFault_Handler 의 어셈블리 네 줄을 쓴다. 힌트: GCC 인라인 어셈블리는 __asm volatile ("… \n" "… \n"); 꼴이고, 스택 포인터 둘은 mrs r0, msp 같은 특수 레지스터 읽기 명령으로 꺼낸다. 마지막은 bl(돌아올 주소를 LR 에 적는 호출)이 아니라 b(그냥 건너뜀)다. 돌아올 일이 없으므로 b 로 충분하고, bl 은 LR 의 EXC_RETURN 을 덮어쓴다 — 값은 이미 r2 로 옮겼으니 포획에는 지장이 없지만, gdb 가 bt 에서 예외 경계를 알아볼 단서가 LR 에서 사라진다 [추정 — gdb 의 동작]. 인자 셋이 r0 · r1 · r2 로 가는 까닭은 C 호출 규약이 앞의 네 인자를 그 순서로 r0~r3 에 받기 때문이다.

힌트 T4 — hardfault_frame_on_psp() · EXC_RETURN 의 비트 하나로 스택을 고른다

할 일 — 입력은 핸들러 안에서 본 LR(EXC_RETURN, §2-1 의 표). 출력은 "프레임이 PSP 에 쌓였는가". 끝났을 때 참이어야 하는 것: 0xFFFFFFF9 · E9 · F1 → false, FD · ED → true — 호스트 시험 case 3 의 다섯 줄 그대로다. 순수 함수라 Mac 에서 채점한다.

완결 코드

/* 완결 코드 T4 - User/Inc/Tools/hardfault.h */
static inline bool hardfault_frame_on_psp(uint32_t exc_return)
{
  /* 0xFFFFFFF9 = ...1001, 0xFFFFFFFD = ...1101 - 다른 자리는 bit 2 하나다. 1 이면 PSP. */
  return (exc_return & (1u << 2)) != 0u;
}

코드 설명

  • 이진수로 적어 본다: F9 = 1111 1001, FD = 1111 1101. 다른 자리는 오른쪽에서 셋째, bit 2(값 4) 하나다. _FPU 값(E9 = 1110 1001, ED = 1110 1101)도 같은 자리가 가른다 — 그래서 값 전체가 아니라 비트 하나를 본다.
  • 1u << 2 — 1 을 왼쪽으로 두 칸 민 값, 0b100 = 4. "bit n" 을 숫자로 적는 관용구다(fw-05 의 & (N - 1) 과 같은 비트 연산). & 는 비트 AND — 그 자리만 남기고 나머지는 0 으로 만든다.
  • != 0u — 남은 값(0 또는 4)을 참 · 거짓으로 바꾼다. C 에서는 0 이 아닌 값이 곧 참이라 이 비교가 없어도 동작은 같지만(동일 — 시험도 통과한다), "비트 검사의 결과를 bool 로 만든다"는 뜻이 글자로 남는다.
  • 다르게 써도 되는 곳 — ① exc_return & 0x4u(동일). ② 이 판단을 C 가 아니라 HardFault_Handler 의 어셈블리에서 해도 된다: tst lr, #4 · ite eq · mrseq r0, msp · mrsne r0, psp 로 골라 r0 하나만 넘기는 꼴(이 Mac 의 arm-gcc 14.3.1 로 어셈블됨을 확인). 그러면 hardfault_capture() 의 인자가 둘(stacked · exc_return)로 줄지만, 스택 고르기가 호스트 시험 밖으로 나간다. 이 가이드는 시험이 닿게 C 에 뒀다 — 둘 다 된다. ③ EXC_RETURN_THREAD_PSP 와 == 로 견주는 것은 안 된다 — case 3 의 _FPU 줄에서 멈춘다(아래 표).

힌트 T5 — hardfault_decode() · 스택의 여덟 워드를 구조체로 옮긴다

할 일 — 입력 stacked 는 예외 진입 직후의 SP 가 가리키던 주소(§2-1 그림의 맨 아래칸, 가장 낮은 주소). 출력 인자 out 에 여덟 칸을 순서대로 채운다. 끝났을 때 참이어야 하는 것: out->pc == stacked[6], out->lr == stacked[5] — 호스트 시험 case 1 이 여덟 칸 전부를, case 2 가 "한 칸 밀림"의 모양을 채점한다.

완결 코드

/* 완결 코드 T5 - User/Inc/Tools/hardfault.h */
static inline void hardfault_decode(const uint32_t *stacked, hardfault_frame_t *out)
{
  out->r0   = stacked[0];                  /* SP + 0x00 - 예외 진입 직후의 SP 가 가리키는 칸 */
  out->r1   = stacked[1];
  out->r2   = stacked[2];
  out->r3   = stacked[3];
  out->r12  = stacked[4];
  out->lr   = stacked[5];                  /* SP + 0x14 - 누가 불렀는가 */
  out->pc   = stacked[6];                  /* SP + 0x18 - 어디서 죽었는가 */
  out->xpsr = stacked[7];                  /* SP + 0x1C - 가장 먼저 밀려 들어간 칸 */
}

코드 설명

  • stacked[0] — 포인터에 [i] 를 붙이면 "그 주소에서 i 번째 칸"이다(*(stacked + i) 와 같다 — fw-07 T3 에서 포인터에 정수를 더한 것과 같은 규칙). uint32_t 포인터라 한 칸 = 4 바이트 = 그림의 SP + 0x04 한 줄이다.
  • out->r0 — -> 는 포인터로 받은 구조체의 칸(fw-05 T2 와 같다). const uint32_t *stacked 의 const 는 "이 함수는 스택을 읽기만 한다"(fw-07 T4 와 같다).
  • 순서 — §2-1 의 그림을 아래에서 위로 읽은 것이다. 그림은 높은 주소가 위라서 xpsr 이 맨 위에 있지만 인덱스는 7 이다. FreeRTOS 포트가 같은 순서로 프레임을 손으로 쌓는 자리(port.c:198-206)에서 확인할 수 있다.
  • 왜 여덟 줄을 따로 쓰는가 — 칸 이름과 인덱스가 한 줄에 같이 보인다. case 2 가 재현하는 "한 칸 밀려 pc 칸에 lr 이 들어온다"를 읽을 때 어느 칸이 어디서 왔는지 눈으로 좇을 수 있다.
  • 다르게 써도 되는 곳 — memcpy(out, stacked, sizeof *out); 한 줄(#include <string.h> 가 필요하다). 구조체의 칸이 선언 순서대로 틈 없이 놓인다는 것(uint32_t 여덟 개)에 기댄다. 시험과 sanitizer 모두 통과한다(2026-10-04 확인) — 둘은 같다(동일).

쓰는 API — 없다(순수 헤더).

힌트 T6 — hardfault_capture() · 프레임을 보관하고, 알리고, 머문다

할 일 — 누가 부르는가: HardFault_Handler 의 어셈블리(T8)가 b 로 건너온다. 인자는 r0 = MSP, r1 = PSP, r2 = EXC_RETURN. 문맥은 핸들러 모드, 설정할 수 있는 어떤 인터럽트도 끼어들지 못한다 — SysTick 이 멈추므로 HAL_Delay() 는 못 쓴다(§2-1 끝). 끝났을 때 참이어야 하는 것: s_last 에 프레임 사본 · exc_return · CFSR · HFSR 이 들어 있고 count 가 1 늘었다, LD3 가 켜졌다, (fw-03 을 했으면) 콘솔에 E hardfault: 한 줄. 그리고 돌아가지 않는다.

완결 코드

/* 완결 코드 T6 - User/Src/Tools/hardfault.c */
#include "Tools/log.h"                     /* 파일 머리의 include 들 곁에 - fw-03 을 마친 경우에만(LOG_ERR) */

void hardfault_capture(const uint32_t *msp, const uint32_t *psp, uint32_t exc_return)
{
  const uint32_t *stacked = hardfault_frame_on_psp(exc_return) ? psp : msp;   /* 걸음 1 */

  hardfault_decode(stacked, &s_last.frame);                                    /* 걸음 2 */
  s_last.exc_return = exc_return;
  s_last.cfsr  = SCB->CFSR;
  s_last.hfsr  = SCB->HFSR;
  s_last.count++;

  HAL_GPIO_WritePin(LD3_GPIO_Port, LD3_Pin, GPIO_PIN_SET);                      /* 걸음 3 */
  LOG_ERR("hardfault", "pc=%08lx lr=%08lx cfsr=%08lx hfsr=%08lx",
          (unsigned long)s_last.frame.pc, (unsigned long)s_last.frame.lr,
          (unsigned long)s_last.cfsr, (unsigned long)s_last.hfsr);

  for (;;) { }                                                                 /* 걸음 4 - 돌아가지 않는다 */
}

  • #include "Tools/log.h" — 파일 머리의 #include "main.h" 곁에 둔다. fw-03 을 아직 안 했으면 이 줄과 LOG_ERR 석 줄을 뺀다. V2 빌드에서는 LOG_ERR 이 ((void)0) 으로 사라지므로(fw-03) 그대로 둬도 된다.
  • const uint32_t *stacked = hardfault_frame_on_psp(exc_return) ? psp : msp; — a ? b : c 는 "a 가 참이면 b, 아니면 c"(삼항 연산자). if / else 로 써도 같다(동일). 판단을 T4 에 맡겨 두었으므로 여기는 고르기만 한다 — 걸음 1.
  • hardfault_decode(stacked, &s_last.frame); — &s_last.frame 은 "구조체 s_last 안의 구조체 frame 의 주소"(출력 인자, fw-05 T3 와 같다). s_last 는 포인터가 아니라 변수라서 . 이다.
  • SCB->CFSR · SCB->HFSR — SCB 는 CMSIS 가 준 포인터 매크로(core_cm7.h:1787)라 -> 다. 잡은 순간에 읽어 둔다 — gdb 없이 현장에서 죽었을 때 남는 것은 콘솔 한 줄뿐이고, 그 줄은 이 값을 찍는다.
  • s_last.count++; — 이 RAM 이 마지막으로 0 이 된 뒤 몇 번 잡았는가. §3-2-4 ⑤ 에서 "리셋 없이 다시 붙었다"의 증거가 된다(count 가 그대로 1).
  • 순서 — 기록(걸음 2) → 알림(걸음 3) → 머묾(걸음 4). LOG_ERR 이 s_last 의 값을 찍으므로 기록이 먼저다. LD3 는 송신보다 먼저 켠다 — 송신이 어떤 이유로든 막혀도(증상 표의 HAL_BUSY) LED 는 켜져 있게.

  • LOG_ERR("hardfault", "pc=%08lx …", (unsigned long)…) — %08lx 는 "소문자 16진수, 8 자리, 앞을 0 으로". (unsigned long) 캐스트는 fw-05 T9 와 같다 — arm-gcc 에서는 uint32_t 가 이미 unsigned long 이라 캐스트 없이도 경고가 없지만(2026-10-04 확인), Mac 의 cc 에서는 다른 형이라 경고가 난다. 두 환경에서 같은 글자가 통하도록 붙인다. "ISR 에서 LOG_* 금지"의 예외인 까닭은 §3-2-3 걸음 4.
  • for (;;) { } — 골격에 있던 줄 그대로. 돌아가면 CPU 가 pc 의 명령을 다시 실행해 또 fault 가 난다. 다르게 써도 되는 곳 — 머무는 대신 NVIC_SystemReset() 을 불러 곧바로 다시 부팅하는 꼴도 있다. 빨리 되살아나는 대신 s_last 가 지워지고(.bss), 원인이 부팅 직후에 있으면 리셋이 끝없이 되풀이된다. 이 가이드는 머문다 — 현장이 보존되어 -g 로 나중에 붙을 수 있다(⑤). fw-06 뒤에는 IWDG 가 이 루프를 리셋으로 끝낸다(디버거로 동결해 두지 않는 한). 둘은 설계 선택이다.

힌트 T7 — hardfault_poll() · gdb 가 요청하면 일부러 죽는다

할 일 — app_loop() 가 바퀴마다 부른다. 입력은 s_trap_request(gdb 가 set var s_trap_request = 1 로 세운다). 끝났을 때 참이어야 하는 것: 요청이 있었으면 그것을 0 으로 지우고 fault 를 낸다(돌아오지 않는다); 없었으면 아무것도 하지 않고 곧바로 돌아온다(주 루프를 막지 않는다).

완결 코드

/* 완결 코드 T7 - User/Src/Tools/hardfault.c */
void hardfault_poll(void)
{
  if (s_trap_request != 0u) {
    s_trap_request = 0u;                   /* 요청을 소비한다 - 트랩 뒤에는 이 줄에 올 수 없으므로 먼저 */
    __builtin_trap();                      /* 컴파일러가 정의되지 않은 명령(udf) 하나를 심는다 -> HardFault */
  }
}

코드 설명

  • if (s_trap_request != 0u) — volatile 변수라서 바퀴마다 메모리에서 다시 읽는다(T1 의 s_blink_ms 와 같은 이유). gdb 가 써 넣은 1 이 다음 바퀴에 보인다. if (s_trap_request) 로 써도 같다(동일).
  • s_trap_request = 0u; 가 먼저인 이유 — 트랩 뒤에는 어떤 줄도 실행되지 않는다. 지우는 줄이 뒤에 있으면 영영 지워지지 않는다. 지우는 까닭: §3-2-4 ⑤ 에서 -g 로 붙어 p s_trap_request 를 치면 0 — "요청은 소비됐고 그 결과가 s_last 다"를 읽을 수 있다.
  • __builtin_trap(); — 함수가 아니라 GCC 내장(built-in)이다. 컴파일러가 "정의되지 않은 명령" 한 개를 심는다 — 이 Mac 의 GCC 14.3.1 은 Thumb 에서 udf #255(기계어 0xdeff)를 낸다(-O0 · -Os 모두, 역어셈블로 확인). UsageFault 를 따로 켜지 않았으므로 HardFault 로 올려 보내진다(§3-2-4 ② 의 cfsr bit 16 · hfsr bit 30). 왜 "없는 주소에 쓰기"가 아닌가는 §3-2-3 걸음 6.
  • 다르게 써도 되는 곳 — 트랩 수단으로 *(volatile uint32_t *)<주소> = 0; 같은 "없는 주소 쓰기"를 쓰는 답도 있다. 그 주소가 이 칩에서 정말 fault 를 내는지(어느 fault 로 오는지)를 먼저 확인해야 한다 — 이 가이드는 그 확인이 필요 없는 __builtin_trap() 하나로 정했다.

코드 설명

  • __asm volatile ( "…" "…" "…" "…" ); — GCC 인라인 어셈블리의 basic 꼴. C 는 나란히 놓인 문자열 리터럴을 하나로 이어 붙이므로 네 문자열이 어셈블러에게는 한 덩어리다. 그래서 문자열 끝마다 \n 이 있어야 어셈블러가 줄을 가른다 — 빠지면 두 명령이 한 줄이 되어 멈춘다(아래 표). volatile 은 "최적화로 빼거나 옮기지 말 것". /* … */ 주석은 문자열 밖(C 쪽)에 있어 어셈블러에게 가지 않는다.
  • mrs r0, msp · mrs r1, psp — mrs = Move from Special Register. MSP · PSP 는 보통 레지스터가 아니라 mov 로 못 읽고 이 명령으로만 읽는다. sp 라고 쓰면 "지금 활성인 쪽" 하나만 보이고 그것이 어느 쪽인지 알 수 없으므로, 둘 다 읽어 C 에서 고른다(T4 · T6 걸음 1).
  • mov r2, lr — LR 은 보통 레지스터라 mov. 핸들러 안의 LR 은 돌아갈 주소가 아니라 EXC_RETURN 이다(§2-1 의 표).
  • 왜 r0 · r1 · r2 인가 — C 호출 규약(AAPCS)은 앞의 네 인자를 r0 ~ r3 에 그 순서로 받는다. hardfault_capture(msp, psp, exc_return) 의 인자 순서와 같아야 한다 — 바꾸면 컴파일러는 모르고 C 함수가 PSP 를 MSP 로 믿는다.
  • b hardfault_capture — b 는 그냥 건너뜀, bl 은 돌아올 주소를 LR 에 적는 호출이다. 돌아올 일이 없으므로 b 로 충분하고, bl 은 LR 의 EXC_RETURN 을 덮어쓴다 — 값은 이미 r2 로 옮겼으니 포획에는 지장이 없지만, gdb 가 bt 에서 예외 경계를 알아볼 단서가 LR 에서 사라진다 [추정 — gdb 의 동작].
  • C 문장이 없다 — naked 함수에는 스택 프레임이 없어 지역변수를 둘 자리가 없다(§2-1). 생성물의 while (1) 은 USER CODE 밖이라 못 지우고, GCC 가 b.w 뒤의 도달하지 않는 b.n 한 줄로 만든다(§3-2-2 끝의 상자, ①의 역어셈블에서 보인다).
  • 다르게 써도 되는 곳 — 스택 고르기를 여기서 하는 꼴(T4 의 "다르게 써도 되는 곳" ②): tst lr, #4 · ite eq · mrseq r0, msp · mrsne r0, psp · mov r1, lr · b …. 인자가 둘로 줄고 C 쪽 시그니처도 바뀐다. 이 가이드는 판단을 C 로 옮겨 호스트 시험이 닿게 했다 — 어셈블리가 짧아지는 대신 인자가 셋이다. 둘 다 된다.

쓰는 API — HAL 은 없다. 명령은 셋뿐이다: mrs(특수 레지스터 읽기) · mov · b. GCC 속성 naked(14.3 매뉴얼 §6.33.5 ARM Function Attributes)는 USER CODE BEGIN PFP 의 선언에 붙어 있고 생성된 정의에 합쳐진다(§2-1).

/* host_tests/test_hardfault.c - 예외 스택 프레임의 인덱스 순서.
 * 프레임 순서: FreeRTOS CM7 포트가 같은 프레임을 손으로 쌓는다. 위에서부터 xPSR, PC, LR, R12, R3..R0
 *   ($FW_H7/Middlewares/Third_Party/FreeRTOS/Source/portable/GCC/ARM_CM7/r0p1/port.c:198-206).
 * EXC_RETURN 값: $FW_H7/Drivers/CMSIS/Include/core_cm7.h:1863-1868. */
#include <assert.h>
#include <stdio.h>
#include "Tools/hardfault.h"

int main(void)
{
  int n = 0;
  uint32_t w[9];
  hardfault_frame_t f;

  /* 워드마다 자기 인덱스를 담는다 - 인덱스가 틀리면 값으로 드러난다 */
  for (uint32_t i = 0; i < 9u; i++) { w[i] = 0xF00D0000u + i; }

  /* case 1: 프레임이 w[0] 에서 시작한다 */
  hardfault_decode(&w[0], &f);
  assert(f.r0 == 0xF00D0000u && f.r1 == 0xF00D0001u && f.r2 == 0xF00D0002u && f.r3 == 0xF00D0003u);
  assert(f.r12 == 0xF00D0004u && f.lr == 0xF00D0005u && f.pc == 0xF00D0006u && f.xpsr == 0xF00D0007u);
  n++;

  /* case 2: 프롤로그가 한 워드를 밀어 넣으면 SP 가 한 워드 내려간다. 진짜 프레임은 w[1] 에 있다;
   * w[0] 에서 풀면 한 칸 어긋나서 'pc' 필드에 진짜 프레임의 LR 이 들어간다. */
  hardfault_decode(&w[1], &f);
  assert(f.lr == 0xF00D0006u && f.pc == 0xF00D0007u);
  hardfault_decode(&w[0], &f);
  assert(f.pc == 0xF00D0006u);
  n++;

  /* case 3: 프레임은 어느 스택에 있는가 */
  assert(hardfault_frame_on_psp(0xFFFFFFF9u) == false);  /* EXC_RETURN_THREAD_MSP     */
  assert(hardfault_frame_on_psp(0xFFFFFFFDu) == true);   /* EXC_RETURN_THREAD_PSP     */
  assert(hardfault_frame_on_psp(0xFFFFFFE9u) == false);  /* EXC_RETURN_THREAD_MSP_FPU */
  assert(hardfault_frame_on_psp(0xFFFFFFEDu) == true);   /* EXC_RETURN_THREAD_PSP_FPU */
  assert(hardfault_frame_on_psp(0xFFFFFFF1u) == false);  /* EXC_RETURN_HANDLER        */
  n++;

  printf("PASS hardfault %d cases\n", n);
  return 0;
}

2. HardFault_Handler 가 평범한 C 함수면 무엇이 어긋나는가? 왜 "그럴듯하게" 틀리는가?

프레임의 주소는 예외 진입 직후의 SP 다. 평범한 C 함수는 첫머리의 프롤로그에서 레지스터를 스택에 밀어 SP 를 옮긴다(-O0 에서 push {r7} — 한 칸). 그 뒤에 읽은 SP 를 프레임의 시작으로 쓰면 모든 칸이 밀려 pc 칸에 원래의 LR 이 들어온다. LR 도 코드 영역의 주소라서 addr2line 은 멀쩡한 함수 이름을 돌려준다 — 죽은 함수가 아니라 그것을 부른 함수를. 오류 메시지가 없으므로 틀린 줄 모르고 엉뚱한 함수를 뒤지게 된다. 그래서 naked 가 먹었는지를 역어셈블로 확인하는 걸음(§3-2-4 ①)과, 일부러 틀려 보는 걸음(④)을 둔다.

3. 스택된 pc · 스택된 lr · 핸들러 안의 LR 레지스터 — 셋은 각각 무엇을 말해 주는가?

스택된 pc = 예외가 끝나면 돌아갈 주소, 곧 "어디서 죽었는가". 스택된 lr = 죽은 함수가 자기 일을 마치면 돌아가려던 주소, 곧 "누가 불렀는가"(bit 0 은 Thumb 표시라 홀수로 보인다). 핸들러 안의 LR 레지스터 = EXC_RETURN. 주소가 아니라 "프레임이 어느 스택에 있고 어떤 모드로 돌아갈 것인가"를 담은 표식이다(core_cm7.h:1863-1868). 셋을 섞으면 증상 표의 두 줄(pc 가 부른 쪽을 가리킨다 / pc 가 0xfffffff9 다)이 된다.

4. Release(-Os -g0) 로 구운 보드가 현장에서 죽었다. 콘솔에 pc=… 한 줄만 남았다. 함수 이름을 알아낼 수 있는가? 조건은?

알아낼 수 있다. -g0 은 디버그 정보(줄 번호 · 변수 · 매크로)를 빼지만 심볼 테이블과 .map 은 남는다. addr2line -f 는 함수 이름을 주고 파일:줄 자리에 ??:? 를 낸다(이 Mac 에서 확인한 출력). .map 의 "시작 + 크기"로도 찾을 수 있다. 조건은 하나다 — 그 보드에 구운 바로 그 빌드의 ELF 나 .map 을 갖고 있어야 한다. 주소는 빌드마다 움직인다. 그래서 배너의 build … 줄(fw-03)과 산출물을 짝지어 보관하는 습관이 값을 한다.

5. 중단점에서 CPU 가 섰다. 그동안 계속 도는 것 둘과, 그래서 생기는 일을 말해 보라. 모터 전원이 들어간 뒤에 중단점을 쓰려면 무엇이 먼저 돼 있어야 하는가?

IWDG 는 자기 클럭으로 계속 센다 — 동결하지 않았으면 생각하는 사이에 보드가 리셋된다(RM0468 §50.3.7, fw-06 에서 동결). TIM1 · TIM8 은 마지막 듀티로 PWM 을 계속 낸다 — 제어 루프 · 보호 · 명령 워치독은 CPU 와 함께 서 있으므로 바퀴를 세울 코드가 없다. 그래서 모터 전원 뒤의 중단점은 fw-08 의 "TIM1 · TIM8 동결 + OSSI + idle LOW"가 끝난 뒤에만 쓴다. 동결하면 고급 타이머의 출력은 MOE = 0 인 것처럼 꺼지고(RM0468 §43.3.29), 핀이 어떤 레벨이 되는가는 OSSI 와 idle 설정이 정한다. 동결 비트는 시스템 리셋으로 지워지지 않는다(전원 리셋에서만) — "세웠다고 믿는 것"과 "지금 서 있는 것"은 gdb 로 DBGMCU 를 읽어 확인한다.

6. 이 프로젝트에서 SWV 를 켜면 안 되는 이유는? ST-LINK_gdbserver 에서 "SWV 를 끈다"는 것은 구체적으로 무엇인가?

SWO 는 PB3 한 핀에만 나오고 PB3 는 FL 엔코더의 B 상(TIM2_CH2)이다. PB3 는 리셋 직후 MX_GPIO_Init 전까지 AF0(JTDO/TRACESWO)이라, 그 구간에 SWV 가 켜지면 MCU 가 PB3 를 출력으로 구동해 엔코더 출력과 맞붙는다(구동한다는 부분은 추정 등급 — hardware/pinmap-h723.md §2-B). gdbserver 에는 SWV 를 끄는 스위치가 없다. -z(SWO 포트) · -a(CPU 클럭) · -b(분주) 셋을 주지 않는 것이 끈 것이다. -d 는 SWD 로 붙으라는 뜻이라 줘야 한다. cortex-debug 에서는 swoConfig 를 두지 않는다(enabled 의 기본값이 false).

7. V2 빌드로 구운 보드에서 "수신 오류가 몇 번 났는가"를 보고 싶다. 콘솔도 명령 창도 없다. 어떻게 보는가? 그때 모터 전원이 들어가 있다면 무엇을 먼저 확인하는가?

그 모듈의 static 카운터를 gdb 로 읽는다. static 도 ELF 의 심볼 표에 있으므로 p <이름> 으로 읽히고, 같은 이름이 여러 파일에 있으면 p '<파일>.c'::<이름> 으로 짚는다. 보드를 리셋하지 않으려면 서버를 -g 로 띄워 붙는다. 계약에 카운터용 메시지를 더하는 길은 택하지 않는다 — 벤치 관측 때문에 계약 v2 를 넓히지 않는다는 것이 이 가이드의 규칙이다(06a §4-2). gdb 가 메모리를 읽는 동안 CPU 는 서 있다. 제어 루프 · 보호 · 명령 워치독도 같이 선다. 그래서 모터 전원이 들어가 있으면 먼저 모터를 세운 상태에서(MOTOR_EN LOW) 붙어 fw-08 의 동결 설정이 살아 있는지를 본다 — p/x DBGMCU->APB2FZ1 의 bit 0 · 1. 붙는 동작 자체가 CPU 를 세우므로, 이것이 확인되기 전에는 바퀴가 도는 동안 붙지 않는다(§2-3 의 예고 상자).
