막혔을 때 — 원인을 스스로 좁히는 법

먼저 읽으십시오: ROS 2 문제의 대부분은 "코드가 틀렸다"가 아니라 "연결이 안 되어 있다"다. 로그를 읽기 전에 그래프를 본다. 그리고 ROS 2 는 틀린 것을 에러로 알려 주지 않는 경우가 많다 — 증상은 에러가 아니라 침묵이다.

이 페이지를 쓰는 법

① §0 의 만능 진단 순서를 먼저 친다 — 어느 단계에서 멈추는지가 곧 문제의 범위다. ② 그 범위의 표에서 증상을 찾아 "첫 확인" 명령을 친다. ③ 그래도 안 되면 §10 대로 정리한다. 정리하는 동안 답이 나오는 경우가 절반이다. 이 페이지는 순서대로 읽는 곳이 아니라 증상으로 뛰어드는 곳이다.

0. 만능 진단 순서

무슨 문제든 이 순서로 좁힌다. 컨테이너

# ① 노드가 떠 있는가
ros2 node list

# ② 토픽이 존재하는가
ros2 topic list

# ③ 데이터가 실제로 흐르는가 (이게 핵심)
ros2 topic hz /문제의_토픽

# ④ 내용이 말이 되는가
ros2 topic echo /문제의_토픽 --once

# ⑤ 연결되어 있는가 (발행자/구독자 수, QoS)
ros2 topic info /문제의_토픽 -v

# ⑥ 좌표 변환이 되는가
ros2 run tf2_tools view_frames

# ⑦ 전체 그림
ros2 run rqt_graph rqt_graph     # 또는 Foxglove 의 Topic Graph 패널

③에서 멈추면 발행 쪽 문제, ⑤에서 구독자가 0 이면 이름/QoS 문제다. ①에서 노드가 없으면 런치·빌드·source 문제(§1)고, ⑥에서 트리가 끊겨 있으면 §4 다.

2-B. 쓰기 레이어는 보존되지 않는다 — apt / pip 로 설치한 것이 사라진다

"어제는 됐는데 오늘 패키지가 없다"

docker compose run --rm dev 로 띄운 컨테이너는 나가는 순간 삭제된다. 그 안에서 sudo apt install, pip install 로 넣은 것은 이미지에 남지 않는다. --rm 을 빼도 해결되지 않는다 — compose run 은 실행마다 새 컨테이너를 만들고, compose 설정·이미지가 바뀐 뒤 up 하면 컨테이너가 재생성된다 (02 단계 §2-2). 계속 필요한 패키지를 남기는 방법은 둘이다 (02 단계 §2-2) — A: docker/Dockerfile 에 넣고 docker compose build, B: compose 에서 /opt /usr /etc /var 를 볼륨으로 잡고 컨테이너에서 설치. 반대로 /ros2_ws(마운트)와 /maps(마운트)는 살아남는다 — "어디가 마운트인가"가 곧 "무엇이 남는가"다.

5. 하드웨어

호스트 OS / 저장장치 (Pi 5, USB SSD 부팅)

증상확인
apt/dpkg 가 Read-only file system 으로 실패루트 파일시스템이 읽기 전용이 된 것. mount | grep ' / ' 에 ro, 또는 emergency_ro. apt 는 피해자다 — mount -o remount,rw / 로 되돌리지 않는다 (손상만 는다)
mount 에 emergency_roext4 가 오류를 감지해 스스로 응급 읽기 전용에 들어갔다. 재부팅 전에 sudo dmesg | grep -iE 'EXT4-fs|I/O error|usb|uas' 로 증거를 남긴다. cmdline.txt 한 줄 끝에 fsck.mode=force fsck.repair=yes 를 덧붙여 재부팅 → sudo tune2fs -l /dev/sda2 | grep -iE 'state|checked' 가 clean 이면 복구. 이후 sudo dpkg --configure -a, sudo apt --fix-broken install, full-upgrade 재실행. 로그에 Data will be lost 가 있었고 01 단계라면 다시 굽는 편이 빠르다
같은 순간 흩어진 수십 블록의 Buffer I/O error … lost async page write배드섹터가 아니라 USB 저장장치가 통째로 끊긴 것. 직전 줄이 원인이다: reset SuperSpeed USB device / uas_eh_abort_handler → UAS 브리지 (cmdline.txt 에 usb-storage.quirks=VID:PID:u), USB disconnect 만 → 전원·케이블 (정품 27W, 셀프파워 허브), USB 흔적 없음 → 매체 불량. 재현할 때는 다른 SSH 세션에 sudo dmesg -w 를 띄워 두면 루트가 죽어도 직전 줄이 남는다

ModemManager — /dev/ttyACM* 을 쓸 때만 나타나는 함정

STM32 Nucleo 의 ST-LINK VCP 는 ttyACM 이다. ModemManager 가 이 장치를 모뎀으로 오인해 AT 명령을 쏘며 탐색하고, 그 사이 우리 프레임이 깨진다. 증상이 GND 문제와 똑같이 보인다. 배선을 뒤지기 전에 먼저 확인한다.

systemctl status ModemManager          # 돌고 있는가
journalctl -u ModemManager -n 30       # 우리 장치를 건드렸는가

해결: udev 규칙에 ENV{ID_MM_DEVICE_IGNORE}="1" (이미 hardware/udev/99-ros2-devices.rules 에 포함), 또는 sudo systemctl disable --now ModemManager.
