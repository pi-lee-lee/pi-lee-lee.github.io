09 · SLAM과 Nav2

SLAM과 Nav2 — 지도를 만들고, 계획하고, 스스로 간다

여기서 당신의 추상 구조 ①(스캔으로 공간을 안다), ③(요청에 대해 계획한다), ④(이동한다), ⑤(수행 정도를 판정한다)가 한꺼번에 실물이 된다. 새 코드를 많이 쓰는 단계가 아니다. 남이 만든 두 덩어리(slam_toolbox, Nav2)를 구조를 이해한 채로 붙이는 단계다. 그래서 03 단계의 액션·파라미터·QoS 와 05 단계의 TF 가 전부 회수된다.

이 단계가 끝나면

방 지도를 직접 만들어 저장하고, 저장한 지도로 Nav2 를 띄워 Foxglove 에서 목표점을 찍으면 로봇이 스스로 그곳까지 주행한다. 주행 중 액션 피드백(distance_remaining 등)을 읽어 "지금 계획 대비 얼마나 왔는가"를 판정할 수 있고, 사람이 앞을 막으면 멈추거나 우회하는 것을 본다.

그래프에서의 위치slam_toolbox 상자 + Nav2 상자(인지·계획·제어). /scan, /odom, TF 를 받아 /map 과 /cmd_vel 을 낸다
전제05 (TF 트리), 06 (/odom 캘리브레이션과 IMU EKF 융합 완료), 07 (/scan 장착 방향 검증). 08 계열은 불필요
예상 소요6~10시간
언어YAML · 런치 · CLI (액션)
전제 조건 — 하나라도 빠지면 여기서 반드시 막힌다
  • /odom 이 정확하다 (06 단계 직진 2 m / 360도 캘리브레이션 완료)
  • /scan 이 정확하고 방향이 맞다 (07 단계 벽 1 m 검증 완료)
  • TF 트리가 odom → base_footprint → base_link → laser_link 로 이어진다 (ros2 run tf2_tools view_frames)

이 단계에서 "지도가 이상하다"의 원인 1위는 SLAM 파라미터가 아니라 위 셋 중 하나다.

1. 개요

                  ── 지도 작성 모드 (mapping) ──                    ── 항법 모드 (navigation) ──

   /scan ──┐                                                  저장된 지도 ──► map_server ──► /map
   /odom ──┼──► slam_toolbox ──► /map  +  TF map→odom         /scan ──┐
   TF    ──┘        │                                         /odom ──┼──► amcl ──► TF map→odom
                    └── map_saver_cli ──► my_room.pgm/.yaml    TF   ──┘            │
                                                                                   ▼
                                                                 목표점 ──► Nav2 ──► /cmd_vel ──► mcu_bridge (06)

이 단계는 두 부분으로 나뉜다. 먼저 지도를 만들고(slam_toolbox), 그 다음 그 지도 위에서 주행한다(Nav2 + AMCL). 두 모드는 같은 TF(map → odom)를 서로 다른 노드가 발행하므로 동시에 띄우지 않는다 — §2-3.

이 단계에 필요한 패키지(slam_toolbox, navigation2, nav2_bringup)는 02 단계 §3-3 에서 이미 넣었다. 컨테이너 안에서 ros2 pkg list | grep -E 'slam_toolbox|nav2_bringup' 로 확인하고, 없으면 02 단계 §2-2 의 방식으로 추가한다 (A: Dockerfile 을 고쳐 재빌드, B: 컨테이너에서 설치).

2. 원리 — 왜

2-1. SLAM 이란 무엇인가

SLAM = Simultaneous Localization And Mapping (동시적 위치추정 및 지도작성). 닭과 달걀 문제다.

  • 지도를 만들려면 내가 어디 있는지 알아야 한다
  • 내가 어디 있는지 알려면 지도가 있어야 한다

SLAM 은 이 둘을 동시에 푼다.

   t=0    ┌─────┐        아무것도 모름. 여기를 원점(map 프레임의 원점)으로 삼는다
          │  🤖 │
          └─────┘

   t=1    스캔을 찍는다 → 주변 벽 모양 기록
          오도메트리: "0.3 m 전진했다"                    ← /odom (06단계)
          새 스캔을 이전 스캔과 맞춰 본다 (스캔 매칭)
            → "실제로는 0.28 m 갔구나"                     ← 오도메트리 보정 = TF map→odom 의 갱신
            → 보정된 위치에 새 벽을 그려 넣는다

   t=N    루프 클로저: "여기 아까 왔던 곳이다!"
            → 그동안 쌓인 오차를 전체 지도에 분산시켜 보정 (지도가 한 번 "출렁"인다)

오도메트리가 정확할수록 스캔 매칭이 쉬워진다. 매칭은 "오도메트리가 말한 위치 근처"에서 정답을 찾기 때문이다. 06 단계 캘리브레이션이 여기서 값을 한다. 그리고 SLAM 이 계산한 "오도메트리가 얼마나 틀렸는가"가 바로 05 단계에서 배운 map → odom 변환이다.

2-2. slam_toolbox — 동작 모드

모드런치파일용도
online_asynconline_async_launch.py실시간 지도 작성 (가장 많이 씀). 스캔을 처리하는 동안 새 스캔이 오면 건너뛴다 — Pi 5 에 맞다
online_synconline_sync_launch.py모든 스캔을 처리. 더 정확하지만 밀리면 지연이 쌓인다

online_async_launch.py 의 런치 인자는 두 개다: use_sim_time (기본값 true) 과 slam_params_file (기본값은 패키지의 config/mapper_params_online_async.yaml). 노드 이름은 slam_toolbox, 실행파일은 async_slam_toolbox_node 다. 기본값이 true 인 것이 이 단계의 첫 번째 함정이다 — §3-3.

2-3. 지도 작성 모드와 항법 모드를 나누는 이유 — 05 의 철칙

   mapping 모드:     slam_toolbox ──► TF map→odom      (스캔 매칭으로 실시간 보정)
   navigation 모드:  amcl         ──► TF map→odom      (저장된 지도 위에서 파티클 필터로 추정)
                                        ▲
                     둘 다 띄우면 같은 자식 프레임(odom)의 부모를 두 노드가 쏜다 → TF 가 떨리고 모든 것이 망가진다

05 단계의 철칙 "하나의 좌표계에는 부모가 하나뿐이다"가 여기서 다시 나온다. 지도를 만들 때는 slam_toolbox 만, 주행할 때는 AMCL(또는 slam_toolbox 의 localization 모드) 만 map → odom 을 발행해야 한다. 그래서 이 가이드는 두 모드를 별도의 런치로 띄운다. 10 단계의 autonomy.launch.py 가 mode:=mapping|navigation 인자로 이 선택을 고정한다.

nav2_bringup 에도 SLAM 옵션이 있다

ros2 launch nav2_bringup bringup_launch.py slam:=True … 로 띄우면 AMCL+map_server 대신 slam_toolbox 를 함께 띄워 준다. 편리하지만 무엇이 무엇을 발행하는지가 런치 안에 감춰진다. 이 단계에서는 이해를 위해 slam_toolbox 를 따로 띄운다. 구조를 안 뒤에는 어느 쪽을 써도 된다.

2-4. Nav2 의 구조 — 노드 구성을 이해한다

                    ┌───────────────────────────────────┐
   목표점 ────────► │  bt_navigator                     │  행동 트리(BT)로 전체 흐름 지휘
 (/navigate_to_pose)└───────┬──────────────┬────────────┘   ← 이것이 액션 서버다 (03단계 §2-4)
    액션                    │              │
              ┌─────────────▼───┐    ┌─────▼─────────────┐
              │ planner_server  │    │ controller_server │
              │ 전역 경로 계획  │    │ 지역 경로 추종    │
              │ (NavFn:         │    │ (DWB, RPP)        │
              │  Dijkstra/A*)   │    │                   │
              └────────┬────────┘    └─────┬─────────────┘
                       │  /plan            │  /cmd_vel_nav
              ┌────────▼───────────────────▼─────┐
              │  global_costmap / local_costmap  │  장애물을 격자(비용)로
              │   ← /map, /scan, TF              │
              └──────────────────────────────────┘
                                                 │
                       ┌─────────────────────────▼──┐
                       │ behavior_server            │  막혔을 때 복구 (spin, backup, wait)
                       └────────────────────────────┘
                                                 │
                       ┌─────────────────────────▼──┐
                       │ velocity_smoother          │  가감속을 부드럽게 → /cmd_vel
                       └────────────────────────────┘
                                                 │
                                          /cmd_vel ──► mcu_bridge (06단계) ──► 모터

여기서 03 단계가 회수된다.

  • /navigate_to_pose 는 액션이다 — 오래 걸리고, 피드백이 있고, 취소 가능. 서비스로는 불가능했던 이유를 03 §2-4 에서 봤다.
  • 각 서버는 별도 노드이고 토픽/TF/액션으로 연결된다. ros2 node list 로 확인할 수 있다.
  • 수백 개의 값이 전부 파라미터다. 코드를 고치지 않고 YAML 로 로봇에 맞춘다.
  • 이것이 "동작 구조에 맞는 노드 구성"의 실제 모습이다. 당신의 ③(계획)·④(이동)·⑤(판정)가 planner / controller / bt_navigator 피드백으로 나뉘어 있다.
/cmd_vel 의 발행자는 누구인가

Humble 의 nav2_bringup 은 controller_server 의 출력을 /cmd_vel_nav 로 리매핑하고 velocity_smoother 가 다듬어 /cmd_vel 로 낸다. Nav2 를 띄운 뒤 ros2 topic info /cmd_vel -v 로 발행자 노드 이름을 직접 확인하십시오. "누가 /cmd_vel 을 쏘는가"를 알아야 10 단계에서 감독 노드가 개입할 자리를 정할 수 있다.

2-5. 두 개의 코스트맵

global_costmaplocal_costmap
범위지도 전체로봇 주변 3 m 정도 (rolling_window)
기준 프레임map (정적 지도)odom (센서 실시간, 연속적)

왜 두 개인가

전체 경로는 지도로 미리 계획하고, 갑자기 나타난 사람은 지역 코스트맵이 즉시 피한다. 요구되는 갱신 주기와 범위가 달라서 하나로 합치면 둘 중 하나가 망가진다. 지역 코스트맵이 odom 기준인 이유는 05 단계 그대로다 — 제어기는 튀지 않는 좌표계를 써야 한다.

2-6. inflation_radius — 초보자가 가장 많이 틀리는 값

inflation_layer:
  plugin: "nav2_costmap_2d::InflationLayer"
  inflation_radius: 0.25        # 장애물 주변을 이만큼 부풀린다 [m]
  cost_scaling_factor: 3.0      # 클수록 비용이 장애물에서 급격히 떨어진다

경로 계획기는 로봇을 점으로 취급한다. 그래서 장애물을 로봇 반지름만큼 부풀려야 "점이 지나갈 수 있는 곳 = 로봇이 지나갈 수 있는 곳"이 된다. 로봇 반지름보다 커야 한다. 작으면 벽에 긁히고, 너무 크면 좁은 통로를 "못 지나간다"고 판단해서 경로를 못 찾는다. 권장: 로봇 반지름 + 5~10 cm.

2-7. Nav2 노드는 lifecycle 노드다 — "떠 있는데 아무 일도 안 한다"의 정체

   unconfigured ──configure──► inactive ──activate──► active ──deactivate──► inactive
        ▲                                               │
        └───────────────── cleanup ◄────────────────────┘

   Nav2 의 모든 서버(planner, controller, bt_navigator, costmap, amcl, map_server…)는 이 상태기계를 가진다.
   inactive 상태에서는 노드가 떠 있고 ros2 node list 에도 보이지만, 토픽을 발행하지도 액션을 받지도 않는다.

일반 노드는 프로세스가 뜨는 순간 동작한다. lifecycle 노드는 configure → activate 를 거쳐야 동작한다. 이렇게 하는 이유는 10개 넘는 노드가 서로의 파라미터·TF·지도를 필요로 하므로 "모두 준비된 뒤 한꺼번에 켜는" 순서 제어가 필요하기 때문이다. 그 일을 lifecycle_manager 가 한다. nav2_bringup 의 런치는 lifecycle_manager_localization 과 lifecycle_manager_navigation 을 포함하고, autostart:=true(기본값)면 뜨자마자 전부 activate 한다.

ros2 lifecycle nodes                              # lifecycle 노드 목록
ros2 lifecycle get /controller_server              # 현재 상태: active [3] 이어야 정상
ros2 lifecycle list /controller_server             # 지금 가능한 전이
ros2 service list | grep lifecycle_manager         # manage_nodes / is_active 서비스
증상: 노드는 전부 떠 있는데 /plan 도 /cmd_vel 도 안 나온다

① ros2 lifecycle get 으로 inactive 인 노드를 찾는다. ② 대개 원인은 의존하는 것이 없어서 activate 에 실패한 것이다 — 지도 파일 경로가 틀려 map_server 가 configure 에 실패하거나, TF 가 끊겨 costmap 이 기다리거나. lifecycle_manager 로그에 "Failed to bring up" 이 남는다. ③ 03 단계에서 "ROS 문제는 에러가 아니라 침묵"이라고 한 것의 또 다른 예다.

2-8. 액션 피드백 — 당신의 ⑤ "수행 정도 판정"은 여기서 나온다

ros2 interface show nav2_msgs/action/NavigateToPose
geometry_msgs/PoseStamped pose         # Goal:     어디로 갈 것인가 (frame_id 는 map)
string behavior_tree                   #           비워 두면 기본 BT
---
std_msgs/Empty result                  # Result:   내용은 비어 있고, 상태 코드(SUCCEEDED/ABORTED/CANCELED)가 결과다
---
geometry_msgs/PoseStamped current_pose # Feedback: 지금 어디인가 (map 기준)
builtin_interfaces/Duration navigation_time        # 출발 후 경과 시간
builtin_interfaces/Duration estimated_time_remaining
int16 number_of_recoveries             # 막혀서 복구 행동(spin/backup/wait)을 몇 번 했는가
float32 distance_remaining             # 남은 경로 길이 [m]

피드백은 목표를 보낸 클라이언트에게 주기적으로 온다. 이것이 "계획 대비 이동의 수행 정도"의 원천이다.

피드백 필드판정에 쓰는 법
distance_remaining시간이 지나도 줄지 않으면 정체(stall). 장애물·미끄러짐·위치추정 실패를 의심한다
number_of_recoveries계속 늘어나면 경로가 실제로 막힌 것. 목표를 취소하고 다른 목표/우회를 결정한다
navigation_time예상 시간의 몇 배가 지나면 타임아웃으로 취소
current_poseFoxglove 에 궤적으로 그려 계획(/plan)과 비교한다

10 단계의 mission_supervisor(C++ 액션 클라이언트)가 이 피드백을 받아 취소·재전송·대기를 결정한다. 이 단계에서는 CLI 로 피드백을 눈으로 읽는 것까지 한다 (§3-9).

3. 실습

3-1. 지도 저장 경로를 컨테이너에 마운트 Mac

저장소의 maps/ 디렉터리가 지도 보관 위치다 (.gitignore 가 maps/*.pgm, maps/*.yaml 을 제외한다). 그런데 docker-compose.yml 은 ../ros2_ws 만 마운트한다. docker/docker-compose.yml 의 x-ros-common → volumes 에 한 줄을 추가한다 (볼륨 변경은 이미지 재빌드가 필요 없다 — 컨테이너를 다시 띄우면 된다).

  volumes:
    - ../ros2_ws:/ros2_ws:rw
    - ../maps:/maps:rw                 # ← 추가: 지도 저장 위치 (호스트 ~/ros2_rpi5/maps)
./scripts/sync-to-pi.sh              # Mac
docker compose run --rm dev ls -ld /maps    # Pi 호스트 — 디렉터리가 보이고 쓰기 가능해야 한다

3-2. SLAM 파라미터 파일 만들기 Mac

slam_toolbox 의 기본 파라미터 파일을 복사해서 시작한다. 수십 개의 값 중 우리가 손댈 것은 몇 개뿐이고, 나머지(solver, 스캔 매처 세부값)는 기본값이 합리적이다.

# 컨테이너 안 — 기본 파일을 우리 패키지로 복사
cp $(ros2 pkg prefix slam_toolbox)/share/slam_toolbox/config/mapper_params_online_async.yaml \
   /ros2_ws/src/rpi5_bringup/config/slam_params.yaml

복사한 ros2_ws/src/rpi5_bringup/config/slam_params.yaml 에서 아래 키를 찾아 우리 로봇의 값으로 고친다. (호스트에 마운트되어 있으므로 Mac 에서 편집해도 된다.) 키 이름은 파일에 이미 있는 것이고, 새로 추가하는 것이 아니다.

slam_toolbox:
  ros__parameters:
    use_sim_time: false             # ★ 실제 로봇. 런치 인자로도 한 번 더 false 를 준다 (§3-3)

    # ── 프레임 / 토픽 ── 05·07 단계와 정확히 일치해야 한다
    odom_frame: odom
    map_frame: map
    base_frame: base_footprint      # ← URDF 의 루트 링크 이름
    scan_topic: /scan
    mode: mapping                   # 지도 작성

    # ── 지도 ──
    resolution: 0.05                # 격자 크기 [m/px]. 실내는 5 cm 면 충분
    max_laser_range: 0.0            # ____ 07단계 실측 max_distance 보다 약간 작게 (예: 실측 12 → 8~10)
    map_update_interval: 5.0        # /map 발행 주기 [s]. 자주 낼수록 CPU 를 먹는다
    transform_publish_period: 0.02  # map→odom TF 발행 주기 [s]. 0 이면 TF 를 발행하지 않는다

    # ── 키프레임 / 루프 클로저 ──
    minimum_travel_distance: 0.2    # 이만큼 움직여야 새 키프레임
    minimum_travel_heading: 0.2     # 또는 이만큼 회전해야 [rad]
    do_loop_closing: true
    loop_search_maximum_distance: 3.0

    # (나머지 키는 기본 파일의 값을 그대로 둔다)
resolution 을 너무 작게 하지 마십시오

0.01 m 로 하면 지도 격자 수가 25배가 되어 Pi 5 의 메모리와 CPU 를 잡아먹는다. 실내 주행에는 0.05 m 면 충분하다.

max_laser_range 를 스펙보다 작게 두는 이유

최대 거리 근처의 측정값은 노이즈가 크고 반사 오류가 많다. 이 값들이 지도에 유령 벽을 만든다. 07 단계에서 드라이버 로그로 확인한 max_distance 의 0.7~0.8 배가 관례다. A1M8 은 삼각측량이라 원거리 정밀도 저하가 특히 크다 (07 §2-2).

rpi5_bringup 의 CMakeLists.txt 는 config/ 디렉터리 전체를 설치하므로 새 파일을 위해 고칠 것은 없다. 빌드만 다시 한다.

cd /ros2_ws && colcon build --symlink-install --packages-select rpi5_bringup && source install/setup.bash
ls $(ros2 pkg prefix rpi5_bringup)/share/rpi5_bringup/config/     # slam_params.yaml 이 보여야 한다

3-3. SLAM 실행 컨테이너

# 터미널 1: 로봇 기동 (TF + mcu_bridge + LiDAR)
ros2 launch rpi5_bringup robot.launch.py use_lidar:=true

# 터미널 2: SLAM
ros2 launch slam_toolbox online_async_launch.py \
  use_sim_time:=false \
  slam_params_file:=$(ros2 pkg prefix rpi5_bringup)/share/rpi5_bringup/config/slam_params.yaml

# 터미널 3: 확인
ros2 topic hz /map                                 # map_update_interval 마다
ros2 run tf2_ros tf2_echo map base_footprint       # 변환이 나오면 SLAM 이 위치를 잡은 것
ros2 run tf2_tools view_frames                     # map → odom → base_footprint 가 이어지는가
ros2 topic info /scan -v                           # slam_toolbox 구독자의 QoS 가 발행자와 호환되는가
use_sim_time:=false 는 생략할 수 없다

online_async_launch.py 의 use_sim_time 기본값은 true 다(시뮬레이터 사용을 전제로 만들어졌다). 실제 로봇에서 true 로 두면 노드는 /clock 토픽을 기다리며 시계가 0 에 멈춘다. 스캔의 타임스탬프(실제 시각)와 노드의 시계(0)가 맞지 않아 TF 조회가 전부 실패하고, 에러 없이 지도가 안 그려진다. 파라미터 파일에도 false 를 적어 두지만, 런치 인자가 우선하므로 명령에도 반드시 붙인다.

/scan 의 QoS 를 다시 본다

07 단계에서 라이다 드라이버의 발행 QoS 를 확인했다. ros2 topic info /scan -v 에서 slam_toolbox 구독자의 Reliability 가 발행자와 호환되는지(발행 BEST_EFFORT ↔ 구독 RELIABLE 이면 연결 안 됨) 지금 확인한다. 호환되지 않으면 /map 은 영원히 나오지 않고 로그는 조용하다.

지도가 두 겹으로 보이거나 휘면

3-8. 초기 위치 설정 — 필수

Nav2(AMCL) 는 로봇이 지도상 어디에 있는지 모른다. 알려 줘야 한다. 초기 위치를 안 주면 아무 일도 일어나지 않는다. AMCL 이 위치를 모르니 map → odom TF 를 발행하지 않고, 따라서 코스트맵도 경로 계획도 시작되지 않는다.

Foxglove 에서 (권장)

  1. 3D 패널 → Frame 을 map 으로. Topics 에 /map, /scan, /robot_description, /particle_cloud(AMCL 파티클) 를 켠다.
  2. 패널 설정의 Publish 항목에서 토픽을 확인한다: pose estimate → /initialpose (geometry_msgs/PoseWithCovarianceStamped), pose → /goal_pose. 발행 프레임은 패널의 Frame(map)이다.
  3. 3D 패널 상단 툴바의 Publish 도구에서 Publish pose estimate 를 고르고, 지도 위에서 로봇이 실제로 있는 곳을 클릭한 채 로봇이 보는 방향으로 드래그한다.
  4. /scan 점들이 지도의 벽과 겹치면 성공이다. 어긋나면 다시 찍는다. 파티클 구름이 로봇 주변으로 모여드는 것이 보인다.

CLI 로 (Foxglove 가 안 될 때)

ros2 topic pub --once /initialpose geometry_msgs/msg/PoseWithCovarianceStamped \
  "{header: {frame_id: 'map'}, pose: {pose: {position: {x: 0.0, y: 0.0}, orientation: {w: 1.0}}}}"
ros2 run tf2_ros tf2_echo map odom          # 이제 값이 나와야 한다

지도를 만들 때 출발한 자리에 로봇을 두면 (0, 0, yaw 0) 이 초기 위치다 — 지도의 원점은 SLAM 을 시작한 자리이기 때문이다.

3-9. 목표점 주기 — 세 가지 방법과 피드백 읽기

첫 자율주행은 반드시 받침대 위에서

바퀴를 띄운 상태로 /cmd_vel 이 상식적인 값(0.15 m/s 이하)으로 나오는 것을 먼저 본다. 바닥에서 처음 돌리면 예상치 못한 방향으로 돌진한다. 비상 정지는 ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist "{}" 가 아니라 목표 취소(Ctrl+C 또는 아래)와 물리 전원 차단이다 — Nav2 가 계속 /cmd_vel 을 쏘는 동안 0 을 한 번 보내는 것은 의미가 없다.

① Foxglove — Publish pose

3D 패널 Publish 도구에서 Publish pose 를 고르고 목표 지점을 클릭·드래그(방향)한다. /goal_pose 로 발행되고 bt_navigator 가 이를 받아 액션을 시작한다. /plan 을 3D 패널에 켜면 계획된 경로가 그려진다.

② 토픽으로

ros2 topic pub --once /goal_pose geometry_msgs/msg/PoseStamped \
  "{header: {frame_id: 'map'}, pose: {position: {x: 2.0, y: 1.0}, orientation: {w: 1.0}}}"

③ 액션으로 — 피드백이 보인다 (이 단계의 핵심 실습)

ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: 'map'}, pose: {position: {x: 2.0, y: 1.0}, orientation: {w: 1.0}}}}" --feedback
Waiting for an action server to become available...
Sending goal: ...
Goal accepted with ID: 3f2a...

Feedback:
  current_pose: {header: {frame_id: map}, pose: {position: {x: 0.41, y: 0.12 ...
  navigation_time: {sec: 2, nanosec: ...}
  estimated_time_remaining: ...
  number_of_recoveries: 0
  distance_remaining: 1.83          ← 줄어드는가?

Feedback: ... distance_remaining: 1.21
Feedback: ... distance_remaining: 0.44
Result: {}

읽는 법:

  • distance_remaining 이 단조롭게 줄어들면 계획대로 수행되고 있는 것이다.
  • 줄지 않는데 number_of_recoveries 가 늘어나면 막힌 것이다 — 로봇이 spin/backup/wait 을 반복한다.
  • Ctrl+C 를 누르면 클라이언트가 cancel 요청을 보내고, 서버가 받아들이면 CANCELED 로 끝나며 로봇이 멈춘다. 서비스였다면 불가능했을 일이다.
  • 경로를 못 찾으면 ABORTED 로 끝난다. 로그의 Failed to create plan — 목표가 장애물/미지 영역 안인지 확인한다.

주행 중 사람이 앞을 막아 보면 로봇이 멈추거나 우회하는 것을 관찰한다. 지역 코스트맵(/local_costmap/costmap)을 Foxglove 에 켜면 사람이 장애물로 찍히는 것이 보인다.

주행 중 이상 동작은 재현이 거의 불가능하다. 기록해서 책상에서 분석한다. 03 §2-10 에서 rosbag 을 익히라고 한 이유가 이것이다.

ros2 bag record -s mcap -o /maps/nav_test \
  /scan /odom /tf /tf_static /map /cmd_vel /plan \
  /global_costmap/costmap /local_costmap/costmap /particle_cloud

ros2 bag info /maps/nav_test
ros2 bag play /maps/nav_test --rate 0.3 --clock      # 천천히 재생하며 Foxglove 로 관찰
--clock 과 use_sim_time 의 관계

재생할 때 --clock 을 주면 bag 의 시각을 /clock 으로 발행한다. 이때 재생된 데이터를 처리하는 노드(예: bag 위에서 SLAM 을 다시 돌려 튜닝할 때)는 use_sim_time:=true 로 띄워야 bag 의 시각을 따라 TF 조회가 맞는다. 즉 실제 로봇에서는 항상 false, 기록 재생 때만 true 다. §3-3 의 함정과 정확히 반대 방향의 같은 원리다. -s mcap 은 Foxglove 가 직접 여는 포맷이다 (Dockerfile 에 rosbag2-storage-mcap 이 들어 있다).

Foxglove 는 mcap 파일을 Open local file 로 직접 연다. scp pi5:~/ros2_rpi5/maps/nav_test/*.mcap /tmp/ 로 가져와 Mac 에서 타임라인을 앞뒤로 움직이며 본다 — Nav2 튜닝은 bag 없이는 사실상 불가능하다.

✅ 검증 체크포인트

🤔 이해 확인

1. SLAM 지도가 휘거나 두 겹으로 보인다. SLAM 파라미터부터 만지면 안 되는 이유는?
원인 1위가 오도메트리 부정확이기 때문이다. 특히 wheel_separation 이 틀리면 회전량이 계속 어긋나고, SLAM 은 이를 보정하려다 지도를 뭉갠다. 06 단계 캘리브레이션을 먼저 검증해야 한다. 파라미터로 덮으려 하면 근본 문제가 남아 Nav2(AMCL)에서 다시 터진다.
2. 전역/지역 코스트맵을 나누는 이유는?
전역은 정적 지도 기준으로 전체 경로를 계획하고(느려도 됨), 지역은 실시간 센서로 갑자기 나타난 장애물을 즉시 피한다(빨라야 함). 요구되는 갱신 주기와 범위가 달라서 하나로 합치면 둘 다 나빠진다. 지역이 odom 기준인 것은 제어기가 튀지 않는 좌표계를 써야 하기 때문이다.
3. 초기 위치(/initialpose)를 안 주면 왜 아무 일도 안 일어나는가?
AMCL 이 로봇 위치를 모르면 map → odom TF 를 발행하지 않는다. 그러면 TF 트리가 map 에서 끊겨서 코스트맵이 로봇 위치를 알 수 없고, 경로 계획 자체가 시작되지 않는다. 에러가 아니라 침묵이라 헷갈린다.
4. inflation_radius 를 로봇 반지름보다 작게 하면?
경로 계획기는 로봇을 점으로 취급하므로, 부풀림이 부족하면 벽에서 로봇 반지름보다 가까운 경로를 만든다. 결과적으로 벽에 긁히거나 끼인다. 반대로 너무 크면 좁은 통로를 통과 불가로 판단해 경로를 못 찾는다.
5. use_sim_time 을 true 로 둔 채 실제 로봇에서 SLAM 을 띄우면 무슨 일이 일어나는가?
노드가 /clock 토픽을 시계로 삼는데 아무도 발행하지 않으므로 시계가 0 에 멈춘다. 스캔의 타임스탬프(실제 시각)와 노드의 "지금"(0)이 맞지 않아 TF 조회가 전부 실패하고 지도가 안 그려진다. 에러 메시지는 거의 없다. online_async_launch.py 의 기본값이 true 라서 반드시 use_sim_time:=false 를 붙여야 한다. 반대로 bag 을 --clock 으로 재생할 때는 true 가 맞다.
6. lifecycle 노드가 inactive 상태면 어떤 증상이 나타나고, 무엇을 확인하는가?
프로세스는 떠 있고 ros2 node list 에도 보이지만 토픽 발행도 액션 처리도 하지 않는다 — /plan, /cmd_vel 이 안 나온다. ros2 lifecycle get /노드 로 상태를 보고, lifecycle_manager 로그에서 어느 노드가 configure/activate 에 실패했는지 찾는다. 흔한 원인은 지도 파일 경로 오타(map_server), TF 끊김(costmap), 파라미터 오타다.
7. 액션 피드백의 distance_remaining 이 줄지 않는다. 무엇을 의심하고, 감독 노드는 무엇을 해야 하는가?
의심 순서: ① 장애물에 막힘(number_of_recoveries 증가, 지역 코스트맵 확인) ② 바퀴 헛돎/미끄러짐(/odom 은 움직이는데 실제는 정지) ③ 위치추정 실패(AMCL 파티클이 흩어짐, map→odom 이 튐). 감독 노드(10 단계)는 일정 시간 동안 거리가 줄지 않으면 목표를 취소하고, 잠시 대기 후 재전송하거나 다음 목표로 넘어가거나 사람에게 알린다. 액션이 취소 가능하기 때문에 이 설계가 성립한다 — 03 단계에서 액션을 고른 이유다.
8. 지도 작성 모드와 항법 모드를 동시에 띄우면 무엇이 망가지는가?
slam_toolbox 와 AMCL 이 둘 다 map → odom TF 를 발행한다. 같은 자식 프레임의 부모를 두 노드가 쏘면 TF 가 두 값 사이에서 떨리고, 코스트맵·경로·로봇 위치가 전부 흔들린다. 05 단계의 철칙 "하나의 좌표계에는 부모가 하나뿐"의 실물이다. 그래서 두 모드를 별도 런치로 나누고 10 단계에서 mode:= 인자로 고정한다.
