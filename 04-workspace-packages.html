overlay / underlay — ROS 환경의 핵심 개념

source /opt/ros/humble/setup.bash     # ① underlay: ROS 본체
source /ros2_ws/install/setup.bash    # ② overlay:  내 패키지

순서가 중요하다. overlay 는 underlay 위에 얹힌다. 같은 이름의 패키지가 양쪽에 있으면 overlay(내 것)가 이긴다. 이 프로젝트의 컨테이너는 .bashrc 와 entrypoint.sh 에서 이 두 줄을 자동으로 실행한다. 그래서 셸을 열면 바로 ros2 가 동작한다.

"ros2: command not found", "내 패키지가 안 보여요"의 99%

source 문제다. 새 터미널을 열면 환경은 초기화된다. 그리고 빌드 직후에도 source install/setup.bash 를 다시 해야 새 실행파일이 보인다. 빌드는 install/ 에 파일을 만들 뿐, 현재 셸의 PATH·AMENT_PREFIX_PATH 는 건드리지 않기 때문이다.

2-3. colcon → CMake → ament — 빌드가 하는 일

  colcon build
    │  src/ 의 package.xml 을 전부 읽어 의존 순서를 정한다 (bringup 은 description 뒤에)
    ├─► 패키지마다 build/<pkg>/ 에서 cmake 를 돌린다
    │      find_package(rclcpp)          ← /opt/ros/humble 에서 헤더·라이브러리 위치를 찾는다
    │      add_executable(hello_node …)  ← 컴파일할 소스
    │      ament_target_dependencies(…)  ← include 경로 + 링크 + 컴파일 옵션을 한 번에 붙인다
    │      install(TARGETS … lib/pkg)    ← ros2 run 이 찾는 위치로 복사
    └─► install/<pkg>/ 에 결과 + setup.bash 를 만든다
왜 lib/${PROJECT_NAME} 인가

ros2 run <pkg> <exe> 는 install/<pkg>/lib/<pkg>/<exe> 를 찾는다. bin/ 에 넣으면 셸에서 직접 실행은 되지만 ros2 run 은 못 찾는다. 이 규칙 하나가 "빌드는 됐는데 ros2 run 이 no executable found 를 낸다"의 원인 대부분이다.

ament_target_dependencies 와 target_link_libraries 의 차이

ament_target_dependencies(node rclcpp std_msgs) 는 ROS 패키지의 include 경로·라이브러리·컴파일 정의를 패키지 단위로 통째로 붙인다. target_link_libraries(node ${OpenCV_LIBS}) 는 일반 CMake 라이브러리를 붙인다. 08a 에서 OpenCV 를 쓸 때 둘을 같이 쓴다.

--dependencies 로 준 이름은 package.xml 의 <depend> 와 CMakeLists.txt 의 find_package 에 자동으로 들어간다. 열어서 확인한다.

패키지 이름은 --dependencies 앞에 둔다

--dependencies 는 값을 여러 개 받는 옵션이다. 그래서 뒤에 패키지 이름을 두면 그 이름까지 의존성 목록으로 삼켜 버리고, 정작 필수 인자가 비어 error: the following arguments are required: package_name 이 난다. 이름을 맨 앞에 두거나, --dependencies rclcpp std_msgs -- rpi5_hello_cpp 처럼 -- 로 옵션을 끊는다. 이 규칙은 06·07·08a·10 단계의 pkg create 에도 그대로 적용된다.

3-2. 첫 노드 — 발행자

src/hello_publisher.cpp 를 만든다. 복사하지 말고 직접 치십시오. 손으로 쳐야 구조가 남는다.

#include <chrono>
#include <memory>
#include <string>

#include "rclcpp/rclcpp.hpp"
#include "std_msgs/msg/string.hpp"       // 메시지 헤더 경로: <pkg>/msg/<snake_case>.hpp

using namespace std::chrono_literals;  // 1s, 500ms 같은 리터럴

// 노드 = rclcpp::Node 를 상속한 클래스. 생성자에서 인터페이스(발행자/타이머)를 만든다.
class HelloPublisher : public rclcpp::Node
{
public:
  HelloPublisher()
  : Node("hello_publisher"), count_(0)          // "hello_publisher" 가 노드 이름
  {
    // 발행자: <메시지 타입>("토픽 이름", 큐 깊이)
    pub_ = this->create_publisher<std_msgs::msg::String>("hello", 10);

    // 타이머: 1초마다 on_timer 를 부른다. std::bind 로 멤버 함수를 콜백으로 넘긴다.
    timer_ = this->create_wall_timer(1s, std::bind(&HelloPublisher::on_timer, this));
  }

private:
  void on_timer()
  {
    auto msg = std_msgs::msg::String();
    msg.data = "hello " + std::to_string(count_++);
    RCLCPP_INFO(this->get_logger(), "publish: '%s'", msg.data.c_str());
    pub_->publish(msg);
  }

  // 멤버로 잡고 있어야 한다. 지역 변수로 만들면 생성자가 끝나는 순간 소멸해 아무 일도 안 일어난다.
  rclcpp::Publisher<std_msgs::msg::String>::SharedPtr pub_;
  rclcpp::TimerBase::SharedPtr timer_;
  size_t count_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);                          // ① ROS 컨텍스트 초기화
  rclcpp::spin(std::make_shared<HelloPublisher>());   // ② 노드 생성 + ③ 콜백 루프 (여기서 블로킹)
  rclcpp::shutdown();                                // ④ 정리
  return 0;
}

rclcpp::spin() 이 하는 일

   spin() 내부 ─ 무한 루프 (Executor)
      ├─ 타이머가 만료됐나?               → on_timer() 호출
      ├─ 구독한 토픽에 새 메시지가 왔나?   → 구독 콜백 호출
      ├─ 서비스 요청 / 액션 피드백이 왔나? → 핸들러 호출
      └─ 반복  (기본 SingleThreadedExecutor: 콜백은 한 번에 하나씩 순서대로)

spin 을 호출하지 않으면 콜백이 하나도 실행되지 않는다. 그리고 콜백 안에서 오래 걸리는 일(sleep, 무거운 추론)을 하면 다른 콜백이 전부 밀린다. 이 사실이 08b 에서 "추론 중에도 파라미터 서비스가 응답해야 한다"는 설계로 이어진다 (부록 A 의 MultiThreadedExecutor). 개념 설명은 03 단계 §2-8.

Python 과 무엇이 대응되는가

create_publisher<T>("topic", 10)create_publisher(T, 'topic', 10)
create_wall_timer(1s, std::bind(&X::cb, this))create_timer(1.0, self.cb)
RCLCPP_INFO(get_logger(), "%s", s.c_str())self.get_logger().info(f'{s}')

의존성을 두 곳(package.xml, CMakeLists.txt)에 적는 이유

3-5. 구독자 노드 추가

src/hello_subscriber.cpp:

#include <memory>

#include "rclcpp/rclcpp.hpp"
#include "std_msgs/msg/string.hpp"

class HelloSubscriber : public rclcpp::Node
{
public:
  HelloSubscriber()
  : Node("hello_subscriber")
  {
    // 구독: <타입>("토픽", 큐 깊이, 콜백). 람다로 쓰면 std::bind 가 필요 없다.
    sub_ = this->create_subscription<std_msgs::msg::String>(
      "hello", 10,
      [this](const std_msgs::msg::String & msg) {
        RCLCPP_INFO(this->get_logger(), "received: '%s'", msg.data.c_str());
      });
  }

private:
  rclcpp::Subscription<std_msgs::msg::String>::SharedPtr sub_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<HelloSubscriber>());
  rclcpp::shutdown();
  return 0;
}

3-6. 파라미터와 QoS — 06 단계에서 바로 쓰는 두 가지

발행 주기를 파라미터로 빼 보자 (개념: 03 단계 §2-6). hello_publisher.cpp 의 생성자를 고친다.

// 생성자 안. ROS 2 는 "선언하지 않은 파라미터"를 거부한다 — 선언이 곧 인터페이스다.
this->declare_parameter<double>("rate_hz", 1.0);
const double rate = this->get_parameter("rate_hz").as_double();

// 주기 = 1/rate. std::chrono::duration<double> 로 만들어 넘긴다.
timer_ = this->create_wall_timer(
  std::chrono::duration<double>(1.0 / rate),
  std::bind(&HelloPublisher::on_timer, this));
colcon build --symlink-install --packages-select rpi5_hello_cpp --parallel-workers 2 && source install/setup.bash
ros2 run rpi5_hello_cpp hello_publisher --ros-args -p rate_hz:=5.0
ros2 topic hz /hello                      # 5 Hz
ros2 param get /hello_publisher rate_hz   # 5.0

QoS 는 rclcpp::QoS 객체로 준다. 센서 스트림은 BEST_EFFORT, 상태·명령은 RELIABLE 이 관례다. 개념·호환 규칙·프리셋은 03 단계 §2-7 에 정리되어 있다. 여기서는 그것을 코드로 돌려 본다.

지금까지 쓰던 그 10 이 곧 QoS 다

create_publisher<T>("hello", 10) 와 create_subscription<T>("hello", 10, cb) 의 10 은 rclcpp::QoS(10) 의 축약이다. 그 자리는 원래 QoS 객체를 받는 자리이고, 숫자만 주면 깊이만 10 으로 지정하고 나머지는 기본값이 된다 — KEEP_LAST + RELIABLE + VOLATILE.

즉 §3-2 부터 만든 노드들은 모두 "깊이 10 · 재전송 보장 · 늦게 온 구독자에게는 주지 않음" 으로 통신하고 있었다. 아래처럼 rclcpp::QoS 를 명시하면 그 기본값을 하나씩 바꿀 수 있다.

// 큐 깊이 10 + 신뢰성 BEST_EFFORT (센서 데이터용 프리셋도 있다: rclcpp::SensorDataQoS())
auto qos = rclcpp::QoS(10).best_effort();
pub_ = this->create_publisher<std_msgs::msg::String>("hello", qos);
지금 직접 확인해 보십시오

발행자를 best_effort() 로 바꿔 빌드하고, 구독자는 그대로(기본 RELIABLE) 띄운다. 메시지가 오지 않는다. 에러도 없다. ros2 topic info /hello -v 로 양쪽 QoS 를 비교해 보고, 구독자도 rclcpp::QoS(10).best_effort() 로 바꾸면 다시 연결된다. 07 단계에서 라이다가 Foxglove 에 안 보일 때 이 경험이 답을 준다.

깊이(depth)를 눈으로 확인하기 — 느린 구독자 실험

깊이는 설명만 들으면 잘 와닿지 않는다. 구독 콜백을 일부러 느리게 만들어 직접 본다. 개념 쪽 설명은 03 단계 §2-7 의 "깊이가 실제로 만드는 동작".

// hello_subscriber.cpp — 상단에 #include <thread> 를 추가한다.
HelloSubscriber() : Node("hello_subscriber")
{
  this->declare_parameter<int>("depth", 10);        // 실행할 때 깊이를 바꿔 비교한다
  const auto depth = this->get_parameter("depth").as_int();

  sub_ = this->create_subscription<std_msgs::msg::String>(
    "hello", rclcpp::QoS(depth),                     // ← 숫자 대신 QoS 객체를 명시
    [this](const std_msgs::msg::String & msg) {
      std::this_thread::sleep_for(500ms);            // 처리에 0.5초 걸리는 노드인 척 (= 2 Hz)
      RCLCPP_INFO(this->get_logger(), "processed: '%s'", msg.data.c_str());
    });
}

ros2 run rpi5_hello_cpp hello_subscriber --ros-args -p depth:=1        # 셸 2: 깊이 1 로 다시
깊이로그에 찍히는 번호무슨 일이 일어난 것인가
100, 1, 2, 3 … 연속이지만 점점 뒤처진다큐에 쌓인 옛 메시지를 순서대로 처리한다. 발행 10 Hz · 처리 2 Hz 이므로 지연이 계속 커진다
10, 5, 10, 15 … 건너뛰지만 항상 최신큐가 하나뿐이라 밀린 것은 버려진다. 지연이 쌓이지 않는다

"빠른 센서 + 느린 처리"는 08b 의 추론 노드에서 그대로 재현된다. 그때 depth 1 을 쓰는 근거가 이 표의 아래 줄이다. 선택 기준은 "몇 개를 보관하느냐"가 아니라 지연이 쌓이느냐라는 점을 로그로 확인하라.

import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class HelloPublisher(Node):
    def __init__(self):
        super().__init__('hello_publisher_py')
        self.declare_parameter('rate_hz', 1.0)
        rate = self.get_parameter('rate_hz').value
        self.pub = self.create_publisher(String, 'hello', 10)
        self.timer = self.create_timer(1.0 / rate, self.on_timer)
        self.count = 0

    def on_timer(self):
        msg = String()
        msg.data = f'hello(py) {self.count}'
        self.pub.publish(msg)
        self.get_logger().info(f'publish: {msg.data}')
        self.count += 1


def main(args=None):
    rclpy.init(args=args)
    node = HelloPublisher()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        if rclpy.ok():
            rclpy.shutdown()


if __name__ == '__main__':
    main()

🤔 이해 확인

1. colcon build 후에 왜 source install/setup.bash 를 해야 하는가?
빌드는 install/ 에 실행파일과 환경 스크립트를 만들 뿐이다. 현재 셸의 PATH, AMENT_PREFIX_PATH, PYTHONPATH 는 그대로다. source 가 그 환경변수들을 갱신해서 ros2 run 이 새 패키지를 찾을 수 있게 한다.
2. 발행자를 지역 변수로 만들면 무슨 일이 일어나는가?
SharedPtr 의 참조 카운트가 생성자 끝에서 0 이 되어 발행자가 즉시 소멸한다. 타이머도 마찬가지다. 노드는 떠 있는데 ros2 topic list 에 토픽이 없거나 콜백이 한 번도 안 불린다. 인터페이스 객체는 반드시 멤버로 잡는다.
3. ament_target_dependencies 와 target_link_libraries 는 언제 각각 쓰는가?
ROS 패키지(rclcpp, sensor_msgs, cv_bridge…)는 ament_target_dependencies 로 include·링크·정의를 통째로 붙인다. 일반 CMake 라이브러리(OpenCV 의 ${OpenCV_LIBS}, 시스템 라이브러리)는 target_link_libraries 로 붙인다. 08a 에서 둘을 같이 쓴다.
4. 실행파일을 bin/ 에 설치하면 왜 ros2 run 이 못 찾는가?
ros2 run <pkg> <exe> 는 install/<pkg>/lib/<pkg>/ 만 뒤진다. 셸에서 직접 실행은 되므로 "빌드는 됐는데 ros2 run 만 안 된다"로 나타난다. install(TARGETS … DESTINATION lib/${PROJECT_NAME}) 이 규칙이다.
5. 발행자는 BEST_EFFORT, 구독자는 RELIABLE 일 때 무슨 일이 일어나는가?
연결되지 않는다. 구독자가 요구하는 품질을 발행자가 보장할 수 없기 때문이다. 에러 없이 데이터가 안 온다. ros2 topic info -v 로 양쪽 QoS 를 비교해야 알 수 있다. 3-6 에서 직접 재현했어야 한다.
6. rclcpp::spin() 의 콜백 안에서 500 ms 짜리 추론을 돌리면 무엇이 곤란한가?
기본 실행기는 콜백을 한 번에 하나씩 처리하므로 그 500 ms 동안 타이머·다른 구독·파라미터 서비스가 전부 멈춘다. 해결은 ① 무거운 일을 별도 스레드/실행기로 분리하거나(MultiThreadedExecutor + 콜백 그룹) ② 큐 깊이를 1 로 두고 최신 프레임만 처리하는 것이다. 08b 에서 다룬다.
7. simulate:=true 로 돌리는 것이 왜 학습에 도움이 되는가?
하드웨어가 준비되기 전에 ROS 쪽 배선(토픽 이름, 메시지 타입, 운동학, TF)을 검증해 둘 수 있다. 나중에 실제 MCU 에서 문제가 생겼을 때 "ROS 쪽은 이미 맞다"를 알고 있으므로 의심 범위가 시리얼/펌웨어로 좁혀진다.
