C7 · Hailo 준비 — 버전과 모델

Hailo 준비 — 버전을 맞추고 모델 파일을 읽는다

Hailo-8 은 추론을 전담하는 칩이다. 드라이버는 호스트에, 라이브러리(HailoRT)는 컨테이너에 있고 둘의 버전이 정확히 같아야 한다. 이 쪽은 코드를 쓰지 않는다. 버전을 맞추고, 컨테이너에서 장치와 모델 파일이 보이는 것을 확인하고, 모델 파일의 입출력을 읽는다. C8 의 코드는 이 쪽에서 읽은 값을 그대로 쓴다.

이 쪽이 끝나면 보이는 것
  • 호스트와 컨테이너의 hailortcli fw-control identify 가 같은 버전을 보인다.
  • 컨테이너에서 hailortcli scan 이 장치를 찾고, /usr/share/hailo-models/ 의 모델 파일이 보인다.
  • hailortcli parse-hef 로 모델의 입력(640 × 640 × 3, 8비트, RGB)과 출력(NMS 포함, 80 클래스)을 읽어 적었다.

필요한 것 — AI HAT+ 가 장착된 Pi, Hailo Developer Zone 계정(패키지 내려받기), Mac.

환경Pi 호스트 컨테이너 Mac
선행C0 §3-1(호스트의 identify), 학습 단계 01 §3-4(hailo-all 설치)
만드는 것docker/Dockerfile 의 HailoRT 블록, docker/docker-compose.yml 의 마운트 한 줄, docker/hailort_4.23.0_arm64.deb(저장소에는 넣지 않는다)
적는 곳노트 — §3-6 의 모델 입출력 표

1. 개요

C6 의 검출기는 동작하지만 CPU 4 코어를 거의 다 차지한다. 자율주행은 인지 · 지도 작성 · 경로 계획 · 제어가 동시에 돌아야 하고, 하나라도 CPU 시간을 얻지 못하면 전체가 멈춘다. Hailo-8 은 추론을 전용 칩으로 옮겨 CPU 를 비운다. 목표는 fps 자체보다 CPU 사용률이다.

호스트 (Raspberry Pi OS)                       컨테이너 (Ubuntu 22.04)
hailo_pci 커널 드라이버  4.23.0                 libhailort 라이브러리  4.23.0   ← hailort_4.23.0_arm64.deb 로 설치
Hailo-8 펌웨어           4.23.0                 hailortcli (확인 명령)
/dev/hailo0  (major 동적)  ───────────────────► compose 장치 규칙 'c ${HAILO_MAJOR}:* rmw' 로 연다
/usr/share/hailo-models/  (모델 파일 .hef) ───► 읽기 전용 마운트

세 숫자가 같아야 한다. 하나라도 다르면 /dev/hailo0 이 보여도 "No Hailo device found" 가 난다. 호스트를 apt full-upgrade 하면 호스트 쪽 둘만 올라간다 — 그 뒤에는 이 쪽의 §3-5 를 다시 한다.

2. 원리

2-1. 모델 파일 .hef

  • Hailo 는 ONNX 를 그대로 실행하지 않는다. Hailo 의 컴파일러가 만든 .hef(Hailo 실행 파일 형식)만 실행한다. 컴파일러는 x86 리눅스에서만 돌고 이 가이드의 범위 밖이다.
  • hailo-all 을 설치하면 호스트의 /usr/share/hailo-models/ 에 컴파일된 모델이 들어 있다. 이 가이드는 그중 yolov8s_h8.hef 를 쓴다. 학습 단계 01 의 데모(hailo_yolov8_inference.json)가 쓴 바로 그 파일이다.
  • 이름 끝의 _h8 은 Hailo-8(AI HAT+, 26 TOPS)용, _h8l 은 Hailo-8L(AI Kit, 13 TOPS)용이다. 다른 칩의 파일은 로드되지 않는다. identify 의 Device Architecture 와 맞춘다.
  • 이 파일은 겹친 박스 정리(NMS)까지 포함한다. 출력이 C6 처럼 8400 개 후보 텐서가 아니라 클래스별 박스 목록이다. 그래서 C8 의 후처리는 C6 보다 짧다.

2-2. 컨테이너에 필요한 것은 패키지 하나다

HailoRT 의 데비안 패키지 hailort_<버전>_arm64.deb 하나면 된다. 그 안에 C++ 노드가 쓰는 네 가지가 들어 있다.

  • 라이브러리 libhailort.so
  • 헤더 hailo/hailort.hpp
  • CMake 설정 — find_package(HailoRT) 가 찾는다
  • 확인 명령 hailortcli

Python 바인딩(wheel)은 이 가이드의 노드가 C++ 이라 필요 없다.

C8 의 CMakeLists.txt 는 find_package(HailoRT 4.23.0 EXACT REQUIRED) 로 버전을 검사한다. 컨테이너의 패키지가 없거나 버전이 다르면 빌드가 그 줄에서 멈춘다. 실행해서 "No Hailo device found" 를 보기 전에 빌드 시점에 드러난다. 이 검사는 컨테이너 쪽만 보므로 호스트와의 일치는 §3-5 에서 양쪽 identify 로 확인한다.

3. 실습

3-1. 호스트 버전 Pi 호스트

hailortcli fw-control identify
#   Control Protocol Version: 2
#   Firmware Version: 4.23.0 (release,app,extended context switch buffer)
#   Board Name: Hailo-8
#   Device Architecture: HAILO8
hailortcli scan
#   Hailo Devices:
#   [-] Device: 0001:01:00.0
dpkg -l | grep -i hailo | awk '{print $2, $3}'
#   hailo-all 5.1.1  hailort 4.23.0  hailort-pcie-driver 4.23.0  hailo-models 1.0.0-2  ...
sudo /usr/sbin/modinfo hailo_pci | grep '^version'      # 4.23.0 — modinfo 는 /usr/sbin 에 있다
ls -l /dev/hailo0                                        # crw-rw-rw- ... 510, 0  → 쉼표 앞이 major (부팅마다 바뀔 수 있다)

hailort · hailort-pcie-driver · 펌웨어 셋이 같은 버전인지 본다. 그 버전이 아래에서 받을 파일 이름의 숫자다.

3-2. 같은 버전의 패키지를 받는다 Mac

  • Hailo Developer Zone(hailo.ai)에 로그인한다(계정 필요). Software Downloads → HailoRT 에서 3-1 과 같은 버전의 Ubuntu package (deb) for arm64 를 고른다.
  • 받은 파일을 Mac 의 ~/ros2_rpi5/docker/ 에 둔다. 파일 이름이 hailort_4.23.0_arm64.deb 꼴인지 확인한다. 다르면 §3-3 의 COPY 줄을 실제 이름에 맞춘다.
  • 저장소에 넣지 않는다: echo 'docker/*.deb' >> .gitignore

3-3. Dockerfile 의 HailoRT 블록 Mac

docker/Dockerfile 에서 # ── 3-B. HailoRT 로 시작하는 주석 블록을 아래로 바꾼다. 비root 사용자 블록(# ── 4.) 앞에 있어야 한다.

# ── 3-B. HailoRT — camera guide C7 ─────────────────────────────────────────────
#  The version must equal the host's `hailortcli fw-control identify` (hardware/INVENTORY.md section 5).
ARG HAILORT_VERSION=4.23.0
COPY hailort_${HAILORT_VERSION}_arm64.deb /tmp/hailort.deb
RUN apt-get update && apt-get install -y --no-install-recommends /tmp/hailort.deb \
 && rm -f /tmp/hailort.deb && rm -rf /var/lib/apt/lists/*

3-4. compose — 장치 규칙과 모델 마운트 Mac

docker/docker-compose.yml 의 device_cgroup_rules 에 'c ${HAILO_MAJOR:?...}:* rmw' 줄이 이미 있다. major 는 부팅마다 바뀔 수 있어 번호 대신 docker/.env 의 값을 읽고, 그 값은 부팅 때 docker/majors.sh 가 적는다(02 §2-3). 3-1 의 major 와 같은지는 Pi cd ~/ros2_rpi5/docker && ./majors.sh --check 로 본다. 그리고 volumes 에 모델 디렉터리를 읽기 전용으로 마운트하는 줄을 더한다.

  volumes:
    - ../ros2_ws:/ros2_ws:rw
    - /dev:/dev
    - /run/udev:/run/udev:ro
    - /sys/class/gpio:/sys/class/gpio
    - ros-cache:/home/ros/.cache
    - /usr/share/hailo-models:/usr/share/hailo-models:ro     # ← 추가. 호스트의 모델 파일을 같은 경로로

같은 경로로 마운트하므로 model_path 가 호스트와 컨테이너에서 같다. 다른 모델 파일을 쓰고 싶으면 호스트의 이 디렉터리에 넣거나 마운트 줄을 하나 더한다.

3-5. 빌드와 양쪽 확인 Mac Pi 호스트

# Mac
./scripts/sync-to-pi.sh
# Pi 호스트
cd ~/ros2_rpi5/docker && docker compose build
hailortcli fw-control identify | grep 'Firmware Version'                          # 호스트
docker compose run --rm dev hailortcli fw-control identify | grep 'Firmware Version'   # 컨테이너
docker compose run --rm dev hailortcli scan                                       # 컨테이너에서 장치가 보이는가
docker compose run --rm dev dpkg -l hailort | awk '/^ii/{print $2, $3}'           # hailort 4.23.0
docker compose run --rm dev ls /usr/share/hailo-models/                           # yolov8s_h8.hef 가 보이는가

두 identify 의 버전과 dpkg 의 버전이 전부 같아야 한다. 다르면 C8 로 가지 않는다.

컨테이너에서 scan 이 "permission denied" 를 낸다

호스트에서 ls -l /dev/hailo0 의 권한을 본다. crw-rw-rw- 가 아니면 hardware/udev/99-ros2-devices.rules 에 아래 한 줄을 더하고 규칙을 다시 읽힌다. 장치 파일이 보이는 것과 열 수 있는 것은 다르다.

KERNEL=="hailo*", MODE="0666"
sudo cp ~/ros2_rpi5/hardware/udev/99-ros2-devices.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules && sudo udevadm trigger
ls -l /dev/hailo0        # crw-rw-rw-

3-6. 모델의 입출력을 읽는다 Pi 호스트

코드를 쓰기 전에 모델이 무엇을 받고 무엇을 내는지 읽는다. 호스트와 컨테이너 어느 쪽에서 실행해도 같다.

hailortcli parse-hef /usr/share/hailo-models/yolov8s_h8.hef
Architecture HEF was compiled for: HAILO8
Network group name: yolov8s, Single Context
    Network name: yolov8s/yolov8s
        VStream infos:
            Input  yolov8s/input_layer1 UINT8, NHWC(640x640x3)
            Output yolov8s/yolov8_nms_postprocess FLOAT32, HAILO NMS BY CLASS(number of classes: 80, maximum bounding boxes per class: 100, maximum frame size: 160320)

줄 모양은 HailoRT 판에 따라 조금 다를 수 있다. 아래 표에 내 출력의 값을 적는다. C8 의 코드는 이 값을 모델 파일에서 직접 읽어 쓰지만, 사람이 먼저 알고 있어야 로그를 읽을 수 있다.

항목기대값내 값C8 에서 쓰이는 곳
컴파일 대상 칩HAILO8____identify 의 Device Architecture 와 같아야 로드된다
입력 이름 · 형식 · 모양yolov8s/input_layer1 · UINT8 · 640 × 640 × 3____입력 버퍼 크기 = 640 × 640 × 3 바이트. RGB 8비트로 넣는다
출력 형식FLOAT32, HAILO NMS BY CLASS____클래스별 박스 목록을 읽는 코드(C8 §2-2)
클래스 수 · 클래스당 최대 박스80 · 100____출력 버퍼 크기 = 80 × (4 + 100 × 20) = 160 320 바이트

number of classes: 80 은 C5 의 coco.names(80 줄)와 같은 COCO 클래스 순서다. 이름 파일을 그대로 다시 쓴다.

🤔 이해 확인

이 쪽에서 설명한 내용만으로 답할 수 있다. 답을 펼치기 전에 먼저 말로 답해 본다.

1. 호스트를 apt full-upgrade 했더니 "No Hailo device found" 가 났다. ROS 코드는 바꾸지 않았다. 원인은 무엇인가.

호스트의 드라이버와 펌웨어가 올라갔지만 컨테이너의 HailoRT 라이브러리는 그대로라 버전이 어긋난 것이다. 새 버전의 패키지를 받아 Dockerfile 의 HAILORT_VERSION 을 바꾸고 이미지를 다시 빌드한다.

2. 이 가이드가 쓰는 모델 파일의 출력은 C6 의 ONNX 출력과 무엇이 다른가.

ONNX 는 8400 개 후보 텐서라 노드가 점수 필터와 NMS 를 직접 했다. 이 .hef 는 NMS 까지 포함해 클래스별 박스 목록(최대 100 개씩, 80 클래스)을 낸다. 그래서 C8 의 후처리는 목록을 읽어 좌표를 되돌리는 것뿐이다.

3. find_package(HailoRT 4.23.0 EXACT REQUIRED) 는 무엇을 잡고 무엇을 못 잡는가.

컨테이너의 HailoRT 가 없거나 4.23.0 이 아니면 빌드가 멈춘다 — 컨테이너 쪽 어긋남을 빌드 시점에 잡는다. 호스트 드라이버와의 일치는 보지 못하므로 양쪽 identify 비교로 따로 확인한다.
