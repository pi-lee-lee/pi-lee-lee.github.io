05 · TF2와 URDF

로봇의 좌표계 세우기 — TF2와 URDF

라이다가 "전방 2.3 m 에 물체"라고 말해도, 그 점이 로봇 기준 어디인지, 지도 기준 어디인지 모르면 아무것도 할 수 없다. 그 변환 사슬을 시간과 함께 관리하는 것이 TF2 이고, 사슬의 고정된 부분(몸통에 볼트로 붙은 관계)을 기술하는 파일이 URDF 다. TF 는 자율주행의 키스톤이다. 07~10 단계에서 막히는 사람의 대부분이 여기를 대충 넘긴 사람이다.

이 단계가 끝나면

로봇의 TF 트리를 그림(view_frames PDF)으로 확인하고, 임의의 두 좌표계 사이 변환을 tf2_echo 로 조회할 수 있다. map → odom → base_link 가 왜 나뉘어 있는지 남에게 설명할 수 있고, 06 단계에서 쓸 C++ TF 브로드캐스트/조회 코드의 모양을 알고 있다. 그리고 섀시를 자로 재서 URDF 의 빈칸을 채웠다.

"TF 는 나중에 필요할 때 보면 되지"가 가장 비싼 오해다. 07 의 /scan 이 Foxglove 에 안 보이는 이유, 09 의 지도가 휘는 이유, 10 의 카메라-라이다 융합이 틀리는 이유가 전부 이 단계의 실측값과 프레임 이름이다. 여기서 30분 재는 것이 뒤에서 3일을 아낀다.

1. 개요 — 왜 TF 가 필요한가

라이다가 "전방 2.3 m 지점에 물체가 있다"고 알려 줬다고 하자. 이것만으로는 아무것도 할 수 없다. 질문이 줄줄이 따라온다.

  • 라이다의 "전방"은 로봇의 전방과 같은가? (뒤집어 달았을 수도 있다)
  • 라이다는 로봇 중심에서 앞으로 5 cm, 위로 9 cm 에 있다. 그럼 로봇 중심 기준으로는?
  • 로봇은 지금 지도상 (3.2, 1.7) 지점에서 45도 돌아 있다. 그럼 지도 기준으로는?
     "라이다 기준 (2.3, 0)"
              ↓  laser_link → base_link 변환        ← URDF (고정, 이 단계)
     "로봇 기준 (2.35, 0)"
              ↓  base_link → odom 변환              ← mcu_bridge (06단계, 엔코더 적분)
     "출발점 기준 (5.1, 3.2)"
              ↓  odom → map 변환                    ← SLAM (09단계, 스캔 매칭 보정)
     "지도 기준 (5.3, 3.0)"  ← 이제서야 "저기에 벽이 있다"고 말할 수 있다

TF2 는 이 변환 사슬을 시간과 함께 관리하는 시스템이다. 각 노드는 자기가 아는 변환만 발행하고, TF2 가 그것들을 이어 붙여 "임의의 A 기준에서 본 B" 를 특정 시각에 대해 계산해 준다. "시간과 함께"가 중요하다 — 0.1초 전 스캔은 0.1초 전 로봇 자세로 변환해야 한다.

표준 TF 트리 — 우리가 만들 것

   map                      ← SLAM / AMCL 이 발행 (09단계)
    │                          "출발점이 지도상 어디였는지" 보정값
    │                          드물게, 튀듯이 갱신됨
    └── odom                 ← mcu_bridge 가 발행 (06단계)
         │                     "출발점 기준 현재 위치" 엔코더 적분
         │                     연속적, 부드러움. 하지만 오차가 누적됨
         └── base_footprint   ← URDF (지면 투영점, z=0 이 바닥)
              └── base_link   ← URDF (로봇 몸통 기준, 바퀴 축 높이)
                   ├── laser_link              ← /scan 의 frame_id
                   ├── imu_link                ← /imu/data_raw 의 frame_id (06, MCU 가 IMU 를 읽는다)
                   ├── camera_link
                   │    └── camera_optical_link ← /camera/image_raw 의 frame_id
                   ├── left_wheel_link          ← /joint_states 로 회전
                   ├── right_wheel_link
                   └── caster_link

이 트리에서 URDF 가 책임지는 부분은 base_footprint 이하 전부다. map → odom, odom → base_footprint 는 다른 노드가 실시간으로 발행한다. 그래서 이 단계가 끝나도 view_frames 에는 odom 이 보이지 않는다 — 06 단계에서 붙는다.

2. 원리 — 왜

2-1. 왜 map 과 odom 을 나누는가 — 가장 중요한 설계

odom → base_linkmap → odom
발행자휠 오도메트리 (mcu_bridge)SLAM / AMCL
성질연속적 (튀지 않음)불연속 (보정 시 튐)
정확도단기 정확, 장기 누적오차장기 정확
용도제어 루프 (부드러워야 함)전역 위치

핵심: 제어기는 부드러운 odom 을 쓰고, 경로 계획은 정확한 map 을 쓴다. 만약 SLAM 이 map → base_link 를 직접 발행하면, 위치 보정이 일어날 때마다 로봇 위치가 순간이동해서 제어기가 미쳐 버린다. 그래서 보정량을 map → odom 에 몰아넣는다. 이것이 ROS 의 표준 설계 (REP-105)다. 두 변환을 곱하면 결국 map 기준 위치가 나오므로 정보는 잃지 않는다.

철칙: 하나의 좌표계에는 부모가 하나뿐이다

두 노드가 같은 자식 프레임의 TF 를 동시에 발행하면 TF 트리가 떨리면서 모든 것이 망가진다. 06 단계의 mcu_bridge 에 publish_tf 파라미터가 있는 이유가 이것이다 — 나중에 IMU 를 융합하는 EKF 가 odom → base_link 를 대신 발행하게 되면 브리지 쪽을 꺼야 한다. 3-8 에서 이 떨림을 직접 재현해 본다.

2-2. 좌표 규약 — 외워야 하는 것

REP-103: 로봇 본체 좌표계

        z (위)
        │
        │
        └────── x (앞)
       ╱
      y (왼쪽)
  • 오른손 좌표계, 단위는 미터와 라디안
  • yaw = z축 회전, 반시계가 +
  • 로봇이 정면을 보고 있으면 yaw = 0

광학 좌표계는 다르다

카메라 영상 처리(OpenCV) 관례는 전혀 다르다.

        ┌──────── x (오른쪽)
        │
        │  z = 광축 방향 (화면 안쪽)
        y (아래)

그래서 URDF 에 camera_link(로봇 규약)와 camera_optical_link(광학 규약)를 둘 다 두고, 그 사이를 rpy = (-π/2, 0, -π/2) 로 연결한다. 이미지 관련 메시지(camera_info, 포인트클라우드, 08b 의 검출 결과를 3D 로 올릴 때)는 camera_optical_link 를 쓴다.

이 값을 왜 외우는가

직접 유도하려면 회전행렬 두 번을 곱해야 한다. 실무에서는 그냥 관례로 쓴다. 다만 왜 두 개가 필요한지는 이해해야 한다 — 두 규약을 한 프레임에 섞으면 어느 쪽 코드가 봐도 축이 틀린다. 08a 에서 OpenCV 로 "화면 오른쪽 아래"의 픽셀을 다룰 때 이 z-전방 규약을 다시 만난다.

2-3. URDF — 로봇의 형상을 XML 로

우리 URDF: ros2_ws/src/rpi5_description/urdf/rpi5_robot.urdf.xacro. 구성 요소는 두 가지뿐이다.

<link name="laser_link">     <!-- 물체 (좌표계를 가진 강체) -->
  <visual>   ... </visual>     <!-- 눈에 보이는 모양 (Foxglove/RViz 용) -->
  <collision>... </collision>  <!-- 충돌 판정용 모양 -->
  <inertial> ... </inertial>   <!-- 질량/관성 (시뮬레이션용) -->
</link>

<joint name="laser_joint" type="fixed">   <!-- 두 링크의 관계 -->
  <parent link="base_link"/>
  <child  link="laser_link"/>
  <origin xyz="0.05 0 0.09" rpy="0 0 0"/>  <!-- 부모 기준 자식의 위치/자세 -->
</joint>
joint type의미우리 로봇에서TF 로 나가는 곳
fixed고정. 절대 안 움직임라이다, 카메라 마운트, 캐스터/tf_static (한 번 발행)
continuous무한 회전바퀴/tf (/joint_states 가 올 때마다)
revolute각도 제한 있는 회전(아커만 조향이면 사용)/tf
prismatic직선 이동(해당 없음)/tf

robot_state_publisher 는 URDF 를 읽어 고정 조인트는 /tf_static 에 한 번, 움직이는 조인트는 /joint_states 를 받을 때마다 /tf 에 발행한다. 따라서 /joint_states 를 아무도 발행하지 않으면 바퀴 링크가 TF 트리에서 빠진다 — 3-9 의 use_fake_joints 가 그 빈자리를 채우는 장치다.

xacro — URDF 의 매크로 확장

순수 URDF 는 반복이 심하다. 바퀴 4개를 쓰려면 똑같은 XML 을 4번 쓴다. xacro 는 변수와 매크로를 제공한다.

<xacro:property name="wheel_radius" value="0.0325"/>
...
<origin xyz="0 0 ${wheel_radius}"/>                       <!-- 변수 사용 -->
<origin xyz="0 ${reflect * wheel_separation/2} 0"/>       <!-- 수식도 가능 -->

<xacro:macro name="wheel" params="prefix reflect"> ... </xacro:macro>
<xacro:wheel prefix="left"  reflect="1"/>
<xacro:wheel prefix="right" reflect="-1"/>

바퀴 반지름을 바꿀 때 한 곳만 고치면 된다. 이것이 xacro 를 쓰는 이유다. 런치 시점에 xacro 명령이 이 파일을 순수 URDF 로 전개해서 robot_state_publisher 에 넘긴다(3-9).

2-4. /tf 와 /tf_static 의 QoS 가 다른 이유

03 단계 §2-7 의 QoS 가 여기서 실물로 나온다. /tf_static 은 Durability = TRANSIENT_LOCAL 로 발행된다. 고정 변환은 시작할 때 한 번만 발행되는데, 그 뒤에 뜬 노드(SLAM, Foxglove)도 그 값을 받아야 하기 때문이다 — "구독 전에 발행된 마지막 값도 받는다"가 TRANSIENT_LOCAL 의 뜻이다. 반대로 /tf 는 초당 수십 번 갱신되므로 기본 VOLATILE 로 충분하다. ros2 topic info /tf_static -v 로 직접 확인한다(3-6). 직접 TF 를 구독하는 코드를 쓸 일은 거의 없고, tf2_ros::Buffer 가 이 QoS 를 알아서 맞춰 준다.

3-1. 실측 — 이 단계에서 가장 중요한 작업 HW

URDF 의 ____ 자리를 자로 재서 채운다. 추측하지 않는다. 측정값은 hardware/INVENTORY.md 3절(라이다 장착)과 6절(구동계)에 먼저 적고, 그 다음 xacro 로 옮긴다.

값재는 법틀리면 생기는 일
wheel_radius바퀴 지름 ÷ 2. 로봇을 올려놓은 상태에서 눌린 높이 기준(고무 바퀴는 하중으로 1~2 mm 눌린다)오도메트리 거리가 비례해서 틀림 (1 m 갔는데 0.9 m 로 기록)
wheel_separation좌우 바퀴의 접지점 사이 거리 (바퀴 폭의 중앙끼리)회전량이 틀림. 90도 돌렸는데 85도로 기록 → SLAM 지도가 휜다
lidar_x / y / zbase_link 원점(바퀴 축 중점, 축 높이)에서 라이다 회전축까지. z 는 바닥이 아니라 바퀴 축 높이 기준벽이 실제보다 안쪽/바깥쪽에 그려짐
lidar_yaw라이다의 0° 방향과 로봇 정면의 각도 차. 0° 방향은 모델마다 다르므로 07 단계의 벽 실험으로 확정하고 여기로 돌아와 적는다지도가 전체적으로 회전해서 그려짐
cam_x / y / z / pitch렌즈 중심까지. 아래로 기울였으면 pitch 가 + 값08b 검출 결과를 3D 로 올릴 때 방향이 틀림
imu_x / y / zIMU 칩 중심까지. 칩의 축이 REP-103(x 앞, y 왼쪽, z 위)과 맞게 장착하거나 06 의 펌웨어에서 축을 재매핑한다. URDF 의 주석 처리된 imu_link 블록을 살려 쓴다기울기 판정과 EKF 의 각속도 부호가 뒤집힌다
base_length / width / height몸통 외곽. Nav2 의 robot_radius 계산 근거(09)코스트맵 부풀림이 틀려 벽에 긁히거나 통로를 못 지남
wheel_separation 이 5 mm 틀리면

간격이 145 mm 라면 3.5 % 오차다. 회전량은 Δθ = (Δd_right − Δd_left) / L 이므로 L 이 3.5 % 틀리면 회전량도 3.5 % 틀린다. 로봇이 한 바퀴(360도) 돌면 12.6도가 어긋난다. SLAM 이 이를 보정하려 애쓰다가 지도가 뭉개진다. "SLAM 지도가 휘어요"의 원인 1위가 이것이다. 06 단계의 360도 회전 캘리브레이션으로 미세 조정하지만, 출발점은 자로 잰 값이어야 한다.

base_link 원점을 어디에 둘 것인가

차동구동 로봇은 좌우 바퀴 축의 중점에 두는 것이 관례다. 이 점이 제자리 회전의 중심이기 때문에 운동학 수식이 가장 단순해진다. base_footprint 는 그 점을 지면에 투영한 것이고, URDF 에서 base_footprint → base_link 는 z 로 wheel_radius 만큼 띄워 놓았다. 그래서 바퀴 반지름이 틀리면 로봇 모형이 지면에 파묻히거나 떠 보인다.

3-2. xacro 에 실측값 반영 Mac

ros2_ws/src/rpi5_description/urdf/rpi5_robot.urdf.xacro 상단의 property 블록을 Mac 에서 편집한다. 값은 미터다. 145 mm 면 0.145.

<xacro:property name="wheel_radius"     value="____"/>  <!-- m, 하중 상태 지름 ÷ 2 -->
<xacro:property name="wheel_separation" value="____"/>  <!-- m, 접지점 사이 -->
<xacro:property name="lidar_x"   value="____"/>
<xacro:property name="lidar_y"   value="____"/>
<xacro:property name="lidar_z"   value="____"/>  <!-- base_link(바퀴 축 높이) 기준 -->
<xacro:property name="lidar_yaw" value="0.0"/>   <!-- 07 단계 벽 실험 후 확정 -->

편집 후 Pi 로 동기화한다: ./scripts/sync-to-pi.sh (02 단계 §3-2).

단위 실수를 잡는 습관

cm 를 m 자리에 적는 실수가 가장 흔하다(14.5 → 로봇이 14.5 m 짜리가 된다). 3-6 의 tf2_echo 출력이 자로 잰 값과 소수점 자리까지 맞는지 본다. Foxglove 3D 에서 로봇이 화면을 꽉 채우면 100배 틀린 것이다.

3-8. 실험: 정적 변환을 손으로 붙이고, 부모 둘을 만들어 보기

TF 트리는 여러 노드가 낸 조각을 이어 붙인 것이다. 그 사실을 손으로 확인한다. Humble 의 static_transform_publisher 는 이름 있는 인자를 쓴다.

# 터미널 A: base_link 아래에 test_link 를 붙인다 (x 0.1 m 앞, z 0.05 m 위)
ros2 run tf2_ros static_transform_publisher \
  --x 0.1 --y 0 --z 0.05 --yaw 0 --pitch 0 --roll 0 \
  --frame-id base_link --child-frame-id test_link

# 터미널 B
ros2 run tf2_ros tf2_echo base_footprint test_link
#   → Translation: [0.100, 0.000, wheel_radius + 0.050] ← 두 변환이 합성된 값이 나온다
ros2 run tf2_tools view_frames               # 트리에 test_link 가 매달려 있다

이제 철칙을 깨 본다. 터미널 C 에서 같은 자식에 다른 부모를 붙인다.

ros2 run tf2_ros static_transform_publisher \
  --x 0 --y 0 --z 0 --yaw 0 --pitch 0 --roll 0 \
  --frame-id laser_link --child-frame-id test_link

ros2 run tf2_ros tf2_echo base_footprint test_link   # 값이 두 가지 사이에서 흔들리거나 경고가 섞인다

이것이 "TF 가 떨린다"의 실체다. 어느 쪽이 맞는지 TF2 는 판단하지 않고 마지막으로 들어온 부모를 쓴다. 실험이 끝나면 세 터미널을 모두 Ctrl+C 로 끝낸다.

static_transform_publisher 는 언제 실무에서 쓰는가

URDF 를 고치기 전에 "센서를 여기에 달면 어떻게 보일까"를 빠르게 시험할 때, 또는 URDF 에 넣기 애매한 외부 장치(삼각대 위 카메라)를 붙일 때다. 로봇 몸에 고정된 것은 전부 URDF 에 넣는 것이 원칙이다 — 한 곳에서 관리되어야 하기 때문이다.

3-9. description.launch.py 읽기 — use_fake_joints 와 ParameterValue

ros2_ws/src/rpi5_description/launch/description.launch.py 를 열어 두 가지를 확인한다.

# xacro 를 실행해서 그 표준출력(=URDF XML)을 파라미터 값으로 넘긴다.
robot_description = ParameterValue(
    Command(['xacro ', xacro_file]), value_type=str
)

① ParameterValue(..., value_type=str) 함정. 이것을 빼면 런치 시스템이 XML 문자열을 YAML 로 해석하려 들어 다른 타입으로 잘못 추론하고, robot_state_publisher 가 "Invalid parameter type" 으로 죽는다. Humble 에서 가장 흔한 런치 함정 중 하나다.

② use_fake_joints. joint_state_publisher 는 바퀴(continuous 조인트)의 각도를 가짜로(0 rad) /joint_states 에 발행한다. 그래야 robot_state_publisher 가 바퀴 TF 를 만들어 트리가 완결된다. 06 단계부터는 mcu_bridge 가 엔코더로 진짜 /joint_states 를 발행하므로 이 노드를 꺼야 한다. rpi5_bringup/launch/robot.launch.py 는 이미 use_mcu 의 반대값을 use_fake_joints 로 넘긴다 — 두 노드가 같은 토픽을 발행하면 바퀴 TF 가 두 값 사이에서 떨리기 때문이다. 3-8 에서 본 것과 같은 종류의 문제다.

3-10. TF 를 코드에서 만지는 두 가지 방법 — C++ 미리보기 C++

이 단계에서는 읽기만 한다. 06 단계에서 (a)를, 10 단계에서 (b)를 실제로 쓴다. 두 패턴의 모양을 미리 눈에 익혀 두면 그때 "TF 코드"가 아니라 "운동학"에 집중할 수 있다.

(a) 발행 — 06 의 mcu_bridge 가 odom → base_link 를 보내는 코드

#include "geometry_msgs/msg/transform_stamped.hpp"
#include "tf2/LinearMath/Quaternion.h"
#include "tf2_geometry_msgs/tf2_geometry_msgs.hpp"   // tf2::toMsg(q) 를 위해
#include "tf2_ros/transform_broadcaster.h"

// 멤버:     std::unique_ptr<tf2_ros::TransformBroadcaster> tf_broadcaster_;
// 생성자:   tf_broadcaster_ = std::make_unique<tf2_ros::TransformBroadcaster>(*this);

void publish_odom_tf(double x, double y, double yaw)
{
  geometry_msgs::msg::TransformStamped tf;
  tf.header.stamp = this->get_clock()->now();
  tf.header.frame_id = "odom";           // 부모
  tf.child_frame_id = "base_link";       // 자식 — 부모는 하나뿐 (2-1 철칙)
  tf.transform.translation.x = x;
  tf.transform.translation.y = y;
  tf.transform.translation.z = 0.0;
  tf2::Quaternion q;
  q.setRPY(0.0, 0.0, yaw);               // 평면 로봇은 yaw 만 변한다
  tf.transform.rotation = tf2::toMsg(q);
  tf_broadcaster_->sendTransform(tf);
}

(b) 조회 — 10 의 감독 노드가 "카메라가 본 것"을 로봇 기준으로 옮기는 코드

#include "tf2_ros/buffer.h"
#include "tf2_ros/transform_listener.h"

// 멤버
std::unique_ptr<tf2_ros::Buffer> tf_buffer_;
std::shared_ptr<tf2_ros::TransformListener> tf_listener_;
// 생성자 — Listener 가 /tf, /tf_static 을 구독해 Buffer 를 채운다 (QoS 도 알아서 맞춘다)
tf_buffer_ = std::make_unique<tf2_ros::Buffer>(this->get_clock());
tf_listener_ = std::make_shared<tf2_ros::TransformListener>(*tf_buffer_);

// 조회 — 실패는 예외로 온다. 반드시 잡는다 (TF 는 늦게 도착할 수 있다)
try {
  auto t = tf_buffer_->lookupTransform(
    "base_link", "camera_optical_link", tf2::TimePointZero);   // Zero = 가장 최근 값
  RCLCPP_INFO(get_logger(), "camera at x=%.3f z=%.3f",
              t.transform.translation.x, t.transform.translation.z);
} catch (const tf2::TransformException & ex) {
  RCLCPP_WARN_THROTTLE(get_logger(), *get_clock(), 2000, "TF lookup failed: %s", ex.what());
}

lookupTransform(target, source, time) 은 "source 프레임의 점을 target 프레임으로 옮기는 변환"을 준다. 인자 순서를 헷갈리면 부호가 뒤집힌다 — tf2_echo base_link laser_link 와 같은 순서라고 기억한다. tf2::TimePointZero 대신 메시지의 header.stamp 를 넣으면 그 시각의 변환을 준다(센서 데이터를 올바른 자세로 옮길 때). 그 시각의 TF 가 아직 안 왔으면 예외가 나므로 try/catch 가 필수다.

✅ 검증 체크포인트

🤔 이해 확인

1. SLAM 이 map → base_link 를 직접 발행하면 안 되는 이유는?
SLAM 의 위치 보정은 불연속적(루프 클로저 시 위치가 갑자기 점프)이다. 제어기가 이 값을 쓰면 로봇이 순간이동한 것처럼 보여 제어가 폭주한다. 그래서 보정량은 map → odom 에 넣고, 제어기는 연속적인 odom → base_link 를 쓴다. 두 변환을 곱하면 결국 map 기준 위치가 나온다.
2. wheel_separation 을 실제보다 크게 적으면 어떤 증상이 나타나는가?
회전 각속도 계산 ω = (v_r − v_l)/L 에서 L 이 크므로 ω 가 작게 추정된다. 즉 실제로 90도 돌았는데 오도메트리는 80도만 돌았다고 기록한다. SLAM 은 스캔 매칭 결과와 이 오도메트리가 계속 어긋나 지도를 휘게 만든다.
3. camera_optical_link 가 따로 필요한 이유는?
로봇 좌표 규약(REP-103, x=앞)과 영상 처리 규약(OpenCV, z=광축)이 다르기 때문이다. 두 규약을 한 프레임에 섞으면 어느 쪽 코드가 봐도 축이 틀린다. 그래서 두 프레임을 두고 그 사이 회전(rpy = −π/2, 0, −π/2)으로 연결한다.
4. TF 가 미세하게 떨린다면 가장 먼저 무엇을 의심하는가?
같은 자식 프레임을 두 노드가 동시에 발행하고 있는지. 예를 들어 mcu_bridge 가 publish_tf:=true 이고 동시에 robot_localization(EKF)도 odom → base_link 를 쏘는 경우, 또는 joint_state_publisher 와 mcu_bridge 가 둘 다 /joint_states 를 내는 경우. 한쪽을 꺼야 한다. 3-8 에서 직접 재현했다.
5. /tf_static 이 TRANSIENT_LOCAL 로 발행되는 이유는? VOLATILE 이면 무엇이 깨지는가?
고정 변환은 시작할 때 한 번만 발행된다. VOLATILE 이면 그 뒤에 뜬 구독자(SLAM, Foxglove, 나중에 띄운 내 노드)는 그 값을 영원히 받지 못해 base_link → laser_link 를 모른다. TRANSIENT_LOCAL 은 발행자가 마지막 값을 보관해 두고 늦게 온 구독자에게도 준다. 03 단계 §2-7 의 Durability 가 실물로 쓰이는 곳이다.
6. lookupTransform 을 try/catch 로 감싸야 하는 이유는?
TF 는 다른 노드가 네트워크로 보내는 데이터라 아직 도착하지 않았거나(노드 기동 직후), 요청한 시각의 값이 버퍼에 없거나(extrapolation), 프레임 이름이 틀렸을 수 있다. tf2 는 이 모두를 tf2::TransformException 예외로 알린다. 잡지 않으면 노드가 죽는다. 조회 실패는 정상적인 일시 상태이므로 throttle 된 경고로 넘기고 다음 주기에 다시 시도한다.
7. view_frames 의 트리에 바퀴 링크가 보이지 않는다. 무엇이 빠진 것인가?
/joint_states 발행자다. robot_state_publisher 는 고정 조인트는 URDF 만으로 /tf_static 에 내지만, continuous 조인트(바퀴)는 현재 각도를 알아야 하므로 /joint_states 가 와야 /tf 에 낸다. 이 단계에서는 joint_state_publisher(use_fake_joints:=true)가, 06 단계부터는 mcu_bridge 가 그 역할을 한다.
8. static_transform_publisher 로 붙인 변환과 URDF 에 적은 변환은 TF2 입장에서 무엇이 다른가?
아무것도 다르지 않다. 둘 다 /tf_static 으로 들어오는 TransformStamped 다. TF2 는 발행자가 누구인지 구분하지 않고 이어 붙인다. 차이는 관리 측면이다 — 로봇 몸에 고정된 것은 URDF 한 곳에서 관리해야 실측값을 고칠 때 한 번만 고치면 되고, Foxglove 가 형상까지 그릴 수 있다.
