05 · TF2와 URDF

로봇의 좌표계 세우기 — TF2와 URDF

라이다가 "전방 2.3 m 에 물체"라고 말해도, 그 점이 로봇 기준 어디인지, 지도 기준 어디인지 모르면 아무것도 할 수 없다. 그 변환 사슬을 시간과 함께 관리하는 것이 TF2 이고, 사슬의 고정된 부분(몸통에 볼트로 붙은 관계)을 기술하는 파일이 URDF 다. TF 는 특별한 서브시스템이 아니라 /tf·/tf_static 두 개의 평범한 토픽과 그 위에 얹은 약속이다 — 1-1 에서 먼저 확인한다. TF 는 자율주행의 키스톤이다. 07~10 단계에서 막히는 사람의 대부분이 여기를 대충 넘긴 사람이다.

이 단계가 끝나면

로봇의 TF 트리를 그림(view_frames PDF)으로 확인하고, 임의의 두 좌표계 사이 변환을 tf2_echo 로 조회할 수 있다. map → odom → base_link 가 왜 나뉘어 있는지 남에게 설명할 수 있고, 06 단계에서 쓸 C++ TF 브로드캐스트/조회 코드의 모양을 알고 있다. 그리고 섀시를 자로 재서 URDF 의 빈칸을 채웠다.

"TF 는 나중에 필요할 때 보면 되지"가 가장 비싼 오해다. 07 의 /scan 이 Foxglove 에 안 보이는 이유, 09 의 지도가 휘는 이유, 10 의 카메라-라이다 융합이 틀리는 이유가 전부 이 단계의 실측값과 프레임 이름이다. 여기서 30분 재는 것이 뒤에서 3일을 아낀다.

1. 개요 — TF 란 무엇인가

1-1. 먼저 — TF 는 토픽이다

이것부터 확인하고 시작한다. 여기를 건너뛰면 TF 를 "ROS 안의 별개 장치" 같은 것으로 오해하게 되고, 뒤의 모든 설명이 어긋난다.

ros2 topic list | grep tf     # →  /tf      /tf_static      ← 토픽으로 존재한다
ros2 node  list | grep tf     # →  (없음)                    ← TF 노드는 없다

토픽은 이 두 개가 전부다. 조율하는 중앙 노드도, 숨은 서비스도 없다. ros2 topic echo /tf 로 내용을 그대로 들여다볼 수 있다. "TF" 라는 말이 가리키는 것은 문맥에 따라 셋이다 — 헷갈리는 지점이므로 여기서 갈라 둔다.

말할 때의 "TF"정체토픽인가
/tf, /tf_static토픽 이름. 타입은 tf2_msgs/msg/TFMessage✅ 토픽
TF2, tf2_ros라이브러리 — Buffer, TransformListener, TransformBroadcaster❌ 라이브러리
"TF 트리", "TF 가 떨린다"좌표 변환이라는 개념과 그 데이터❌ 개념
그래서 TF 는 "약속"이다

메시지 타입(TFMessage) · 토픽 이름(/tf, /tf_static) · QoS(2-4) 세 가지를 지키기로 한 약속이고, tf2_ros 는 그 약속대로 쓰기 쉽게 만든 라이브러리다. 그래서 어느 노드든 그 약속만 지키면 발행자가 될 수 있다 — 3-8 에서 명령줄 한 줄로 직접 해 본다.

1-2. 무엇이 흐르는가 — 메시지의 구조

포맷은 엄격하게 고정이다. ROS 2 는 타입이 있는 pub/sub 이라, 타입이 맞지 않으면 발행자와 구독자가 서로 보이지도 않는다.

tf2_msgs/msg/TFMessage
└── geometry_msgs/TransformStamped[] transforms   ← 배열. 한 메시지에 엣지 여러 개

    geometry_msgs/TransformStamped                ← 트리의 엣지 한 개 + 시각
    ├── std_msgs/Header header
    │   ├── builtin_interfaces/Time stamp         언제 시점의 관계인가
    │   └── string frame_id                       부모 프레임 이름   예) "odom"
    ├── string child_frame_id                     자식 프레임 이름   예) "base_footprint"
    └── geometry_msgs/Transform transform
        ├── Vector3    translation  (x, y, z)     이동, 단위 m
        └── Quaternion rotation  (x, y, z, w)     회전

필드의 이름·타입·개수는 고정이고 값만 각 노드가 채운다. 3-10 의 C++ 코드가 이 필드를 하나씩 채우는 모습이다.

여기서 가장 중요한 한 가지 — 발행되는 것은 트리가 아니라 엣지 낱개다

TransformStamped 하나는 부모 하나 ↔ 자식 하나의 관계일 뿐이다. 트리 전체를 담는 메시지는 존재하지 않는다. 각 발행자는 자기가 아는 한 칸만 쏘고, 트리는 받는 쪽 메모리 안에서만 조립된다(1-4 · 2-5).

그리고 프레임 이름은 그냥 문자열이다. "map" 이 무엇을 뜻하는지는 이 포맷 어디에도 없다 — 그건 REP-105 라는 별도의 합의이고(2-1), TF2 자체는 "banana" 도 똑같이 유효한 이름으로 받아들인다.

1-3. 왜 필요한가

라이다가 "전방 2.3 m 지점에 물체가 있다"고 알려 줬다고 하자. 이것만으로는 아무것도 할 수 없다. 질문이 줄줄이 따라온다.

  • 라이다의 "전방"은 로봇의 전방과 같은가? (뒤집어 달았을 수도 있다)
  • 라이다는 로봇 중심에서 앞으로 5 cm, 위로 9 cm 에 있다. 그럼 로봇 중심 기준으로는?
  • 로봇은 지금 지도상 (3.2, 1.7) 지점에서 45도 돌아 있다. 그럼 지도 기준으로는?
     "라이다 기준 (2.3, 0)"
              ↓  laser_link → base_link 변환        ← URDF (고정, 이 단계)
     "로봇 기준 (2.35, 0)"
              ↓  base_link → odom 변환              ← mcu_bridge (06단계, 엔코더 적분)
     "출발점 기준 (5.1, 3.2)"
              ↓  odom → map 변환                    ← SLAM (09단계, 스캔 매칭 보정)
     "지도 기준 (5.3, 3.0)"  ← 이제서야 "저기에 벽이 있다"고 말할 수 있다

TF2 는 이 변환 사슬을 시간과 함께 관리하는 시스템이다. 각 노드는 자기가 아는 변환만 발행하고, TF2 가 그것들을 이어 붙여 "임의의 A 기준에서 본 B" 를 특정 시각에 대해 계산해 준다. "시간과 함께"가 중요하다 — 0.1초 전 스캔은 0.1초 전 로봇 자세로 변환해야 한다.

1-4. 표준 TF 트리 — 우리가 만들 것

   map                      ← SLAM / AMCL 이 발행 (09단계)
    │                          "출발점이 지도상 어디였는지" 보정값
    │                          드물게, 튀듯이 갱신됨
    └── odom                 ← mcu_bridge 가 발행 (06단계)
         │                     "출발점 기준 현재 위치" 엔코더 적분
         │                     연속적, 부드러움. 하지만 오차가 누적됨
         └── base_footprint   ← URDF (지면 투영점, z=0 이 바닥)
              └── base_link   ← URDF (로봇 몸통 기준, 바퀴 축 높이)
                   ├── laser_link              ← /scan 의 frame_id
                   ├── imu_link                ← /imu/data_raw 의 frame_id (06, MCU 가 IMU 를 읽는다)
                   ├── camera_link
                   │    └── camera_optical_link ← /camera/image_raw 의 frame_id
                   ├── front_left_wheel_link   ← /joint_states 로 회전 (4륜 전부)
                   ├── front_right_wheel_link
                   ├── rear_left_wheel_link
                   └── rear_right_wheel_link

이 트리에서 URDF 가 책임지는 부분은 base_footprint 이하 전부다. map → odom, odom → base_footprint 는 다른 노드가 실시간으로 발행한다. 그래서 이 단계가 끝나도 view_frames 에는 odom 이 보이지 않는다 — 06 단계에서 붙는다.

2. 원리 — 왜

2-1. 왜 map 과 odom 을 나누는가 — 가장 중요한 설계

odom → base_linkmap → odom
발행자휠 오도메트리 (mcu_bridge)
표기는 REP-105 기준. 실제 발행 엣지는 odom → base_footprint — URDF 루트가 그것이기 때문이다 (06 §2-5 ④)		SLAM / AMCL
성질연속적 (튀지 않음)불연속 (보정 시 튐)
정확도단기 정확, 장기 누적오차장기 정확
용도제어 루프 (부드러워야 함)전역 위치

핵심: 제어기는 부드러운 odom 을 쓰고, 경로 계획은 정확한 map 을 쓴다. 만약 SLAM 이 map → base_link 를 직접 발행하면, 위치 보정이 일어날 때마다 로봇 위치가 순간이동해서 제어기가 미쳐 버린다. 그래서 보정량을 map → odom 에 몰아넣는다. 이것이 ROS 의 표준 설계 (REP-105)다. 두 변환을 곱하면 결국 map 기준 위치가 나오므로 정보는 잃지 않는다.

철칙: 하나의 좌표계에는 부모가 하나뿐이다

두 노드가 같은 자식 프레임의 TF 를 발행하면 TF2 는 마지막으로 들어온 값을 쓴다. 어느 쪽이 맞는지 판단하지 않고, 경고도 내지 않는다. /tf(동적)면 둘이 계속 쏘므로 값이 번갈아 나타나고(떨림), /tf_static이면 조용히 한쪽 값으로 고정된다 — 후자가 더 위험하다. 3-8 에서 둘을 구분해 본다.

06 단계의 mcu_bridge 에 publish_tf 파라미터가 있는 이유가 이것이다 — 나중에 IMU 를 융합하는 EKF 가 odom → base_footprint 를 대신 발행하게 되면 브리지 쪽을 꺼야 한다.

2-2. 좌표 규약 — 외워야 하는 것

REP-103: 로봇 본체 좌표계

        z (위)
        │
        │
        └────── x (앞)
       ╱
      y (왼쪽)
  • 오른손 좌표계, 단위는 미터와 라디안
  • yaw = z축 회전, 반시계가 +
  • 로봇이 정면을 보고 있으면 yaw = 0

광학 좌표계는 다르다

카메라 영상 처리(OpenCV) 관례는 전혀 다르다.

        ┌──────── x (오른쪽)
        │
        │  z = 광축 방향 (화면 안쪽)
        y (아래)

그래서 URDF 에 camera_link(로봇 규약)와 camera_optical_link(광학 규약)를 둘 다 두고, 그 사이를 rpy = (-π/2, 0, -π/2) 로 연결한다. 이미지 관련 메시지(camera_info, 포인트클라우드, 08b 의 검출 결과를 3D 로 올릴 때)는 camera_optical_link 를 쓴다.

이 값을 왜 외우는가

직접 유도하려면 회전행렬 두 번을 곱해야 한다. 실무에서는 그냥 관례로 쓴다. 다만 왜 두 개가 필요한지는 이해해야 한다 — 두 규약을 한 프레임에 섞으면 어느 쪽 코드가 봐도 축이 틀린다. 08a 에서 OpenCV 로 "화면 오른쪽 아래"의 픽셀을 다룰 때 이 z-전방 규약을 다시 만난다.

2-3. URDF — 로봇의 형상을 XML 로

우리 URDF: ros2_ws/src/rpi5_description/urdf/rpi5_robot.urdf.xacro. 구성 요소는 두 가지뿐이다.

<link name="laser_link">     <!-- 물체 (좌표계를 가진 강체) -->
  <visual>   ... </visual>     <!-- 눈에 보이는 모양 (Foxglove/RViz 용) -->
  <collision>... </collision>  <!-- 충돌 판정용 모양 -->
  <inertial> ... </inertial>   <!-- 질량/관성 (시뮬레이션용) -->
</link>

<joint name="laser_joint" type="fixed">   <!-- 두 링크의 관계 -->
  <parent link="base_link"/>
  <child  link="laser_link"/>
  <origin xyz="0.05 0 0.09" rpy="0 0 0"/>  <!-- 부모 기준 자식의 위치/자세 -->
</joint>
joint type의미우리 로봇에서TF 로 나가는 곳
fixed고정. 절대 안 움직임라이다, 카메라 마운트, IMU/tf_static (한 번 발행)
continuous무한 회전바퀴/tf (/joint_states 가 올 때마다)
revolute각도 제한 있는 회전(아커만 조향이면 사용)/tf
prismatic직선 이동(해당 없음)/tf

robot_state_publisher 는 URDF 를 읽어 고정 조인트는 /tf_static 에 한 번, 움직이는 조인트는 /joint_states 를 받을 때마다 /tf 에 발행한다. 따라서 /joint_states 를 아무도 발행하지 않으면 바퀴 링크가 TF 트리에서 빠진다 — 3-9 의 use_fake_joints 가 그 빈자리를 채우는 장치다.

xacro — URDF 의 매크로 확장

순수 URDF 는 반복이 심하다. 바퀴 4개를 쓰려면 똑같은 XML 을 4번 쓴다. xacro 는 변수와 매크로를 제공한다.

<xacro:property name="wheel_radius" value="0.0325"/>
...
<origin xyz="0 0 ${wheel_radius}"/>                       <!-- 변수 사용 -->
<origin xyz="${x_reflect * wheelbase/2} ${y_reflect * wheel_separation/2} 0"/>   <!-- 수식도 가능 -->

<xacro:macro name="wheel" params="prefix x_reflect y_reflect"> ... </xacro:macro>
<xacro:wheel prefix="front_left"  x_reflect="1"  y_reflect="1"/>
<xacro:wheel prefix="front_right" x_reflect="1"  y_reflect="-1"/>
<xacro:wheel prefix="rear_left"   x_reflect="-1" y_reflect="1"/>
<xacro:wheel prefix="rear_right"  x_reflect="-1" y_reflect="-1"/>

바퀴 반지름을 바꿀 때 한 곳만 고치면 된다. 이것이 xacro 를 쓰는 이유다. 런치 시점에 xacro 명령이 이 파일을 순수 URDF 로 전개해서 robot_state_publisher 에 넘긴다(3-9).

2-4. /tf 와 /tf_static 의 QoS 가 다른 이유

03 단계 §2-7 의 QoS 가 여기서 실물로 나온다. /tf_static 은 Durability = TRANSIENT_LOCAL 로 발행된다. 고정 변환은 시작할 때 한 번만 발행되는데, 그 뒤에 뜬 노드(SLAM, Foxglove)도 그 값을 받아야 하기 때문이다 — "구독 전에 발행된 마지막 값도 받는다"가 TRANSIENT_LOCAL 의 뜻이다. 반대로 /tf 는 초당 수십 번 갱신되므로 기본 VOLATILE 로 충분하다. ros2 topic info /tf_static -v 로 직접 확인한다(3-6). 직접 TF 를 구독하는 코드를 쓸 일은 거의 없고, tf2_ros::Buffer 가 이 QoS 를 알아서 맞춰 준다.

2-5. /tf 는 왜 보통 토픽처럼 다루지 않는가

1-1 에서 봤듯 /tf 는 평범한 토픽이다. 그런데 /scan 을 다루듯 create_subscription 으로 구독해서 쓰는 코드는 거의 없다. 토픽은 같은데 쓰는 방법이 다르다 — 그 차이가 어디서 오는지가 이 절이다.

보통 토픽 (/scan)/tf
발행자 수보통 1 (드라이버 하나)여럿 — 06 이후 3개 (아래)
메시지가 담는 것전체 — 그 순간의 스캔 한 장조각 — 트리의 엣지 한 칸
발행자가 여럿이면사고. 마지막 값이 이긴다정상. 겹치지만 않으면 이어 붙는다
구독 방법콜백을 직접 등록TransformListener 가 대신 구독 → Buffer
언제 읽는가메시지가 도착할 때내가 조회할 때 (lookupTransform)
과거 값안 남는다버퍼에 수 초치 이력, 보간까지 해 준다
없는 값을 물으면—빈 값이 아니라 예외가 난다 (3-10)

① 발행자가 여럿이어도 되는 이유 — 메시지가 "조각"이라서

우리 로봇의 /tf 발행자 명단이다. 아무도 전체를 모른다.

/tf         ├─ robot_state_publisher   바퀴 관절            (05)
            ├─ mcu_bridge  또는  EKF   odom → base_footprint (06 / 10, 둘 중 하나만!)
            └─ slam_toolbox            map → odom            (09)

/tf_static  └─ robot_state_publisher   base_footprint 이하 고정 전부 (05)

/cmd_vel 은 반대다. 메시지가 로봇 전체의 속도 명령이라 두 개가 오면 이어 붙일 방법이 없고 하나가 다른 하나를 덮는다 — 10 §2-4 가 그 이야기다. /tf 는 조각이라 합쳐지지만, 조각이 겹치는 순간(같은 자식 프레임) 똑같은 문제가 된다. 2-1 의 철칙이 그래서 필요하다.

② 구독하지 않고 조회하는 이유 — 세 가지가 콜백으로는 안 된다

문제콜백으로 최신값만 들고 있으면Buffer 라서 가능
도착 순서가 보장 안 됨스캔이 TF 보다 먼저 오면 변환 불가잠깐 기다렸다 조회 (타임아웃 인자)
과거 시각이 필요함0.05초 전 자세를 모른다이력 보관 + 보간
발행이 조각나 있음한 발행자도 map←base_link 를 모른다트리에서 경로를 찾아 합성

그래서 노드는 /tf 를 직접 구독하지 않고, 생성자에 Buffer 와 TransformListener 를 한 번 만들어 두고 필요할 때 당겨 온다(3-10 (b)). 버퍼는 중앙에 하나가 아니라 소비하는 노드마다 하나씩이다 — 그래서 그 두 줄이 노드마다 반복된다.

조회 결과도 같은 TransformStamped 다. 트리에 실제로 없는 쌍을 물어도 된다 — 08d 가 camera_optical_link ← laser_link 를 조회하는데, URDF 에 그 엣지는 없다. laser_link → base_link → camera_link → camera_optical_link 를 조회하는 순간 곱해서 만들어 준다.

③ 예외 하나 — 토픽 그대로 쓰는 곳

foxglove_bridge 는 조회하지 않는다. /tf·/tf_static 을 토픽 그대로 구독해서 통째로 Mac 으로 넘기고, 트리 조립은 Foxglove Studio 가 한다. ros2 bag record … /tf /tf_static 도 같다 — 그래서 bag 에 /tf_static 을 빼먹으면 재생할 때 트리가 끊긴다.

정리 — 포맷은 평범하고, 특별한 것은 그 위에 얹힌 것이다

TFMessage 는 sensor_msgs/LaserScan 이나 nav_msgs/Odometry 와 똑같은 방식의 평범한 메시지다. ROS 가 .msg 로 양식을 정하고 노드가 값을 채운다.

/tf 를 특별하게 만드는 것은 포맷이 아니라 — ① 조각을 나눠 발행한다는 규약, ② 그 조각을 시간축과 함께 모아 합성해 주는 라이브러리, ③ "부모는 하나"라는 트리 제약 셋이다. 셋 다 ROS 가 강제하지 않는다. 사람이 지켜야 한다.

wheel_separation 이 5 mm 틀리면

간격이 145 mm 라면 3.5 % 오차다. 회전량은 Δθ = (Δd_right − Δd_left) / L 이므로 L 이 3.5 % 틀리면 회전량도 3.5 % 틀린다. 로봇이 한 바퀴(360도) 돌면 12.6도가 어긋난다. SLAM 이 이를 보정하려 애쓰다가 지도가 뭉개진다. "SLAM 지도가 휘어요"의 원인 1위가 이것이다. 06 단계의 360도 회전 캘리브레이션으로 미세 조정하지만, 출발점은 자로 잰 값이어야 한다.

위 식 Δθ = (Δd_right − Δd_left) / L 은 2륜 차동구동의 정운동학이다. 우리 로봇은 4륜 스키드 스티어라 방향을 바꿀 때 바퀴가 옆으로 미끄러지므로 이 식은 근사이고, wheel_separation 은 "재서 넣으면 끝나는 상수"가 아니라 출발점이다. 06 §3-9 의 360도 회전 캘리브레이션은 이 값을 물리 치수와 다른 "유효 축간 거리"로 조정하는 작업이다 — 슬립을 그 숫자 하나에 흡수시키는 것이다. 05 에서 할 일은 자로 재서 넣는 것까지다.

IMU 는 각도만 고쳐 준다 — 위치는 고쳐 주지 못한다

슬립은 두 가지를 동시에 망가뜨리는데, 고치는 수단이 서로 다르다.

슬립이 망가뜨리는 것무엇이 고치는가
회전각 (yaw)IMU 자이로 z — 06 §3-9 캘리브레이션, §3-10 EKF
위치 (x, y)❗ IMU 로는 안 된다 — 09 의 SLAM 스캔 매칭이 필요하다

제자리 회전처럼 보여도 스키드 스티어는 실제 회전 중심이 기하 중심에 있지 않아 로봇이 조금씩 밀린다(3-3 의 ICR 이야기). IMU 는 "얼마나 돌았는가"만 알려 줄 뿐 "얼마나 밀렸는가"는 모른다. 가속도계를 두 번 적분해 위치를 얻는 방법은 오차가 발산해서 실제로는 쓰지 못한다.

EKF(06 §3-10)도 마찬가지다. yaw 를 정확하게 만들어 각도 오차가 위치로 번지는 것은 크게 줄여 주지만, 슬립으로 직접 생긴 위치 오차 자체는 없애지 못한다 — 그것을 관측하는 센서가 없기 때문이다.

위치 오차를 실제로 붙잡는 것은 09 의 SLAM 스캔 매칭이다. 그리고 이것이 2-1 에서 map 과 odom 을 나눈 이유와 정확히 같은 이야기다 — odom 은 "단기 정확, 장기 누적오차", map 은 "장기 정확". 스키드 스티어의 슬립은 그 누적오차를 키우는 주범이고, map → odom 이 그것을 흡수한다. 4륜을 고른 대가를 어디서 치르는지가 여기서 정해진다.

base_link 원점을 어디에 둘 것인가

2륜 차동구동 로봇은 좌우 바퀴 축의 중점에 두는 것이 관례다. 이 점이 제자리 회전의 중심이기 때문에 운동학 수식이 가장 단순해진다. base_footprint 는 그 점을 지면에 투영한 것이고, URDF 에서 base_footprint → base_link 는 z 로 wheel_radius 만큼 띄워 놓았다. 그래서 바퀴 반지름이 틀리면 로봇 모형이 지면에 파묻히거나 떠 보인다.

4륜 스키드 스티어에서는 이 근거가 그대로 성립하지 않는다

우리 로봇은 4륜이고 조향 장치가 없다. 방향을 바꿀 때 좌우 바퀴의 속도를 다르게 줘서 바퀴를 옆으로 미끄러뜨리며(skid) 돈다. 그래서 실제 회전 중심은 노면 마찰·하중 배분·회전 속도에 따라 움직인다 — 2륜처럼 기하학만으로 한 점이 정해지지 않는다.

그럼 05 에서는 어떻게 하는가. 네 바퀴의 기하 중심(좌우 축간의 중점이자 앞뒤 축간의 중점)에 base_link 를 둔다. URDF 는 "로봇이 실제로 어떻게 도는가"가 아니라 "부품이 어디에 붙어 있는가"를 적는 파일이기 때문이다. 이 단계에서 필요한 건 그것뿐이다.

더 알아보고 싶다면 — 이 주제의 검색어는 differential drive kinematics, skid steer kinematics, instantaneous center of rotation (ICR) 세 가지다. 지금 파고들 필요는 없다. 06 단계에서 수식을 직접 쓸 때 다시 만난다.

실제 슬립에 대응하는 곳은 06 단계다. §2-1·§2-2 에서 역·정운동학을 세우고, §3-9 에서 360도 회전으로 회전량을 IMU 기준으로 캘리브레이션하며, §3-10 에서 robot_localization 의 EKF 로 휠 오도메트리와 IMU 를 융합한다. hardware/INVENTORY.md 6절이 "스키드 스티어는 회전 시 바퀴 슬립이 커서 엔코더만의 회전 추정이 흔들린다 — IMU 융합(EKF)이 필요한 이유" 라고 적어 둔 것이 이 이야기다.

  --x 0.1 --y 0 --z 0.05 --yaw 0 --pitch 0 --roll 0 \

# 터미널 B

ros2 run tf2_tools view_frames               # 트리에 test_link 가 매달려 있다

이제 철칙을 깨 본다. 터미널 C 에서 같은 자식에 다른 부모를 붙인다.

ros2 run tf2_ros static_transform_publisher \
  --x 0 --y 0 --z 0 --yaw 0 --pitch 0 --roll 0 \
  --frame-id laser_link --child-frame-id test_link

ros2 run tf2_ros tf2_echo base_footprint test_link   # 값이 한 번 바뀌고, 그 값에서 멈춘다

TF2 는 어느 쪽이 맞는지 판단하지 않고 마지막으로 들어온 부모를 쓴다. 그런데 무엇이 관찰되는지는 정적이냐 동적이냐에 따라 전혀 다르다 — 이 실험의 핵심이다.

정적 중복은 떨리지 않는다 — 조용히 틀린다

/tf_static 은 한 번만 발행된다. 두 발행자가 각각 한 번씩 쏘고 나면 새 메시지가 없으니 덮어쓸 일도 없다. 그래서 값이 한 번 바뀌고 그대로 고정된다. 오가며 흔들리지 않는다.

직접 확인해 보라 — 터미널 C 를 Ctrl+C 로 끝내고 다시 tf2_echo 를 보면 값이 원래대로 돌아오지 않는다. tf2 에는 변환을 취소하는 수단이 없다. 버퍼에 한 번 들어간 정적 변환은 조회하는 노드를 재시작해야 사라진다.

에러도, 경고도, 떨림도 없다. 그래서 정적 중복이 더 위험하다 — 값만 조용히 틀린 채로 07~10 까지 따라간다.

반대로 /tf(동적) 발행자가 둘이면 진짜로 떨린다. 둘 다 주기적으로 계속 쏘므로 매 발행마다 덮어쓰고, 조회할 때마다 다른 값이 나온다. 06 §3-10 의 상황이 그것이다 — 브리지와 EKF 가 odom → base_footprint 를 같이 쏘면 로봇 위치가 50 Hz 로 두 추정치 사이를 떤다.

정적 중복 (이 실험)동적 중복 (06 의 브리지 + EKF)
증상마지막 값으로 고정값이 번갈아 나타남 = 떨림
눈에 띄는가안 띈다띈다 — 로봇이 덜컥거린다
발행자를 종료하면안 사라진다 (재시작 필요)즉시 멎는다
위험도높다 — 조용히 틀림낮다 — 바로 보인다

둘 다 같은 철칙 위반이다(2-1). 증상만 다를 뿐이다. 실험이 끝나면 세 터미널을 모두 Ctrl+C 로 끝내고, test_link 가 남아 있으면 tf2_echo 쪽도 다시 띄운다.

static_transform_publisher 는 언제 실무에서 쓰는가

URDF 를 고치기 전에 "센서를 여기에 달면 어떻게 보일까"를 빠르게 시험할 때, 또는 URDF 에 넣기 애매한 외부 장치(삼각대 위 카메라)를 붙일 때다. 로봇 몸에 고정된 것은 전부 URDF 에 넣는 것이 원칙이다 — 한 곳에서 관리되어야 하기 때문이다.

3-9. description.launch.py 읽기 — use_fake_joints 와 ParameterValue

ros2_ws/src/rpi5_description/launch/description.launch.py 를 열어 세 가지를 확인한다.

# xacro 를 실행해서 그 표준출력(=URDF XML)을 파라미터 값으로 넘긴다.
robot_description = ParameterValue(
    Command(['xacro ', xacro_file]), value_type=str
)

① ParameterValue(..., value_type=str) 함정. 이것을 빼면 런치 시스템이 XML 문자열을 YAML 로 해석하려 들어 다른 타입으로 잘못 추론하고, robot_state_publisher 가 "Invalid parameter type" 으로 죽는다. Humble 에서 가장 흔한 런치 함정 중 하나다.

② use_fake_joints. joint_state_publisher 는 바퀴(continuous 조인트)의 각도를 가짜로(0 rad) /joint_states 에 발행한다. 그래야 robot_state_publisher 가 바퀴 TF 를 만들어 트리가 완결된다. 06 단계부터는 mcu_bridge 가 엔코더로 진짜 /joint_states 를 발행하므로 이 노드를 꺼야 한다. rpi5_bringup/launch/robot.launch.py 는 이미 use_mcu 의 반대값을 use_fake_joints 로 넘긴다 — 두 노드가 같은 토픽을 발행하면 바퀴 TF 가 두 값 사이에서 떨리기 때문이다. 3-8 에서 본 것과 같은 종류의 문제다.

③ model. urdf/ 안의 어느 xacro 를 띄울지 고르는 인자다. 기본값은 실측용 rpi5_robot.urdf.xacro 이고, 섀시를 아직 재지 않았다면 가짜 치수 모델로 3-3 부터 3-8 까지를 먼저 돌려 볼 수 있다.

ros2 launch rpi5_description description.launch.py                                 # 실측용 (기본)
ros2 launch rpi5_description description.launch.py model:=test_robot.urdf.xacro   # 가짜 치수
왜 -p 로 URDF 를 직접 넘길 수 없는가 — ① 을 뒤집어 본 것

런치 파일 없이 이렇게 해 보면 실패한다.

ros2 run robot_state_publisher robot_state_publisher --ros-args \
  -p robot_description:="$(xacro src/rpi5_description/urdf/test_robot.urdf.xacro)"

# Couldn't parse parameter override rule: '-p robot_description:=<?xml version="1.0" ?> ...

xacro 는 제대로 실행됐고 쉘도 결과를 펼쳤다. 문제는 --ros-args -p 이름:=값 의 값이 YAML 스칼라로 파싱된다는 데 있다 — 줄바꿈이 나온 순간 파서가 거기서 끊고, 남은 XML 을 인자로 오해한다.

런치 파일은 이 문자열을 애초에 명령줄에 올리지 않는다. Command(['xacro ', xacro_file]) 를 런치 시스템이 직접 실행해서 그 표준출력을 파라미터 값 객체로 노드에 건넨다. 명령줄 파서를 거치지 않으니 줄바꿈도 따옴표도 문제가 되지 않는다. ①의 value_type=str 과 함께, 이 두 줄이 "URDF 를 노드에 넘기는 일"의 전부다.

3-10. TF 를 코드에서 만지는 두 가지 방법 — C++ 미리보기 C++

이 단계에서는 읽기만 한다. 06 단계에서 (a)를, 10 단계에서 (b)를 실제로 쓴다. 두 패턴의 모양을 미리 눈에 익혀 두면 그때 "TF 코드"가 아니라 "운동학"에 집중할 수 있다.

(a) 발행 — 06 의 mcu_bridge 가 odom → base_footprint 를 보내는 코드

#include "geometry_msgs/msg/transform_stamped.hpp"
#include "tf2/LinearMath/Quaternion.h"
#include "tf2_geometry_msgs/tf2_geometry_msgs.hpp"   // tf2::toMsg(q) 를 위해
#include "tf2_ros/transform_broadcaster.h"

// 멤버:     std::unique_ptr<tf2_ros::TransformBroadcaster> tf_broadcaster_;
// 생성자:   tf_broadcaster_ = std::make_unique<tf2_ros::TransformBroadcaster>(*this);

void publish_odom_tf(double x, double y, double yaw)
{
  geometry_msgs::msg::TransformStamped tf;
  tf.header.stamp = this->get_clock()->now();
  tf.header.frame_id = "odom";           // 부모
  tf.child_frame_id = "base_footprint";  // 자식 — URDF 루트가 base_footprint 다 (2-1 철칙)
  tf.transform.translation.x = x;
  tf.transform.translation.y = y;
  tf.transform.translation.z = 0.0;
  tf2::Quaternion q;
  q.setRPY(0.0, 0.0, yaw);               // 평면 로봇은 yaw 만 변한다
  tf.transform.rotation = tf2::toMsg(q);
  tf_broadcaster_->sendTransform(tf);
}

(b) 조회 — 10 의 감독 노드가 "카메라가 본 것"을 로봇 기준으로 옮기는 코드

#include "tf2_ros/buffer.h"
#include "tf2_ros/transform_listener.h"

// 멤버
std::unique_ptr<tf2_ros::Buffer> tf_buffer_;
std::shared_ptr<tf2_ros::TransformListener> tf_listener_;
// 생성자 — Listener 가 /tf, /tf_static 을 구독해 Buffer 를 채운다 (QoS 도 알아서 맞춘다)
tf_buffer_ = std::make_unique<tf2_ros::Buffer>(this->get_clock());
tf_listener_ = std::make_shared<tf2_ros::TransformListener>(*tf_buffer_);

// 조회 — 실패는 예외로 온다. 반드시 잡는다 (TF 는 늦게 도착할 수 있다)
try {
  auto t = tf_buffer_->lookupTransform(
    "base_link", "camera_optical_link", tf2::TimePointZero);   // Zero = 가장 최근 값
  RCLCPP_INFO(get_logger(), "camera at x=%.3f z=%.3f",
              t.transform.translation.x, t.transform.translation.z);
} catch (const tf2::TransformException & ex) {
  RCLCPP_WARN_THROTTLE(get_logger(), *get_clock(), 2000, "TF lookup failed: %s", ex.what());
}

lookupTransform(target, source, time) 은 "source 프레임의 점을 target 프레임으로 옮기는 변환"을 준다. 인자 순서를 헷갈리면 부호가 뒤집힌다 — tf2_echo base_link laser_link 와 같은 순서라고 기억한다. tf2::TimePointZero 대신 메시지의 header.stamp 를 넣으면 그 시각의 변환을 준다(센서 데이터를 올바른 자세로 옮길 때). 그 시각의 TF 가 아직 안 왔으면 예외가 나므로 try/catch 가 필수다.

✅ 검증 체크포인트

🤔 이해 확인

0-A. ros2 node list 에 TF 노드가 없는데 TF 는 어떻게 동작하는가?
TF 는 노드가 아니라 약속이기 때문이다 — 메시지 타입(tf2_msgs/msg/TFMessage), 토픽 이름(/tf·/tf_static), QoS 세 가지. 좌표계 관계를 아는 노드들이 각자 자기 엣지를 그 약속대로 발행하고, 필요한 노드가 tf2_ros::Buffer 로 모아 조회한다. 모아서 변환을 만들어 주는 중앙 주체는 없다.
0-B. /cmd_vel 은 발행자가 둘이면 사고인데 /tf 는 왜 셋이어도 되는가?
메시지가 담는 것이 다르다. /cmd_vel 한 장은 로봇 전체의 속도 명령이라 두 개를 이어 붙일 방법이 없고 마지막 값이 이긴다. /tf 한 장은 트리의 조각(엣지)이라 서로 다른 칸이면 합쳐진다. 단 같은 칸(같은 자식 프레임)을 둘이 쏘면 /tf 도 똑같이 사고다 — 2-1 의 철칙이고 3-8 에서 재현한다.
1. SLAM 이 map → base_link 를 직접 발행하면 안 되는 이유는?
SLAM 의 위치 보정은 불연속적(루프 클로저 시 위치가 갑자기 점프)이다. 제어기가 이 값을 쓰면 로봇이 순간이동한 것처럼 보여 제어가 폭주한다. 그래서 보정량은 map → odom 에 넣고, 제어기는 연속적인 odom → base_link 를 쓴다. 두 변환을 곱하면 결국 map 기준 위치가 나온다.
2. wheel_separation 을 실제보다 크게 적으면 어떤 증상이 나타나는가?
회전 각속도 계산 ω = (v_r − v_l)/L 에서 L 이 크므로 ω 가 작게 추정된다. 즉 실제로 90도 돌았는데 오도메트리는 80도만 돌았다고 기록한다. SLAM 은 스캔 매칭 결과와 이 오도메트리가 계속 어긋나 지도를 휘게 만든다.
3. camera_optical_link 가 따로 필요한 이유는?
로봇 좌표 규약(REP-103, x=앞)과 영상 처리 규약(OpenCV, z=광축)이 다르기 때문이다. 두 규약을 한 프레임에 섞으면 어느 쪽 코드가 봐도 축이 틀린다. 그래서 두 프레임을 두고 그 사이 회전(rpy = −π/2, 0, −π/2)으로 연결한다.
4. TF 가 미세하게 떨린다면 가장 먼저 무엇을 의심하는가? 그리고 떨리지 않는데 값이 틀린 경우는?
둘 다 같은 자식 프레임을 두 노드가 발행하는 것이다. 증상이 갈리는 이유는 /tf 는 계속 발행되고 /tf_static 은 한 번만 발행되기 때문이다 — 동적 중복은 값이 번갈아 나타나고, 정적 중복은 마지막 값으로 조용히 고정된다(발행자를 꺼도 남는다. 조회하는 노드를 재시작해야 한다). 떨리는 쪽의 예 — mcu_bridge 가 publish_tf:=true 이고 동시에 robot_localization(EKF)도 odom → base_footprint 를 쏘는 경우, 또는 joint_state_publisher 와 mcu_bridge 가 둘 다 /joint_states 를 내는 경우. 한쪽을 꺼야 한다. 3-8 에서 직접 재현했다.
5. /tf_static 이 TRANSIENT_LOCAL 로 발행되는 이유는? VOLATILE 이면 무엇이 깨지는가?
고정 변환은 시작할 때 한 번만 발행된다. VOLATILE 이면 그 뒤에 뜬 구독자(SLAM, Foxglove, 나중에 띄운 내 노드)는 그 값을 영원히 받지 못해 base_link → laser_link 를 모른다. TRANSIENT_LOCAL 은 발행자가 마지막 값을 보관해 두고 늦게 온 구독자에게도 준다. 03 단계 §2-7 의 Durability 가 실물로 쓰이는 곳이다.
6. lookupTransform 을 try/catch 로 감싸야 하는 이유는?
TF 는 다른 노드가 네트워크로 보내는 데이터라 아직 도착하지 않았거나(노드 기동 직후), 요청한 시각의 값이 버퍼에 없거나(extrapolation), 프레임 이름이 틀렸을 수 있다. tf2 는 이 모두를 tf2::TransformException 예외로 알린다. 잡지 않으면 노드가 죽는다. 조회 실패는 정상적인 일시 상태이므로 throttle 된 경고로 넘기고 다음 주기에 다시 시도한다.
7. view_frames 의 트리에 바퀴 링크가 보이지 않는다. 무엇이 빠진 것인가?
/joint_states 발행자다. robot_state_publisher 는 고정 조인트는 URDF 만으로 /tf_static 에 내지만, continuous 조인트(바퀴)는 현재 각도를 알아야 하므로 /joint_states 가 와야 /tf 에 낸다. 이 단계에서는 joint_state_publisher(use_fake_joints:=true)가, 06 단계부터는 mcu_bridge 가 그 역할을 한다.
8. static_transform_publisher 로 붙인 변환과 URDF 에 적은 변환은 TF2 입장에서 무엇이 다른가?
아무것도 다르지 않다. 둘 다 /tf_static 으로 들어오는 TransformStamped 다. TF2 는 발행자가 누구인지 구분하지 않고 이어 붙인다. 차이는 관리 측면이다 — 로봇 몸에 고정된 것은 URDF 한 곳에서 관리해야 실측값을 고칠 때 한 번만 고치면 되고, Foxglove 가 형상까지 그릴 수 있다.
