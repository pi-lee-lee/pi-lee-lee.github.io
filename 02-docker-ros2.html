02 · Docker + ROS 2 Humble

컨테이너 안에 ROS 2 를 구성하고, Mac 의 Foxglove 를 연결한다

호스트는 Raspberry Pi OS(Debian 13) 인데 우리가 쓸 ROS 는 Ubuntu 22.04 용 Humble 이다. 이 불일치는 Docker 로 해결한다. 이 단계가 끝나면 이후 모든 단계의 명령이 컨테이너 안에서 실행된다.

이 쪽이 끝나면 보이는 것

이 쪽이 끝나면 다음 넷이 갖춰진다.

  • Pi 의 컨테이너 안에서 ros2 topic list 가 실행된다.
  • 두 컨테이너의 talker/listener 가 서로를 찾아 통신한다.
  • Mac 의 Foxglove 가 Pi 의 ROS 그래프에 연결된다.
  • 02~11 단계에서 필요한 apt 패키지가 전부 이미지 안에 들어가 있다. 그래서 이후 단계에서 이미지를 다시 빌드할 일은 08(camera_ros)·08c(HailoRT) 두 번뿐이다.
그래프에서의 위치그래프의 바탕 — 모든 노드가 실행되는 컨테이너 + Foxglove(관측)
전제01 (ssh 접속, 장치 인식)
예상 소요1~2시간 (+ 이미지 빌드 10~20분 대기)
언어셸 Dockerfile · compose

이 단계에서 만드는 것은 셋이다.

  1. 이미지 rpi5-ros2:humble — docker/Dockerfile 로 정의. ROS 2 Humble + 이 학습에 필요한 패키지 + 호스트와 UID(리눅스 사용자 번호)가 같은 비root 사용자.

2. 원리 — 왜

2-1. 왜 Docker 인가 — 이 프로젝트 구조의 핵심 근거

ROS 2 Humble 의 공식 타깃은 Ubuntu 22.04 (jammy) 다. Debian 13 에 Humble 을 apt 로 설치할 방법은 없다. 소스 빌드는 Pi 5 에서 몇 시간이 걸리고, 의존성 문제를 하나씩 직접 풀어야 한다.

        ┌─────────────────────────────────────────────────┐
        │  컨테이너: Ubuntu 22.04 (jammy) 유저스페이스    │
        │   · /opt/ros/humble/...                         │
        │   · libstdc++, python3.10, DDS 라이브러리       │
        └───────────────────┬─────────────────────────────┘
                            │  시스템 콜
        ┌───────────────────▼─────────────────────────────┐
        │ 호스트 커널 (Raspberry Pi OS Trixie의 Linux 6.x)│
        │   · USB serial, V4L2, dma_heap                  │
        │   · hailo_pci  ← Hailo-8 드라이버도 여기 있다   │
        └─────────────────────────────────────────────────┘

컨테이너는 커널을 공유하고 유저스페이스는 자기 것을 쓴다. 따라서 호스트가 Raspberry Pi OS 든 Ubuntu 든, 컨테이너 안은 항상 jammy + Humble 이다.

01 단계의 결정과 이 결정은 같은 논리에서 나온다

ROS 쪽 제약이 Docker 로 사라졌기 때문에, 호스트 선택은 순수하게 드라이버 문제가 되었다. 반대로 말하면 커널이 제공하는 것(장치 드라이버)은 호스트 것이므로, 호스트에서 안 보이는 장치는 컨테이너에서도 안 보인다. 01 단계를 먼저 끝내야 하는 이유다.

부수적으로 얻는 것:

  • 호스트에 ROS 패키지가 설치되지 않는다 → 호스트 OS 를 언제든 다시 설치할 수 있다
  • 환경을 Dockerfile 한 장으로 재현할 수 있다 → "내 Pi 에서만 되는" 현상이 없다
  • 나중에 Jazzy 로 옮길 때 베이스 이미지 한 줄만 바꾸면 된다

참고(비차단): Humble 은 2027년 5월 EOL(지원 종료), Jazzy(Ubuntu 24.04 기반)가 현행 LTS(장기 지원판)다. 지금은 자료가 압도적으로 많은 Humble 로 배우고, 개념을 익힌 뒤 옮기는 것이 낫다. 개념은 그대로이고 바뀌는 것은 일부 API 이름 정도다.

2-2. 이미지·컨테이너·볼륨 — 쓰기 레이어는 저장소가 아니다

   Dockerfile ──(docker compose build)──► 이미지 rpi5-ros2:humble   ← 영구. 읽기 전용 레이어들
                                               │
                                 docker compose run --rm dev
                                               ▼
                                          컨테이너 (쓰기 레이어)   ← 수명 = 컨테이너 수명. 보존을 선언할 방법이 없다
                                               │
                                   sudo apt install ros-humble-xxx   ← 여기 설치한 것은 쓰기 레이어에 있다
                                               ▼
                               컨테이너 삭제·재생성  →  쓰기 레이어 삭제  →  xxx 는 사라졌다
             (--rm 종료 · compose run 재실행 · compose 설정/이미지 변경 후 up · down · prune)

컨테이너 안에서 apt install·pip install 한 것은 그 컨테이너의 쓰기 레이어에 있고, 컨테이너가 삭제·재생성되면 사라진다. 이미지는 바뀌지 않았기 때문이다.

--rm 은 삭제 시점을 "셸 종료"로 정해 줄 뿐, 사라지는 원인이 아니다. --rm 을 빼도 보존은 보장되지 않는다. 컨테이너는 다음 세 경우에도 새로 만들어지거나 지워진다.

  • docker compose run 은 실행할 때마다 새 컨테이너를 만든다.
  • docker compose up 은 compose 설정이나 이미지가 바뀌면 컨테이너를 재생성한다.
  • down·prune 은 컨테이너를 지운다.

그래서 남겨야 할 것은 수명을 선언할 수 있는 곳에 둔다. 실행 중에 생기는 데이터(코드·빌드 결과·지도·bag)는 볼륨/바인드 마운트에 둔다 — 이 규칙은 아래 두 방식에 공통이다. 패키지 같은 환경을 남기는 방법은 두 가지이고, 대등한 선택지다.

A. 이미지에 넣는다 (Dockerfile)B. 시스템 경로를 볼륨으로 마운트한다
구성Dockerfile 에 설치 줄을 적는다compose volumes: 에 /opt /usr /etc /var 등을 named volume 으로 추가한다. 볼륨이 처음 생성될 때 이미지 내용으로 채워진다
패키지 추가·업데이트Dockerfile 수정 → docker compose build → 새 컨테이너컨테이너 셸에서 sudo apt install / sudo dpkg -i / pip install → 볼륨에 남는다. 환경 변경은 컨테이너 안에서 한다(이미 채워진 볼륨에는 이미지 변경이 반영되지 않는다)
한 번 바꿀 때 바뀌는 범위캐시가 무효화된 줄부터 다시 실행된다. 버전을 고정하지 않은 apt 줄은 그 시점의 버전으로 함께 바뀔 수 있다설치한 패키지만 바뀐다. 설치 직후 실제 장치에 연결해 확인할 수 있다
설치 목록 확인Dockerfile 을 읽는다컨테이너에서 dpkg -l, pip list
이미지로 만들기·배포이미지 그 자체 (레지스트리 / docker save)필요한 시점에 볼륨을 tar 로 내보내 이미지로 만든다. docker commit 은 볼륨 내용을 포함하지 않는다

이 가이드의 docker/ 구성과 각 단계의 절차는 A 로 적혀 있다. B 를 쓴다면 "Dockerfile 에 추가 → 재빌드"라고 적힌 곳을 "컨테이너에서 설치"로 읽으면 된다.

학습 패키지는 §3-3 에서 한 번에 넣는다

새 패키지가 필요한지 확실하지 않으면 우선 컨테이너 안에서 sudo apt install 로 써 본다. 계속 쓸 것은 고른 방식으로 남긴다 — A 는 Dockerfile 에 적고 빌드, B 는 그 설치가 그대로 남는다.

A 는 Pi 에서 첫 빌드가 10~20분이므로, 이 가이드에서 필요한 apt 패키지는 §3-3 에서 한 번에 넣는다. B 도 같은 목록을 한 번에 설치해 두면 단계마다 멈추지 않는다.

2-3. compose 의 항목은 왜 하나라도 빠지면 오류 표시 없이 고장나는가

docker/docker-compose.yml 의 아래 항목은 빠져도 오류가 나지 않는다. 증상이 "아무 일도 안 일어남"이라 원인을 찾기 어렵다.

항목왜 필요한가빠지면 나타나는 증상
network_mode: hostROS 2 는 DDS 위에서 동작하고, DDS 는 UDP 멀티캐스트(한 번 보낸 UDP 패킷을 같은 네트워크의 여러 수신자가 받는 방식)로 서로를 찾는다(디스커버리). Docker 기본 bridge 네트워크는 멀티캐스트를 NAT(컨테이너 주소를 호스트 주소로 바꾸는 변환) 너머로 전달하지 못한다노드는 실행 중인데 다른 컨테이너에서 ros2 topic list 에 아무것도 안 나온다
ipc: hostHumble 기본 RMW(ROS 2 와 DDS 구현을 잇는 계층 — 기본은 Fast DDS)는 같은 머신 안 통신에 공유 메모리(/dev/shm) 를 쓴다. IPC(프로세스 사이 통신) 네임스페이스가 분리되면 오류 표시 없이 루프백 UDP 로 전환된다이미지·포인트클라우드 같은 큰 메시지에서 프레임 드롭
FASTRTPS_DEFAULT_PROFILES_FILE 과 ./fastdds_profile.xml 마운트Fast DDS 의 공유 메모리 구획은 기본 512 KB 다. 이보다 큰 메시지는 ipc: host 가 있어도 UDP 로 간다. 설정 파일로 구획을 16 MB 로 키운다 (아래 상자)카메라 영상이 초당 30 장 중 일부만 도착한다. 받기만 하는 노드에서도 생기고, CPU 부하가 오르면 초당 몇 장까지 줄어든다
volumes: ../ros2_ws:/ros2_ws소스는 호스트에 두고 컨테이너가 빌드한다(없으면) 컨테이너를 지울 때 코드와 빌드 결과가 함께 사라진다
/dev:/dev, device_cgroup_rules/dev 를 통째로 마운트해도 cgroup 규칙이 없으면 장치 접근이 막힌다. 규칙은 경로가 아니라 major 번호로 장치를 허용한다. 부팅마다 번호가 바뀔 수 있는 media·dma_heap·hailo 은 .env 의 값을 읽는다 (아래 상자)카메라/Hailo 가 "컨테이너에서만" 인식되지 않는다. 장치 파일은 보이는데 열 때 Operation not permitted
ROS_DOMAIN_ID같은 네트워크에 여러 ROS 시스템이 있으면 서로 섞인다. 도메인 ID(0~101)로 격리한다다른 로봇의 토픽이 이 로봇의 토픽 목록에 섞여 나온다
ROS_LOCALHOST_ONLY: "0"1 이면 localhost 로만 통신한다Mac 에서 토픽이 안 보인다 (단, Foxglove 는 WebSocket 이라 영향이 없다)

Mac 의 Foxglove 는 WebSocket 으로 연결하므로 도메인 ID 와 무관하다. 나중에 Mac 에 ROS 를 설치해 직접 DDS 로 통신할 계획이라면 양쪽 도메인 ID 를 같게 맞춰야 한다.

큰 메시지와 Fast DDS 공유 메모리 구획 — 왜 설정 파일이 필요한가

구획은 노드 프로세스가 보내는 메시지를 담아 두는 /dev/shm 의 파일이다. 노드 프로세스마다 하나씩 만들어진다. 받는 쪽은 이 파일에서 메시지를 읽는다.

메시지 한 개가 구획보다 크면 공유 메모리를 쓰지 못하고 UDP 로 간다. UDP 로 가면 메시지는 여러 조각으로 나뉜다. 받는 쪽 소켓의 기본 수신 버퍼는 212,992 B 다. 조각이 하나라도 버퍼에서 넘쳐 버려지면 메시지 전체를 버린다. 커널은 이 경우를 /proc/net/snmp 의 Udp 줄 RcvbufErrors 칸에 센다.

메시지크기기본 구획 512 KB (524,288 B) 에
640×480 RGB 영상 한 장 (08 단계의 카메라 영상)921,600 B들어가지 않는다 → UDP
1280×720 RGB 영상 한 장2,764,800 B들어가지 않는다 → UDP
/rosout 로그, camera_info 같은 작은 메시지수백 B ~ 수 KB들어간다

이 프로젝트의 Pi 실측(hardware/INVENTORY.md 4절): 기본 설정에서는 카메라 영상을 받기만 하는 노드도 초당 30 장 중 20 ~ 22 장만 받았다(CPU 두 코어에 부하를 건 상태). 설정 파일을 적용한 뒤에는 CPU 네 코어에 부하를 걸어도 30.0 장을 받았고 RcvbufErrors 는 늘지 않았다.

16 MB 의 근거: 구획에는 보낸 메시지 가운데 받는 쪽이 아직 다 읽지 않은 것이 남는다. 카메라 노드(camera_ros)의 발행 보관 깊이는 1 장이지만, 구독하는 노드가 여럿이고 각자 몇 장씩 쌓아 두면 그만큼 구획에 남는다. 16 MB 는 640×480 영상 약 17 장 분량이고, 위 실측에서 손실이 없었다. 1280×720 이면 약 5 장 분량이라 구독 노드가 늘면 모자랄 수 있다. 해상도를 올리면 수신 수와 RcvbufErrors 를 다시 확인하고, 모자라면 32 MB 로 올린다.

메모리 비용: 구획 파일은 크기만큼 메모리를 실제로 차지한다. 16 MB × 노드 프로세스 수다. 노드 20 개면 약 320 MB 다.

적용 범위: compose 의 공통 블록(x-ros-common)에 있으므로 이 compose 로 띄우는 모든 컨테이너의 모든 노드에 적용된다. 카메라, Hailo, Foxglove 브리지 단계에서 따로 설정하지 않는다. 적용되지 않는 경우는 둘이다. compose 를 거치지 않고 띄운 ROS 프로세스, 그리고 RMW_IMPLEMENTATION 을 rmw_cyclonedds_cpp 로 바꾼 경우다(이 파일은 Fast DDS 전용이다).

UDP 버퍼 4 MB: Pi 안의 노드끼리는 공유 메모리로 전달되므로 UDP 를 쓰지 않는다. UDP 는 Pi 밖의 기기와 DDS 로 직접 통신할 때 쓰인다. 설정값은 호스트의 net.core.rmem_max(이 Pi 실측 4,194,304 B)를 넘을 수 없다.

docker/fastdds_profile.xml (compose 가 컨테이너의 /etc/fastdds/profile.xml 로 마운트한다):

<?xml version="1.0" encoding="UTF-8"?>
<!-- Fast DDS transport profile, applied to every node via FASTRTPS_DEFAULT_PROFILES_FILE -->
<profiles xmlns="http://www.eprosima.com/XMLSchemas/fastRTPS_Profiles">
  <transport_descriptors>
    <!-- shared memory between processes on this Pi: segment large enough for camera images -->
    <transport_descriptor>
      <transport_id>shm_large</transport_id>
      <type>SHM</type>
      <segment_size>16777216</segment_size>
    </transport_descriptor>
    <!-- UDP for other machines; socket buffers capped by the host's net.core.rmem_max -->
    <transport_descriptor>
      <transport_id>udp_large_buf</transport_id>
      <type>UDPv4</type>
      <sendBufferSize>4194304</sendBufferSize>
      <receiveBufferSize>4194304</receiveBufferSize>
    </transport_descriptor>
  </transport_descriptors>
  <participant profile_name="default_participant" is_default_profile="true">
    <rtps>
      <!-- replace the built-in transports (default SHM 512 KB + UDP) with the two above -->
      <useBuiltinTransports>false</useBuiltinTransports>
      <userTransports>
        <transport_id>shm_large</transport_id>
        <transport_id>udp_large_buf</transport_id>
      </userTransports>
    </rtps>
  </participant>
</profiles>

compose 쪽은 공통 블록의 두 줄이다.

  environment:
    FASTRTPS_DEFAULT_PROFILES_FILE: /etc/fastdds/profile.xml
  volumes:
    - ./fastdds_profile.xml:/etc/fastdds/profile.xml:ro
major 번호는 왜 compose 에 적지 않는가

major 번호는 ls -l /dev/media0 의 238, 0 에서 쉼표 앞 숫자다. 이 장치 파일을 어느 드라이버가 맡는지를 나타낸다. 번호를 정하는 방식은 둘이다.

방식번호이 프로젝트의 장치
고정커널의 공식 목록에 정해져 있어 어느 부팅이든 같다/dev/video* 81, i2c 89, ttyUSB 188, ttyACM 166
동적드라이버가 올라올 때 커널이 빈 번호를 골라 준다. 어느 번호가 되는지는 그 부팅에서 드라이버가 올라온 순서에 달려 있다/dev/media*, /dev/hailo0, /dev/dma_heap

이 프로젝트의 Pi 는 같은 커널에서도 media 가 511, 237, 238 로, hailo 가 510, 238 로 바뀌었다(hardware/INVENTORY.md 8절). 그래서 compose 에는 번호 대신 변수를 쓴다.

  device_cgroup_rules:
    - 'c 81:* rmw'                       # /dev/video* — fixed
    - 'c ${MEDIA_MAJOR:?...}:* rmw'      # /dev/media* — dynamic, value from docker/.env
    - 'c ${DMA_HEAP_MAJOR:?...}:* rmw'   # /dev/dma_heap
    - 'c ${HAILO_MAJOR:?...}:* rmw'      # /dev/hailo0

docker/majors.sh 가 /proc/devices 에서 드라이버 이름(media, hailo, dma_heap)으로 이번 부팅의 번호를 읽어 .env 에 적는다. 드라이버가 없으면(HAT 미장착) 0 을 적는다 — 0 번 규칙은 어떤 장치에도 맞지 않아 해가 없다. 부팅마다 자동으로 실행되도록 systemd 유닛으로 설치한다(§3-4). ${…:?…} 는 값이 없으면 compose 가 그 문구를 내고 멈추게 한다 — 조용히 틀린 규칙으로 뜨지 않는다.

2-4. 비root 사용자와 HOST_UID

컨테이너를 root 로 실행하면 마운트된 ros2_ws 에 colcon 이 만드는 build/ install/ log/ 가 전부 root 소유가 된다. 그러면 호스트에서 편집·삭제할 때마다 sudo 가 필요하고, git·rsync 를 쓸 때도 권한 문제가 생긴다. 그래서 Dockerfile 은 빌드 인자로 호스트 UID/GID(사용자 번호 · 그룹 번호)를 받아 같은 번호의 사용자를 만든다.

왜 변수명이 UID 가 아니라 HOST_UID 인가

bash 에서 UID 는 읽기 전용 변수라 export UID=$(id -u) 가 오류를 낸다. 게다가 export 가 실패해도 compose 는 기본값 1000 으로 오류 표시 없이 진행해서, 명령은 실패했는데 결과는 맞아 보이는(첫 사용자의 UID 가 우연히 1000 인) 최악의 상황이 된다. 변수명을 바꾸고 docker/.env 파일로 관리해 이 함정을 피한다.

2-5. Hailo-8 을 컨테이너에서 쓸 때의 함정 — 버전 락

이 프로젝트에만 있는 특수 문제라 미리 짚는다. 08c 단계에서 실제로 겪는다.

   호스트                              컨테이너
   ┌──────────────────────┐            ┌─────────────────────────────┐
   │ hailo_pci (커널 모듈)│◄──────────►│ libhailort (유저 라이브러리)│
   │  버전 4.x.y          │ /dev/hailo0│  버전 4.x.y                 │
   └──────────────────────┘            └─────────────────────────────┘
              ▲                                    ▲
              └────────── 이 둘이 정확히 같아야 한다 ─────┘

드라이버는 호스트에, 런타임 라이브러리는 컨테이너에 있다. HailoRT 는 이 둘의 버전이 다르면 장치를 아예 인식하지 않는다. 더 곤란한 점: 호스트에서 sudo apt upgrade 를 하면 호스트 쪽만 올라간다. 어제까지 되던 추론이 오늘 갑자기 "No Hailo device found" 를 내고, ROS 코드는 하나도 안 건드렸으므로 원인을 엉뚱한 데서 찾게 된다.

대응은 세 줄이다.

# ① 호스트에서 현재 버전을 확인해 기록한다 (01 단계에서 INVENTORY.md 5절에 적었다)
hailortcli fw-control identify | grep -i version

# ② 컨테이너 쪽 HailoRT 를 그 버전으로 맞춘다 (08c 단계, §2-2 의 A/B 중 쓰는 방식으로)
#    A: Dockerfile 3-B 블록의 ARG HAILORT_VERSION=4.xx.y  ← 호스트에서 확인한 값 → 빌드
#    B: 컨테이너에서 같은 버전의 .deb / .whl 을 설치

# ③ 호스트를 업그레이드한 뒤에는 반드시 재확인하고, 다르면 ②를 새 버전으로 다시 한다
hailortcli fw-control identify                                   # 호스트
docker compose run --rm dev hailortcli fw-control identify       # 컨테이너 → 두 출력의 버전이 같아야 한다
devices: 로 /dev/hailo0 을 명시하지 않은 것은 의도적이다

compose 는 /dev 전체를 마운트하므로 노드 자체는 보인다. devices: 에 명시하면 HAT(Hailo-8 이 달린 AI HAT+ 확장 기판)을 아직 장착하지 않았거나 DKMS(커널 모듈을 새 커널에 맞춰 다시 빌드하는 도구) 빌드가 실패한 상태에서 dev, foxglove 를 포함한 모든 서비스가 시작되지 않는다. compose 의 오류 메시지는 원인을 알려 주지 않는다.

대신 device_cgroup_rules 의 'c ${HAILO_MAJOR}:* rmw' 로 연다. 번호는 부팅 때 docker/majors.sh 가 .env 에 적는다(§2-3 상자). 컨테이너에서만 장치가 열리지 않으면 ./majors.sh --check 로 .env 의 값이 지금 값과 같은지 본다.

대안(더 단순하지만 덜 깔끔한 구성): 추론을 호스트에서 실행하고 결과만 ROS 로 넘기는 방법도 있다. 버전 락이 사라지지만 시스템이 컨테이너 안팎으로 나뉜다. 08c 에서 두 방식을 비교한다.

2-6. 왜 RViz 가 아니라 Foxglove 인가

RViz 를 Pi 에서 실행하고 macOS 로 X11 포워딩하는 방법은 XQuartz 설정, OpenGL 미지원, 극심한 지연 때문에 실용성이 없다. Foxglove 는 foxglove_bridge(ROS 노드)가 WebSocket 으로 데이터만 내보내고, Mac 에서 네이티브로 렌더링하므로 Pi 의 CPU 를 거의 쓰지 않는다. 그래서 Dockerfile 은 ros:humble-ros-base(RViz/Gazebo 없는 이미지) 를 쓴다 — -desktop 은 2 GB 가 더 크고 헤드리스 Pi 에서 한 번도 쓰지 않는다.

왜 Pi 에서 직접 편집하지 않는가

로봇은 자주 껐다 켜지고, SD 카드는 언젠가 고장 난다. 원본은 Mac(+git)에 두고 Pi 는 "실행 사본"으로 취급하는 것이 안전하다. Pi 를 새로 굽더라도 rsync 한 번이면 복구된다.

스크립트는 저장소 루트의 .syncignore 에 적힌 build/ install/ log/ 를 제외하므로(--delete 가 빌드 산출물을 지우지 않도록) 동기화해도 매번 풀빌드가 되지 않는다. 같은 파일이 Pi 에서 생기는 기록 · 지도 · 녹화도 지킨다(L 트랙 l-00 §3-4-1).

규칙 한 줄 — 패키지는 Mac 에서 만들거나, Pi 에서 만들었으면 다음 동기화 전에 Mac 으로 가져와 git 에 넣는다. --delete 는 "Mac 에 없는 것은 Pi 에서도 지운다"는 뜻이다. 뒤 단계에서 Pi 의 컨테이너 안에서 ros2 pkg create 로 만든 패키지를 Mac 에 가져오지 않은 채 동기화하면 그 패키지가 지워진다. 그래서 스크립트는 ros2_ws/src/ 아래에 Pi 에만 있는 디렉터리를 지우게 되면 그 목록과 가져오는 명령을 보여 주고 멈춘다(정말 지우려면 ALLOW_DELETE_SRC=1). 07·08 에서 ros2_ws/src/drivers.repos 로 받는 외부 드라이버 소스는 보내지도 지우지도 않는다.

talker 와 listener 가 도는 동안 Pi 호스트 의 세 번째 터미널에서 공유 메모리 구획의 크기를 본다 (§2-3 상자).

ls -l /dev/shm/fastrtps_*
#   16802336 바이트 파일이 노드 프로세스 수만큼 보이면 설정 파일이 적용된 것 (16 MB + 관리 영역)
#   549408 바이트 파일은 기본 구획 512 KB — 그 프로세스에는 설정 파일이 적용되지 않았다
#   크기가 0 인 *_el 파일은 짝이 되는 잠금 파일이다
#   강제로 종료된 프로세스의 파일이 남아 있을 수 있다 — ls -l 의 시각으로 지금 실행한 것을 구분한다

3-8. Foxglove 연결 — Mac 에서 Pi 의 데이터 보기

Pi 호스트 브리지를 백그라운드로 상시 실행한다.

cd ~/ros2_rpi5/docker
docker compose up -d foxglove
docker compose logs -f foxglove      # "Server started" 확인 후 Ctrl+C (로그만 끊기고 컨테이너는 계속 돈다)

Mac Foxglove 는 무료 플랜으로 충분하다. 첫 실행 때 계정 로그인을 요구하고, 그 뒤로는 로컬 파일과 WebSocket 연결이 오프라인에서도 된다. 유료 플랜은 클라우드 저장·팀 기능용이라 이 프로젝트에는 필요 없다.

Foxglove 에서 아래 순서로 연결한다.

  1. Open connection → Foxglove WebSocket
  2. 주소: ws://192.168.50.97:8765 (이 프로젝트의 Pi. mDNS 를 쓰면 ws://roshost.local:8765)
  3. 연결되면 좌측에 토픽 목록이 보인다. Raw Messages 패널에 /rosout 을 표시해 talker 의 로그가 계속 수신되는지 확인한다.
  4. Topic Graph 패널을 추가한다 — 03 단계부터 "그래프를 보는" 습관의 도구다.

3-10. 자주 쓸 명령 정리

cd ~/ros2_rpi5/docker

docker compose run --rm dev            # 일회성 개발 셸 (종료 시 컨테이너 삭제 — §2-2)
docker compose up -d foxglove          # 시각화 브리지 상시 실행
docker compose logs -f foxglove        # 로그 보기
docker compose down                    # 모두 정지
docker exec -it ros2_foxglove bash     # 이미 떠 있는 컨테이너에 들어가기

docker compose build                   # Dockerfile 수정 후 재빌드 (캐시 사용)
docker compose build --no-cache        # 캐시까지 버리고 처음부터 (apt 미러가 바뀌었을 때 등)

docker compose --profile robot up      # 로봇 본체 기동 (bringup 서비스, 06 단계부터)
팁

컨테이너 셸을 여러 개 열 때는 docker compose run --rm dev 를 여러 번 호출해도 된다. network_mode: host 이므로 서로 같은 ROS 그래프를 본다. 각 단계의 "터미널 A / 터미널 B" 는 전부 이 방식이다.

✅ 검증 체크포인트

🤔 이해 확인

1. 호스트가 Debian 13 인데 컨테이너 안은 왜 Ubuntu 22.04 인가? 문제되지 않는가?
컨테이너는 커널만 공유하고 유저스페이스(libc, 라이브러리, 패키지)는 자기 이미지의 것을 쓴다. Humble 이 필요로 하는 jammy 유저스페이스가 이미지 안에 그대로 있으므로 문제가 없다. 단 커널이 제공하는 것(장치 드라이버)은 호스트 것이므로, 호스트에서 안 보이는 장치는 컨테이너에서도 안 보인다.
2. network_mode: host 를 빼면 정확히 어떤 증상이 나타나는가?
노드는 정상적으로 실행되지만 서로를 발견하지 못한다. 다른 컨테이너에서 ros2 node list 가 비거나 자기 자신만 보인다. 오류 메시지가 없어서 코드를 의심하게 되는 것이 함정이다. 원인은 DDS 디스커버리가 쓰는 UDP 멀티캐스트가 bridge 네트워크를 넘지 못하는 것.
3. 컨테이너를 root 로 실행하면 무엇이 곤란해지는가?
마운트된 /ros2_ws 에 colcon 이 생성하는 build/install/log 디렉터리가 root 소유가 된다. 호스트에서 편집·삭제하려면 매번 sudo 가 필요하고, git 이나 rsync 를 쓸 때도 권한 문제가 생긴다. 그래서 빌드 인자로 호스트 UID/GID 를 주입한다 — 그리고 그 변수명이 UID 가 아니라 HOST_UID 인 이유는 bash 의 UID 가 읽기 전용이기 때문이다.
4. Foxglove 가 ROS_DOMAIN_ID 의 영향을 받지 않는 이유는?
foxglove_bridge 노드 자체는 ROS 그래프 안에 있고 도메인 ID 를 따르지만, Mac 의 Foxglove Studio 는 DDS 가 아니라 WebSocket 으로 그 브리지에 연결된다. Mac 은 ROS 그래프의 참여자가 아니라 브리지의 클라이언트다.
5. 컨테이너 안에서 sudo apt install ros-humble-slam-toolbox 를 했는데 다음 날 없다. 왜이고, 어떻게 해야 하는가?
docker compose run --rm dev 는 매번 이미지에서 새 컨테이너를 만들고 종료 시 지운다. apt 가 쓴 것은 그 컨테이너의 쓰기 레이어에 있었으므로 함께 사라졌다. 이미지는 바뀌지 않았다. --rm 을 빼는 것은 해법이 아니다 — compose run 은 실행마다 새 컨테이너를 만들고, 설정·이미지가 바뀌면 up 도 재생성한다. 쓰기 레이어는 보존 수단이 아니다. 계속 필요한 패키지를 남기는 방법은 §2-2 의 두 가지다 — A: Dockerfile 에 적고 docker compose build, B: 시스템 경로를 볼륨으로 마운트한 컨테이너에서 설치.
6. docs 초안대로 ros2 run demo_nodes_cpp talker 를 쳤는데 "package 'demo_nodes_cpp' not found" 가 났다. 원인은?
ros:humble-ros-base 이미지의 ros_base 메타패키지에는 데모 노드가 들어 있지 않다(데모 노드는 desktop 변형에 들어 있다). §3-3 목록의 ros-humble-demo-nodes-cpp/-py 를 넣었어야 한다 (A: 2-B 블록 + 재빌드, B: 컨테이너에서 설치). "패키지가 이미지에 있는가"는 ros2 pkg list | grep … 로 바로 확인할 수 있다.
7. 호스트를 apt upgrade 한 뒤 컨테이너에서 Hailo 가 "No Hailo device found" 를 낸다. ROS 코드는 안 건드렸다. 무엇을 보는가?
호스트의 hailo_pci 드라이버/HailoRT 가 업그레이드됐지만 컨테이너의 libhailort 는 그대로라 버전이 어긋난 것. 호스트와 컨테이너에서 각각 hailortcli fw-control identify 를 쳐 비교하고, 다르면 컨테이너 쪽을 호스트 버전으로 맞춘다 — A: Dockerfile 의 HAILORT_VERSION 을 새 값으로 바꿔 재빌드, B: 컨테이너에서 같은 버전 .deb/.whl 설치. /dev/hailo0 이 보이는 것과 장치를 "인식"하는 것은 다른 문제다.
8. compose 에 ipc: host 가 있는데도 640×480 카메라 영상이 초당 30 장 중 일부만 도착한다. camera_info 는 30 장 다 온다. 왜이고, 무엇을 확인하는가?
영상 한 장(921,600 B)이 Fast DDS 의 기본 공유 메모리 구획(512 KB)보다 커서 UDP 로 갔고, 소켓 수신 버퍼(기본 212,992 B)에서 조각이 넘쳐 영상째 버려진 것이다. camera_info 는 작아서 구획에 들어가므로 영향이 없다. 확인은 셋이다 — 컨테이너에서 printenv | grep FASTRTPS 로 설정 파일 경로가 잡혔는지, 호스트에서 ls -l /dev/shm/fastrtps_* 의 크기가 16802336 인지, /proc/net/snmp 의 Udp 줄 RcvbufErrors 가 영상을 받는 동안 늘어나는지. 이미 떠 있던 컨테이너는 compose 를 바꿔도 그대로이므로 다시 만들어야 적용된다.
