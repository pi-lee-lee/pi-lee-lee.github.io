02 · Docker + ROS 2 Humble

컨테이너 안에 ROS 2 를 세우고, Mac 의 Foxglove 를 붙인다

호스트는 Raspberry Pi OS(Debian 13) 인데 우리가 쓸 ROS 는 Ubuntu 22.04 용 Humble 이다. 이 모순을 Docker 가 푼다. 이 단계가 끝나면 이후 모든 단계의 명령이 컨테이너 안에서 실행된다.

이 단계가 끝나면

Pi 의 컨테이너 안에서 ros2 topic list 가 돌고, 두 컨테이너의 talker/listener 가 서로를 찾아 통신하고, Mac 의 Foxglove 가 Pi 의 ROS 그래프에 붙는다. 그리고 03~10 단계에서 필요한 apt 패키지가 전부 이미지 안에 들어가 있어서, 이후 단계에서 이미지를 다시 빌드할 일은 08(camera_ros)·08c(HailoRT) 두 번뿐이다.

그래프에서의 위치그래프의 바탕 — 모든 노드가 도는 컨테이너 + Foxglove(관측)
전제01 (ssh 접속, 장치 인식)
예상 소요1~2시간 (+ 이미지 빌드 10~20분 대기)
언어셸 Dockerfile · compose

이 단계에서 만드는 것은 셋이다.

  1. 이미지 rpi5-ros2:humble — docker/Dockerfile 로 정의. ROS 2 Humble + 이 학습에 필요한 패키지 + 호스트와 UID 가 같은 비root 사용자.
  2. 서비스 3개 — docker/docker-compose.yml 의 dev(일회성 개발 셸), foxglove(상시 브리지), bringup(로봇 본체, 06 단계부터).

2. 원리 — 왜

2-1. 왜 Docker 인가 — 이 프로젝트 구조의 핵심 근거

ROS 2 Humble 의 공식 타깃은 Ubuntu 22.04 (jammy) 다. Debian 13 에 Humble 을 apt 로 깔 방법은 없다. 소스 빌드는 Pi 5 에서 몇 시간이 걸리고 의존성 지옥이 기다린다.

        ┌─────────────────────────────────────────────────┐
        │  컨테이너: Ubuntu 22.04 (jammy) 유저스페이스    │
        │   · /opt/ros/humble/...                         │
        │   · libstdc++, python3.10, DDS 라이브러리       │
        └───────────────────┬─────────────────────────────┘
                            │  시스템 콜
        ┌───────────────────▼─────────────────────────────┐
        │ 호스트 커널 (Raspberry Pi OS Trixie의 Linux 6.x)│
        │   · USB serial, V4L2, dma_heap                  │
        │   · hailo_pci  ← Hailo-8 드라이버도 여기 있다   │
        └─────────────────────────────────────────────────┘

컨테이너는 커널을 공유하고 유저스페이스는 자기 것을 쓴다. 따라서 호스트가 Raspberry Pi OS 든 Ubuntu 든, 컨테이너 안은 항상 jammy + Humble 이다.

01 단계의 결정과 이 결정은 같은 논리의 앞뒤다

ROS 쪽 제약이 Docker 로 사라졌기 때문에, 호스트 선택은 순수하게 드라이버 문제가 되었다. 반대로 말하면 커널이 제공하는 것(장치 드라이버)은 호스트 것이므로, 호스트에서 안 보이는 장치는 컨테이너에서도 안 보인다. 01 단계를 먼저 끝내야 하는 이유다.

부수적으로 얻는 것:

  • 호스트가 ROS 패키지로 더럽혀지지 않는다 → 언제든 갈아엎을 수 있다
  • 환경을 Dockerfile 한 장으로 재현할 수 있다 → "내 Pi 에서만 되는" 현상이 없다
  • 나중에 Jazzy 로 옮길 때 베이스 이미지 한 줄만 바꾸면 된다

참고(비차단): Humble 은 2027년 5월 EOL, Jazzy(Ubuntu 24.04 기반)가 현행 LTS 다. 지금은 자료가 압도적으로 많은 Humble 로 배우고, 개념을 익힌 뒤 옮기는 것이 낫다. 개념은 그대로이고 바뀌는 것은 일부 API 이름 정도다.

2-2. 이미지·컨테이너·볼륨 — 쓰기 레이어는 저장소가 아니다

   Dockerfile ──(docker compose build)──► 이미지 rpi5-ros2:humble   ← 영구. 읽기 전용 레이어들
                                               │
                                 docker compose run --rm dev
                                               ▼
                                          컨테이너 (쓰기 레이어)   ← 수명 = 컨테이너 수명. 보존을 선언할 방법이 없다
                                               │
                                   sudo apt install ros-humble-xxx   ← 여기 설치한 것은 쓰기 레이어에 있다
                                               ▼
                               컨테이너 삭제·재생성  →  쓰기 레이어 삭제  →  xxx 는 사라졌다
             (--rm 종료 · compose run 재실행 · compose 설정/이미지 변경 후 up · down · prune)

컨테이너 안에서 apt install·pip install 한 것은 그 컨테이너의 쓰기 레이어에 있고, 컨테이너가 삭제·재생성되면 사라진다. 이미지는 바뀌지 않았기 때문이다.

--rm 은 삭제 시점을 "셸 종료"로 정해 줄 뿐, 사라지는 원인이 아니다. --rm 을 빼도 보존은 보장되지 않는다 — docker compose run 은 실행할 때마다 새 컨테이너를 만들고, docker compose up 은 compose 설정이나 이미지가 바뀌면 컨테이너를 재생성하며, down·prune 은 지운다. 그래서 남겨야 할 것은 수명을 선언할 수 있는 곳에 둔다. 실행 중에 생기는 데이터(코드·빌드 결과·지도·bag)는 볼륨/바인드 마운트에 둔다 — 이것은 아래 두 방식 공통이다. 패키지 같은 환경을 남기는 방법은 두 가지이고, 대등한 선택지다.

A. 이미지에 넣는다 (Dockerfile)B. 시스템 경로를 볼륨으로 잡는다
구성Dockerfile 에 설치 줄을 적는다compose volumes: 에 /opt /usr /etc /var 등을 named volume 으로 추가한다. 볼륨이 처음 생성될 때 이미지 내용으로 채워진다
패키지 추가·업데이트Dockerfile 수정 → docker compose build → 새 컨테이너컨테이너 셸에서 sudo apt install / sudo dpkg -i / pip install → 볼륨에 남는다. 환경 변경은 컨테이너 안에서 한다(이미 채워진 볼륨에는 이미지 변경이 반영되지 않는다)
한 번 바꿀 때 바뀌는 범위캐시가 무효화된 줄부터 다시 실행된다. 버전을 고정하지 않은 apt 줄은 그 시점의 버전으로 함께 바뀔 수 있다설치한 패키지만 바뀐다. 설치 직후 실제 장치에 붙여 확인할 수 있다
설치 목록 확인Dockerfile 을 읽는다컨테이너에서 dpkg -l, pip list
이미지로 굳히기·배포이미지 그 자체 (레지스트리 / docker save)필요한 시점에 볼륨을 tar 로 뽑아 이미지로 만든다. docker commit 은 볼륨 내용을 포함하지 않는다

이 가이드의 docker/ 구성과 각 단계의 절차는 A 로 적혀 있다. B 를 쓴다면 "Dockerfile 에 추가 → 재빌드"라고 적힌 곳을 "컨테이너에서 설치"로 읽으면 된다.

학습 패키지는 §3-3 에서 한 번에 넣는다

새 패키지가 필요한지 확실하지 않으면 우선 컨테이너 안에서 sudo apt install 로 써 본다. 계속 쓸 것은 고른 방식으로 남긴다 — A 는 Dockerfile 에 적고 빌드, B 는 그 설치가 그대로 남는다. A 는 Pi 에서 첫 빌드가 10~20분이므로, 이 가이드에서 필요한 apt 패키지는 §3-3 에서 한 번에 넣는다. B 도 같은 목록을 한 번에 설치해 두면 단계마다 멈추지 않는다.

2-3. compose 의 항목은 왜 하나라도 빠지면 "조용히" 고장나는가

docker/docker-compose.yml 의 아래 항목은 빠져도 에러가 나지 않는다. 증상이 "아무 일도 안 일어남"이라 원인을 찾기 어렵다.

항목왜 필요한가빠지면 나타나는 증상
network_mode: hostROS 2 는 DDS 위에서 돌고, DDS 는 UDP 멀티캐스트로 서로를 찾는다(디스커버리). Docker 기본 bridge 네트워크는 멀티캐스트를 NAT 너머로 전달하지 못한다노드는 떠 있는데 다른 컨테이너에서 ros2 topic list 에 아무것도 안 나온다
ipc: hostHumble 기본 RMW(Fast DDS)는 같은 머신 안 통신에 공유 메모리(/dev/shm) 를 쓴다. IPC 네임스페이스가 분리되면 루프백 UDP 로 조용히 강등된다이미지·포인트클라우드 같은 큰 메시지에서 프레임 드롭
volumes: ../ros2_ws:/ros2_ws소스는 호스트에 두고 컨테이너가 빌드한다(없으면) 컨테이너를 지울 때 코드와 빌드 결과가 함께 사라진다
/dev:/dev, device_cgroup_rules/dev 를 통째로 마운트해도 cgroup 규칙이 없으면 장치 접근이 막힌다. major 번호가 동적인 dma_heap·hailo0 은 01 에서 확인한 값을 직접 적는다카메라/Hailo 가 "컨테이너에서만" 안 잡힌다
ROS_DOMAIN_ID같은 네트워크에 여러 ROS 시스템이 있으면 서로 섞인다. 도메인 ID(0~101)로 격리한다남의 로봇 토픽이 내 목록에 섞여 나온다
ROS_LOCALHOST_ONLY: "0"1 이면 localhost 로만 통신한다Mac 에서 토픽이 안 보인다 (단, Foxglove 는 WebSocket 이라 영향이 없다)

Mac 의 Foxglove 는 WebSocket 으로 붙으므로 도메인 ID 와 무관하다. 나중에 Mac 에 ROS 를 깔아 직접 DDS 로 통신할 계획이라면 양쪽 도메인 ID 를 같게 맞춰야 한다.

2-4. 비root 사용자와 HOST_UID

컨테이너를 root 로 돌리면 마운트된 ros2_ws 에 colcon 이 만드는 build/ install/ log/ 가 전부 root 소유가 되어 호스트에서 편집·삭제하려면 매번 sudo 가 필요하고 git·rsync 가 꼬인다. 그래서 Dockerfile 은 빌드 인자로 호스트 UID/GID 를 받아 같은 번호의 사용자를 만든다.

왜 변수명이 UID 가 아니라 HOST_UID 인가

bash 에서 UID 는 읽기 전용 변수라 export UID=$(id -u) 가 에러를 낸다. 게다가 export 가 실패해도 compose 는 기본값 1000 으로 조용히 넘어가서, 명령은 실패했는데 결과는 맞아 보이는(첫 사용자의 UID 가 우연히 1000 인) 최악의 상황이 된다. 변수명을 바꾸고 docker/.env 파일로 관리해 이 함정을 피한다.

2-5. Hailo-8 을 컨테이너에서 쓸 때의 함정 — 버전 락

이 프로젝트에만 있는 특수 문제라 미리 짚는다. 08c 단계에서 실제로 부딪힌다.

   호스트                              컨테이너
   ┌──────────────────────┐            ┌─────────────────────────────┐
   │ hailo_pci (커널 모듈)│◄──────────►│ libhailort (유저 라이브러리)│
   │  버전 4.x.y          │ /dev/hailo0│  버전 4.x.y                 │
   └──────────────────────┘            └─────────────────────────────┘
              ▲                                    ▲
              └────────── 이 둘이 정확히 같아야 한다 ─────┘

드라이버는 호스트에, 런타임 라이브러리는 컨테이너에 있다. HailoRT 는 이 둘의 버전이 다르면 장치를 아예 인식하지 않는다. 더 곤란한 점: 호스트에서 sudo apt upgrade 를 하면 호스트 쪽만 올라간다. 어제까지 되던 추론이 오늘 갑자기 "No Hailo device found" 를 내고, ROS 코드는 하나도 안 건드렸으므로 원인을 엉뚱한 데서 찾게 된다.

대응은 세 줄이다.

# ① 호스트에서 현재 버전을 확인해 기록한다 (01 단계에서 INVENTORY.md 5절에 적었다)
hailortcli fw-control identify | grep -i version

# ② 컨테이너 쪽 HailoRT 를 그 버전으로 맞춘다 (08c 단계, §2-2 의 A/B 중 쓰는 방식으로)
#    A: Dockerfile 3-B 블록의 ARG HAILORT_VERSION=4.xx.y  ← 호스트에서 확인한 값 → 빌드
#    B: 컨테이너에서 같은 버전의 .deb / .whl 을 설치

# ③ 호스트를 업그레이드한 뒤에는 반드시 재확인하고, 다르면 ②를 새 버전으로 다시 한다
hailortcli fw-control identify                                   # 호스트
docker compose run --rm dev hailortcli fw-control identify       # 컨테이너 → 두 출력의 버전이 같아야 한다
devices: 로 /dev/hailo0 을 못박지 않은 것은 의도적이다

compose 는 /dev 전체를 마운트하므로 노드 자체는 보인다. devices: 에 명시하면 HAT 을 아직 장착하지 않았거나 DKMS 빌드가 실패한 상태에서 dev, foxglove 를 포함한 모든 서비스가 뜨지 않는다(그리고 compose 의 에러 메시지는 원인을 알려 주지 않는다). 컨테이너에서 장치가 안 잡히면 ls -l /dev/hailo0 의 major 번호를 device_cgroup_rules 에 추가한다. 이 보드의 실측은 238, 0 → 'c 238:* rmw' 이고, media 237·dma_heap 252 와 함께 compose 에 이미 들어 있다 (INVENTORY 8절). 셋 다 부팅 시 동적으로 배정되므로 호스트 커널이 올라가면 다시 확인한다.

대안(더 단순하지만 덜 깔끔한 길): 추론을 호스트에서 돌리고 결과만 ROS 로 넘기는 방법도 있다. 버전 락이 사라지지만 시스템이 컨테이너 안팎으로 쪼개진다. 08c 에서 두 방식을 비교한다.

2-6. 왜 RViz 가 아니라 Foxglove 인가

RViz 를 Pi 에서 띄우고 macOS 로 X11 포워딩하는 방법은 XQuartz 설정, OpenGL 미지원, 극심한 지연 때문에 실용성이 없다. Foxglove 는 foxglove_bridge(ROS 노드)가 WebSocket 으로 데이터만 내보내고, Mac 에서 네이티브로 렌더링하므로 Pi 의 CPU 를 거의 쓰지 않는다. 그래서 Dockerfile 은 ros:humble-ros-base(RViz/Gazebo 없는 이미지) 를 쓴다 — -desktop 은 2 GB 가 더 크고 헤드리스 Pi 에서 한 번도 쓰지 않는다.

3-8. Foxglove 연결 — Mac 에서 Pi 의 데이터 보기

cd ~/ros2_rpi5/docker
docker compose up -d foxglove
docker compose logs -f foxglove      # "Server started" 확인 후 Ctrl+C (로그만 끊기고 컨테이너는 계속 돈다)

Mac Foxglove 에서 (무료 플랜. 첫 실행 때 계정 로그인을 요구하고, 그 뒤로는 로컬 파일과 WebSocket 연결이 오프라인에서도 된다. 유료 플랜은 클라우드 저장·팀 기능용이라 이 프로젝트에는 필요 없다):

  1. Open connection → Foxglove WebSocket
  2. 주소: ws://192.168.50.97:8765 (이 프로젝트의 Pi. mDNS 를 쓰면 ws://roshost.local:8765)
  3. 연결되면 좌측에 토픽 목록이 보인다. Raw Messages 패널에 /rosout 을 띄워 talker 의 로그가 흐르는지 확인한다.
  4. Topic Graph 패널을 추가한다 — 03 단계부터 "그래프를 보는" 습관의 도구다.

✅ 검증 체크포인트

🤔 이해 확인

1. 호스트가 Debian 13 인데 컨테이너 안은 왜 Ubuntu 22.04 인가? 문제되지 않는가?
컨테이너는 커널만 공유하고 유저스페이스(libc, 라이브러리, 패키지)는 자기 이미지의 것을 쓴다. Humble 이 필요로 하는 jammy 유저스페이스가 이미지 안에 그대로 있으므로 문제가 없다. 단 커널이 제공하는 것(장치 드라이버)은 호스트 것이므로, 호스트에서 안 보이는 장치는 컨테이너에서도 안 보인다.
2. network_mode: host 를 빼면 정확히 어떤 증상이 나타나는가?
노드는 정상적으로 뜨지만 서로를 발견하지 못한다. 다른 컨테이너에서 ros2 node list 가 비거나 자기 자신만 보인다. 에러 메시지가 없어서 코드를 의심하게 되는 것이 함정이다. 원인은 DDS 디스커버리가 쓰는 UDP 멀티캐스트가 bridge 네트워크를 넘지 못하는 것.
3. 컨테이너를 root 로 돌리면 무엇이 곤란해지는가?
마운트된 /ros2_ws 에 colcon 이 생성하는 build/install/log 디렉터리가 root 소유가 된다. 호스트에서 편집·삭제하려면 매번 sudo 가 필요하고, git 이나 rsync 도 꼬인다. 그래서 빌드 인자로 호스트 UID/GID 를 주입한다 — 그리고 그 변수명이 UID 가 아니라 HOST_UID 인 이유는 bash 의 UID 가 읽기 전용이기 때문이다.
4. Foxglove 가 ROS_DOMAIN_ID 의 영향을 받지 않는 이유는?
foxglove_bridge 노드 자체는 ROS 그래프 안에 있고 도메인 ID 를 따르지만, Mac 의 Foxglove Studio 는 DDS 가 아니라 WebSocket 으로 그 브리지에 붙는다. Mac 은 ROS 그래프의 참여자가 아니라 브리지의 클라이언트다.
5. 컨테이너 안에서 sudo apt install ros-humble-slam-toolbox 를 했는데 다음 날 없다. 왜이고, 어떻게 해야 하는가?
docker compose run --rm dev 는 매번 이미지에서 새 컨테이너를 만들고 종료 시 지운다. apt 가 쓴 것은 그 컨테이너의 쓰기 레이어에 있었으므로 함께 사라졌다. 이미지는 바뀌지 않았다. --rm 을 빼는 것은 해법이 아니다 — compose run 은 실행마다 새 컨테이너를 만들고, 설정·이미지가 바뀌면 up 도 재생성한다. 쓰기 레이어는 보존 수단이 아니다. 계속 필요한 패키지를 남기는 방법은 §2-2 의 두 가지다 — A: Dockerfile 에 적고 docker compose build, B: 시스템 경로를 볼륨으로 잡은 컨테이너에서 설치.
6. docs 초안대로 ros2 run demo_nodes_cpp talker 를 쳤는데 "package 'demo_nodes_cpp' not found" 가 났다. 원인은?
ros:humble-ros-base 이미지의 ros_base 메타패키지에는 데모 노드가 들어 있지 않다(그것은 desktop 변형의 일부다). §3-3 목록의 ros-humble-demo-nodes-cpp/-py 를 넣었어야 한다 (A: 2-B 블록 + 재빌드, B: 컨테이너에서 설치). "패키지가 이미지에 있는가"는 ros2 pkg list | grep … 로 바로 확인할 수 있다.
7. 호스트를 apt upgrade 한 뒤 컨테이너에서 Hailo 가 "No Hailo device found" 를 낸다. ROS 코드는 안 건드렸다. 무엇을 보는가?
호스트의 hailo_pci 드라이버/HailoRT 가 올라갔지만 컨테이너의 libhailort 는 그대로라 버전이 어긋난 것. 호스트와 컨테이너에서 각각 hailortcli fw-control identify 를 쳐 비교하고, 다르면 컨테이너 쪽을 호스트 버전으로 맞춘다 — A: Dockerfile 의 HAILORT_VERSION 을 새 값으로 바꿔 재빌드, B: 컨테이너에서 같은 버전 .deb/.whl 설치. /dev/hailo0 이 보이는 것과 장치를 "인식"하는 것은 다른 문제다.
