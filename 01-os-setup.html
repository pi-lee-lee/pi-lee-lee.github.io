01 · OS 선정과 설치

Raspberry Pi 5 — 호스트를 세우고 장치를 전부 인식시킨다

ROS 2 는 한 줄도 나오지 않는 단계다. 그런데 여기서 카메라·Hailo·시리얼이 호스트에서 안 보이면 뒤의 어느 단계에서도 보이지 않는다. 컨테이너는 호스트 커널의 장치를 빌려 쓸 뿐이기 때문이다.

이 단계가 끝나면

Mac 에서 ssh pi5 로 비밀번호 없이 접속하고, 카메라(IMX708)·라이다·MCU·Hailo-8 이 모두 호스트에서 인식된 상태가 된다. 그리고 hardware/INVENTORY.md 의 빈칸이 추측이 아니라 실측·실행 결과로 채워진다. 그 파일이 이 단계의 진짜 산출물이다.

그래프에서의 위치그래프 밖 — 모든 상자가 올라갈 호스트(커널·드라이버·Docker)

1. 개요

이 프로젝트에서 ROS 2 는 Docker 컨테이너 안에만 산다(02 단계). 컨테이너는 호스트와 커널만 공유하고 유저스페이스는 자기 것을 쓴다. 그 결과 호스트 OS 가 하는 일은 딱 세 가지로 줄어든다.

   호스트 OS 의 역할 = ① 커널 / 장치 드라이버   ② 펌웨어   ③ Docker
                          ▲
                          └── 카메라(IMX708, CSI), Hailo-8(PCIe), USB 시리얼(LiDAR·MCU), dma_heap 이 전부 여기 달려 있다

이 단계는 그 세 가지를 세우는 단계다. 순서는 이렇다.

  1. OS 를 정한다 — 기준은 "ROS 에 좋은 OS"가 아니라 "드라이버가 가장 잘 붙는 OS" (§2-1)
  2. 이미지를 굽고 ssh 로 붙는다 — 모니터 없이 끝낸다
  3. Hailo-8 과 카메라를 호스트에서 확인한다 — 여기서 되면 08·08c 단계의 성공이 예약된다
  4. 하드웨어를 식별하고 이름을 고정한다 — scripts/detect-hardware.sh → hardware/INVENTORY.md → udev

2. 원리 — 왜

2-1. 왜 Ubuntu 가 아니라 Raspberry Pi OS 인가

처음 계획은 "최신 Ubuntu"였다. Hailo-8 AI HAT+ (26 TOPS)가 추가되면서 이 결정의 기준이 바뀌었다. 결론부터 쓰고 근거를 든다.

권장: Raspberry Pi OS Trixie (64-bit)

02 단계에서 자세히 다루지만, ROS 2 는 어느 호스트에서든 컨테이너 안에서 똑같이 jammy + Humble 로 돈다. 즉 "ROS 에 좋은 OS"를 고를 이유가 없어졌다. 남은 기준은 하나 — 하드웨어 드라이버가 가장 잘 지원되는 OS. 그리고 우리 하드웨어 3개 중 2개(카메라, Hailo)가 Raspberry Pi OS 를 가리킨다.

그래도 Ubuntu 를 쓰고 싶다면

가능은 하다. Canonical 이 공식 가이드(canonical/pi-ai-kit-ubuntu)를 낸다. 다만 아래를 감수해야 한다.

2-2. 왜 시간 동기화가 ROS 2 에서 중요한가

ROS 2 의 모든 메시지에는 타임스탬프가 붙고, TF(05 단계)는 "이 시각의 변환"을 조회한다. 시계가 틀어지면 TF 조회가 실패하고 SLAM/Nav2 가 센서 데이터를 아예 쓰지 못한다. 증상은 extrapolation into the future 같은 에러로 나타나고, 원인이 "시계"라는 것을 알아차리기 어렵다. 그래서 §3-3 에서 timedatectl 의 synchronized: yes 를 확인한다.

2-3. 왜 장치 이름을 udev 로 고정하는가 — ttyUSB 와 ttyACM

커널은 USB 시리얼 장치에 인식된 순서대로 번호를 붙인다. 순서는 부팅마다, 케이블을 다시 꽂을 때마다 바뀔 수 있다. 런치파일에 /dev/ttyUSB0 을 박아 두면 "어제는 됐는데 오늘은 라이다가 모터 명령을 받는" 상황이 생긴다. udev 규칙으로 VID/PID(+시리얼번호)에 이름을 묶어 /dev/lidar, /dev/mcu 로 고정한다.

장치USB 칩커널 이름udev 심볼릭 링크
RPLIDAR A1M8Silicon Labs CP2102 (USB-UART, 보통 10c4:ea60)/dev/ttyUSB*/dev/lidar
NUCLEO-H723ZGST-LINK/V3E 가상 COM 포트 (USB CDC-ACM, 0483:374e 계열)/dev/ttyACM*/dev/mcu
ttyACM 에는 ModemManager 라는 함정이 하나 더 있다

ModemManager 는 새로 꽂힌 /dev/ttyACM* 을 "모뎀일지도 모른다"고 보고 AT 명령을 쏘며 탐색한다. 그 몇 초 동안 MCU 프레임과 섞여 간헐적 CRC 오류, 초기 연결 실패로 나타나고, 이 증상은 배선(GND) 문제와 구분되지 않는다. 저장소의 udev 규칙에 들어 있는 ENV{ID_MM_DEVICE_IGNORE}="1" 한 줄이 그것을 막는다. 06 단계에서 다시 본다.

2-4. 왜 HailoRT 버전을 지금 기록해 두는가

커널 드라이버 hailo_pci 는 호스트에, 런타임 라이브러리 libhailort 는 컨테이너에 있다. 이 둘의 버전이 정확히 같지 않으면 /dev/hailo0 이 보여도 "No Hailo device found" 가 난다. 호스트 apt upgrade 는 호스트 쪽만 올린다. 그래서 hailortcli fw-control identify 의 출력을 hardware/INVENTORY.md 5절에 그대로 붙여넣어 둔다. 08c 단계에서 이 값으로 컨테이너를 고정한다.

2-5. 전원 — 모든 이상한 증상의 숨은 원인

Pi 5 는 5V/5A(25W) 협상이 되는 어댑터가 아니면 USB 포트 전류를 600 mA 로 제한한다. 여기에 Hailo-8(부하 시 수 W) + LiDAR(모터 기동 전류 400~600 mA) + 카메라가 붙는다. 27W(5V/5A) 정품 PD 어댑터 또는 그에 준하는 레귤레이터가 사실상 필수다. 부족하면 "추론을 켜면 라이다가 끊긴다", "모터가 도는 순간 리셋된다" 같은 재현 어려운 장애로 나타난다. 확인 명령은 vcgencmd get_throttled 하나다 — 0x0 이 아니면 전원부터 의심한다.

3. 실습

3-1. 이미지 굽기 Mac

  1. Raspberry Pi Imager 를 설치하고 실행한다.
  2. Raspberry Pi Device: Raspberry Pi 5
  3. Operating System: Raspberry Pi OS Lite (64-bit) — Trixie 기반. 모니터가 없고 전부 ssh 로 작업하므로 Lite 를 고른다. 데스크톱은 보지도 못하면서 CPU·RAM·발열만 쓰고, 이 로봇은 그 자원을 SLAM·Nav2·추론에 써야 한다. 이 가이드의 모든 확인은 터미널 출력, 파일을 Mac 으로 가져와 보기, Foxglove 로 한다. 카메라 미리보기 창이 필요한 곳은 없다. Lite 에서 하나만 보충한다 — §3-3 의 rpicam-apps 교체.
  4. Storage: microSD 또는 NVMe. AI HAT+ 가 PCIe 커넥터를 점유한다. M.2 NVMe HAT 과 동시에 쓰려면 PCIe 분기/적층 구성이 필요하다. 확인하지 못했다면 일단 microSD 로 시작한다. 이 프로젝트의 실제 구성은 USB 3 외장 SSD 부팅(/dev/sda, ASMedia ASM246X 브리지)이다. 동작하지만 Pi 5 의 USB 전류 제한(§2-5)과 UAS 브리지 문제에 노출된다. 업그레이드 도중 루트가 읽기 전용으로 바뀐 사고의 처리는 99 §5 "호스트 OS / 저장장치" 를 본다.
  5. ⚙️ 설정 편집 — 모니터 없이 끝내기 위해 반드시 한다.

3-2. ssh 접속 설정 Mac

이 프로젝트의 접속 방식은 ssh test@192.168.50.97 이다. 공개키를 Pi 에 직접 등록해 두어 비밀번호 없이 들어간다. 이것만으로 충분하다.

ssh test@192.168.50.97          # 키 로그인 — 비밀번호를 묻지 않아야 한다

가이드의 뒤 단계는 ssh pi5, scp pi5:… 처럼 별칭 pi5 로 쓴다. 별칭은 위 주소와 사용자명을 한 번 적어 두는 것뿐이다. 별칭을 만들지 않으려면 뒤에 나오는 pi5 를 test@192.168.50.97 로 바꿔 읽으면 된다.

cat >> ~/.ssh/config <<'CONF'

Host pi5
    HostName 192.168.50.97    # 이 프로젝트의 Pi (호스트명 roshost). 공유기 DHCP 예약으로 고정한다
    User test
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 30
CONF

ssh pi5                          # ssh test@192.168.50.97 과 같다
고정 IP 를 권장한다

로봇 IP 가 바뀌면 Foxglove 주소도 매번 바뀐다. 공유기 DHCP 예약으로 MAC 주소에 IP 를 묶는 것이 가장 간단하다. mDNS 이름(roshost.local)은 편하지만 네트워크에 따라 느리거나 안 될 때가 있어 이 가이드는 IP 를 쓴다.

3-4. Hailo-8 AI HAT+ 설치 하드웨어 Pi 호스트

물리 장착

전원을 완전히 끈 상태에서 AI HAT+ 를 Pi 5 의 PCIe FFC 커넥터에 연결하고 스탠드오프로 고정한다. FFC 케이블의 접점 방향을 확인한다.

전원

Hailo-8 은 부하 시 수 W 를 먹는다. 여기에 LiDAR(USB) + 모터까지 붙으면 27W(5V/5A) 정품 PD 어댑터가 사실상 필수다. 부족하면 추론 중 리셋된다 (§2-5).

드라이버 + 런타임 설치

sudo apt update
sudo apt install -y dkms
sudo apt install -y hailo-all
sudo reboot

hailo-all 이 설치하는 것:

  • hailo_pci 커널 드라이버 (DKMS — 커널이 올라가도 자동 재빌드)
  • HailoRT 런타임 + hailortcli
  • Hailo TAPPAS Core (영상 파이프라인 후처리)
  • rpicam-apps 의 Hailo 후처리 연동

PCIe Gen 3: AI HAT+ 는 자동 적용된다. (구형 AI Kit 은 raspi-config → 6 Advanced → A8 PCIe Speed 에서 수동 설정이 필요했다.)

확인

lspci | grep -i hailo                 # PCIe 에 보이는가
ls -l /dev/hailo0                     # 장치 노드가 생겼는가 — "238, 0" 의 앞 숫자가 major (02 의 cgroup 규칙)

(2026-09-13 실측: 1280×720 에서 약 29 fps, 사람 박스 확인.) 실시간으로 보고 싶다면 -o tcp://0.0.0.0:8888 --listen 으로 스트림을 열고 Mac 에서 ffplay tcp://192.168.50.97:8888 로 받는 방법도 있다(Mac 에 ffmpeg 필요). 그리고 여기서 보는 것이 곧 08b 단계에서 배울 YOLOv8 이다 — 같은 모델을 08b 에서는 직접 돌리고, 08c 에서는 이 칩으로 돌린다.

vcgencmd get_throttled     # 0x0 이 아니면 전원 부족 (bit0 = 현재 저전압, bit16 = 저전압 이력)
vcgencmd measure_temp      # 발열 (액티브 쿨러 권장)

get_throttled 는 Pi 본체의 저전압만 본다. USB 포트의 전류 제한(어댑터가 5A 로 협상되지 않으면 합계 600 mA)은 여기에 나타나지 않는다. 이 프로젝트는 루트 SSD 까지 USB 에 달려 있으므로, 어댑터가 정품 27W 가 아니면 0x0 이어도 저장장치가 끊길 수 있다 (99 §5 "호스트 OS / 저장장치").

3-7. 하드웨어 식별 — 이 단계의 실제 산출물 Mac

cd ~/ros2_rpi5
scp scripts/detect-hardware.sh pi5:~/
ssh pi5 'bash ~/detect-hardware.sh' | tee /tmp/hw-report.txt

출력을 보고 hardware/INVENTORY.md 의 빈칸을 채운다.

  • 4번의 /dev/serial/by-id/... → 어느 것이 LiDAR 이고 어느 것이 MCU 인가. 우리 구성은 커널 이름부터 다르다(LiDAR = ttyUSB, MCU = ttyACM). 그래도 구분이 안 되면 하나씩 뽑았다 꽂으며 ls /dev/serial/by-id/ 를 비교한다.
  • 3번의 VID:PID → hardware/udev/99-ros2-devices.rules 의 값과 대조 (CP2102 10c4:ea60, ST-LINK 0483:374x)
  • 4-B ModemManager 가 active 인가 → udev 규칙 적용 후 다시 확인
  • 5번 카메라 인식 여부와 libcamera 버전, 5-B Hailo 버전 → INVENTORY.md 4절·5절
  • 5번의 /dev/dma_heap, 5-B 의 /dev/hailo0 major 번호 → 02 단계 compose 의 cgroup 규칙에 쓴다 (이 보드: media 237, hailo0 238, dma_heap 252 — INVENTORY 8절)
  • 리포트의 "(실패 또는 미설치)" 가운데 libcamera-hello 는 Trixie 에 없는 것이 정상(rpicam-hello 만 있다), docker 는 02 에서 설치한다

3-8. udev 규칙 적용 Mac → Pi 호스트

규칙 파일의 VID/PID 가 3-7 에서 확인한 값과 맞는지 보고, 다르면 Mac 에서 고친 뒤 복사한다.

# Mac 에서
scp hardware/udev/99-ros2-devices.rules pi5:~/
ssh pi5 'sudo cp ~/99-ros2-devices.rules /etc/udev/rules.d/ && \
         sudo udevadm control --reload-rules && sudo udevadm trigger'
ssh pi5 'ls -l /dev/lidar /dev/mcu'

장치를 뽑았다 다시 꽂아도 두 링크가 그대로 살아나면 성공이다. MCU 쪽은 추가로 ModemManager 가 무시하는지 본다.

# Pi 에서
udevadm info -q property -n /dev/mcu | grep ID_MM      # ID_MM_DEVICE_IGNORE=1 이 보여야 한다

3-9. INVENTORY.md 채우기 Mac

hardware/INVENTORY.md 를 열고 1절(보드/OS/커널/전원), 2절(MCU by-id 경로, VID:PID), 3절(LiDAR by-id 경로), 4절(카메라 인식, libcamera 버전, 오버레이), 5절(HailoRT·펌웨어·드라이버 버전, /dev/hailo0 major)을 채운다. 6절(섀시 실측)과 7절(배선)은 05·06 단계에서 채운다. 모르는 값은 비워 둔다. 추측값은 빈칸보다 나쁘다 — 나중에 "설정된 값"으로 보여 원인을 숨긴다.

🤔 이해 확인

1. ROS 2 를 컨테이너에서 돌릴 건데, 왜 호스트 OS 선택이 여전히 중요했는가?
컨테이너는 호스트와 커널을 공유한다. 장치 드라이버(카메라 CSI, Hailo PCIe, USB 시리얼, dma_heap)는 전부 호스트 커널이 제공한다. 그래서 "호스트에서 안 보이는 장치는 컨테이너에서도 안 보인다". ROS 쪽 기준으로는 OS 가 무관해졌기 때문에, 오히려 하드웨어 드라이버 지원이 유일한 선택 기준이 되었다.
2. Hailo 드라이버가 DKMS 로 설치되는 것이 왜 중요한가?
DKMS 는 커널이 업데이트될 때마다 모듈을 자동으로 재빌드한다. 수동 빌드 방식이면 apt upgrade 한 번에 /dev/hailo0 이 사라지고, 그 원인이 "커널이 바뀌어서"라는 걸 알아차리기 어렵다.
3. /dev/ttyUSB0 대신 /dev/mcu 를 쓰는 이유는?
ttyUSB/ttyACM 번호는 커널이 장치를 인식한 순서대로 붙어서 부팅마다 뒤바뀔 수 있다. udev 로 VID/PID/시리얼번호에 이름을 묶으면 순서와 무관하게 고정된다. 그리고 우리 MCU 는 ttyUSB 가 아니라 ttyACM(ST-LINK VCP 는 USB CDC-ACM 장치) 이라는 것도 여기서 알아 둔다.
4. 호스트의 HailoRT 버전을 기록해 두라고 한 이유는?
커널 드라이버(hailo_pci)는 호스트에, libhailort 는 컨테이너에 있다. 이 둘의 버전이 정확히 일치하지 않으면 컨테이너가 장치를 감지하지 못한다. 호스트를 업그레이드할 때마다 컨테이너 쪽도 다시 맞춰야 한다.
5. MCU 의 시리얼 통신이 "가끔 되고 가끔 안 된다". 배선을 뒤지기 전에 먼저 확인할 것은?
ModemManager. ttyACM 장치를 모뎀으로 오인해 AT 명령을 쏘며 탐색하고, 그동안 프레임이 깨진다. 증상이 GND 미공통과 똑같이 보인다. udevadm info -q property -n /dev/mcu | grep ID_MM 으로 ID_MM_DEVICE_IGNORE=1 이 적용됐는지 보고, 로봇 전용 Pi 라면 systemctl disable --now ModemManager 로 아예 꺼도 된다.
6. "추론을 켜면 라이다가 끊긴다"는 증상을 어디서부터 의심해야 하는가?
전원. Pi 5 + Hailo(부하 시 수 W) + LiDAR 모터 기동 전류 + 카메라의 합이 어댑터 용량을 넘으면 USB 전류가 제한되거나 리셋된다. vcgencmd get_throttled 가 0x0 이 아니면 소프트웨어를 보기 전에 27W PD 어댑터(또는 셀프파워 USB 허브)부터 해결한다.
7. INVENTORY.md 의 빈칸을 "대충 스펙 시트 값"으로 채우면 왜 안 되는가?
빈칸은 "아직 모른다"는 정직한 신호라서 그 단계에서 멈추게 해 준다. 추측값은 "설정된 값"으로 보여서 오도메트리가 조금씩 틀어지거나(섀시 값), 라이다 최대 거리가 과대평가되어 유령 벽이 생기거나(max_distance), 버전 락에 걸리는(HailoRT) 원인을 숨긴다. 실측·실행 결과만 적는다.
