이 쪽이 끝나면 보이는 것

2. 원리 — 왜 이렇게 나누고, 왜 이 도구인가

2-1. CubeMX 가 만드는 것과 내가 만드는 것 — 경계는 파일마다 다르다

펌웨어 쪽은 끝까지 가는 동안 .ioc 를 열댓 번 고친다(타이머를 켜고, UART 를 켜고, DMA 를 켜고 …). 고칠 때마다 CubeMX 가 코드를 다시 써낸다. 그래서 "어느 파일의 어느 부분이 다시 써지는가"를 모르면, 내가 쓴 코드가 다음 생성 한 번에 사라진다. 경계는 파일마다 같지 않다.

파일 · 디렉터리다시 생성하면내가 손대도 되는 범위근거
Core/Src/*.c · Core/Inc/*.h (main.c · stm32h7xx_it.c · main.h …)파일 전체를 다시 쓰되 /* USER CODE BEGIN x */ ~ /* USER CODE END x */ 사이는 옮겨 적는다마커 사이만. 마커 주석 자체는 고치지 않는다(고친 마커를 CubeMX 가 어떻게 다루는지는 확인하지 않았다).ioc 의 ProjectManager.KeepUserCode=true · firmware/README.md 규칙 1
cmake/stm32cubemx/CMakeLists.txt다시 쓴다 — 주변장치를 켜면 컴파일할 HAL 소스 목록(이 파일의 STM32_Drivers_Src)이 바뀌기 때문이다없다. 마커도 없다파일 내용(§2-2). 실제로 다시 써지는지는 실습 B 에서 직접 본다
최상위 CMakeLists.txt다시 쓰지 않는다전부. 내 소스 · 포함 경로 · 매크로를 넣는 자리가 주석으로 표시돼 있다파일 머리 주석: "This file is generated only once, and is not re-generated if converter is called multiple times. User is free to modify the file as much as necessary"
Drivers/HAL 팩(STM32Cube FW_H7 V1.13.0)에서 필요한 파일만 복사해 온다. 주변장치를 켜면 파일이 는다없다(고치면 팩과 달라진다)주변장치 0개인 프로젝트의 $HAL/Src 에는 .c 가 18개, 팩 원본 $FW_H7 의 Src/ 에는 125개다(2026-09-22 에 센 값. 변수 둘은 §2-5). 복사를 시키는 키는 ProjectManager.LibraryCopy=1
startup_stm32h723xx.s · STM32H723xG_flash.ld · cmake/gcc-arm-none-eabi.cmake · CMakePresets.json확인하지 못했다 — 실습 B 에서 수정 시각으로 직접 확인해 노트에 적는다링커 스크립트는 뒤 쪽(메모리 지도 · 플래시 저장)에서 조각을 더한다. 그때 이 관찰이 필요하다학습자 관찰 (§3-2-4)
User/Inc · User/SrcCubeMX 는 이 디렉터리를 모른다 — 만들지도, 지우지도 않는다(실습 C 의 마지막 걸음에서 직접 확인한다)전부. 내 코드는 전부 여기 — 루트에는 app 둘만, 나머지는 목적별 묶음 폴더(§2-2-1)firmware/README.md 예정 트리 · 규칙 1

Drivers 행의 125개는 ls $FW_H7/Drivers/STM32H7xx_HAL_Driver/Src/*.c | wc -l 로 센 값이다(2026-09-22). Src/Legacy/ 의 ETH 2개는 이 수에 들지 않는다.

여기서 규칙 하나가 나온다: 생성물(Core/)에는 User/ 의 함수를 부르는 호출만 넣고, 로직은 전부 User/ 에 둔다. 이렇게 하면 다시 생성할 때 영향을 받는 것이 호출 두 줄뿐이고, git diff 에서 "CubeMX 가 바꾼 것"과 "내가 바꾼 것"이 섞이지 않는다.

마커에 기대어 main.c 안에 로직을 길게 쓰는 방법도 동작은 한다. 다만 그 방법에서는 생성물과 내 코드가 한 파일에 섞여 diff 를 읽기 어렵고, 마커 근처를 잘못 고쳤을 때 잃을 수 있는 양이 커진다.

왜 "밖에 쓰면 사라진다"를 글로 읽지 않고 실습으로 하는가

한 번 직접 겪어야 기억에 남는 규칙이다. 겪는 날을 고를 수 있다면 잃을 것이 주석 한 줄뿐인 오늘이 낫다 — 실습 B 는 일부러 밖에 쓰고 사라지는 것을 grep 으로 본다(발동 확인).

2-2. 내 소스는 User/ 에, 등록은 최상위 CMakeLists.txt 한 곳에

C 에는 "디렉터리에 파일을 두면 자동으로 컴파일된다"가 없다. 빌드 시스템에 적힌 파일만 컴파일된다. CubeMX 가 만든 CMake 구조는 두 층이다.

CMakeLists.txt                       최상위 — 한 번만 생성된다. 내 것
   add_executable(h723zg)                실행 파일 하나를 선언한다
   add_subdirectory(cmake/stm32cubemx)   아래 파일을 끌어온다
   target_sources(...)                   # Add user sources here            ◄── 내 .c
   target_include_directories(...)       # Add user defined include paths   ◄── User/Inc
   target_compile_definitions(...)       # Add user defined symbols         ◄── 빌드 스위치

cmake/stm32cubemx/CMakeLists.txt     매번 다시 생성된다. CubeMX 것
   stm32cubemx      포함 경로 + 매크로 (USE_HAL_DRIVER, STM32H723xx …)
   STM32_Drivers    Drivers/ 의 HAL 소스 묶음
   + Core/Src/*.c 와 startup_*.s 를 h723zg 에 더한다

생성물 쪽 목록(cmake/stm32cubemx/)은 CubeMX 가 관리하고, 내 목록은 최상위 파일의 세 자리에 내가 적는다. 파일을 User/Src 에 만들어 놓고 등록을 잊으면 컴파일은 오류 없이 지나가고 링크에서 멈춘다: undefined reference to `app_init'. 포함 경로를 잊으면 더 앞에서 멈춘다: fatal error: app.h: No such file or directory (두 메시지 모두 2026-09-22 에 이 구조로 실제로 내 본 것이다).

와일드카드로 User/Src 아래의 .c 를 통째로 넣는 방법도 있다. 폴더를 묶음으로 나누므로(§2-2-1) 한 층만 보는 file(GLOB …) 이 아니라 하위 폴더까지 도는 file(GLOB_RECURSE …) 여야 한다. 두 방법의 빌드 결과는 동일하다. 다른 점은 둘이다.

  • GLOB: 등록을 잊을 일이 없다. 새 파일은 다시 configure 해야 목록에 들어간다(build.sh 는 매번 configure 를 부르므로 차이는 작다).
  • 명시 목록: 파일마다 한 줄을 적어야 한다. 어느 쪽에서 어떤 모듈이 더해졌는지가 diff 로 남는다.

이 가이드의 본문은 명시 목록으로 쓴다 — 뒤 쪽들이 "한 줄을 더한다"고 말할 수 있어야 해서다.

main.c 가 아는 내 함수는 끝까지 둘이다: 초기화가 끝난 뒤 한 번 불리는 app_init(), while (1) 안에서 계속 불리는 app_loop(). 뒤의 쪽들은 main.c 가 아니라 User/Src/app.c 에 한 줄씩 더한다. 생성물에 손을 대야만 하는 예외가 뒤에 몇 번 나온다. 그때마다 그 쪽이 이유를 적는다. C 파일에서는 그 경우에도 마커 사이에만 쓴다. 마커가 없는 링커 스크립트(STM32H723xG_flash.ld)에 fw-07 이 조각을 더하는 것만 예외이고, 다시 생성한 뒤 그 조각이 남았는지 grep 으로 확인한다(fw-07).

2-2-1. User/ 안의 폴더 — 루트에는 app 둘, 나머지는 목적별 일곱 묶음

이 가이드가 끝날 때 User/ 에는 모듈이 서른 개쯤 된다(.c/.h 한 쌍을 하나로 센다). 한 디렉터리에 두면 이름순 목록이 곧 구조가 되는데, 이름순 목록은 구조를 보여 주지 않는다 — adc.c 옆에 app.c 가, cli.c 옆에 comm_frame.c 가 놓인다. 그래서 폴더 하나가 질문 하나에 대응하도록 나눈다. 규칙은 셋이다.

  • User/Inc · User/Src 의 루트에는 app.h · app.c 만 둔다. main.c 가 아는 두 함수가 있는 곳이고, 모듈을 연결하는(초기화 순서 · 주 루프) 자리다.
  • 나머지는 전부 묶음 폴더에 두고, Inc 와 Src 가 같은 폴더 이름을 쓴다 — User/Inc/Tools/console.h ↔ User/Src/Tools/console.c. 헤더만 있는 모듈(log.h · dma_buf.h · imu_sample.h · frames.h · Config/ 의 둘)은 Src 쪽 폴더가 없다.
  • 묶음 폴더는 그 묶음의 첫 파일을 만드는 쪽에서 만든다(mkdir -p User/Inc/<묶음> User/Src/<묶음>). 일곱 개를 미리 만들어 두지 않는다 — 아래 표의 "처음 만드는 쪽"이 그 자리다.
폴더넣는 기준 — 이 질문에 "예"면 여기들어가는 모듈 (처음 만드는 쪽)
Config/값만 있고 실행 코드가 없는가 — 빌드 스위치와 공용 상수fw_config.h (fw-03) · robot_params.h (fw-08)
Tools/사람이 보고 진단하려고 둔 것인가 — 글자 창 · 로그 · 명령 창 · 고장의 흔적console · log.h · reset_cause (fw-03) · hardfault (fw-04) · cli (fw-05)
System/MCU 자체의 기반 기능인가 — 시간 · 감시 · 메모리 배치 · DMA 수신 버퍼 · 저장tick · wdg (fw-06) · dma_buf.h · stream_rx (fw-07) · nvstore (fw-16)
Periph/MCU 주변장치 하나를 감싸 핀의 신호(PWM · 펄스 · 전압)를 다루는가motor (fw-08) · encoder (fw-09) · adc (fw-12)
Device/보드 밖 부품의 프로토콜(레지스터 맵 · 프레임)을 아는가ina226 (fw-10) · imu_sample.h (fw-13) · wt901_parse · wt901 (fw-14) · bno055 (fw-15)
Control/판단하는가 — 상태기계와 제어식power (fw-11) · pid · protect · control (fw-13) · safety (fw-18) · traction (fw-20)
Comm/Pi 와의 계약 v2 를 다루는가frames.h · crc8 · frame_parser · comm_frame (fw-17)

질문 둘에 걸치는 파일은 그 파일의 알맹이(가장 많은 줄이 하는 일)로 정한다. 경계에 있는 넷이 판정의 예다.

  • stream_rx 는 UART 수신을 다루지만 Periph/ 가 아니라 System/ 이다. 주변장치 레지스터에 접근하지 않는 순수 모듈이고, 명령 창 · WT901 · 계약 v2 의 수신이 함께 쓰는 기반이다. fw-07 이 만들고 fw-14 · fw-17 이 다시 쓴다.
  • adc 가 읽는 ACS758 은 보드 밖 부품이지만 adc 는 Periph/ 다 — 그 부품은 레지스터 없이 전압 하나만 내보내므로 할 일이 ADC3 설정과 환산뿐이다. 같은 전류를 재도 INA226 은 레지스터를 I2C 로 읽어야 해서 Device/ 다.
  • power 는 릴레이 핀을 직접 구동하지만 Control/ 이다 — 알맹이가 상태기계(power_fsm_step())이고, 핀을 구동하는 몇 줄은 그 결과를 내보내는 끝단이다.
  • imu_sample.h 는 코드가 없지만 Config/ 가 아니라 Device/ 다 — 값이 아니라 자료형이고, 센서 모듈 둘(WT901 · BNO055)이 채워서 내놓는 형식이다.

폴더를 나눠도 빌드 결과는 동일하다 — 컴파일러가 보는 것은 등록된 파일 목록과 포함 경로뿐이다. 달라지는 것은 사람이 읽는 쪽이다. ls User/Src/Control 이 "판단하는 코드 전부"가 된다. fw-19 실습 A 의 경계 검사는 "통신 쪽 이름이 Control/ · Periph/ · Device/ 에 있는가"라는 질문이 된다.

2-2-2. 헤더를 찾는 방법 — 포함 경로는 User/Inc 하나, #include "묶음/이름.h"

폴더를 나누면 컴파일러가 헤더를 어떻게 찾을지도 정해야 한다. 이 가이드는 포함 경로를 User/Inc 하나로 두고, 헤더를 묶음 이름째 포함한다. 생성물 헤더(main.h · stm32h7xx_hal.h)와 루트의 app.h 는 폴더 없이 그대로다.

/* User/Src/Control/control.c */
#include "Control/control.h"     /* 자기 헤더도 같은 "묶음/이름.h" 꼴 */
#include "Device/imu_sample.h"
#include "Config/robot_params.h"
#include "main.h"                /* 생성물: 묶음 없음 (Core/Inc) */

따옴표 꼴(#include "…")을 만나면 컴파일러는 ① 포함하는 파일이 있는 디렉터리를 먼저 보고, ② 없으면 포함 경로(-I)를 적힌 순서대로 본다. 위의 둘째 줄이라면 ① User/Src/Control/Device/imu_sample.h — 없다, ② User/Inc/Device/imu_sample.h — 있다.

포함 경로는 둘이다.

  • 최상위 CMakeLists.txt 의 User/Inc 한 줄.
  • 생성물 쪽 cmake/stm32cubemx/CMakeLists.txt 의 MX_Include_Dirs(Core/Inc · Drivers/…/Inc …). 그래서 main.h 는 폴더 없이 찾아진다.

묶음 이름을 빼먹고 #include "log.h" 라고 쓰면 ① User/Src/Tools/log.h 도, ② User/Inc/log.h 도 없어서 전처리에서 멈춘다. 메시지는 fatal error: log.h: No such file or directory 다(Mac 의 cc 는 'log.h' file not found). 세 가지 모두 2026-09-29 에 arm-none-eabi-gcc 14.3.1(CubeCLT 1.21.0)과 Mac 의 cc 로 같은 폴더 구조를 만들어 확인했다.

다른 방법도 있다 — 묶음마다 포함 경로를 하나씩 더하고(User/Inc/Tools, User/Inc/Control …) #include "control.h" 처럼 이름만 쓰는 방법이다. 1세대 펌웨어가 이렇게 했다(~/stm32/learn/stm32h7r_boot_app_xip/Appli/CMakeLists.txt:67-71, 묶음 다섯). 빌드 결과는 동일하다. 다른 점은 아래 표와 같다.

이 가이드 — User/Inc 하나 + "묶음/이름.h"묶음마다 포함 경로 + "이름.h"
포함 경로처음 한 줄(User/Inc)이 끝까지 바뀌지 않는다. 호스트 시험의 cc 도 -I…/User/Inc 하나묶음을 만들 때마다 CMake 에 한 줄, 그 묶음을 쓰는 모든 호스트 시험의 cc 에 -I 하나가 는다
포함 줄에서 알 수 있는 것어느 묶음에 기대는지가 줄에 보인다 — Control/ 파일이 Comm/ 을 포함하면 줄만 보고 경계 위반을 안다이름만 보인다. 어느 묶음인지는 파일을 찾아봐야 안다
파일을 다른 묶음으로 옮기면그 헤더를 포함하는 줄을 전부 고친다(빠뜨리면 위의 fatal error 로 드러난다)포함 줄은 그대로다. CMake 의 등록 줄만 고친다
같은 파일 이름묶음이 다르면 겹쳐도 된다겹치면 안 된다 — 포함 경로에서 먼저 찾은 쪽이 경고 없이 쓰인다(위와 같은 날 같은 두 컴파일러로 확인). 예: CubeMX 의 CoupleFile 을 켜면 Core/Inc/adc.h 가 생겨 내 adc.h 와 이름이 같아진다

한 가지 함정: 헤더 안에서는 이름만 써도 찾아지는 경우가 있다. User/Inc/Tools/console.h 가 #include "log.h" 라고 쓰면 ① 에서 자기 디렉터리(User/Inc/Tools/)의 log.h 가 찾아져 오류가 나지 않는다. 그래도 묶음째 쓴다 — 한 꼴이어야 grep 한 번으로 의존을 셀 수 있다(이해 확인 3번).

cmake 에 넘길 옵션(생성기 · 툴체인 파일 · 빌드 종류 · 출력 디렉터리)을 매번 손으로 치지 않도록 CubeMX 가 CMakePresets.json 에 이름을 붙여 둔다. 생성된 파일을 읽으면 이렇다.

이 표에서 세 가지를 가져간다.

  • 컴파일러는 PATH 에서 찾는다. 툴체인 파일은 arm-none-eabi-gcc 를 이름만으로 부르고, 주석에 "arm-none-eabi- must be part of path environment"라고 적어 둔다. CubeCLT 의 bin 디렉터리들이 PATH 에 없으면 configure 단계에서 멈춘다 — build.sh 가 맨 앞에서 PATH 부터 검사하는 이유다.

  • 두 프리셋의 차이는 최적화와 디버그 정보, 둘뿐이다. 소스 · 링커 스크립트 · 매크로(단 DEBUG 하나 빼고)는 같다.

    이 가이드의 도구는 Debug 를 기본으로 부른다. 디버거(fw-04)가 -g3 의 심볼을 읽고, -O0 에서는 기계어가 소스 줄과 1:1 에 가깝다.

    Release 는 실행 시간과 크기가 달라진다 — 시간을 재는 쪽에 가서 FW_PRESET=Release firmware/tools/build.sh 로 견주어 볼 수 있다. 어느 쪽을 최종으로 삼을지는 이 쪽이 정하지 않는다.

  • 링크가 끝나면 메모리 사용표가 찍힌다(--print-memory-usage). FLASH 몇 바이트, 그리고 RAM 이 어느 영역 줄에 들어가는지. 생성된 링커 스크립트는 .data · .bss · 스택을 DTCMRAM 에 둔다(STM32H723xG_flash.ld 의 >DTCMRAM AT> FLASH · _estack). 지금은 보기만 한다 — 메모리 지도를 다루는 fw-07에서 이 줄이 주제가 된다.

build/ 는 통째로 지워도 되는 디렉터리다(firmware/.gitignore 가 무시한다). 빌드가 설명할 수 없는 오류를 낼 때의 첫 조치가 rm -rf firmware/h723zg/build 인 이유다 — 원본은 .ioc 와 소스이고 build/ 는 언제든 다시 만들어진다.

2-4. ST-LINK/V3E 는 H7 에 SWD 와 VCP 만 준다 — 끌어다 놓기를 기대하지 않는다

Nucleo 보드에는 MCU 가 둘 있다. 내가 프로그램하는 STM32H723ZG, 그리고 USB 커넥터(CN1) 뒤에서 디버그 프로브 역할을 하는 ST-LINK/V3E. USB 케이블 하나로 세 가지가 전달된다: 보드 전원(JP2 기본 위치 [1-2] = 5V_USB_STLK, UM2407 표 4), SWD, VCP.

UM2407 (Rev 6) 의 문장자리
"The embedded STLINK-V3E supports only SWD and VCP for STM32H7 devices."§7.3, 18쪽
"USB reenumeration capability: Virtual COM port, mass storage, debug port"§1 Features, 7쪽

두 문장은 어긋난다. 이 가이드는 §7.3 을 따른다 — 특징 목록은 Nucleo-144 계열 공통 문구이고 §7.3 은 H7 보드에 한정해 쓴 문장이기 때문이다. .bin 을 드라이브에 끌어다 놓는 플래시는 기대하지 않는다. Mac 에 드라이브가 보이더라도 그 방법을 쓰지 않는다 — 검증 · 리셋 · 디버거(fw-04)가 전부 SWD 를 쓴다.

그래서 플래시 도구는 CubeCLT 에 든 STM32_Programmer_CLI 하나다. flash.sh 가 쓰는 인자는 넷이고, 넷 다 이 Mac 의 STM32_Programmer_CLI --help(STM32CubeProgrammer v2.22.0) 에서 확인한 것이다.

2-5. 에디터와 코드 탐색 — HAL 소스를 빨리 뒤질 수 있어야 한다

펌웨어 쪽의 이해 확인 1번은 매번 같은 꼴이다: 그 쪽에서 쓴 HAL 함수 하나를 네 군데에서 찾는다 — ① 헤더(시그니처) ② __weak 기본 구현 ③ 누가 언제 부르는가 ④ ST 의 예제. HAL 은 문서보다 소스가 정확하고, 소스는 이 Mac 에 전부 있다. 뒤질 곳은 두 군데이고 둘은 같지 않다.

뒤지는 수단은 고르면 된다. 빌드와 플래시는 어느 쪽을 골라도 build.sh · flash.sh 다(동일).

(가) 터미널 grep(나) compile_commands.json 을 읽는 에디터

얻는 것파일:줄 이 그대로 나온다 — 노트에 옮겨 적기 좋다. 가이드의 4중 검색 명령이 이 꼴이다"정의로 이동" · "참조 찾기"로 호출 관계를 따라간다. 매크로 · #ifdef 가 내 빌드 설정(STM32H723xx …)대로 풀린다
드는 것호출 관계를 따라가려면 grep 을 여러 번 친다. #ifdef 로 꺼진 코드도 걸려 나온다교차 컴파일러의 내장 헤더 경로를 언어 서버가 찾게 하는 설정이 필요할 수 있다(clangd 라면 --query-driver) — 이 가이드는 확인하지 못했다. 에디터의 빨간 줄과 build.sh 의 결과가 다르면 build.sh 가 맞다. 가장 흔한 경우는 아직 등록하지 않은 새 파일이다. compile_commands.json 에는 CMake 에 등록된 파일만 들어간다. 등록 전의 파일은 에디터가 포함 경로 없이 읽어 main.h 에서 온 이름 전부에 빨간 줄을 긋는다(fw-03 의 console.c 에서 실제로 겪었다). 새 .c 는 만들자마자 등록하고 build.sh 를 한 번 돌린다
저장소남는 것 없음에디터 설정 디렉터리(.vscode/ 등)를 커밋할지는 firmware/README.md 의 "학습자 선택"이다

둘을 같이 써도 된다. 이 가이드의 본문은 (가)의 명령으로 적는다 — 에디터가 무엇이든 따라 칠 수 있어서다. VS Code 는 필수가 아니다(firmware/README.md).

2-6. Debug = Serial Wire, 그리고 PB3 를 첫날 풀어 두는 이유

디버그 포트는 핀을 차지한다. CubeMX 의 디버그 모드에 따라 차지하는 핀이 다르다.

모드 이름과 신호 이름은 CubeMX 6.18.1 의 DB 파일 DEBUG-STM32H7_sys_v1_1_Modes.xml 에서 읽었다(이 파일에는 핀 번호가 없다). 핀 번호는 DS13313 Rev 5 표 7 의 핀 이름 괄호(리셋 직후의 기능)에서 읽었다: PA13(JTMS/SWDIO) · PA14(JTCK/SWCLK) p.66, PA15(JTDI) p.67, PB3(JTDO/TRACESWO) p.69, PB4(NJTRST) p.70.

Serial WirePA13(SWDIO) · PA14(SWCLK)이것을 쓴다. 보드의 ST-LINK 가 H7 에 주는 것이 SWD 다(§2-4)
Trace Asynchronous SwPA13 · PA14 · PB3(SWO)PB3 를 잃는다

이 프로젝트의 확정 핀맵에서 PA15 · PB3 는 앞 왼쪽(FL) 엔코더의 A · B 상이다(TIM2_CH1 · TIM2_CH2 — hardware/pinmap-h723.md §2-B). 엔코더는 fw-09에서야 켜지만, 핀을 비워 두는 일은 오늘 해야 한다. 이유가 둘 있다.

  • 보드 프리셋이 PB3 를 미리 잠가 둔다. CubeMX 에 든 보드 프리셋 파일 G75_Nucleo_NUCLEO-H723ZG_STM32H723ZGT_Board_AllConfig.ioc 의 121~125줄이 그 설정이다. PB3 를 Mode=Trace_Asynchronous_SW · Locked=true · 라벨 SWO 로 설정해 둔다(파일에서 확인). "Trace Asynchronous Sw 를 고르지 않는다"로는 부족하다 — 이미 골라져 있다. Serial Wire 로 바꾸고, PB3 의 핀 잠금을 풀어야 나중에 TIM2_CH2 가 PB3 에 놓인다(hardware/pinmap-h723.md §6 #2).
  • 증상이 먼 쪽에서 난다. 오늘 풀어 두지 않으면 fw-09 에서 "TIM2 의 엔코더 모드가 PA15/PB3 에 안 놓인다"로 나타난다. 그때는 원인이 일곱 쪽 앞에 있다.
안전 규칙 — 디버그에서 SWV(SWO 트레이스)를 켜지 않는다

리셋 직후부터 MX_GPIO_Init() 가 돌기 전까지 디버그 핀은 디버그 기능으로 활성 상태다. RM0468 Rev 3 §11.3.1(511쪽): "PA15: JTDI in pull-up … PB3: JTDO in floating state". 이 구간에 디버거가 SWV 를 켜면 MCU 가 PB3 를 출력으로 구동하고, PB3 에 엔코더의 B 상 출력이 연결돼 있으면 두 출력이 서로 반대 레벨로 구동돼 충돌한다.

그래서 이 프로젝트의 규칙은 둘이 한 짝이다: ① CubeMX 에서 Debug = Serial Wire + PB3 잠금 해제(이 쪽, §3-1-1) ② 디버그 구성에서 SWV 를 켜지 않는다(fw-04 에서 디버거를 연결할 때 다시 확인한다). 엔코더를 실제로 꽂는 것은 fw-09 다.

등급 — 추정

"SWV 를 켜면 그 구간에 MCU 가 PB3 를 구동한다"는 SWJ-DP 의 동작에서 추정한 것이다. RM0468 은 "리셋 후 PB3 = JTDO, floating" 까지만 말한다. 확인된 사실이 아니라서 이 가이드는 "켜지 않는다"를 절차로 둔다(hardware/INVENTORY.md 2절 "배선 전 필수 조건 4가지"의 ②, hardware/pinmap-h723.md §6 #14).

또 하나의 추정: 위 프리셋 파일은 "보드를 고를 때 나오는 주변장치를 기본 모드로 초기화할까 물음에 Yes 로 답했을 때" 적용된다. 파일 이름(…_AllConfig)에서 짐작한 것이고, 같은 폴더의 …_Board.ioc 에는 PB3 항목이 없다. 어느 쪽이 적용됐든 §3-1-1 의 grep 이 결과를 알려 준다.

3. 실습

실습은 셋이고, 각각 관찰 하나로 끝난다: A 생성 → 빌드 → ELF 가 생긴다 · B 다시 생성 → 밖에 쓴 줄이 사라진다 · C app.c 등록 → 굽기 → LD1 이 깜박인다. 소절 번호의 끝자리는 펌웨어 쪽 전체에서 같은 뜻이다(1 = CubeMX 설정, 2 = 골격, 3 = 직접 채우기, 4 = 굽고 보기). 해당 없는 걸음은 번호째 건너뛴다.

채울 자리마다 힌트 카드가 있다 — 읽는 순서

골격의 채울 자리에는 TODO(you) [T1] 처럼 번호가 붙어 있고(이 쪽은 T1 하나 — 실습 C 의 app_loop()), 그 주석 안에 번호 걸음이 있다. 먼저 걸음을 보고 직접 써 본다. 막히면 "직접 채우기" 절에서 같은 번호의 힌트 카드를 연다. 카드에는 그 자리의 완결 코드와, 그 코드를 줄마다 풀어 쓴 설명이 있다. 칸은 언제나 같다: 할 일 · 완결 코드 · 코드 설명 · 쓰는 API · 흔한 실수 · 확인.

완결 코드는 이 프로젝트의 펌웨어 빌드(링크까지 — User/ 에 app.c 하나만 등록한 Debug 프리셋, User/ 경고 0)를 통과한 코드다(2026-10-04). 이 쪽에는 호스트 시험이 없다(§3-3-3). 주기 값은 카드도 주지 않는다 — 내가 정하고, 비워 둔 채 빌드하면 가드가 빌드를 멈춘다. 보드에서 도는 것 — LD1 의 깜박임과 그 주기 — 은 "굽고 보기"에서 내가 확인한다. 붙여 넣는 것으로 끝내지 않는다 — 설명을 읽고 줄마다 "왜 이 줄이 여기 있는가"를 말할 수 있게 된 뒤, 카드를 접고 직접 친다.

H723 의 CPU 상한은 VOS0 에서 520 MHz 이고, 550 MHz 는 VOS0 그리고 옵션 바이트 CPU_FREQ_BOOST = 1 일 때만 규격 안이다(DS13313 표 12). 공장 기본값은 0 이다(RM0468 표 18). 이 프로젝트는 부스트를 쓰지 않는다(결정 9, hardware/INVENTORY.md 2절 "클럭" 행). 얻는 것과 잃는 것은 이렇다: 부스트를 켜면 CPU · 타이머가 +5.8 % 빨라지고, 그 대가로 ITCM · DTCM 의 ECC 가 꺼진다(RM0468 §2.4). 이 프로젝트는 ECC 를 유지하고 +5.8 % 를 포기한다.

그래서 이 쪽에서 최종값으로 맞춘다. 생성 전에 Clock Configuration 에서 PLL1 의 DIVN1 을 275 → 260 으로 내린다. 그러면 8 MHz ÷ 4 × 260 = 520 MHz 이고, HCLK 260 MHz · APB 130 MHz 다(분주는 그대로 ÷1 · ÷2 · ÷2). ST 의 템플릿($FW_H7/Projects/NUCLEO-H723ZG/Templates/Src/main.c 136~139줄: PLLM = 4 · PLLN = 260 · PLLP = 1)과 같은 값이다.

fw-03 은 이 값을 바꾸지 않는다 — fw-03 에서는 옵션 바이트를 읽기만 해서 부스트 비트가 0(= TCM ECC 동작)인지 기록한다. (나) 출발점은 HSI 분수 PLL 이라 값이 다르다 — 그 경우 여기서는 SYSCLK 를 520 MHz 이하로 맞추고, 소스를 HSE 로 옮기는 것은 fw-03 에서 한다. 아래 ③ 의 grep 이 550000000 을 내면 이 걸음을 빠뜨린 것이다.

#include "app.h"
#include "main.h"   /* HAL + LD1_GPIO_Port / LD1_Pin (CubeMX 의 User Label "LD1" 에서 생성) */

  /* 문맥: main(), 인터럽트 켜짐, SysTick 이미 동작 중(HAL_Init).
   * 뒤 쪽들이 저마다 <module>_init() 한 줄씩을 의존 순서대로 더한다. */
}

void app_loop(void)
{
  /* 문맥: main(), 끝없이 연달아 불린다. 불변식: 빨리 돌아오고, 막지 않는다.
   * TODO(you) [T1]: HAL_Delay() 없이 LD1 을 heartbeat 로 점멸시킨다 - 힌트 카드 T1
   *   1) 파일 머리(#include "main.h" 아래, app_init() 위)에 주기 상수를 둔다:
   *      #define HEARTBEAT_MS 0u  와  _Static_assert(HEARTBEAT_MS > 0u, "app.c: HEARTBEAT_MS is still EMPTY");
   *      0 은 자리표시다 - 눈으로 셀 수 있는 내 값 [ms] 을 적는다. 비워 두면 빌드가 여기서 멈춘다(의도된 것)
   *   2) 마지막으로 뒤집은 시각을 함수 안의 static uint32_t last_ms 에 기억한다 [ms] (부팅 때 0)
   *   3) uint32_t now_ms = HAL_GetTick();  - 지금 시각 [ms], 한 호출에 한 번만 읽는다
   *   4) (uint32_t)(now_ms - last_ms) >= HEARTBEAT_MS 이면: last_ms = now_ms; 그리고 HAL_GPIO_TogglePin(LD1_GPIO_Port, LD1_Pin);
   *      (부호 없는 뺄셈은 32비트가 한 바퀴 돌아도(wrap) 맞다 - 이해 확인 4번. 더해서 견주지 않는다)
   *   지울 자리표시는 없다 - 빈 본문에 바로 쓴다. 위의 "문맥 · 불변식" 줄은 남긴다.
   */
}

골격은 그대로 빌드된다(두 함수 모두 빈 본문). 다음은 등록 — 최상위 CMakeLists.txt 의 두 자리에 한 줄씩이다. 뒤의 쪽들은 모듈을 만들 때마다 첫 자리에 묶음 폴더까지 적은 한 줄(예: User/Src/Tools/console.c)을 더하고, 둘째 자리(User/Inc)는 끝까지 그대로 둔다(§2-2-2).

이 블록은 전량 제공이다 — 이유: 경로 철자 하나가 틀리면 링크 오류가 나고, 그 오류는 C 코드의 잘못처럼 보인다.

# Add sources to executable
target_sources(${CMAKE_PROJECT_NAME} PRIVATE
    # Add user sources here
    User/Src/app.c
)

# Add include paths
target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE
    # Add user defined include paths
    User/Inc            # 사용자 포함 경로는 이것 하나 - 묶음 헤더는 "묶음/이름.h" (fw-02 2-2-2)
)

마지막으로 Core/Src/main.c — 생성물에 넣는 것은 #include 한 줄과 호출 두 줄이 전부이고, 셋 다 마커 사이다. 아래는 생성된 main.c 의 해당 부분에 세 줄을 넣은 모습이다(나머지 줄은 CubeMX 가 쓴 그대로).

/* USER CODE BEGIN Includes */
#include "app.h"
/* USER CODE END Includes */

  /* ... main() 안, MX_..._Init() 호출들 뒤 ... */
  /* USER CODE BEGIN 2 */
  app_init();
  /* USER CODE END 2 */

  /* Infinite loop */
  /* USER CODE BEGIN WHILE */
  while (1)
  {
    app_loop();
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */
  }
  /* USER CODE END 3 */

while (1) 은 main.c 에 하나 더 있다 — Error_Handler() 안의 것이다. 그 while (1) 이 아니다. BEGIN WHILE 과 END WHILE 사이에 while (1) { 가 끼어 있는 모양이 낯설지만, 그래서 루프의 첫 줄이 마커 안쪽이 된다.

3-3-3. 직접 채우기

  1. 위 네 가지(파일 둘 · 등록 두 줄 · main.c 세 줄)를 넣고 빈 골격인 채로 firmware/tools/build.sh 를 돌린다. 빌드가 되면 등록과 호출은 맞다.
  2. 일부러 한 번 틀린다. 최상위 CMakeLists.txt 에서 User/Src/app.c 줄을 지우고 빌드한다 → 어느 단계(컴파일 / 링크)에서, 어떤 문장으로 멈추는지 노트에 적고 줄을 되돌린다. 같은 방법으로 User/Inc 줄도 해 본다. 두 메시지가 어떻게 다른가?

  3. app_loop() 의 TODO(you) [T1] 를 채운다(막히면 아래 힌트 T1). 조건은 둘이다 — LD1 이 눈으로 셀 수 있는 주기로 깜박일 것, 그리고 HAL_Delay() 를 쓰지 않을 것.

    힌트: 지금 시각은 HAL_GetTick()(ms 단위, stm32h7xx_hal.c:338), 뒤집기는 HAL_GPIO_TogglePin(LD1_GPIO_Port, LD1_Pin). "마지막으로 뒤집은 시각"을 함수 안의 static 변수에 두고, 부호 없는 뺄셈으로 지난 시간을 구한다(32비트가 한 바퀴 돌아도 차는 맞다 — 왜 그런지는 이해 확인 4번).

  4. 왜 HAL_Delay() 가 안 되는가: stm32h7xx_hal.c:405 의 본문은 HAL_GetTick() 이 목표에 닿을 때까지 도는 while 하나다. 그 동안 app_loop() 는 돌아오지 않는다. 뒤 쪽에서는 이 루프에서 명령 창의 입력 처리와 워치독 갱신도 같이 실행된다 — 첫 모듈부터 "막지 않는다"를 지킨다.

위 걸음과 골격의 번호가 이렇게 짝을 이룬다: 걸음 3 = T1. 막힌 자리의 카드를 연다 — 카드는 접혀 있을 뿐 잠겨 있지 않다.

힌트 T1 — app_loop() · HAL_Delay() 없이 LD1 을 heartbeat 로 점멸시킨다

할 일 — main() 의 while (1) 이 이 함수를 끝없이 부른다(§3-3-2 의 main.c 세 줄). 입력은 HAL_GetTick() 이 주는 지금 시각 [ms] 하나, 출력은 LD1 핀의 뒤집기다. 끝났을 때 참이어야 하는 것은 둘이다.

  • 마지막으로 뒤집은 뒤 내 주기(HEARTBEAT_MS)만큼 지났을 때만, 한 번 뒤집는다.
  • 어느 호출도 기다리지 않고 바로 돌아온다 — 그래야 뒤 쪽에서 같은 루프에 들어오는 명령 창(fw-05)과 워치독 갱신(fw-06)이 제때 실행된다.

주기 값은 내가 정한다 — 이 카드는 숫자를 주지 않는다.

완결 코드

/* 완결 코드 T1 - User/Src/app.c */
#define HEARTBEAT_MS 0u   /* ____ 내가 정한다 [ms] - LD1 을 뒤집는 간격. 눈으로 셀 수 있을 만큼 느리게. 옆의 0 은 자리표시일 뿐 값이 아니다 */
_Static_assert(HEARTBEAT_MS > 0u, "app.c: HEARTBEAT_MS is still EMPTY");

void app_loop(void)
{
  /* 문맥: main(), 끝없이 연달아 불린다. 불변식: 빨리 돌아오고, 막지 않는다. */
  static uint32_t last_ms;             /* 마지막으로 뒤집은 시각 [ms]. static 이라 호출 사이에 남고, 부팅 때 0 */
  uint32_t now_ms = HAL_GetTick();     /* 지금 시각 [ms]. SysTick 인터럽트가 1 ms 마다 1 씩 올리는 수 */

  if ((uint32_t)(now_ms - last_ms) >= HEARTBEAT_MS) {   /* 부호 없는 차: 32비트가 한 바퀴 돌아도(wrap) 맞다 */
    last_ms = now_ms;
    HAL_GPIO_TogglePin(LD1_GPIO_Port, LD1_Pin);
  }
}

코드 설명

  • 어디에 넣는가 — 상수 두 줄은 #include "main.h" 아래 · app_init() 위(파일 범위), 함수는 골격의 app_loop() 자리에. 골격의 "문맥 · 불변식" 주석은 그대로 두었다 — 뒤 쪽들이 이 함수에 줄을 더할 때 그 규칙을 다시 읽는다. 지울 자리표시는 없다.
  • #define HEARTBEAT_MS 0u — 전처리기 상수. 컴파일 전에 글자 그대로 바꿔 넣으므로 메모리를 쓰지 않고, 주기를 한 곳에서만 바꾼다. 끝의 u 는 "부호 없는 정수" 표시다 — 아래 뺄셈의 결과(uint32_t)와 같은 부호로 견주기 위해서다. 0 은 값이 아니라 자리표시(____)다: 눈으로 셀 수 있는 값을 내가 적는다. 뒤 쪽의 robot_params.h(fw-08)가 쓰는 "EMPTY 키"와 같은 꼴이다.
  • _Static_assert(HEARTBEAT_MS > 0u, "…") — 컴파일 시간 검사(C11). 조건이 거짓이면 빌드가 그 메시지로 멈춘다. 왜 두는가: 0 인 채로 구우면 >= 0 이 늘 참이라 매 호출마다 뒤집혀 LD1 이 흐릿하게 켜진 것처럼 보인다 — 오류 표시 없이 틀리는 것보다 빌드가 멈추는 것이 낫다. 메시지 앞에 파일 이름을 붙이는 것이 이 프로젝트의 꼴이다. 함수 밖에 둘 수 있는 문장이고, 실행 코드를 만들지 않는다.
  • static uint32_t last_ms; — 함수 안의 static: 이 변수는 함수가 돌아가도 사라지지 않고 다음 호출까지 값을 유지한다(보통의 지역 변수는 호출마다 새로 생기고 값이 정해져 있지 않다). 부팅 때 0 으로 시작한다 — C 가 static 변수를 0 으로 초기화하므로 = 0 을 안 써도 같다. uint32_t 는 "정확히 32비트 부호 없는 정수"(stdint.h — main.h → HAL 헤더를 거쳐 들어온다). HAL_GetTick() 의 반환형과 같아야 아래 뺄셈이 wrap 에 안전하다.
  • uint32_t now_ms = HAL_GetTick(); — 지금 시각을 한 번만 읽어 둔다. 한 호출 안에서 두 번 읽으면 그 사이에 1 ms 가 지나 두 값이 달라질 수 있다 — 비교에 쓴 값과 기억할 값이 같아야 한다.

  • if ((uint32_t)(now_ms - last_ms) >= HEARTBEAT_MS) — "마지막 뒤집기부터 주기 이상 지났는가". 빼서 견준다. last_ms + HEARTBEAT_MS 와 견주는 꼴은 덧셈이 넘치는 순간 틀린다(이해 확인 4번).

    (uint32_t) 캐스트는 이 MCU 에서는 없어도 같은 코드가 나온다(uint32_t 끼리의 뺄셈은 이미 uint32_t 다). 캐스트는 "일부러 부호 없는 차를 쓴다"는 뜻을 읽는 사람에게 남기는 표시다. HAL 도 같은 꼴로 쓴다(HAL_Delay() 의 while ((HAL_GetTick() - tickstart) < wait), stm32h7xx_hal.c:416).

  • last_ms = now_ms; — 뒤집은 시각을 기억한다. 뒤집기와의 앞뒤 순서는 상관없지만(둘 다 이 호출 안에서 끝난다) 조건 안에 있어야 한다 — 밖에 두면 매 호출마다 갱신돼 차가 늘 0 이 되고 한 번도 뒤집히지 않는다.
  • HAL_GPIO_TogglePin(LD1_GPIO_Port, LD1_Pin); — 핀의 현재 출력을 읽어 반대로 쓴다. 두 매크로는 CubeMX 가 User Label LD1 에서 만든 것이다. Core/Inc/main.h 에 #define LD1_Pin GPIO_PIN_0 · #define LD1_GPIO_Port GPIOB 로 있다. 줄 번호는 내 생성물에서 grep -n LD1 Core/Inc/main.h 로 찾는다. 포트가 먼저, 핀이 뒤다.

  • 다르게 써도 되는 곳 — 넷이다.

    • (가) 갱신: last_ms = now_ms; 는 루프가 늦으면 늦은 만큼 다음 뒤집기도 밀린다. last_ms += HEARTBEAT_MS; 는 평균 주기를 지키는 대신, 오래 멈췄다 돌아오면 밀린 횟수만큼 연달아 뒤집는다. LED 에서는 어느 쪽이든 된다.
    • (나) 뒤집기: TogglePin 대신 static bool on; 을 두고 HAL_GPIO_WritePin(LD1_GPIO_Port, LD1_Pin, on ? GPIO_PIN_SET : GPIO_PIN_RESET); on = !on; 로 써도 된다(<stdbool.h> 포함) — 핀 상태를 내 변수가 갖게 된다.
    • (다) 가드: 값을 처음부터 적는다면 _Static_assert 줄 없이 #define HEARTBEAT_MS <내 값>u 한 줄로 끝내도 된다 — 가드는 "비워 둔 채 굽는 것"만 막는다.
    • (라) static uint32_t last_ms = 0; 으로 써도 같다.

    이 함수는 fw-05 에서 led 명령이 생기고 fw-06 에서 1 kHz(주기 1 ms) 박자가 생기면 다시 고치게 된다.

쓰는 API

  • uint32_t HAL_GetTick(void) — 선언 stm32h7xx_hal.h:1081, 정의 stm32h7xx_hal.c:338(__weak). 인자 없음, 반환은 부팅 뒤 지난 ms 수(uwTick 을 돌려준다, :340).

    올리는 쪽은 HAL_IncTick() 이다(:327, uwTick += (uint32_t)uwTickFreq;). HAL_IncTick() 을 1 ms 마다 부르는 것이 생성물 Core/Src/stm32h7xx_it.c 의 SysTick_Handler() 다(이해 확인 1번). 1 카운트 = 1 ms 인 것은 uwTickFreq 의 기본값(:73 의 HAL_TICK_FREQ_DEFAULT = HAL_TICK_FREQ_1KHZ, stm32h7xx_hal.h:48) 때문이다.

    변수 하나를 읽을 뿐이라 주 루프 · ISR 어디서나 부를 수 있다. 약 49.7 일마다 0 으로 되감긴다(이해 확인 4번).

  • void HAL_GPIO_TogglePin(GPIO_TypeDef *GPIOx, uint16_t GPIO_Pin) — 선언 stm32h7xx_hal_gpio.h:267, 정의 stm32h7xx_hal_gpio.c:446. 첫째 인자는 포트(GPIOB — 그 포트의 레지스터 묶음이 있는 주소라서 포인터다), 둘째는 핀 비트마스크(GPIO_PIN_0 = ((uint16_t)0x0001), stm32h7xx_hal_gpio.h:85). 반환 없음. 본문은 ODR 을 읽어 BSRR 에 "낮았던 핀은 set, 높았던 핀은 reset" 을 한 번에 쓴다(:454~457). 주 루프 · ISR 어디서나 부를 수 있다.
  • 쓰지 않는 것 — void HAL_Delay(uint32_t Delay)(stm32h7xx_hal.c:405). 본문이 while ((HAL_GetTick() - tickstart) < wait) {}(:416) 라서 그 시간 동안 app_loop() 는 돌아오지 못한다. 3-3-3 의 4번.

3-3-4. 굽고 보기

보드의 CN1(ST-LINK 쪽 USB)에 케이블을 꽂는다. 다른 커넥터(CN13, 사용자 USB)에는 꽂지 않는다. LD5(초록)가 켜지고 LD4 가 빨강 켜짐으로 안정되면 Mac 이 ST-LINK 를 인식한 것이다(§2-4 의 표). 공장 출하 데모(LD1~LD3 점멸 — UM2407 §6.1)는 이번 굽기로 지워진다.

처음 꽂았을 때 한 번 — ST-LINK 펌웨어 갱신. /opt/ST/STM32CubeCLT_1.21.0/STLinkUpgrade.sh 를 실행한다(UM2407 §7.3.2). 스크립트가 무엇을 띄우는지는 fw-00 의 도구 표 4행에 있다. 갱신 창이 보여 주는 갱신 전·후의 ST-LINK 펌웨어 판을 노트에 적어 둔다 — 아래 flash.sh 배너의 "펌웨어 판"과 같은 값이어야 한다. 집필자는 이 갱신 창을 보지 못했다(보드 미접속) — 화면이 다르면 화면이 맞다.

그리고 LD1(초록)이 깜박인다. 세 가지를 더 본다.

  • 주기를 시계로 잰다. 뒤집는 간격을 P ms 로 정했다면 한 번의 "켜짐 + 꺼짐"은 2P ms, 열 번이면 20 × P ms 다. 손목시계로 열 번을 재서 계산값과 견준다(____ s ↔ ____ s). 크게 다르면 1 ms 박자(SysTick)와 클럭 설정이 어긋난 것이다 — 이해 확인 1번이 그 경로를 따라간다.
  • B2(검정, RESET)를 누른다. 누르는 동안 LD1 은 꺼져 있고(리셋 중에는 핀이 구동되지 않는다), 떼면 처음부터 다시 깜박인다.
  • 다시 생성하고 다시 굽는다. ① CubeMX 에서 설정을 바꾸지 않고 GENERATE CODE ② grep -n 'app_' ~/ros2_rpi5/firmware/h723zg/Core/Src/main.c 에 세 줄이 그대로 있는지 확인 ③ firmware/tools/flash.sh ④ 여전히 깜박인다. 이것이 이 쪽 제목의 뒷절 "다시 생성해도 내 코드는 남는다"다.

3. (일부러 틀리면) User/Src/app.c 의 등록을 빼면 왜 컴파일이 아니라 링크에서 멈추는가? User/Inc 를 빼면 왜 더 앞에서 멈추는가? 그리고 User/Src/Tools/console.c 에서 #include "log.h" 는 안 되는데 User/Inc/Tools/console.h 에서는 같은 줄이 되는 이유는?

main.c 는 app.h 의 선언만 보고 컴파일된다 — "app_init 이 어딘가에 정의돼 있다"는 선언이면 충분하다. 그 정의(app.c 의 목적 파일)가 목록에 없다는 것은 모든 목적 파일을 모으는 링크 단계에서야 드러난다: undefined reference to `app_init'. 포함 경로가 없으면 그 선언(app.h)조차 찾지 못하므로 main.c 의 전처리에서 멈춘다: fatal error: app.h: No such file or directory. 오류가 난 단계를 보면 무엇을 빠뜨렸는지 절반은 알 수 있다.

셋째: 따옴표 꼴은 포함하는 파일의 디렉터리를 먼저 본다(§2-2-2 의 ①). console.c 의 디렉터리는 User/Src/Tools/ 라서 그 디렉터리에 log.h 가 없고, 포함 경로 User/Inc 바로 아래에도 없다. 그래서 fatal error: log.h: No such file or directory 가 난다. console.h 의 디렉터리는 User/Inc/Tools/ — log.h 와 같은 디렉터리라서 ① 에서 찾아진다. 되는데도 묶음째("Tools/log.h") 쓰는 이유는 한 꼴이어야 grep -rn '#include "Comm/' User 한 번이 "통신 묶음에 기대는 파일 전부"가 되기 때문이다. fw-19 실습 A 의 6) 이 같은 꼴의 검사다. 이름만 쓴 줄은 어느 묶음을 가리키는지 줄만 보고 알 수 없다.

4. now - last >= period 를 부호 없는 32비트로 계산하면 HAL_GetTick() 이 한 바퀴 돌아 0 으로 돌아간 직후에도 맞는 이유는? 한 바퀴는 며칠인가?

부호 없는 뺄셈은 232 을 법으로 하는 연산이라, last = 0xFFFFFFF0 · now = 0x00000010 이면 now - last = 0x20(32 ms)이 나온다 — 실제로 지난 시간과 같다. 반대로 now >= last + period 처럼 더해서 비교하면 last + period 가 넘쳐 작은 수가 되는 순간 조건이 곧바로 참이 된다. 한 바퀴는 232 ms = 4 294 967 296 ms ÷ 86 400 000 ms/일 ≈ 49.7 일. 책상 위에서는 만나기 어렵지만, 같은 꼴의 계산이 뒤에서 32비트 엔코더 카운터와 명령 워치독(200 ms)에 그대로 쓰인다.

5. FW_PRESET=Release 로 빌드해 구우면 무엇이 달라지고 무엇이 같은가? 빌드 디렉터리가 프리셋마다 따로인 것은 왜 편한가?

달라지는 것: 최적화(-O0 → -Os)와 디버그 정보(-g3 → -g0), 매크로 DEBUG 의 유무. 그래서 크기와 실행 시간이 달라지고, 디버거가 소스 줄 · 변수 이름을 알지 못하게 된다. 같은 것: 소스, 링커 스크립트, CPU · FPU 옵션, 나머지 매크로. 디렉터리가 따로(build/Debug · build/Release)라서 둘을 오가도 서로의 목적 파일을 덮어쓰지 않고, 두 ELF 를 나란히 두고 arm-none-eabi-size 로 견줄 수 있다.

6. UM2407 은 한 곳에서 "mass storage"를, 다른 곳에서 "only SWD and VCP"를 말한다. 이 가이드는 어느 쪽을 따르고, 굽는 명령에 -v 를 넣는 이유는 무엇인가?

§7.3("only SWD and VCP for STM32H7 devices")을 따른다 — 계열 공통의 특징 목록보다 이 보드에 한정한 문장이 구체적이기 때문이다. 그래서 굽는 경로는 SWD 하나(STM32_Programmer_CLI -c port=SWD)다. -v 는 쓴 내용을 되읽어 파일과 견준다. 이것이 없으면 "구웠다"는 도구의 보고와 "플래시에 그 내용이 있다"는 사실 사이를 확인할 수단이 없다. 뒤 쪽에서 "고쳤는데 동작이 안 바뀐다"를 만났을 때 도구 단계를 의심 목록에서 뺄 수 있게 해 준다.

7. (안전 규칙) 엔코더는 fw-09 에서야 꽂는다. 그런데 왜 PB3 의 잠금을 오늘 푸는가? 그리고 CubeMX 에서 풀었는데도 디버거의 SWV 를 켜면 안 되는 이유는?

오늘 푸는 이유: 보드 프리셋이 PB3 를 SWO 로 이미 잠가 둔 채 프로젝트가 시작되고, 그 상태로는 TIM2_CH2 가 PB3 에 놓이지 않는다. 미뤄 두면 증상이 일곱 쪽 뒤에서 "핀이 안 잡힌다"로 나타나 원인을 찾기 어렵다. SWV 를 켜면 안 되는 이유: CubeMX 설정은 MX_GPIO_Init() 이후의 핀 상태만 정한다. 리셋 직후부터 그때까지 PB3 는 JTDO/TRACESWO 기능으로 활성 상태다(RM0468 §11.3.1). 그 구간에 디버거가 SWV 를 켜면 MCU 가 PB3 를 출력으로 구동해, 엔코더의 B 상 출력과 서로 반대 레벨로 구동돼 충돌한다(추정 — 그래서 끄는 쪽으로 정했다). 두 조치는 서로를 대신하지 못한다.
